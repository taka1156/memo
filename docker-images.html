Docker イメージの種類

slim / alpine / bookworm / trixie / distroless … タグの意味と glibc・musl・ABI の違い

ざっくり言うと
  • bookworm や trixie は Debian のバージョン名、slim は 中身を削った版、alpine は 別ディストロ。軸が違う。
  • 一番効く違いは C ライブラリ (libc)。Debian / Ubuntu / distroless は glibc、Alpine は musl。glibc 前提でビルドされたバイナリ（workerd など）は Alpine で動かない。
  • Alpine は「小さい → pull が速い」だけで、実行が速いわけではない。迷ったら *-slim（Debian・glibc）が無難。
  • 本番の「まっさら」枠は distroless / Chainguard / Docker Hardened Images / Chiseled Ubuntu / scratch。シェルもパッケージ管理も無く、ビルドは別ステージで行ってコピーする。

サイズは Docker Hub の圧縮済み・amd64 の目安。node:24 系の場合と OS 単体の場合を併記。アイコンは区別用の簡易バッジです。

*-alpine

Alpine Linux ベース（BusyBox + musl）

musl 1.2.xapksh (ash)
node ≈ 55MB / OS ≈ 4MB

  • 無料で使えるのは基本 :latest / :latest-dev のみ。バージョン固定は有償プラン

glibc・musl・ABI の違い

API は「ソースコードで呼べる関数の約束」、ABI (Application Binary Interface) は「コンパイル済みバイナリ同士の約束」。関数のシンボル名、引数の渡し方、構造体のレイアウト、どのローダーで起動するか、まで含む。

ソース（API）レベルでは glibc も musl もほぼ同じ C 標準関数を提供するので、ソースから再ビルドすればどちらでも動くことが多い。困るのは「glibc 向けにビルド済みのバイナリ」を musl 環境に持ち込むとき。

観点glibcmusl
採用ディストロDebian, Ubuntu, RHEL, distroless など大多数Alpine, Void (musl 版) など
設計思想高機能・互換性重視・GNU 拡張多数小さく単純・標準準拠を厳格に
動的ローダー/lib64/ld-linux-x86-64.so.2/lib/ld-musl-x86_64.so.1
シンボルのバージョンあり（GLIBC_2.34 など）。古い glibc では新しい glibc 向けバイナリが動かないなし
静的リンク非推奨（NSS などで問題）得意。単一バイナリ配布に向く
malloc 性能マルチスレッドで速い遅めと言われがち（1.2.1 で入った mallocng は堅牢性と省メモリ重視で、速さが目的ではない）。jemalloc や mimalloc に差し替えて回避されることも
スレッドの既定スタック8MB 程度（ulimit 依存）128KB と小さい → 深い再帰でクラッシュすることがある
DNS 解決NSS / /etc/nsswitch.conf に従う独自実装。昔は TCP フォールバックなし（1.2.4 で対応）、search の扱いに差
ロケール / iconv充実最小限
Python wheelmanylinuxmusllinux（無いパッケージはソースビルド）
Node ネイティブlinux-x64-gnulinux-x64-musl（用意されていないパッケージあり）

npm の optionalDependencies 名や Rust のターゲット名（x86_64-unknown-linux-gnu / -musl）に gnu / musl が入っているのは、まさにこの ABI の違いのため。

workerd（Cloudflare Workers のランタイム、wrangler dev の中身）は npm で glibc にリンク済みのバイナリとして配られている。Alpine に持ち込むと:

$ npx wrangler dev
exec .../workerd: no such file or directory   ← ファイルはあるのに！
  1. カーネルが ELF ヘッダを読み、指定のローダー /lib64/ld-linux-x86-64.so.2 を探す
  2. Alpine にはそのファイルが無い（あるのは ld-musl）
  3. 「ローダーが無い」ことが ENOENT = no such file or directory として返る

確認方法：

$ file node_modules/@cloudflare/workerd-linux-64/bin/workerd
... interpreter /lib64/ld-linux-x86-64.so.2 ...   ← glibc 向け
$ ldd ./some-binary                                  ← 足りない .so が出る

apk add gcompat（glibc 互換の薄いシム）で動く場合もあるが、V8 を抱える workerd のような大きなバイナリでは不完全。素直に node:*-slim を使うのが正解。また glibc は新しい方向にしか互換が無いので、古い Debian（bullseye など）だと glibc が古すぎて動かないこともある点にも注意。

Dockerfile の定番パターン

# ビルドは Debian、本番は distroless の Node（シェルなし・非 root）
FROM node:24-trixie AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

FROM gcr.io/distroless/nodejs24-debian13:nonroot
WORKDIR /app
COPY --from=build /app /app
# ENTRYPOINT が node なのでファイル名だけ渡す
CMD ["server.js"]
# glibc 必須なので slim。OS 世代はタグで固定する
FROM node:24-trixie-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["npx", "wrangler", "dev", "--ip", "0.0.0.0"]
# ビルドはフル版、実行は distroless で最小に
FROM golang:1.27-trixie AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

FROM gcr.io/distroless/static-debian13
COPY --from=build /app /app
ENTRYPOINT ["/app"]
# 純 JS（ネイティブ依存なし）なら alpine でも OK
FROM node:24-alpine3.24
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

よくある誤解

Alpine は軽いから実行も速い

速いのは pull と起動前の転送だけ。実行時は malloc やソースビルドの影響でむしろ遅いことがある。

slim と alpine は同じようなもの

slim は「Debian（glibc）のダイエット版」、alpine は「別の OS（musl）」。互換性がまったく違う。

node:24 と書けば中身はずっと同じ

OS 部分を省略すると Debian の世代交代（bookworm → trixie）で glibc ごと変わる。本番では -trixie-slim まで書いて固定する。

distroless = OS が入っていない

Debian 由来の glibc・証明書・tzdata は入っている。無いのはシェルとパッケージ管理。完全に空なのは scratch。

まっさらイメージなら脆弱性ゼロで放置できる

中身が少ないので件数は激減するが、libc や OpenSSL の更新は来る。定期的に再ビルドして取り込む前提。

Alpine はカーネルが違うから動かない

カーネルはホストのものを共有。動かない原因は libc（ABI）とローダーの違い。
