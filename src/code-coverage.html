カバレッジ基準：C0・C1・C2・MC/DC・MCC

同じ if 文で、基準ごとにどのテストが何件要るかを比べる

ざっくり言うと
  • カバレッジ基準は「何を 1 回は通せば網羅したとみなすか」の決まりで、命令・分岐・条件・条件の組み合わせの順に細かくなる。
  • 条件網羅（C2）は分岐網羅（C1）を含まない。両方を満たす判定条件網羅、各条件の効き目を示す MC/DC と強くなる。
  • 単体テストでは分岐網羅を目安に未実行の所を読み、複雑な条件は MC/DC で考える。率の高さは正しさを保証しない。

基準の一覧

コードの構造を見てテストを選ぶ（ホワイトボックス）ときの物差しを、カバレッジ基準（coverage criteria）と呼ぶ。下の表は弱い順。右端の件数は、次の節の例（条件が 3 つある if 文 1 つ）で基準を満たすのに要る最少のテスト数。

呼び名名前（英語）1 回は通すもの例での最少件数
C0命令網羅（statement coverage）すべての命令（文）1
C1分岐網羅・判定網羅（branch / decision coverage）すべての判定の真と偽2
C2条件網羅（condition coverage）判定の中の個々の条件の真と偽2
—判定条件網羅（decision/condition coverage）C1 と C2 の両方2
MC/DC改良条件判定網羅（modified condition/decision coverage）C1・C2 に加え、各条件が単独で判定の結果を変えること4
MCC複合条件網羅（multiple condition coverage）条件の真偽のすべての組み合わせ8

「C2」が指すものは資料によって違い、条件網羅とする資料も、複合条件網羅（MCC）とする資料もある。話がずれやすいので、チームでは「条件網羅」「MC/DC」のように名前で呼ぶほうが安全。分岐網羅と判定網羅もほぼ同じ意味で使われるが、switch や例外の扱いなど細かい所で区別する資料もある。

例：送料無料の判定

会員で 5000 円以上買ったか、クーポンを持っていれば送料を無料にする関数。判定（decision）は if の式全体、条件（condition）はその中の &&・|| でつながった 1 つ 1 つの式。

function shippingFee(isMember, total, hasCoupon) {
  let fee = 500;
  if ((isMember && total >= 5000) || hasCoupon) {  // 判定
    fee = 0;
  }
  return fee;
}
// 条件 A: isMember   B: total >= 5000   C: hasCoupon

条件が 3 つなので、真偽の組み合わせは 23 = 8 通り。次の節では、この 8 行の表から基準ごとにテストを選ぶ。T は真、F は偽で、判定が真なら送料無料、偽なら 500 円。

強さの関係：C2 は C1 を含まない

「上の基準を 100% 満たせば、下の基準も 100% 満たす」という関係を矢印で表すと次のようになる。条件網羅（C2）だけが横に外れている。

矢印の元は先を含む（元を満たせば先も満たす）点線：どちらも相手を含まない

C1 と C2 が比べられないのは、見ている所が違うから。C1 は判定全体の結果だけ、C2 は各条件の値だけを見る。前の節の C2 の例のように、条件は全部 T・F を取ったのに判定は真のまま、ということが起こる。逆に C1 の例では、クーポン（C）は F しか取っていない。

MC/DC と MCC は、判定条件網羅をさらに強めたもの。MC/DC は「各条件が結果に効いているか」まで求め、MCC は効き目に関係なく全組み合わせを求める。

MC/DC の作り方：条件ごとに「効き目の組」を探す

MC/DC の要は独立性（independence）：ほかの条件を固定したまま 1 つの条件だけを変えると、判定の結果が変わることを、テストの組で示す。

  1. 条件を書き出す判定 (A && B) || C の条件は A・B・C の 3 つ。
  2. 条件ごとに組を探す真理値表から、その条件だけが違い、判定も違う 2 行を探す。例えば A なら No.2（TTF・真）と No.6（FTF・偽）。
  3. 組を重ねて行を減らすどの条件の組も共有できる行を優先して選ぶ。条件が N 個なら最少 N+1 行で済むことが多い。
  4. 期待値を仕様から決める選んだ行の正しい結果は、コードではなく仕様（ここでは送料のルール）から決める。
条件組（その条件だけが違う 2 行）判定の変化
A 会員No.2（T T F）と No.6（F T F）真 → 偽
B 5000円以上No.2（T T F）と No.4（T F F）真 → 偽
C クーポンNo.3（T F T）と No.4（T F F）。No.5 と 6、No.7 と 8 でもよい真 → 偽

A の組は No.2 と No.6 の 1 通りしかない。A が結果に効くのは「B が T で C が F」のときだけだからで、ほかの組（No.1 と No.5 など）は A を変えても判定が変わらない。こうした「効かない組み合わせ」を除けるので、MCC よりずっと少ない件数で、すべての条件が意味を持っていることを確かめられる。

例：演算子の取り違えを見つけられるか

書き手が && を || と打ち間違え、コードが isMember || total >= 5000 || hasCoupon になっていたとする。仕様どおりなら送料 500 円のはずの No.4（会員だが 5000 円未満）と No.6（会員でないが 5000 円以上）で、誤って無料になる。

カバレッジは書かれたコードに対して測るので、間違ったコードに対して各基準を満たすテストを選んだとき、No.4 か No.6 が必ず入るかを比べる。

基準間違ったコードで基準を満たすテストの例誤りが見つかるか
C0No.1 だけ見逃すことがある
C1No.1 と No.8（真と偽が 1 回ずつ）見逃すことがある
C2・判定条件網羅No.1（TTT）と No.8（FFF）見逃すことがある
MC/DC（unique-cause）No.4・No.6・No.7・No.8 の 1 通りしかない必ず見つかる
MC/DC（masking）No.1・No.5・No.7・No.8 でも満たせる見逃すことがある
MCC全 8 件必ず見つかる
どう選んでも誤りの出る行が入る誤りの出る行を含まない選び方がある

A || B || C では、A が結果に効くのは B と C が両方 F のときだけ。ほかの条件を固定して 1 つだけ変える unique-cause MC/DC はその行（No.4）を強制し、B についても同じ理由で No.6 を強制する。C0〜判定条件網羅は「通ったか」「値を取ったか」しか見ないので、運よく No.4・No.6 を選ばない限り誤りは表に出ない。

ただし、GCC や Clang が測る masking MC/DC（後述）では、A=T の行の B・C は評価されないので値は何でもよく、No.1（TTT）と No.8（FFF）の組で A の効き目を示せる。No.1・No.5・No.7・No.8 は仕様でも間違ったコードでも結果が同じなので、誤りは表に出ない。ツールの MC/DC が 100% でも、この種の誤りを必ず拾えるとは限らない。条件ごとの組を自分で選ぶときに、ほかの条件を固定した組（unique-cause の形）を選べば見つかる。

どの基準も、選んだ行の期待値を仕様から正しく書いて初めて誤りが見つかる。>= を > にした境界の誤りは、条件の真偽の組み合わせではなく値の選び方の問題なので、どの基準でも見逃しうる（境界値分析で拾う）。

短絡評価とツールが数えるもの

多くの言語の &&・|| は短絡評価（short-circuit evaluation）で、結果が決まった時点で右側を評価しない。例の判定では、A が F なら B は評価されず、A && B が T なら C は評価されない。

  • MCC は実際の件数が減る：評価される条件の値の並びで数えると、8 通りのうち区別できるのは 5 通り（A=F で C が T/F、A=T・B=F で C が T/F、A=T・B=T）。
  • MC/DC にも流儀がある：「ほかの条件を固定して 1 つだけ変える」厳密な形を unique-cause MC/DC、評価されない条件（結果に効かない条件）は違っていてもよいとする形を masking MC/DC と呼ぶ。短絡評価のある言語では masking の方が組を作りやすい。

ツールのレポートにある「branch」の意味も、ツールによって違う。率を指標にする前に、自分のツールが何を数えているかを確かめる。

ツール分岐として数えるもの条件・MC/DC
coverage.py（Python、--branch）ある行から次の行への移り（どちらの行へ進んだか）and・or の各項は数えない
Istanbul（JavaScript。nyc や Jest・Vitest の istanbul プロバイダ）if・三項演算子の両側に加え、&&・|| の各項が評価されたか各項の真偽の組み合わせは見ない

単体テストの指標として使う

カバレッジは「テストがどこを通っていないか」を機械的に教えてくれる数少ない指標で、単体テストの抜けを見つけるのに向いている。一方で「通った所を正しく確かめたか」は測らない。この性質を踏まえて使う。

  1. 分岐まで測る設定にする行・命令だけだと、else のない if の偽側が抜けても 100% になる。--branch など分岐を測る設定を入れ、分岐の率を見る。
  2. 率より「通っていない所」を読む未実行の分岐を 1 つずつ見て、テストを足すか、要らないコード（到達しない防御コードなど）かを判断する。率はその結果として上がるもの。
  3. しきい値は下限として使うCI では「変更で率が下がったら止める」「変更した行は高い率を求める」のように、悪化を防ぐ使い方が向く。全体の率を上げること自体を目標にすると、確かめないテストが増える。
  4. 複雑な条件は MC/DC で考えるツールが MC/DC を測れなくても、&&・|| が 3 つ以上並ぶ判定は、条件ごとの組を表にしてテストを選ぶ。条件が多すぎるなら、関数に分けて判定を単純にする方が先。
  5. 確かめているかは別の方法で見るアサーションの強さはミューテーションテスト、どの値を試すかは境界値分析やデシジョンテーブルで補う。

率の目安として、Google は 2020 年のブログで 60% を「許容できる」、75% を「称賛に値する」、90% を「模範的」としつつ、全チームに一律の数字を課すべきではないと書いている。安全性が求められる分野では、規格が基準そのものを決めている。

規格求められる構造カバレッジ
DO-178C（航空機のソフトウェア）レベル C：命令網羅。レベル B：＋判定網羅。レベル A（最も厳しい）：＋MC/DC
ISO 26262-6（自動車。ソフトウェアユニット）命令網羅は ASIL A・B で強く推奨、分岐網羅は ASIL B〜D で強く推奨、MC/DC は ASIL D で強く推奨（それ以外は推奨）

よくある誤解

C2（条件網羅）を満たせば C1（分岐網羅）も満たせる

満たせないことがある。各条件が T と F を取っても、判定全体が一度も偽にならない選び方がある（例では No.2 と No.7）。分岐も確かめたいなら判定条件網羅以上にする。

MC/DC は条件のすべての組み合わせを試す

全組み合わせは MCC（複合条件網羅）。MC/DC は各条件が単独で結果を変える組だけを求めるので、条件が N 個なら最少 N+1 件程度で済み、条件が増えても件数は直線的にしか増えない。

ツールの branch の率は C1（分岐網羅）のことだ

ツールによって違う。行の移りを数えるもの、&&・|| の各項まで数えるもの、オブジェクトコードの分岐を数えるものがあり、同じコードでも率は変わる。

カバレッジが 100% ならバグはない

カバレッジはコードが実行されたかしか見ない。アサーションのないテストでも上がり、境界値の誤りや、そもそも書かれていない処理（仕様の抜け）は見つからない。
