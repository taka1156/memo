テストから証明まで：正しさを確かめる 5 つの手法

Fuzzing・Property-based Testing・Design by Contract・モデル検査・形式検証を、数式なしで

ざっくり言うと
  • 5 つとも「プログラムが正しいか」を確かめる方法で、違いはどこまで広く・どれだけ確実に確かめるか。
  • はしごを進むほど、試す入力を増やす段階から、全部の場合をまとめて確かめる段階へ進む。そのぶん手間も増える。
  • 普段は例のテストに Fuzzing や PBT を足し、並行処理の設計や絶対に外せない部分だけ、検査や証明まで進める。

確かめ方のはしご

ふだん書くテストは「この入力ならこの答え」をいくつか試すものです。ここからはしごを進むほど、確かめる範囲が広く、結果が確実になります。代わりに、書くものと手間が増えます。

例のテスト境界値など、選んだ入力を数個試す
Fuzzing変な入力を大量に投げて、落ちないか見る
Property-based Testingルールを書いて、ランダムな入力で大量に試す
モデル検査設計の模型の状態を全部たどる
定理証明すべての入力で正しいと論証する
手軽・すぐ回せる確実・手間が大きい

Design by Contract（契約）は、はしごの 1 段ではありません。「何が正しいか」を書き表す方法で、どの段でも確かめる基準として使えます（下で説明）。

図で見る：確かめる範囲の違い

四角の 1 マスを「入力 1 つ」と考えます。右下の点線のマスだけにバグがあります。端の、めったに来ない入力で起きるバグ、という想定です。タブを切り替えて、各手法がどこまで確かめるかを見比べてください。

試したのは 3 マスだけ

人が選んだ入力だけを試す。上手に選ぶなら、バグが集まりやすい境界値（左端・真ん中・右端のような境目）を狙います。選んだ所はきちんと確かめられます。

それでも試せるのは、思いついた境目だけです。この図では横方向の端は試しましたが、縦方向の端と重なる右下の角は思いつきませんでした。テストは全部通るので、バグに気づけません。選び方は境界値分析と同値分割にまとめています。

端に寄った変な入力を大量に試す

ふつうは来ない入力を機械が大量に作って投げる。壊れたファイル、極端に長い文字列、ありえない数値などです。

見ているのは主に「落ちたか・固まったか」だけです。答えが合っているかまでは、ふつうは見ません。そのぶん準備が少なくて済み、端のバグに届きやすくなります。

ランダムに試し、失敗したら小さく縮める

「いつも成り立つはずのルール」を書いて、ランダムな入力で大量に試す。見るのは落ちたかではなく、ルールが成り立つかどうかです。

失敗する入力が見つかると、もっと小さく単純な入力へ自動で縮めて（shrink）くれます。矢印はこの縮める動きです。おかげで原因を調べやすくなります。

模型の中は 1 マス残らず調べる

設計を小さな模型にして、ありうる状態を全部たどる。たとえば「客は 2 人まで、在庫は 3 個まで」のように範囲を絞ります。その範囲の中は漏れなく調べ、バグの場所を全部見つけます。

調べるのは実物のコードではなく模型です。模型が実物と違えば、見逃しも出ます。

全体を 1 つずつではなく、まとめて扱う

1 マスずつ試すのではなく、「どのマスでも成り立つ」ことを筋道立てて示す。入力が無限にあっても扱えます。

バグがある所では証明が通りません。図の赤い枠のように、どこで成り立たないかが分かります。証明が全部通れば、書いた仕様の範囲ではすべての入力で正しいと言えます。

試した入力 バグが起きる入力 見つけたバグ 証明で全部確かめた範囲

共通の例：自動販売機

以下では、同じ自動販売機を例にして各手法を説明します。

  • 商品は 1 種類で 100 円。使える硬貨は 10・50・100・500 円。
  • 入れたお金が 100 円以上になったら、ボタンで商品とおつりが出る。
  • 在庫が 0 なら「売り切れ」で、お金は返す。

Fuzzing（ファジング）

変な入力を大量に与えて、壊れるかを見るFuzzing / fuzz testing

たとえ: 小さな子どもに自販機を触らせる。硬貨を 100 枚連続で入れる、ボタンを連打する、曲がった硬貨を押し込む。正しい使い方は知らないけれど、機械が止まったら壊れた場所が分かる。

今のファジングの多くはカバレッジ誘導型です。「新しい分かれ道を通った入力」を覚えておき、それを少しずつ変えて奥へ進みます。でたらめに投げるより、ずっと深い所まで届きます。

  1. 種を用意するふつうの入力をいくつか渡す（例: 正しい硬貨の並び）。
  2. 少し変える値を変える、つなぐ、削る、繰り返すなどを機械が自動でやる。
  3. 動かして見張る落ちた・固まった・メモリを壊した、を検出する。
  4. 新しい道を通った入力は種に足す次はそこからさらに変えて、奥の分かれ道を探す。

見つけやすいもの

  • クラッシュ・無限ループ・固まる
  • メモリ破壊（C/C++ など）
  • パーサや通信の入口の脆弱性

苦手なもの

  • 「落ちないが答えが違う」バグ（アサーションや契約を足すと拾える）
  • パスワードのように、正しい値でしか先へ進めない処理

主な道具: AFL++、libFuzzer（開発はバグ修正のみに縮小。今も広く使われる）、Go の go test -fuzz、Rust の cargo-fuzz。オープンソース向けには OSS-Fuzz があります。

Property-based Testing（PBT）

答えではなく「いつも成り立つルール」を書くProperty-based Testing

たとえ: 「150 円入れたらおつり 50 円」と 1 件ずつ書く代わりに、「どんな入れ方でも、おつり ＝ 入れた額 − 100 円」というルールを 1 つ書く。あとは機械が入れ方を何百通りも考えて試してくれる。

例のテスト

150 円入れる → おつり 50 円
500 円入れる → おつり 400 円
100 円入れる → おつり 0 円

書いた 3 件しか確かめない

プロパティ（ルール）

どんな硬貨の組み合わせでも
（合計 100 円以上なら）
  おつり ＝ 入れた額 − 100
  おつり ≧ 0

入力は機械が作る（1 回に数百通りほど。既定は道具しだいで、Hypothesis や fast-check は 100、proptest は 256、jqwik は 1000）

入力はでたらめではありません。多くの道具は、0・空の配列・空文字・とても大きな数のような端の値を出やすくしてあります。人が境界値を選ぶ作業の一部を、機械が肩代わりしてくれます。ただし、「65 歳からシニア料金」のような仕様の中の境目までは知りません。そうした境目は、人がテストに書くか、ルールの中で狙って入力を作らせます。

失敗したら「縮める」

たとえば、おつりに 50 円玉が入る場合だけ計算を間違えるバグがあるとします。機械がランダムに試すと、最初は複雑な入力で失敗が見つかります。そこから PBT の道具は、失敗したままの、もっと単純な入力へ自動で縮めます。

  1. 見つかった失敗[100, 10, 500, 50, 10] を入れると、おつりが 570 円のはずなのに 520 円
  2. 硬貨を減らして試す失敗が続く限り、硬貨を減らしたり小さくしたりする
  3. 最小の失敗[100, 50] を入れると、おつり 50 円が出ない。これで「50 円玉のおつり」が怪しいと分かる

赤い丸は、ルールが破れた（失敗した）入力です。

ルールの見つけ方

  • 行って戻る: 保存して読み込んだら元どおり（decode(encode(x)) == x）。
  • 順番によらない: 硬貨を入れる順番を変えても、おつりは同じ。
  • 2 回やっても同じ: 並べ替えた物をもう一度並べ替えても変わらない。
  • 素朴な版と比べる: 速い実装と、遅いが分かりやすい実装の答えが一致する。

主な道具: fast-check（JavaScript / TypeScript）、Hypothesis（Python）、QuickCheck（Haskell）、proptest（Rust）、jqwik（Java）。

Design by Contract（契約による設計）

関数の「約束」を、コードに書いて確かめるDesign by Contract

たとえ: お店と客の約束。客は「100 円以上入れる」と約束し、店は「商品と正しいおつりを出す」と約束する。どちらが約束を破ったかで、どちらの責任かが決まる。

事前条件呼ぶ側が守る約束入れた額 ≧ 100 円／硬貨は 10・50・100・500 円だけ／在庫 ≧ 1
買う()関数の中身商品を出し、おつりを計算し、在庫を減らす
事後条件関数が守る約束おつり ＝ 入れた額 − 100／在庫が 1 減った
不変条件（いつ見ても成り立つ約束）：在庫は 0 以上／機械の中のお金は、マイナスにならない

約束が破れたら、その場で止めて知らせます。どの約束が破れたかで、直す場所が分かるのが大きな利点です。

破れた約束悪いのは
事前条件呼ぶ側（たとえば 50 円しか入っていないのに「買う」を呼んだ）
事後条件関数の中身（おつりの計算が間違っている）
不変条件状態を変えた処理のどれか（在庫を減らしすぎた）

契約は、ほかの手法と組み合わせると強くなります。Fuzzing や PBT で大量に動かすと、その間ずっと契約が「答えは正しいか」を見張ります。Dafny のような検証用の言語では、契約がそのまま証明する仕様になります（定理証明の例）。

言語の機能として持つ例: Eiffel（この考え方を広めた言語）、D、Ada / SPARK、Dafny。そのほかの言語でも assert やライブラリで書けます。

モデル検査

設計の模型の状態を、機械が全部たどるModel Checking

たとえ: 迷路の分かれ道を、ロボットに 1 本残らず歩かせる。行き止まりやゴールに着けない道があれば、その道順を教えてくれる。

いちばん力を発揮するのは、複数のものが同時に動く場面です。順番の組み合わせが多すぎて、人も普通のテストも見落とすからです。

例：在庫が 1 個なのに、2 人が同時にボタンを押す

自販機がネットにつながり、スマホからも買えるとします。「買う」は次の 2 段階で動きます。

  1. 在庫を見る在庫が 1 以上なら「売れる」と判断する
  2. 商品を出して、在庫を 1 減らす段階 1 で見た在庫の数から 1 を引いて書き込む

A さんと B さんがそれぞれこの 2 段階を進めると、実行の順番は全部で 6 通りあります。モデル検査はこの 6 通りを全部試します。

順番（A1 = A さんの段階 1）結果
A1 → A2 → B1 → B2A さんが買い、B さんは売り切れOK
B1 → B2 → A1 → A2B さんが買い、A さんは売り切れOK
A1 → B1 → A2 → B22 人とも在庫 1 を見たので、2 個出そうとするNG
A1 → B1 → B2 → A2同上NG
B1 → A1 → A2 → B2同上NG
B1 → A1 → B2 → A2同上NG

手元のテストでは、ほとんど毎回 1 行目の順で動くので、テストは通ってしまいます。本番でたまにしか起きず、再現もしにくい種類のバグです。モデル検査なら、失敗する順番そのものを示してくれます。

見つけやすいもの

  • 同時に動くときの順番の不具合（競合状態）
  • デッドロック（お互いを待って止まる）
  • 分散システムの設計ミス

限界

  • 状態の数がすぐ爆発的に増える（状態爆発）。模型を小さく絞る必要がある
  • 確かめるのは模型。実物のコードとずれると見逃す

主な道具: TLA+（TLC）、Alloy、SPIN。C のコードを直接、範囲を区切って調べる CBMC のような道具もあります。

形式検証（定理証明）

すべての入力で正しいことを、論証して機械に確かめさせるFormal Verification / Theorem Proving

たとえ: 「偶数 ＋ 偶数 は必ず偶数」。これを信じるのに、すべての数を足して確かめた人はいません。「偶数は 2 × 何か と書ける。足しても 2 × 何か になる」という筋道で、無限にある組み合わせを一度に片づけられるからです。

定理証明は、この筋道をプログラムに対して行います。人が書いた（AI が書いた）筋道に穴がないかは、ツールが 1 段ずつ機械的に調べます。ツールが受け入れた証明は、書いた人を信用しなくても信用できます。

数式を書かなくてもよい例（Dafny）

Dafny という言語では、契約を書くだけで、ツールが自動で証明を探します。

method Change(paid: int, price: int) returns (change: int)
  requires paid >= price   // 事前条件：入れた額 ≧ 価格
  ensures change >= 0      // 事後条件：おつり ≧ 0
{
  change := paid - price;
}

このコードを Dafny に通すと、「事前条件を満たすすべての paid と price で、おつりは 0 以上」と確かめられます。テストのように値を試してはいません。仮に requires の行を消すと、Dafny は「事後条件を証明できない」と指摘します。

向いている所

  • 間違えると被害が大きい所（暗号、OS のカーネル、コンパイラ、決済の中心部）
  • 何年も変わらない、小さくて大事な部品

限界

  • 手間が大きい。難しい性質は、人が証明の道筋を書く必要がある
  • 保証されるのは書いた仕様どおりであること。仕様が間違っていれば意味がない

主な道具: 自動寄りの Dafny・SPARK、人が道筋を書く Lean・Rocq（旧 Coq）・Isabelle。実例として、証明済みの C コンパイラ CompCert や、OS カーネル seL4 があります。

言葉の整理：「形式検証」はどこまでを指す？

「形式検証」は、広い意味では数学的な方法で正しさを確かめる手法の総称です。モデル検査も定理証明もその中に入ります。狭い意味で「証明すること」だけを指す人もいます。

形式検証（広い意味）：仕様を厳密に書き、機械が漏れなく確かめる
モデル検査状態を全部たどる。自動で動き、反例（失敗する道順）を出してくれる
定理証明論証で全部をまとめて扱う。無限の入力も扱えるが、手間が大きい
FuzzingPBT例のテスト＝ 試して探す側（形式検証には入らない）

Design by Contract はその間にあります。実行時に確かめれば「試す側」、Dafny のように証明に使えば「形式検証の仕様」になります。また、TypeScript や Rust の型チェックも「すべての入力について、ある性質を機械が確かめる」という点で、軽い形式検証の仲間と見ることができます。

どれも新しい考え方ではありません。証明の考え方は 1960 年代、契約とファジングは 1980 年代、PBT は 2000 年ごろから広まりました。最近注目されているのは、AI が書いたコードや証明を、ツールで機械的に確かめる使い方が増えているためです（2026 年 11 月時点）。

5 つの比較

手法人が書くもの確かめる範囲得意なこと手間
例のテスト入力と期待する答え書いた分だけ決まった仕様の確認小
Fuzzing入力を流し込む入口（ハーネス）大量・ランダム（実物のコード）クラッシュ・固まる・脆弱性小〜中（回す時間は長め）
PBTいつも成り立つルール大量・ランダム（実物のコード）境界や組み合わせの見落とし中
契約事前・事後・不変条件動かすたび（または証明で全部）責任の切り分け・早期発見小〜中
モデル検査設計の模型と、守るべき性質模型の全状態並行・分散の順番の不具合中〜大
定理証明仕様と証明（の道筋）すべての入力絶対に外せない部分の保証大

いつどれを使う？

こんなときまず試す手法
外から来るデータを読む（ファイル・通信・ユーザー入力のパーサ）Fuzzing
「元に戻る」「順番によらない」など、ルールが言える関数PBT
関数やクラスの責任の範囲をはっきりさせたい契約
複数のプロセスやサーバーが同時に動く設計を作るモデル検査
間違えると大事故・大損・重大な脆弱性につながる、小さな中心部定理証明

実際には組み合わせて使います。よくあるのは、契約を書き、PBT や Fuzzing で大量に動かして、その間ずっと契約に見張らせるやり方です。設計の段階でモデル検査を使い、実装は普通のテストで確かめる、という分け方もよく使われます。

よくある誤解

形式検証で証明すれば、バグは 1 つもなくなる

保証されるのは「書いた仕様どおりに動く」ことだけです。仕様そのものが意図とずれていれば、正しく間違えます。また、証明の前提の外（コンパイラ、OS、ハードウェア、設定、外部のサービス）は保証の外です。

Fuzzing を長く回しても何も見つからなければ、そのコードは安全だ

見つからないことは、ないことの証明にはなりません。届いていない分かれ道が残っていることもあります。どのコードを通ったか（カバレッジ）を見て、届いていない所を確かめます。

PBT はランダムなので、失敗しても再現できない

道具は失敗したときの乱数の種（seed）と、縮めた最小の入力を報告します。同じ種で再実行すれば再現できます。Hypothesis のように、失敗した例を保存して次回も必ず試す道具もあります。

形式検証は数学者でないと使えない

モデル検査は、模型と性質を書けば機械が自動で調べます。Dafny のような道具では、条件（契約）を書くだけで証明が自動で見つかることも多いです。難しい証明を人が書くのは、一部の深い性質だけです。

契約はコメントに書く注意書きと同じだ

コメントは実行しても誰も確かめません。契約はコードとして書くので、動かすたびに確かめられ、破れたらその場で止まります。証明に使える道具もあります。
