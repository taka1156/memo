Rust 学習フローと仕組み

どの順で学ぶか ＋ コンパイラが何を保証しているか

ざっくり言うと
  • Rust は GC（ガベージコレクタ）なしでメモリ安全を実現する言語。その鍵が 所有権 (ownership)・借用 (borrowing)・ライフタイム (lifetime)。
  • 安全性のチェックは実行時ではなくコンパイル時に行われる。だから「コンパイルが通れば、メモリ破壊やデータ競争は起きにくい」。
  • 学習は「基本文法 → 所有権 → 型（enum / トレイト）→ エラー処理 → 実践」の順が王道。所有権で一度つまずくのは全員通る道。

仕組み 1: コンパイル時に何をしているか

Rust のコンパイラ rustc は、ソースコードを段階的に変換しながらチェックする。安全性の要となる借用チェッカ (borrow checker) は、中間表現 MIR の上で動く。

ソース.rs ファイル
→
AST / HIR構文解析
マクロ展開
→
型チェック型推論
トレイト解決
→
MIR借用チェック
ライフタイム検証
→
LLVM IR最適化
→
機械語実行ファイル

太枠が「Rust らしい安全性」を保証する段階。ここで弾かれたコードは実行ファイルにならない。所有権・借用の検査はコンパイル時に終わるので、そのぶんの実行時コスト（GC など）はかからない（配列の範囲チェックなど、一部のチェックは実行時に残る）。

仕組み 2: 所有権 — スタックとヒープで見る

String の中身（文字列データ）はヒープ、変数はスタックにある「ポインタ・長さ・容量」の組。代入したときに何が起きるかを比べる。

let s1 = String::from("hello");
let s2 = s1;           // 所有権が s2 へ移動（ムーブ）
// println!("{s1}");  // ✕ コンパイルエラー: borrow of moved value
println!("{s2}");      // ○

ヒープのデータはコピーされず、持ち主の名札だけが付け替わる。もし s1 も有効なままだと、スコープを抜けたとき同じメモリを 2 回解放してしまう（二重解放）。Rust はそれをコンパイル時に禁止する。

let s1 = String::from("hello");
let s2 = s1.clone();   // ヒープのデータごと複製
println!("{s1} {s2}"); // ○ 両方使える

持ち主が 2 人になる代わりに、データも 2 つになる。コストがあるので明示的に .clone() と書かせる設計。

fn len(s: &String) -> usize { s.len() }

let s1 = String::from("hello");
let n = len(&s1);      // 貸すだけ。所有権は s1 のまま
println!("{s1} {n}");  // ○ s1 はまだ使える

参照は「持ち主を指す矢印」。借りた側がスコープを抜けても、データは解放されない。

let a: i32 = 5;
let b = a;             // i32 は Copy 型 → ビットごと複製
println!("{a} {b}");   // ○ 両方使える

整数・浮動小数点・bool・char・それらだけのタプルなどは Copy トレイトを実装しており、代入してもムーブではなくコピーになる（自作の struct も、中身がすべて Copy なら #[derive(Clone, Copy)] で Copy にできる）。ヒープを持つ String や Vec は Copy にできない。

スコープを抜けた値は、所有者が自動で drop して解放する（RAII）。手動の free は不要。

仕組み 3: 借用ルール

同じ値に対して、ある時点で持てる参照は次のどちらか一方だけ。

&T 共有参照

何個でも OK。ただし読み取り専用。

&s&s&s
読む人は大勢いてもいい

&mut T 可変参照

同時に1 つだけ。他の参照と共存できない。

&mut s&s&mut s
書く人がいる間は誰も見られない 
let mut v = vec![1, 2, 3];
let first = &v[0];     // 共有参照
// v.push(4);          // ✕ 可変借用と共有参照が同時に存在
println!("{first}");   // ← first の最後の使用。ここで共有参照は終わる
v.push(4);             // ○ もう共有参照がないので OK

なぜ禁止？ push で Vec が再確保されると、first は解放済みメモリを指す「ダングリング参照」になる。このルールはその事故とデータ競争を同時に防いでいる。参照の有効範囲は「最後に使われた場所まで」で判定される（NLL: Non-Lexical Lifetimes）。

仕組み 4: ライフタイムとエラー処理

// 戻り値の参照は、x と y の「短い方」と同じだけ生きる
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

ライフタイムは「寿命を延ばす」ものではなく、参照同士の寿命の関係をコンパイラに伝える注釈。これがあるから「関数が返した参照が、元データより長生きしていないか」を検査できる。

引数が 1 つ、または &self メソッドなどは省略規則 (lifetime elision) で自動推論されるので、普段書く場面は限られる。

use std::{fs, io};

fn read_config() -> Result<String, io::Error> {
    let text = fs::read_to_string("config.toml")?; // 失敗なら即 Err を返す
    Ok(text)
}

match read_config() {
    Ok(t)  => println!("{t}"),
    Err(e) => eprintln!("読めなかった: {e}"),
}

例外 (exception) はない。失敗の可能性は戻り値の型に現れるので、呼び出し側は見落としにくい（成功時の値を使うには match や ? などで取り出す必要があり、結果を使わずに捨てるとコンパイラが警告する）。

よくある誤解

clone() を使うのは負け

学習初期は clone で回避して動かすのが正解。動いてから、借用に置き換えて最適化すればいい。

ライフタイムを毎回書く必要がある

省略規則で大半は不要。コンパイラに求められたときに書けば足りる。

GC がない ＝ 手動でメモリを解放する

所有者がスコープを抜けると自動で drop される（RAII）。free を書くことはない。

unsafe はバグだらけの危険なコード

「コンパイラが安全性を確かめられない操作（生ポインタの参照外しや FFI 呼び出しなど）を、人間が責任を持って保証する」という印。範囲を小さく閉じ込め、safe な API で包むのが作法。

コンパイルエラーが多い ＝ 書きにくい言語

実行時に出るはずだったバグを前倒しで見せている。エラーメッセージには直し方の提案（help:）まで付くので、読むこと自体が学習になる。
