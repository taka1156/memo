OpenTofu 概念図

設定ファイルから State・Provider を経てインフラに反映されるまでの流れと、役割ごとのファイル名の対応

ざっくり言うと
  • *.tf ファイル（設定）に「あるべき状態」を書く。手順ではなく結果を書く点が Ansible と違う
  • tofu plan は State（前回の実行結果の記録）を実体の現状で更新したうえで設定と比べ、変更点だけを洗い出す
  • 実際のクラウド API を叩くのは Provider（プラグイン）。tofu apply が Provider 経由でインフラに反映する

概念図

青＝自分で書く定義ファイル、緑＝実行時の処理ステップ、紫＝State（実行結果の記録）、黄緑＝外部との接続。破線は参照・取り込みを表す。

定義ファイル 実行ステップ State（記録） 外部との接続 破線＝参照・取り込み

役割ごとのファイル名

ファイル名は 1 ファイルにまとめても動くが、慣例として役割ごとに分けることが多い。同じディレクトリ内の .tf（OpenTofu 1.8 以降は .tofu も）ファイルはすべてまとめて 1 つの「設定」として読み込まれる。

概念種別ファイル / 場所役割
Terraform Block全体設定 設定 versions.tf OpenTofu 自体のバージョン制約、required_providers（使う Provider とそのバージョン）を書く。
Provider 設定 定義 providers.tf どの Provider をどの認証情報・リージョンで使うか（provider "aws" { region = ... }）。
Resource 定義 main.tf 作りたいインフラの「あるべき状態」。resource "aws_instance" "web" { ... } のように書く。
Variables入力値 定義 variables.tf variable "name" { type = ... } で入力項目を宣言する（値そのものではなく器）。
Variables値 定義 terraform.tfvars*.auto.tfvars variables.tf で宣言した変数に実際の値を入れる。環境ごとに分けられる。
Outputs 定義 outputs.tf apply 後に表示・他の仕組みから参照したい値（IP アドレスなど）を定義する。
Locals 定義 locals.tf 設定内だけで使う計算済みの値。変数のように外からは渡せない。
Module 定義 modules/<名前>/ Resource 群をひとまとめにした再利用部品。自前でも Registry 公開のものでも可。
Backend 設定 接続 backend.tf State をどこに保存するか（backend "s3" { ... } など）。チームで共有する場合は必須。
State 記録 terraform.tfstate 最後に apply した時点の実体の記録。手で編集しない。Backend 未設定時はローカルに作られる。
Lock File依存関係 設定 .terraform.lock.hcl init 時に決まった Provider の正確なバージョンを固定する。Git にコミットする。
キャッシュ 生成物 .terraform/ init でダウンロードされた Provider 本体・Module の実体。.gitignore に入れる。

ディレクトリ構成例

project/
├── versions.tf           # OpenTofu / Provider バージョン
├── providers.tf          # Provider 設定
├── backend.tf            # State の保存先
├── main.tf                # Resource 定義
├── variables.tf          # 入力変数の宣言
├── outputs.tf             # 出力値
├── locals.tf               # 内部変数
├── terraform.tfvars      # 変数の値
├── .terraform.lock.hcl  # 依存バージョンの固定
├── .terraform/            # init の生成物（Git 管理外）
└── modules/
    └── web-server/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
# main.tf
resource "aws_instance" "web" {
  ami           = "ami-0abcd1234"
  instance_type = var.instance_type   # variables.tf を参照

  tags = {
    Name = "server-${var.env}"
  }
}
# variables.tf（器の宣言）
variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "env" {
  type = string
}

# terraform.tfvars（実際の値）
env = "staging"

各要素の考え方

Resource 何を作るか

手順ではなく「こうあってほしい」という結果を宣言する（宣言的）。同じ Resource ブロックを何度 apply しても、既に望む状態ならなにも変わらない。

State 今の状態の記録

OpenTofu が「前回自分が何を作ったか」を知っている唯一の手がかり。plan はこの State を実体の現状で更新（refresh）してから設定ファイルと比較して差分を出す。壊れたり他人と競合したりすると大きな事故につながるため、チームでは Backend（S3 など）で共有しロックをかける。また State には DB のパスワードなど機密の値も平文で入るので、保存先の読み取り権限を絞る。OpenTofu では State そのものを暗号化する設定もできる。

Provider 誰が実行するか

AWS・GCP・Azure など、クラウドごとの API 呼び出しを引き受けるプラグイン。init でダウンロードされ、apply 時に実際の作成・変更・削除リクエストを送る。Ansible の Connection Plugin に近い役割だが、対象は「サーバーへの接続」ではなく「API」。

Module まとめて使い回す

複数の Resource をまとめた部品。呼び出し元からは Resource と同じ感覚で module "web" { source = "./modules/web-server" } のように使う。

Data Source 作らずに読むだけ

data "aws_ami" "ubuntu" { ... } のように書き、すでにあるもの（最新の AMI、別チームが作った VPC など）を Provider 経由で読み取って値として使う。Resource と違って作成・削除はせず、State には読み取った結果が入るだけ。参照は data.aws_ami.ubuntu.id の形になる。

Plan と Apply 安全に反映する

plan は「何が変わるか」を事前に見せるだけで何も実行しない。内容を確認してから apply で実際に反映する、という 2 段階が事故を防ぐ仕組みになっている。

実行の流れ

初めてのディレクトリで tofu apply までを行う場合の順序。

tofu init設定を解析し、必要な Provider と Module をダウンロードする。.terraform.lock.hcl を書く（または検証する）。
tofu planまず Provider 経由で実際のリソースの現状を読んで State を最新にし（refresh。State ファイル自体は書き換えない）、それと設定ファイルを比較して（State がなければ空として扱う）、作成・変更・削除される Resource の一覧（実行計画）を作る。
内容を確認するplan の出力（+ 追加 / ~ 変更 / - 削除）を見て、意図通りか確認する。
tofu apply承認後、計画どおりに Provider 経由で API を呼び、実際にインフラを作成・変更する。
State を更新する成功した Resource の情報を State に書き込む。次回の plan はこの新しい State を基準にする。

依存関係と並列実行

Resource を書く順番は関係ない。OpenTofu は Resource 同士の参照から依存グラフを作り、依存が解けたものから並行して作る（同時に動かすのは既定で最大 10 個まで。-parallelism で変えられる）。

矢印は「先に作るもの → それを参照するもの」。削除（tofu destroy）はこの逆順で、EC2 インスタンスから消える。

暗黙の依存 参照が順番になる

vpc_id = aws_vpc.main.id のように別の Resource の属性を参照すると、それだけで「VPC が先」という依存になる。VPC の ID は作るまで決まらないので、plan では (known after apply) と表示される。

depends_on 参照に表れない依存

属性を参照しないが順番が必要なとき（IAM の権限を付けてからでないと動かないアプリ、など）だけ depends_on = [aws_iam_role_policy.app] で明示する。参照で表せるなら参照で書くほうが、何に依存しているかが読み取れる。

plan の記号と作り直し

plan の出力の行頭の記号で、何が起きるかがわかる。特に -/+ は見落とすと事故になる。

記号意味起きること
+create新しく作る。
~update in-place今ある実体のまま設定を変える（タグの変更など）。
-/+replace削除してから作り直す。その場で変えられない属性（EC2 の AMI など）を変えたとき。原因の属性に # forces replacement が付く。中のデータや IP は失われる。
+/-replace先に新しいものを作ってから古いものを消す（create_before_destroy を付けたとき）。
-destroy削除する。
<=readData Source を読む（値が apply まで決まらないとき）。

lifecycle 作り直し・削除の扱いを変える

Resource の中に lifecycle { ... } を書くと、差分の扱いを変えられる。

  • create_before_destroy = true … 作り直すとき、新しいほうを先に作る。止まる時間を減らせるが、名前が重複できないものでは使えない。
  • prevent_destroy = true … この Resource を消す plan をエラーにする。本番 DB などの誤削除よけ。
  • ignore_changes = [tags] … 外の仕組みが書き換える属性を差分として扱わない。

count と for_each

同じ Resource を複数作る方法は 2 つあり、State の中での呼び名（アドレス）が違う。["a", "b", "c"] の 3 つを作ったあと、"b" を消したときの plan を比べる。

count 番号で呼ぶ

web[0] a変わらない
web[1] b → c中身が変わる
web[2] c削除

番号が詰まるので、b を消しただけなのに c まで変更・作り直しの対象になる。

for_each キーで呼ぶ

web["a"]変わらない
web["b"]削除
web["c"]変わらない

キーで対応するので、消したものだけが消える。

変わらない 変更・作り直し 削除

どれも同じものを N 個並べるだけ（台数だけを変える）なら count、名前や設定がそれぞれ違うものを並べるなら for_each を使う。count = var.enabled ? 1 : 0 のように「作るか作らないか」の切り替えにも count がよく使われる。

コードと実体のずれを直す

設定・State・実体の 3 つがずれたときに使うもの。moved などのブロックはコードに残るので、PR でレビューでき、ほかの環境にも同じ操作が適用される。

起きたこと使うもの何が起きるか
コンソールで手で設定を変えた（ドリフト）tofu planrefresh で実体の変化を見つけ、設定どおりに戻す差分を出す。手の変更を残したいなら、設定のほうを合わせる。
手で作った実体を管理下に入れたいimport ブロック / tofu import実体を State に登録する。設定は自分で書くか、tofu plan -generate-config-out=生成先.tf で下書きを作る。
Resource の名前を変えた・Module に移したmoved ブロック作り直さずに State 上のアドレスだけを移す。書かないと「古い名前を削除・新しい名前を作成」になる。
管理をやめたい（実体は残す）removed ブロック / tofu state rmremoved ブロックに lifecycle { destroy = false } を書くと、State から外すだけで実体は消さない（destroy = true だと実体も削除される）。tofu state rm でも外せるが、コードに記録が残らない。
 
# aws_instance.web を Module の中に移したとき
moved {
  from = aws_instance.web
  to   = module.web.aws_instance.this
}

# 管理だけやめて、実体は残すとき
removed {
  from = aws_instance.legacy
  lifecycle {
    destroy = false
  }
}

よくある質問

OpenTofu と Terraform は別の言語？いいえ
State を手で直接編集してよい？非推奨
.terraform/ は Git にコミットする？しない
.terraform.lock.hcl は Git にコミットする？する
変数に sensitive = true を付ければ State からも隠れる？いいえ
plan が通れば apply も必ず成功する？いいえ

sensitive = true は plan や出力の画面で値を伏せるだけで、State には平文で入る。また plan は設定と State の差分を計算するだけなので、名前の重複・権限不足・上限（クォータ）など、API を実際に呼んで初めてわかるエラーは apply で起きる。途中で失敗しても、成功した Resource は State に記録されるので、直して apply し直せば続きから進む。

OpenTofu は、Terraform のライセンスが BSL に変わったことを受けて、最後のオープンソース版（1.5 系）からフォークされたプロジェクトで、現在は Linux Foundation 配下の CNCF でホストされている。HCL 構文・State 形式・Provider エコシステムに高い互換性がある。コマンド名が terraform から tofu に変わるほか、State の暗号化など OpenTofu 独自の機能も追加されている。State を直接編集したい場合は tofu state コマンド群（mv / rm など）や tofu import、上の moved などのブロックを使う。
