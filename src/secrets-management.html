シークレット管理

API キー・パスワード・秘密鍵をどこに置き、どう渡し、どう替えるか

ざっくり言うと
  • シークレットは「持っているだけで本人として振る舞える」値で、Git・ログ・イメージ・フロントエンドのコードから漏れやすい。
  • 置き場所は .env → プラットフォームの Secrets → シークレットマネージャー → 期限付きの動的シークレット → そもそも持たない、の順に安全になる。
  • 漏れたら履歴を消すより先に無効化して替える。替えても止まらないよう、2 つを並行して有効にできる作りにしておく。

シークレットとは

API キー、DB のパスワード、クラウドのアクセスキー、OAuth のクライアントシークレット、署名用の秘密鍵、Webhook の検証用の鍵など、知っているだけで本人（そのサービス）として振る舞えてしまう値です。パスワードのように人が覚えるものではなく、プログラムが使うものがほとんどです。

扱いの基本は 3 つです。見られる人と場所を最小にする、有効な期間を短くする、漏れたときにすぐ替えられるようにする。以下はこの 3 つをどう実現するかの話です。

どこから漏れるか

Git のコミット

設定ファイルや .env を一度コミットすると、消すコミットを足しても履歴に残る。公開リポジトリは数分で自動収集される。

ログ・エラー出力

リクエスト全体や環境変数をそのままログに出す。例外のスタックトレースに接続文字列が載る。

コンテナイメージ

ビルド中に COPY .env や ARG で渡した値がレイヤーや履歴に残る。後の層で消しても前の層から取り出せる。

フロントエンドのコード

ブラウザに配るバンドルに入れた値は誰でも読める。NEXT_PUBLIC_ や VITE_ の付いた環境変数はバンドルに埋め込まれる。

CI のログ・成果物

デバッグで env を出力する。マスクは完全一致でしか効かず、加工された値は素通しになる。

チャット・チケット・AI ツール

「これで動かない」と設定を丸ごと貼る。共有の場所は見られる人が多く、消しても控えが残る。

どれも「シークレットを、見られる人の多い場所に、長く有効なまま置いた」ことが原因。置き場所・期間・替えやすさで防ぐ。

置き場所の段階

上ほど漏れやすく、下ほど安全です。いきなり一番下を目指さなくても、1 段下がるだけで効果があります。

0
コードに直書き

リポジトリを見られる人全員と、履歴を取得した全員に漏れる。替えるにはコードの変更とデプロイが要る。

const API_KEY = "sk_live_..."
1
.env ファイル（Git に入れない）

手元の開発では普通の形。.gitignore に入れ、見本は値を空にした .env.example にする。サーバーにファイルを手で置く運用は、誰が持っているか分からなくなりやすい。

.env / .env.example
2
プラットフォームの Secrets

GitHub Actions の Secrets、Cloudflare Workers の secret、Kubernetes の Secret など。実行時だけ環境変数やファイルとして渡される。権限で読める人を絞れる。

wrangler secret put / gh secret set
3
シークレットマネージャー

HashiCorp Vault、AWS Secrets Manager、Google Secret Manager、Azure Key Vault など。誰がいつ読んだかの監査ログ、版の管理、自動ローテーションがある。アプリは起動時や実行中に API で取りに行く。

vault kv get / aws secretsmanager get-secret-value
4
動的シークレット

頼まれるたびに期限付きの認証情報を新しく作って渡し、期限が来たら消す。Vault の database secrets engine なら、アプリごと・起動ごとに別の DB ユーザーが作られ、リース（lease）が切れると削除される。

vault read database/creds/readonly
5
そもそも持たない

実行環境そのものの身元（ワークロード ID）で、その場限りの認証情報をもらう。CI から OIDC でクラウドに入る、クラウド上のサーバーに IAM ロールを付ける、など。保存するシークレットがないので漏れようがない。

permissions: id-token: write
避けるできるならここを目指す

環境変数で渡すときの注意

アプリへの渡し方としては、環境変数がいちばん一般的です。コードと設定を分けられ、どの言語からも読めます。ただし、思ったより多くの場所から見えます。

見えてしまう場所対策
子プロセス（環境変数は引き継がれる）外部コマンドを呼ぶときは必要な変数だけを渡す
クラッシュレポート・エラー監視・デバッグ用のエンドポイント送る前に環境変数を除く設定にする。/debug/env のような画面を本番で出さない
同じユーザーで動くほかのプロセス（Linux の /proc/<pid>/environ）アプリごとにユーザーやコンテナを分ける
docker inspect・Kubernetes の Pod 定義値を直接書かず、Secret の参照にする。読める人を RBAC で絞る

環境変数の代わりに、メモリ上のファイル（tmpfs）としてマウントし、権限を絞って（例: 0400）読ませる方法もある。Kubernetes の Secret をボリュームでマウントすると tmpfs 上のファイルになる。権限の既定は 0644 なので、絞るには defaultMode を指定する。値を更新すると、Pod を再起動しなくてもしばらくして反映される（subPath でマウントした場合は反映されない）。

Git に置きたいとき：値だけ暗号化する

設定はリポジトリで管理したい（GitOps）が、シークレットは平文で置けない、というときは、SOPS で暗号化してからコミットします。SOPS は YAML・JSON・ENV などのキーの名前は残し、値だけを暗号化するので、差分でどの項目が変わったかが分かります。

db:
    user: app
    password: ENC[AES256_GCM,data:3q9f...,iv:...,tag:...,type:str]
sops:
    kms:
        - arn: arn:aws:kms:ap-northeast-1:111122223333:key/...
          enc: AQICAH...                 # 暗号化されたデータ鍵
データ鍵で値を暗号化

ファイルごとにランダムな鍵を作り、各値を AES-GCM で暗号化

データ鍵を親鍵で暗号化

親鍵は KMS（AWS・GCP・Azure）、age、PGP などにあり、ファイルには出てこない

復号できるのは親鍵を使える人だけ

KMS なら IAM の権限で決まる。権限を外せば、その人はもう復号できない

このように「中身を暗号化する鍵」をさらに別の鍵で暗号化する形を、エンベロープ暗号化（envelope encryption）と呼びます。KMS の親鍵は外に出ないので、取り出して持ち去られる心配がありません。Kubernetes では、SOPS のほか、クラスタの公開鍵で暗号化してコミットする Sealed Secrets や、外部のシークレットマネージャーから値を取ってきて Secret を作る External Secrets Operator がよく使われます。

シークレットを持たない：OIDC とワークロード ID

  1. CI がその実行専用のトークンをもらうGitHub Actions はジョブごとに、「どのリポジトリの、どのブランチの、どのワークフローか」を書いた署名付きの OIDC トークンを発行する。
  2. クラウドに見せて、短期の認証情報と交換するクラウド側には「このリポジトリの main ブランチからなら、このロールを使ってよい」と前もって登録しておく。
  3. ジョブが終われば使えなくなる認証情報は 1 時間ほどで切れる。リポジトリの Secrets に長期のアクセスキーを置かなくてよい。

CI の設定の具体例は CI/CD と GitHub Actions にあります。同じ考え方で、クラウドのサーバーや Kubernetes の Pod にも身元（IAM ロール、サービスアカウント）を付け、そこから短期の認証情報をもらえます。信頼の条件を広げすぎないのがこつで、「どのリポジトリでも」「どのブランチでも」にすると、他人のリポジトリやフォークから入られます。

ローテーション：止めずに替える

替えるたびにサービスが止まると、誰も替えなくなります。古い値と新しい値が同時に有効な期間を作れば、止めずに替えられます。

  1. 新しい値を発行する古い値はまだ有効なまま。多くの API は、キーを 2 つ同時に持てる。
  2. 使う側を新しい値に切り替えるシークレットマネージャーの値を更新し、アプリが読み直す（再起動、または定期的な再取得）。
  3. 古い値が使われていないことを確かめるアクセスログや最終使用日時で確認する。
  4. 古い値を無効にするここで初めて消す。

署名の検証鍵（JWT の公開鍵、Webhook の署名鍵など）も同じで、検証する側は新旧両方の鍵を受け付ける期間を設ける。JWT なら鍵に ID（kid）を付けて、どちらの鍵で署名したかを示す（JWT とセッション）。

漏れたときの手順

  1. まず無効化して替える履歴の掃除より先。公開リポジトリに push した時点で、もう誰かが取ったと考える。GitHub の文書も、まず無効化・ローテーションするよう勧めている。
  2. 使われた形跡を調べる漏れた時刻から無効化までの間に、そのキーでの操作がないかをサービス側のログで確かめる。
  3. 履歴から消す（必要なら）git filter-repo --sensitive-data-removal で履歴を書き換えて force push する。ほかの人の clone やフォーク、キャッシュには残るので、これは後始末であって対策ではない。
  4. 次を防ぐGitHub のプッシュ保護（push protection）で、既知の形式のシークレットを含む push を止める。手元では gitleaks などを pre-commit フックで回す。

赤い番号の 1 番目が、いちばん急ぐ手順。2〜4 番目はそのあとでよい。

道具の選び方

状況合う道具理由
個人・小さなチームで、1 つのプラットフォームに載っているそのプラットフォームの Secrets追加のしくみが要らない。まずここから
設定を Git で管理したいSOPS（＋KMS か age）差分が読め、復号の権限を KMS で管理できる
複数のサービス・環境で同じ値を使い、監査が要るクラウドのシークレットマネージャー、Vault1 か所で管理し、読んだ記録とローテーションがある
DB やクラウドの権限を人や処理ごとに短期で配りたいVault の動的シークレット漏れても期限で消える。誰に配ったかも分かる
CI からクラウドへデプロイするOIDC（ワークロード ID 連携）保存するシークレットがなくなる

よくある誤解

シークレットを消すコミットを足せば、もう漏れていない

Git の履歴には前のコミットが残っていて、誰でも取り出せる。しかも公開した時点で取られている可能性がある。まず無効化して替え、そのうえで必要なら履歴を書き換える。

Kubernetes の Secret は暗号化されている

値は base64 で書かれているだけで、誰でも元に戻せる。守っているのは RBAC で、etcd での暗号化は設定が要る（Kubernetes の全体像）。

フロントエンドの環境変数なら、ビルド時に入るのでユーザーには見えない

ブラウザに配るコードに埋め込まれるので、開発者ツールで読める。フロントエンドに置いてよいのは公開してよい値（公開鍵や公開用の ID）だけで、秘密の API 呼び出しはサーバー側に寄せる。

非公開リポジトリならシークレットをコミットしても大丈夫

メンバー全員、連携したアプリや CI、clone した手元の PC すべてに広がる。退職者の手元にも残り、後で公開に切り替えることもある。非公開でもコミットしない。
