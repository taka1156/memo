境界値分析と同値分割

テストで試す値を、勘ではなく理由で選ぶ。エッジケース・コーナーケース・エラー推測も

境界値分析と同値分割 デシジョンテーブルとペアワイズ法 状態遷移テストとユースケーステスト
ざっくり言うと
  • 入力を「同じように扱われるグループ」に分け（同値分割）、その境目を重点的に試す（境界値分析）テストの作り方。
  • バグは < と <= の取り違えのように境目に集まるので、グループの真ん中より両端を試す方がよく見つかる。
  • 仕様に書かれていない端（エッジケース）、端の重なり（コーナーケース）、過去の経験（エラー推測）でも値を足す。

なぜ値を「選ぶ」のか

入力になりうる値は、ふつう多すぎて全部は試せません。年齢を受け取るだけの関数でも、0 歳から 120 歳まで、さらにマイナスや小数、文字まで来るかもしれません。

そこで 2 つの考え方で、少ない件数で、見つかりやすい所を試します。

同値分割

同じように扱われる値をひとまとめにする。グループの中のどれか 1 つが正しければ、ほかも正しいだろうと考え、代表を 1 つだけ試す。

英語では equivalence partitioning

境界値分析

グループとグループの境目のすぐ両側を試す。実装の書き間違いは、この境目で起きやすい。

英語では boundary value analysis

例：年齢で入場料が変わる

次の仕様の fareOf(age) をテストします。

  • 0〜5 歳は無料、6〜12 歳は子ども料金 500 円、13〜64 歳は大人料金 1000 円、65〜120 歳はシニア料金 700 円。
  • 年齢は整数。マイナス・121 以上・小数はエラーにする。

同値分割すると、6 つのグループ（同値クラス）に分かれます。点線の 2 つは、エラーになるべき無効なグループです。

2 値12, 13境目をはさむ両側を 1 つずつ。< と <= の取り違えや、境目が 1 つずれたバグを捕まえる。ふつうはこれで足りる。

代表値（大人なら 30）も別に試しているなら、== の書き間違いはそちらでも捕まるので、2 値で十分なことが多いです。

無効な値は 1 つずつ試す

エラーになるべき値も、グループに分けて試します。年齢なら、マイナス、上限超え、小数（12.5）、数でない値（NaN）などです。

このとき、1 回のテストに無効な値を 2 つ以上入れないのが決まりです。入場料の関数が年齢と会員番号を受け取る場合で考えます。

  1. まとめて試す年齢 -1・会員番号が空、で呼ぶ。エラーになったのでテストは通過
  2. 何が確かめられたか分からない年齢のチェックで先に止まったので、会員番号のチェックは一度も動いていない。会員番号のチェックが壊れていても気づけない
  3. 1 つずつ試す「年齢だけ無効」「会員番号だけ無効」を別々のテストにする。どちらのチェックも動いたことが確かめられる

赤い番号はまずいやり方、緑の番号は正しいやり方です。1 つのエラーが別のエラーを隠してしまうことを、欠陥のマスキング（defect masking）と呼びます。

エッジケース：仕様に書かれていない端

エッジケースは、1 つの条件が取りうる範囲の端に来る場合のことです。境界値分析が試す「仕様の区切りの両側」もその一部ですが、端は仕様書の数字だけではありません。データの型や、扱う物の性質からも生まれます。仕様に書かれていなくても、次のような所は狙って試します。

種類試したい境目の例詳しく
個数0 件（空の配列・空文字）、1 件、ちょうど 1 ページ分と、その 1 件多い数ページネーション
数の大きさ0、負の数、型の上限（32 ビット整数なら 2147483647）とその 1 つ上浮動小数点と数値表現
小数丸めの境目（x.5）、0.1 + 0.2 のように誤差が出る計算浮動小数点と数値表現
文字最大文字数ちょうどと 1 文字超え、絵文字や結合文字（見た目 1 文字でも、内部では 2 単位以上になる）文字コードと Unicode
日付と時刻月末、うるう日（2 月 29 日）、年またぎ、夏時間の切り替え、タイムゾーンで日付が変わる時刻日付・時刻・タイムゾーン

コーナーケース：端が重なる所

コーナーケースは、2 つ以上の条件が同時に端に来る場合です。1 つずつなら問題なくても、重なると初めて壊れることがあります。

一覧画面を、「表示する件数」と「回線の速さ」の 2 つの条件で考えます。

速い ふつう 遅い とても遅い✗ 0 件100 件最大

横：表示する件数　縦：回線の速さ

エッジケース（どちらか 1 つが端） コーナーケースで起きたバグ（最大件数 × とても遅い回線でタイムアウト）

最大件数だけなら速い回線では間に合い、遅い回線だけなら件数が少ないので間に合います。両方が端に来たときだけタイムアウトします。端を 1 つずつ試すテストでは、この角に届きません。

条件が増えると角の数は 2 倍ずつ増えます（条件 3 つで 8 か所、10 個で 1024 か所）。全部の角は試せないので、次のどれかで絞ります。

  • 危ない組み合わせを選ぶ: 「重い × 遅い」「多い × 同時」のように、負荷や時間が積み重なる組み合わせを優先する。
  • 2 つずつの組み合わせを網羅する: ペアワイズ法で、どの 2 条件の端の組み合わせも 1 回は出るように件数を減らす（デシジョンテーブルとペアワイズ法）。
  • 機械に探させる: Property-based Testing や Fuzzing は、端の値を組み合わせた入力を大量に作る（正しさを確かめる 5 つの手法）。

エラー推測：経験で値を足す

エラー推測は、過去の不具合や「ここは作る人が思い込みやすい」という経験から、怪しい入力や操作を足す方法です。理屈で選ぶ同値分割・境界値分析の抜けを、経験で埋める役割です。

分類よく当たる例
入力空、空白だけ、前後の空白、特殊文字（< > ' " \）、絵文字、とても長い文字列、全角と半角の数字
操作ボタンの連打・二重送信、ブラウザバック、リロード、同じ画面を 2 つのタブで開く
環境タイムアウト、途中で回線が切れる、端末の時計がずれている、画面がとても狭い
データ同じ値が 2 件ある、削除済みのデータを参照する、ほかの人が同時に更新した

操作の欄の多くは「ふつうと違う順番」で起きるバグです。順番は状態遷移テストで、理屈で洗い出すこともできます。

この一覧は、チームで育てるものです。障害が起きたら、ポストモーテムで分かった原因を一覧に足すと、次の機能のテストで同じ種類のバグを先に探せます。

テストを作る手順

  1. 入力と出力を書き出す関数が受け取る値と、返す値・起こすことを並べる。
  2. 有効なグループに分ける出力が同じになる範囲ごとに区切る（無料・子ども・大人・シニア）。
  3. 無効なグループに分けるエラーになるべき値を、理由ごとに分ける（マイナス・上限超え・小数・数でない）。
  4. 境目ごとに両側の値を選ぶ2 値なら境目をはさむ 2 つ。仕様に書かれていない端（エッジケース）も足す。
  5. 重なりと経験で足す危ないコーナーケースと、エラー推測の一覧から当てはまるものを足す。
  6. 表にしてテストにする値と期待する結果を表に並べ、1 つのテストで回す。

6 の「表にして回す」書き方は、テスト戦略の単体テストの例と同じです。Vitest ならこう書けます。

test.each([
  [0, 0],    [5, 0],      // 無料の両端
  [6, 500],  [12, 500],   // 子どもの両端
  [13, 1000], [64, 1000], // 大人の両端
  [65, 700], [120, 700],  // シニアの両端
])('%i 歳は %i 円', (age, fare) => {
  expect(fareOf(age)).toBe(fare);
});

// 無効な値は 1 件ずつ
test.each([-1, 121, 12.5, NaN])('%s 歳はエラー', (age) => {
  expect(() => fareOf(age)).toThrow();
});

ほかの手法とのつながり

境界値分析は、人が考えて値を選ぶ方法です。その弱点を補う手法があります。

困りごと補う手法
境界値のテストが抜けていないか確かめたいミューテーションテスト。>= を > に変えた版が生き残れば、そこの境界値のテストがない
思いつかなかった境目も探したいProperty-based Testing や Fuzzing。端の値を出やすくした入力を、機械が大量に作る（正しさを確かめる 5 つの手法）
入力が複数あり、組み合わせで結果が変わるデシジョンテーブルとペアワイズ法。条件の組み合わせを表にして漏れを探す・件数を減らす
操作の順番で結果が変わる状態遷移テストとユースケーステスト

よくある誤解

境界値さえ試しておけば、テストとして十分だ

仕様の境目だけを試しても、型の上限・空・日付のような仕様に書かれていない端や、複数の端が重なって起きるバグは残ります。エッジケースとコーナーケースも足し、組み合わせが効く所は別の手法で補います。

エッジケースはめったに起きないので、後回しでよい

1 人にとってまれでも、利用者が多ければ毎日どこかで起きます。空の入力や二重送信は、ふつうの利用者が普通に起こします。攻撃者はむしろ端を狙って入力を作ります。

無効な値はまとめて 1 つのテストに入れた方が効率がよい

最初のチェックでエラーになると、後ろのチェックは動きません。後ろのチェックが壊れていてもテストは通るので、無効な値は 1 件ずつ試します（無効な値は 1 つずつ試す）。

カバレッジが 100% なら、境目も確かめられている

30 歳を試せば age >= 13 の行は通ります。ただ、それを age > 13 に変えても 30 歳のテストは通るので、境目は確かめていません。行を通ったかと、境目を確かめたかは別です。

同じグループの代表値が正しければ、そのグループの値は全部正しい

それは「仕様どおりに区切られているはず」という仮定に立った近道です。実装が仕様にない所で区切っていれば（たとえば 60 歳で分岐している）、グループの中でも結果が変わります。だから代表値に加えて境目を試し、怪しい所は実装も読みます。
