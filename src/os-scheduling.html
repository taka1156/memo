OS のスケジューリング

プロセスの状態 / コンテキストスイッチ / アルゴリズム / Linux の nice・公平スケジューラ / コンテナの CPU 制限

ざっくり言うと
  • CPU コアの数より動きたいスレッドのほうがずっと多い。OS のスケジューラが「次にどれを、どのコアで、どれだけ動かすか」を決め、短い時間で切り替えて同時に動いているように見せる。
  • 切り替え（コンテキストスイッチ）にはコストがある。細かく切り替えるほど応答は良くなるが、切り替えの手間が増える。
  • Linux は各スレッドに CPU を公平に配り、nice 値で配分の重みを変える。コンテナの CPU 上限は「一定期間に使える時間」の上限で、使い切ると止められる（スロットリング）。

スレッドの 3 つの状態

スケジューラが扱う単位はスレッド（Linux ではプロセスもスレッドも「タスク」として同じに扱う）。どのタスクも、大きく 3 つの状態を行き来する。

  1. スケジューラが CPU を渡す
  2. 持ち時間を使い切った・より優先すべきタスクが来たので取り上げられる
  3. read() やロック、sleep などで待ちに入る
  4. データが届く・ロックが空くと、また順番待ちの列に戻る（すぐ RUNNING には戻らない）
  • CPU を使い続ける処理（CPU バウンド）は READY と RUNNING を行き来する。I/O を待つ処理（I/O バウンド）はほとんどの時間 BLOCKED にいて、CPU を使わない。
  • BLOCKED のタスクはスケジューラの選択肢に入らない。だから、待ちの多い処理を何千本動かしても CPU は空いている。
  • ps や top の STAT 列では、R（実行中・実行可能）、S（割り込み可能な待ち）、D（割り込み不可の待ち。主にディスク I/O）として見える（Linux プロセスの仕組み）。

コンテキストスイッチ

CPU を別のタスクに渡すとき、OS は今のタスクの続きを再開できるよう状態を保存し、次のタスクの状態を戻す。

タイマー割り込み（持ち時間切れ）や、システムコールでの待ちをきっかけにカーネルに入る
今のタスクのレジスタ（プログラムカウンタ・スタックポインタなど）をカーネルのメモリに保存する
スケジューラが次のタスクを選ぶ
別のプロセスなら、アドレス空間（ページテーブル）も切り替える。同じプロセスのスレッド同士なら不要
次のタスクのレジスタを戻し、ユーザー空間に戻って続きを実行する
  • 直接の手間はマイクロ秒単位だが、本当のコストはその後。CPU キャッシュや TLB（アドレス変換のキャッシュ）が前のタスクのデータで埋まっていて、しばらく遅くなる（仮想メモリとページング）。
  • スレッドを何千本も作って細かく切り替えるより、少数のスレッドで多くの仕事を回すほうが速いのはこのため。イベントループや goroutine のような軽量スレッドは、OS の切り替えを減らす工夫（並行処理のモデル）。

スケジューリングの方式

「どれを次に動かすか」の決め方には古典的な型がいくつかある。実際の OS はこれらを組み合わせている。

FIRST COME FIRST SERVED

来た順に最後まで動かす。単純だが、長い処理の後ろに短い処理が並ぶと、短い処理まで長く待たされる（コンボイ効果、convoy effect）。途中で取り上げない（非プリエンプティブ）。

SHORTEST JOB FIRST

短い仕事から先に動かす。平均の待ち時間は最小になるが、実行時間を前もって知る必要があり、長い仕事がいつまでも後回しになりうる（飢餓 (starvation)）。

ROUND ROBIN

全員に同じ持ち時間（タイムスライス）を順に配り、時間が来たら取り上げて列の後ろに回す（プリエンプティブ）。誰も長く待たされないので対話的な処理に向く。持ち時間の長さが性能を左右する（下のシミュレーション）。

PRIORITY / MLFQ

優先度の高いものから動かす。そのままだと低いものが飢えるので、待った時間に応じて優先度を上げる（エージング）。多段フィードバックキュー (MLFQ) は、持ち時間を使い切る CPU バウンドな処理の優先度を下げ、すぐ I/O 待ちに入る対話的な処理を上に保つ。

Linux のスケジューラ

普通のタスクは、長らく CFS (Completely Fair Scheduler) が、6.6 以降は後継の EEVDF が受け持つ。どちらも各タスクが使った CPU 時間を重み付きで記録する。CFS は使った時間がいちばん少ないタスクを次に動かす。EEVDF は、取り分より使いすぎていないタスクのうち、締め切り（仮想デッドライン）がいちばん早いものを動かす。I/O 待ちから起きたタスクは CPU を使っていないぶん順番が回ってきやすいが、必ずすぐ動けるとは限らない。

nice 値 — 配分の重み

nice は −20〜19（既定 0）。大きいほど「他に譲る」＝優先度が低い。1 段違うと CPU の取り分がおよそ 1.25 倍（約 10%）変わる。CPU を取り合う 2 つのタスクの取り分の目安:

CPU を取り合っていないとき（他に動きたいタスクがないとき）は、nice 19 でも CPU を使い切れる。nice は「取り合ったときの割合」を決めるもの。

スケジューリングクラス

ポリシー動き使いどころ
SCHED_OTHER公平スケジューラ。nice で重みを変える（既定）ほぼすべての処理
SCHED_BATCH / IDLE対話性を気にしない／他に何もないときだけ動くバッチ処理、バックグラウンドの集計
SCHED_FIFO / RRリアルタイム。優先度が高いものは普通のタスクより先に動く（既定では、暴走しても普通のタスクに 1 秒のうち約 5% が残るよう制限される）音声・制御系など遅れが許されない処理。誤るとシステムを固める

優先度逆転

優先度だけで決めると、低い優先度のタスクがロックを持ったまま、中くらいのタスクに追い出されることで、高い優先度のタスクがいつまでも待たされることがある。

高 H
中 M
低 L

L がロックを取る（紫）→ H が起きて同じロックを待つ（斜線）→ ロックと無関係な M が L より優先されて動き続ける → L がロックを返せず、H も止まったまま。

対策は優先度継承: ロックを持つタスクに、待っている中でいちばん高い優先度を一時的に貸す。Linux では PI 対応の futex（pthread_mutexattr_setprotocol の PTHREAD_PRIO_INHERIT）で使える。

コンテナの CPU 制限とスロットリング

cgroup v2 の cpu.max（Kubernetes の resources.limits.cpu もこれになる）は「期間（既定 100ms）ごとに使える時間」の上限。limits.cpu: 500m なら 100ms ごとに 50ms。

  • マルチスレッドの処理が 4 コアで同時に動くと、50ms 分を 12.5ms ほどで使い切り、残りの約 87ms は止められる。平均の CPU 使用率は低いのに、応答が数十 ms 単位で遅れる原因になる。
  • 確認は cpu.stat の nr_throttled・throttled_usec（Kubernetes なら cAdvisor の container_cpu_cfs_throttled_periods_total）。
  • requests.cpu は上限ではなく、取り合ったときの重み（cpu.weight）と配置の目安。上限を付けずに requests だけにする運用もある。
  • ランタイムがコア数を見てスレッド数を決める場合は、コンテナの上限より多いスレッドを作らないか確かめる。Go 1.25 以降と最近の JVM は CPU 上限を読んで自動で合わせるが、古いバージョンや、自分でコア数を数えてワーカーを作るコード（Node.js の cluster で os.cpus().length 個起動する、など）は注意。Node.js の libuv スレッドプールはコア数に関係なく既定 4 本（UV_THREADPOOL_SIZE で変更）。

コマンド例

nice -n 19 ./backup.sh          # 優先度を下げて起動
renice -n 10 -p 1234             # 動いているプロセスの nice を変える
chrt -i 0 ./batch-job            # SCHED_IDLE で起動（他に何もないときだけ動く）
taskset -c 0,1 ./app             # 使う CPU コアを 0 と 1 に限定
vmstat 1                         # r = 実行可能なタスク数、cs = 1 秒あたりの切り替え回数
pidstat -w -p 1234 1             # cswch/s = 自発的（待ち）、nvcswch/s = 取り上げられた切り替え
cat /proc/loadavg                # ロードアベレージ（Linux では D 状態も数える）

ロードアベレージがコア数を大きく超えていても CPU 使用率が低いなら、CPU の取り合いではなく、ディスクや NFS の I/O 待ち（D 状態）が溜まっている可能性が高い。

よくある誤解

スレッドを増やせば処理は速くなる

CPU バウンドな処理はコア数を超えて増やしても速くならず、切り替えとキャッシュの汚れで遅くなる。増やして効くのは I/O 待ちが多い処理。

nice 19 にすれば、そのプロセスは CPU をほとんど使わない

取り合う相手がいなければ使い切れる。nice は取り合ったときの配分の重み。

コンテナの CPU 上限 1 コアは「1 コアだけ使える」

「100ms ごとに合計 100ms まで」。複数のコアで同時に動けるが、合計が上限に達するとその期間の残りは止められる。
