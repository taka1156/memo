OAuth 2.0 / OIDC

「ログインさせる」と「権限を渡す」を分けて理解する

ざっくり言うと
  • 認証は「誰か」を確かめること、認可は「何をしていいか」を決めること
  • OAuth 2.0 は認可の仕組み。アプリにパスワードを渡さず、限定的な権限（アクセストークン）だけを渡す
  • OIDC (OpenID Connect) は OAuth の上に認証を足したもの。「誰がログインしたか」を ID トークンで伝える

認証と認可

AUTHENTICATION / AuthN

認証 ＝ あなたは誰？

ホテルのフロントで身分証を見せて、本人だと確認してもらう段階。

担当：OIDC（ID トークン）

AUTHORIZATION / AuthZ

認可 ＝ 何をしていい？

渡されたカードキー。開けられるのは自分の部屋とジムだけで、持っている人が誰かは問わない。

担当：OAuth 2.0（アクセストークン）

OIDC の文脈では、認可サーバーを OP（OpenID Provider）、クライアントを RP（Relying Party）と呼ぶ。

認可コードフロー ＋ PKCE

今のブラウザアプリやスマホアプリで使うべき、標準のフロー。矢印をクリックするか、ボタンで1ステップずつ進められる。

フロントチャネル（ブラウザのリダイレクト経由。URL に乗るので見られうる） バックチャネル（サーバー同士の直接通信）

PKCE（ピクシー）は何を防ぐ？

手順 4 の認可コードはブラウザの URL に乗って戻ってくる。スマホでは同じカスタム URL スキームを登録した悪意あるアプリに横取りされることがあり、コードだけでトークンが取れると乗っ取られてしまう。

PKCE (Proof Key for Code Exchange) は「コードを頼んだのと同じクライアントか」を、使い捨ての秘密で確かめる。

code_verifierランダムな秘密（手元に保持）
→ SHA-256 → Base64URL →
code_challenge手順 2 で送る（ハッシュだけ）
手順 5 で verifier を送る
→
認可サーバーがハッシュして照合一致したときだけトークン発行

コードを盗んでも、verifier を知らない攻撃者はトークンに交換できない。セキュリティのベストプラクティス（RFC 9700）は client_secret を持つサーバー側アプリにも PKCE を推奨しており、策定中の OAuth 2.1 では原則として必須になっている。

state と nonce の違い

パラメーターどこで照合防ぐもの
state手順 4 でリダイレクトを受けたとき、クライアントが自分の出した値と比べるCSRF（攻撃者が用意した code で、被害者を攻撃者のアカウントにログインさせる）
nonceID トークンの中の nonce クレームを、クライアントが自分の出した値と比べるID トークンの使い回し（リプレイ）。OIDC 固有
code_verifier手順 5 で認可サーバーが照合する認可コードの横取り

OIDC が足すもの

OIDC は新しいプロトコルを作ったのではなく、OAuth 2.0 のフローに scope=openid を付けると、トークンと一緒に ID トークンが返ってくるようにした追加仕様。

ID TOKEN

「誰が・いつ・どこで認証されたか」を表す JWT。クライアントは署名と中身を検証して、ログインユーザーを特定する。

{
  "iss": "https://accounts.example.com",
  "sub": "248289761001",
  "aud": "my-client-id",
  "exp": 1793635200,
  "iat": 1793631600,
  "nonce": "n-0S6_WzA2Mj",
  "email": "taro@example.com"
}

ユーザーを識別するキーは sub（発行者 iss と組で一意）。メールアドレスは変わりうるので主キーにしない。

ほかに足されるもの

UserInfo エンドポイント
アクセストークンで叩くと、名前やメールなどのプロフィールが返る。

Discovery
/.well-known/openid-configuration に、各エンドポイントの URL や署名鍵（JWKS）の場所がまとまっている。

標準スコープ
openid（必須）、profile、email など。

3つのトークンは「宛先」が違う

ID トークン
→
クライアント宛て
誰がログインしたかを知るため。API には送らない
アクセストークン
→
API（リソースサーバー）宛て
クライアントは中身を解釈せず、そのまま渡すだけ
リフレッシュトークン
→
認可サーバー宛て
新しいアクセストークンをもらうためだけに使う
トークン形式寿命の目安注意点
ID トークン必ず JWT短い（数分〜1時間）署名・iss・aud・exp・nonce を検証してから使う
アクセストークンJWT のことも、ランダム文字列（opaque）のこともある短い（数分〜1時間）盗まれたら有効期限まで使える。短くするのが基本
リフレッシュトークンたいてい opaque長い（日〜月）一番大事な秘密。使うたびに新しいものに替える「ローテーション」で被害を抑える

フロー（グラント）の種類

使う場面：ユーザーがいるアプリ全般（Web、SPA、スマホ、デスクトップ）。

上の図のフロー。迷ったらこれ。

使う場面：ユーザーがいない、サーバー同士の通信（バッチ、マイクロサービス間）。

POST /token
grant_type=client_credentials
&client_id=...&client_secret=...
&scope=reports:read

「ユーザーの代わり」ではなく「アプリ自身」の権限になる。ID トークンは出ない。

使う場面：入力が不便な機器（テレビ、CLI ツール、IoT）。

機器に「example.com/device でコード ABCD-1234 を入力」と表示し、ユーザーはスマホやPCでログインする。その間、機器は認可サーバーに完了したかを定期的に問い合わせる（ポーリング）。gh auth login などでおなじみ。

インプリシット：トークンを URL のフラグメントで直接返していた SPA 向けの旧方式。漏えいしやすく、今は認可コード＋PKCE に置き換え。

リソースオーナーパスワード (ROPC)：アプリがユーザーのパスワードを直接受け取る方式。OAuth の目的（パスワードを渡さない）に反するので使わない。

どちらも RFC 9700 で非推奨とされ、OAuth 2.1 のドラフトでは削除されている。

よくある誤解

OAuth でログインしている

素の OAuth は「権限を渡す」だけで、誰がログインしたかは保証しない。アクセストークンを持っているからといって本人とは限らない（他アプリ向けのトークンを使い回される危険がある）。ログインには OIDC の ID トークンを使う。

ID トークンを API に送って認可に使う

ID トークンの aud はクライアント自身。API の認可にはアクセストークンを使う。

PKCE はスマホアプリだけのもの

今はすべてのクライアントで使うのが推奨。client_secret があっても付けておく。

アクセストークンは JWT

仕様上は形式自由。中身を読めるかどうかに依存せず、クライアントにとっては「意味のわからない文字列」として扱う。
