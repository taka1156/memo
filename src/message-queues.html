メッセージキューと Pub/Sub

「今すぐ返事はいらない仕事」を間に置いた箱に預ける —— 送る側と受ける側を切り離すしくみ

ざっくり言うと
  • キューを挟むと、送る側（プロデューサー）は受ける側（コンシューマー）が落ちていても遅くても処理を続けられる。急なアクセス増もキューが吸収する。
  • 形は 3 つ：キュー（1 件を誰か 1 人が処理）／Pub/Sub（1 件を購読者全員に配る）／ログ型（Kafka。消さずに保持して、各自が好きな位置から読む）。
  • ほとんどのキューは「少なくとも 1 回」届ける。重複は起きる前提で、受ける側を冪等にする。処理できないメッセージは DLQ に退避する。

なぜキューを挟むのか

直接呼ぶと
  • メール送信サービスが落ちていると、注文 API までエラーになる
  • メール送信が 3 秒かかると、注文 API も 3 秒待たされる
  • セールで 100 倍のアクセスが来ると、下流がまとめて落ちる
キューを挟むと
  • 注文 API は「メールを送って」とキューに入れてすぐ返す
  • メール送信側は自分のペースで取り出して処理する
  • 落ちていても、復旧後に溜まった分から処理すればよい

急増をキューが吸収する

プロデューサーが一気に投入しても、コンシューマーは一定のペースで処理します。台数を増やすと溜まった分（バックログ）が早く減ります。

送る側
0 件
「60 件まとめて投入」を押して、台数を切り替えてみてください。

3 つの形

キュー（1 対 1）

1 件のメッセージは A か B のどちらか一方だけが処理する。仕事の分担（ワーカー）向き。SQS・Cloudflare Queues・RabbitMQ のキュー。

Pub/Sub（1 対 多）

「注文が入った」を購読者全員が受け取る。送る側は誰が聞いているかを知らなくてよい。SNS・Google Pub/Sub・Redis Pub/Sub。

ログ型（Kafka）

メッセージは読んでも消えず、保持期間まで残る。グループごとに「どこまで読んだか（オフセット）」を持ち、巻き戻して読み直せる。

組み合わせも多い：Pub/Sub のトピックから購読者ごとのキューへ配る（SNS → SQS など）と、「全員に配る」と「各自のペースで確実に処理」を両立できる。

ack・再配信・DLQ

キューは「取り出した＝処理完了」とはみなしません。コンシューマーが処理し終えてから ack（確認応答）を返したときに初めて消します。

1. 受け取る

メッセージは他のコンシューマーから一時的に見えなくなる（SQS の可視性タイムアウト）。

2. 処理する

メール送信・DB 更新など。

3a. ack

成功を伝える → キューから削除。

3b. ack なし

失敗・タイムアウト・クラッシュ → しばらくして再配信。

4. DLQ

決まった回数失敗したら、デッドレターキューに移して人が調べる。

「処理は終わったが ack を返す前に落ちた」ときも再配信されるので、同じメッセージが 2 回届くことがあります。これが「少なくとも 1 回 (at-least-once)」配信の意味で、対策は受ける側の冪等化です（詳しくは 分散システムの基本：配送保証・冪等性）。

ポイズンメッセージ（poison message、有害メッセージとも）：形式が壊れているなど、何度やっても失敗するメッセージ。DLQ がないと再配信が永遠に続き、後ろのメッセージが詰まったりコストがかさんだりする。DLQ は必ず設定する。

順序の保証

順序と並列はトレードオフです。全メッセージを厳密に順番どおり処理するなら、コンシューマーは 1 台しか使えません。そこで多くのしくみは「同じキーの中だけ順序を守る」という形をとります。

しくみ順序の単位使い方
Kafkaパーティション内キー（例：user_id）でパーティションが決まるので、同じユーザーのイベントは順番どおり
SQS FIFOメッセージグループ内MessageGroupId を注文 ID などにする
SQS 標準・Cloudflare Queues保証しない前提順序に依存しない設計にする（バージョン番号・タイムスタンプで新旧を判断）

DB 更新と送信をそろえる：Outbox パターン

「注文を DB に保存してから、キューに『注文が入った』を送る」とき、保存後・送信前に落ちるとイベントが消えます。逆順だと、送ったのに保存されていない注文が生まれます。

1. 同じトランザクション

注文テーブルへの INSERT と、outbox テーブルへのイベント INSERT を 1 つのトランザクションで行う。

2. 中継役

別のプロセスが outbox を読み、キューに送る。

3. 送ったら印

送信済みにする。途中で落ちても再送するだけ（だから受け手は冪等に）。

トランザクションの話は インデックスとトランザクション。

リアルタイム通信との違い

WebSocket や SSE（リアルタイム通信）は「今つながっている相手に即座に届ける」もので、相手がいなければ届きません。キューは「相手がいなくても預かって、後で確実に処理させる」もの。チャットなら、送信はキューで確実に保存・配信処理し、表示は WebSocket で即時に、と組み合わせることが多いです。

よくある誤解

キューに入れれば必ず 1 回だけ処理される

多くは少なくとも 1 回。ack 前の障害で 2 回届くことがあるので、受け手を冪等にする。

Kafka は高性能なキュー

Kafka はメッセージを保持し続けるログで、複数のグループが別々の位置から読み直せる。1 件ごとの ack や、パーティション数を超える並列処理は従来のキューのほうが得意。

キューを入れれば負荷の問題は解決する

キューは急増を平らにするだけ。平均でも処理能力が足りなければバックログは増え続ける。キューの長さ・最古メッセージの経過時間を監視する（オブザーバビリティ）。
