Ansible 概念図

Control Node から Managed Nodes までの流れと、役割ごとのファイル名の対応

ざっくり言うと
  • Inventory（対象ホスト）と Playbook（手順）はどちらも自分で書く定義ファイル
  • Playbook は実行時に Play → Tasks → Modules へと分解される
  • Connection Plugin（SSH / WinRM）が Control Node と各サーバーをつなぐ

概念図

青＝自分で書く定義ファイル、緑＝実行時に組み立てられる処理、黄＝接続方式。破線は参照・取り込みを表す。

定義ファイル 実行時の処理単位 接続方式 破線＝参照・取り込み

役割ごとのファイル名

ファイル名はベストプラクティスとして広く使われる慣例。Play・Tasks・Modules のように独立ファイルを持たず、他ファイルの中に書くものもある。

概念種別ファイル / 場所役割
Control Node実行環境 設定 ansible.cfgrequirements.yml Ansible 自体の動作設定。requirements.yml は使う Collection / Role の一覧。
Inventory管理対象ホスト 定義 inventory/hosts.yml どのサーバーを管理するか、どのグループに属するか。
Playbook実行手順 定義 site.ymlplaybooks/web.yml 1 つ以上の Play を並べたファイル。用途別に分けるのが定番。
Play 処理 Playbook 内の - hosts: 単位 「どのホストに」「何を」するかの組。独立ファイルはない。
Tasks 処理 roles/<名前>/tasks/main.yml モジュールを 1 回呼ぶ操作の単位。上から順に実行。
HandlersTask の一種 処理 roles/<名前>/handlers/main.yml 変更があったときだけ動く Task（再起動など）。notify: から呼ぶ。
Modules 処理 ansible.builtin.*library/（自作） 実際に作業をするプログラム。通常は書かずに使うだけ。
Roles再利用単位 定義 roles/<名前>/ tasks・handlers・templates・変数をひとまとめにしたもの。
Variablesグループ/ホスト 定義 group_vars/all.ymlhost_vars/server-a.yml Inventory のグループ名・ホスト名と同名にすると自動で読み込まれる。
VariablesRole 単位 定義 roles/<名前>/defaults/main.ymlroles/<名前>/vars/main.yml defaults は上書き前提の初期値（優先度最低）。vars は固定値。
Templates / Files 定義 roles/<名前>/templates/*.j2roles/<名前>/files/ .j2 は Jinja2 テンプレート。files/ はそのまま配る静的ファイル。
Secrets 定義 group_vars/all/vault.yml ansible-vault で暗号化して保存する。
Connection Plugin 接続 ansible.cfg / ansible_connection 既定は ssh。Windows は winrm、コンテナは docker。

project/
├── ansible.cfg           # 動作設定

│   └── hosts.yml         # Inventory
├── group_vars/
│   ├── all.yml
│   └── web.yml
├── host_vars/
│   └── server-a.yml
├── site.yml              # Playbook（入口）
└── roles/
    └── nginx/
        ├── tasks/main.yml
        ├── handlers/main.yml
        ├── templates/nginx.conf.j2
        ├── files/
        ├── defaults/main.yml
        ├── vars/main.yml
        └── meta/main.yml
all:
  children:
    web:
      hosts:
        server-a:
          ansible_host: 192.168.10.11
        server-b:
          ansible_host: 192.168.10.12
# ↓ ここから 1 つの Play
- name: Web サーバー構築
  hosts: web          # Inventory のグループ
  become: true
  roles:
    - nginx            # roles/nginx を実行
  tasks:
    - name: パッケージ更新   # Task
      ansible.builtin.apt:  # Module
        update_cache: true

各要素の考え方

Control Node 実行する側

Ansible をインストールしてコマンドを打つマシン。管理対象側には Ansible 不要で、Linux なら SSH と Python があれば動く（エージェントレス）。Windows は WinRM と PowerShell を使い、ネットワーク機器では Python が要らないモジュールもある。

Inventory 誰に

管理するサーバーの一覧とグループ分け。Playbook 側は IP ではなくグループ名（web など）で対象を指すので、サーバーが増えても Inventory を直すだけで済む。

Playbook と Play 何を

Playbook はファイル、Play はその中の 1 ブロック。対象ごとに Play を分けて 1 つの Playbook に並べる。

Tasks と Modules どうやって

Task は「nginx をインストールする」という 1 つの操作、Module はそれを実行する部品。ほとんどのモジュールは「あるべき状態」を宣言する作りなので、何度実行しても結果が同じになる（冪等性）。ただし command / shell は任意のコマンドを実行するだけなので、creates などで条件を付けないと冪等にならない。

Roles まとめて使い回す

Playbook が長くなったら機能単位で Role に切り出す。決まったディレクトリに置くだけで tasks や templates が自動で読み込まれる。

Connection Plugin どう繋ぐか

Control Node と管理対象の間の通信方法。Ansible はモジュールを一時ファイルとして相手に送り込み、実行して結果を回収し、後片付けする。

Collections と FQCN 部品の配り方

Modules・Roles・Plugin は Collection という単位で配布される。ansible.builtin.apt の ansible.builtin が Collection 名で、この「名前空間.Collection名.モジュール名」の書き方を FQCN（完全修飾コレクション名）と呼ぶ。短く apt と書いても動くことが多いが、別の Collection に同名のモジュールがあると取り違えるので FQCN で書くのが推奨。ansible-core だけを入れた環境では、ansible.builtin 以外（community.general など）は requirements.yml に書いて ansible-galaxy で入れる。ansible パッケージには主要な Collection が同梱されているが、使うものとそのバージョンは requirements.yml に書いて固定しておくとよい。

実行の流れ

ansible-playbook -i inventory/hosts.yml site.yml を実行したときの順序。

設定を読むansible.cfg を探して読み込む。
Inventory と変数を読むホスト一覧を作り、group_vars / host_vars を紐付ける。
Playbook を解析するPlay ごとに対象ホストを決め、Roles を展開して Task 一覧を作る。
ファクト（facts）を集めるgather_facts で OS や IP などのホスト情報を取得する。
Task を順に実行するConnection Plugin で接続し、モジュールを送って実行する。
Handler を実行するchanged になった Task から notify された Handler を最後にまとめて実行。
結果を表示するPLAY RECAP でホストごとの集計が出る。

複数ホストでの進み方

既定（strategy: linear）では、1 つの Task を全ホストで終えてから次の Task に進む。ホストを 1 台ずつ最後まで流すのではない。

Task 1Task 2Task 3 server-aokchangedok server-bchangedfailed外れる server-cokokchanged
ok（変更なし） changed（変更した） failed（失敗） 以降の Task から外れる

色分けは ansible-playbook の画面表示（ok・changed・failed で色が変わる）に合わせている。

forks 同時に何台触るか

1 つの Task を何台に同時に実行するか。既定は 5 なので、20 台あれば 5 台ずつ 4 回に分けて同じ Task を流す。ansible.cfg の forks か -f で変える。Control Node の CPU・メモリと相談して決める。

serial 何台ずつ最後まで流すか

Play に serial: 2 と書くと、ホストを 2 台ずつの組に分け、組ごとに Play を最後まで流してから次の組に進む。全台を同時に再起動して止めてしまうのを防ぐ、ローリング更新に使う。max_fail_percentage と組み合わせると、失敗が多い組が出た時点で残りの組に進まずに止められる。

失敗したホスト ほかは止まらない

ある Task が失敗したホストは、その Play の残りから外れる。ほかのホストはそのまま続く（上の図の server-b）。1 台でも失敗したら全体を止めたいときは any_errors_fatal: true を使う。

結果の 5 つの状態と冪等性

Task はホストごとに次のどれかで終わる。PLAY RECAP の ok= は changed を含む成功した Task の数で、そのうち変更したものが changed= にも数えられる（ほかに rescued=・ignored= も並ぶ）。

状態意味そのあと
okすでにあるべき状態だった。何も変えていない。次の Task へ。
changedあるべき状態にするために変更した。notify: があれば Handler が予約される。
skippedwhen: の条件が偽だった、などで実行しなかった。次の Task へ。
failedモジュールがエラーを返した。そのホストは以降の Task から外れる（ignore_errors で続けることもでき、その場合 RECAP では ignored に数えられる）。
unreachableSSH などで接続できなかった。そのホストは以降の Task から外れる。

冪等かどうかの確かめ方 2 回流す

同じ Playbook を続けて 2 回実行し、2 回目の PLAY RECAP で changed=0 になれば冪等に書けている。2 回目にも changed が出る Task は、毎回なにかを変えている（または変えたと報告している）。よくあるのは command / shell で、中身を判断できないので実行すれば必ず changed になる。確認だけのコマンドなら changed_when: false、作るものがあるなら creates: で「もうあれば実行しない」と教える。

check と diff 変更せずに予告する

ansible-playbook site.yml --check --diff は、実際には変更せず「変わるはずのもの」を changed として報告し、--diff でファイルの中身の差分も見せる。ただし予告できるのは check モードに対応したモジュールだけで、command / shell は creates / removes を付けない限り check モードでは実行されず、変更なし（changed=False）として報告される。また前の Task で入れるはずのパッケージが check では実際には入らないので、それを前提にした後ろの Task が失敗することがある。

条件・繰り返し・結果の受け渡し

Task はどれも「ホストごとに」評価される。同じ Task でも、ホストによって実行されたりスキップされたりする。

- name: nginx の設定を検査する
  ansible.builtin.command: nginx -t
  register: nginx_test        # 結果（rc・stdout など）をこのホストの変数に入れる
  changed_when: false         # 検査だけなので changed と報告しない
  failed_when: false          # 失敗しても止めず、下で結果を見る

- name: 検査に通ったときだけ再読み込み
  ansible.builtin.service:
    name: nginx
    state: reloaded
  when: nginx_test.rc == 0    # 前の Task の結果で分岐

- name: Debian 系だけにパッケージを入れる
  ansible.builtin.apt:
    name: "{{ item }}"         # Jinja2 で変数を埋め込む
    state: present
  loop: [nginx, curl]          # 1 項目ずつ繰り返す
  when: ansible_facts['os_family'] == "Debian"   # facts で分岐

register 結果を次へ渡す

Task の結果を変数として保存する。変数はホストごとに別々に持つので、server-a の結果で server-b の動きが変わることはない（ほかのホストの値は hostvars['server-a'] で明示的に読む）。

when と loop 分岐と繰り返し

when: は Jinja2 の式で、{{ }} を付けずに書く。loop: は項目ごとに同じモジュールを呼ぶ。apt の name のようにリストをそのまま受け取れるモジュールなら、loop より一度に渡すほうが速い。

変数の優先順位（抜粋）

同じ名前の変数が複数箇所にあるときは、上にあるものが勝つ。

コマンドラインの -e最優先
Task / Block の vars:
Role の vars/main.yml
Play の vars:
host_vars/
group_vars/<グループ>
Role の defaults/main.yml最も弱い

よくある誤解

Playbook から Task を消せば、その Task が作ったものも消える

Ansible は「前回何を作ったか」を記録しないので、Task を消しても管理対象には何も起きず、作ったものはそのまま残る。消したいときは state: absent の Task を書いて一度流してから、その Task を消す。前回の結果を State に記録して差分で消す OpenTofu との大きな違い（OpenTofu 概念図）。

Ansible は宣言的なので、Task を書く順番は関係ない

宣言的なのは各モジュールの中身（「この状態にする」）で、Task そのものは書いた順に上から実行される。設定ファイルを置く前にパッケージを入れる、のような順序は自分で並べて決める。

Handler は notify した Task の直後に実行される

Handler は予約されるだけで、実行されるのはそのセクション（pre_tasks・roles と tasks・post_tasks）の最後。何度 notify されても 1 回だけ動く。途中で動かしたいときは ansible.builtin.meta: flush_handlers を置く。

--check で問題がなければ、本番で流しても必ず成功する

check モードは対応しているモジュールの予告にすぎない。command / shell は check では実行されず、前の Task の結果を前提にした Task は check では正しく評価できない。予告として使い、検証環境で一度流すのが確実。
