日付・時刻・タイムゾーン

「いつ起きたか」と「何時と書いてあるか」は別物 —— UTC で保存して、表示するときにその人の時刻にする

ざっくり言うと
  • 時刻データには 3 種類ある：瞬間（ログの時刻・決済日時）、壁時計の時刻（「毎朝 9:00」）、日付だけ（誕生日・締切日）。混ぜると 1 日ずれる・9 時間ずれる。
  • 過去の瞬間は UTC で保存し、表示時に相手のタイムゾーンへ変換する。未来の予定は「現地の時刻＋タイムゾーン名」で保存する（夏時間のルールが変わることがあるため）。
  • +09:00（オフセット）と Asia/Tokyo（タイムゾーン）は別物。夏時間のある地域ではオフセットが季節で変わる。JS では Date の代わりに Temporal で型を分けて扱える。

3 種類の「時刻」

瞬間 (instant)

世界共通の一点。どこで見ても同じ瞬間。
例：注文日時・ログ・トークンの有効期限

保存：UTC（2026-11-06T01:15:00Z）や Unix 時刻
Temporal：Instant・ZonedDateTime

壁時計の時刻 (wall clock)

場所によって指す瞬間が変わる。
例：「毎朝 9:00 に通知」「店の営業時間」

保存：09:00 ＋ タイムゾーン名
Temporal：PlainDateTime・PlainTime

日付だけ (date)

時刻もタイムゾーンもない。
例：誕生日・祝日・請求の締め日

保存：2026-11-06（DB の DATE 型）
Temporal：PlainDate

誕生日を「その日の 0 時 UTC」の瞬間として保存すると、アメリカのユーザーには前日として表示される。日付だけの値に時刻やタイムゾーンを付けない。

オフセットとタイムゾーン

オフセット

UTC からのずれ。+09:00・-05:00。ある瞬間について言える固定の値。

タイムゾーン

地域のルールの名前。Asia/Tokyo・America/New_York。「いつからいつまではオフセットいくつ」という履歴と規則を持つ（IANA tz データベース）。

ニューヨークは冬は -05:00、夏は -04:00。「-05:00 で保存」すると、夏の予定が 1 時間ずれます。下で日付と UTC の時刻を動かしてみてください。初期値は 2026 年 3 月 8 日、アメリカで夏時間が始まる日です。

タイムゾーンのルールは国の決定で変わる（夏時間の廃止・導入など）。OS・ランタイム・DB の tz データは更新され続けているので、古いままにしない。

保存と表示の流れ

1. 受け取る

クライアントは瞬間を 2026-11-06T10:15:00+09:00 のようにオフセット付きで送る（RFC 3339 / ISO 8601）。

2. 保存

サーバーは UTC に揃えて保存。PostgreSQL なら timestamptz。

3. 計算

集計の「日ごと」は、誰の 1 日か（どのタイムゾーンの 0 時で区切るか）を決めて変換してから行う。

4. 表示

ユーザーのタイムゾーンに変換して表示。Intl.DateTimeFormat が使える。

DB の型中身注意
PostgreSQL timestamptzUTC の瞬間として保存し、表示時にセッションのタイムゾーンに変換瞬間はこれを使う。名前に反してタイムゾーン名は保存しない
PostgreSQL timestampタイムゾーンなしの壁時計の時刻瞬間を入れると、どこの時刻かわからなくなる
MySQL TIMESTAMPUTC に変換して保存2038 年 1 月 19 日までしか入らない
MySQL DATETIMEタイムゾーンなしの値をそのまま保存UTC で入れる・読むを徹底する

BigQuery の TIMESTAMP と DATETIME も同じ区別（BigQuery と BI の SQL）。「日別売上」が日本時間でなく UTC の 1 日で区切られていた、はよくある集計ミス。

未来の予定は「現地時刻＋タイムゾーン」

来年の「ニューヨーク 10:00 の会議」を今 UTC に変換して保存すると、その後に夏時間のルールが変わったとき、会議が 9:00 や 11:00 にずれます。人が決めた現地の時刻が本体なので、2027-06-01 10:00 と America/New_York を保存し、通知の直前に瞬間へ変換します。

夏時間の落とし穴

現象例（America/New_York）対策
存在しない時刻3 月の切り替え日、2:00 → 3:00 に飛ぶので 2:30 は無いどちらに寄せるかを決める（Temporal の disambiguation）
2 回ある時刻11 月の切り替え日、1:30 が 2 回来るオフセットで区別する（-04:00 と -05:00）
1 日が 24 時間でない23 時間の日・25 時間の日がある「1 日後」と「24 時間後」を区別する
cron が飛ぶ・2 回動く毎日 2:30 のジョブは開始日に 2:30 が無く、1:30 のジョブは終了日に 2 回来る（cron の実装によっては補正される）サーバーの cron は UTC で設定する

日本には現在夏時間がないので国内だけなら起きにくいが、海外ユーザー・海外リージョンのサーバー・SaaS の設定で必ず出会う。

JS の Date の問題と Temporal

new Date(2026, 0, 31)           // 月は 0 始まり：1 月 31 日
new Date('2026-11-06')          // UTC の 0 時として解釈（日付だけの書式）
new Date('2026-11-06T00:00')    // 実行環境のローカル時刻の 0 時として解釈
const d = new Date(); d.setMonth(1);  // 元のオブジェクトを書き換える（可変）

Date の中身は「瞬間」1 種類だけで、日付だけ・壁時計の時刻を表す型がありません。Temporal は種類ごとに型を分け、すべて変更不可 (immutable) です。

型持つもの用途
Temporal.Instant瞬間（ナノ秒）ログ・保存用の時刻
Temporal.ZonedDateTime瞬間＋タイムゾーン「東京の 10:00」として計算・表示する
Temporal.PlainDateTime日付＋時刻（ゾーンなし）未来の予定の現地時刻
Temporal.PlainDate日付だけ誕生日・締切日
Temporal.Duration期間「1 か月と 3 日」
const meeting = Temporal.ZonedDateTime.from('2026-11-06T10:00[America/New_York]');
meeting.withTimeZone('Asia/Tokyo').toString();  // '2026-11-07T00:00:00+09:00[Asia/Tokyo]'
meeting.add({ days: 1 });    // 翌日の 10:00（夏時間をまたいでも 10:00）
meeting.add({ hours: 24 });  // ちょうど 24 時間後（またぐと 9:00 や 11:00）
Temporal.PlainDate.from('2026-01-31').add({ months: 1 });  // 2026-02-28（月末に寄せる）

Temporal は Firefox・Chrome・Edge・Node.js 26 以降で使える。Safari は 2026 年半ばの時点で安定版が未対応だったので、ブラウザで使うときは対応状況を確認し、必要なら polyfill（提案の champion が始めた @js-temporal/polyfill や temporal-polyfill）を入れる。

書式と Unix 時刻

形式例注意

Unix 時刻1793927700秒かミリ秒か（JS の Date.now() はミリ秒）を API ごとに確認。うるう秒は数えない

よくある誤解

日本時間は UTC+9 と覚えておけば変換は足し算で済む

日本だけならそうだが、夏時間のある地域はオフセットが季節で変わる。オフセットではなくタイムゾーン名で変換する。

全部 UTC で保存すれば安全

過去の瞬間はそれでよいが、日付だけの値と未来の現地時刻の予定は UTC にすると壊れる。

timestamptz はタイムゾーンを保存する型

PostgreSQL の timestamptz は UTC に変換して保存し、元のタイムゾーンは残さない。必要なら別の列に持つ。
