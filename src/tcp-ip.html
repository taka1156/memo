TCP/IP とネットワーク基礎

IP・CIDR・ルーティング・NAT・ポート・TCP/UDP — HTTP の下で何が起きているか

ざっくり言うと
  • 通信は層に分かれていて、HTTP のデータに TCP（どのプロセス宛て）、IP（どのホスト宛て）、Ethernet（隣の機器まで）のヘッダーを順に付けて送る。
  • 宛先が同じネットワーク（CIDR の範囲内）なら直接、外ならデフォルトゲートウェイ（ルーター）に渡す。家庭や VPC 内のプライベートアドレスは NAT でグローバルアドレスに変換されて外に出る。
  • TCP は接続を張って順序と再送を保証する、UDP は投げっぱなしで軽い。HTTP/3（QUIC）は UDP の上に信頼性を自前で作っている。

層とカプセル化

各層は自分の仕事に必要なヘッダーだけを付け足し、受け取った側は外から順に剥がしていく。

IP アドレスは最終目的地まで変わらない（NAT を除く）が、MAC アドレスはルーターを越えるたびに「次の機器」のものに付け替えられる。

IP アドレスと CIDR

IPv4 アドレスは 32 bit。192.168.1.10/24 の /24 は「先頭 24 bit がネットワーク部（同じネットワークの印）、残り 8 bit がホスト部」という意味。

TRY · CIDR 計算
  • ホスト部が全部 0 はネットワークアドレス、全部 1 はブロードキャストなので、機器に割り当てられるのは 2 つ少ない（クラウドの VPC ではさらに数個を予約する）。
  • /16 は /24 を 256 個含む。VPC を /16、サブネットを /24 で切る、のような設計をよく見る。
  • VPC ピアリングや VPN でつなぐ予定のネットワーク同士は、範囲が重ならないように最初に決める。後から変えるのは大変。

覚えておく範囲

範囲用途

IPv6 は 128 bit（2001:db8::1 のように 16 進）。アドレスが十分にあるので各機器がグローバルアドレスを持て、LAN は通常 /64。ループバックは ::1、リンクローカルは fe80::/10。

ルーティング — 誰に渡すか

パケットを送るとき、OS は宛先 IP を自分のルーティングテーブルと照らし合わせる。

同じネットワーク内

例: 自分 192.168.1.10/24 → 宛先 192.168.1.20

範囲内なので直接送る。ARP で「192.168.1.20 の MAC アドレスは？」と尋ね、その MAC 宛てに送る。

外のネットワーク

例: 自分 192.168.1.10/24 → 宛先 203.0.113.14

範囲外なのでデフォルトゲートウェイ（例: 192.168.1.1 のルーター）の MAC 宛てに送る。ルーターが同じ判断を繰り返して目的地まで運ぶ。

$ ip route
default via 192.168.1.1 dev eth0          # どこにも当てはまらなければルーターへ
192.168.1.0/24 dev eth0 proto kernel      # この範囲は直接
172.17.0.0/16 dev docker0                 # Docker のブリッジネットワーク

複数の行に当てはまるときは、より長いプレフィックス（範囲が狭い方）が優先される（最長一致）。

NAT — プライベートからインターネットへ

ルーターは、内側からの通信の送信元を自分のグローバル IP とポートに書き換え、その対応を表に覚えておく。返事が来たら表を見て内側へ戻す。

内側（送信元）書き換え後宛先
192.168.1.10:51000198.51.100.5:40001203.0.113.14:443
192.168.1.23:51000198.51.100.5:40002203.0.113.14:443
  • 表に載るのは内側から始めた通信だけ。外から内側のサーバーに直接つなぐには、ポートフォワーディング（静的な対応）を設定する。
  • docker run -p 8080:80 も同じ仕組み（ホストの 8080 宛てをコンテナの 80 に転送）。
  • クラウドのプライベートサブネットから外に出るための「NAT ゲートウェイ」も、これをマネージドにしたもの。

コンテナのネットワーク名前空間は Docker 動作原理、ports の書き方は Dockerfile と Compose の書き方 を参照。

ポートとソケット

IP アドレスでホストまで届いたあと、ポート番号（0〜65535）でどのプロセスに渡すかが決まる。1 本の通信は 送信元 IP・送信元ポート・宛先 IP・宛先ポート・プロトコルの 5 つ組で識別される。

サーバーがどのアドレスで待ち受けるか（bind）で、届く範囲が変わる。

127.0.0.1:3000

同じマシンの中からだけ。コンテナ内でこう待ち受けると、-p で公開してもホストから届かない。

0.0.0.0:3000

すべてのインターフェースで待ち受ける。外から届くので、ファイアウォールの設定とセットで考える。

TCP と UDP

TCP

接続して、確実に順番どおり

  • 最初に 3 ウェイハンドシェイクで接続を張る
  • 番号（シーケンス番号）で順序を保証し、届かなければ再送
  • 受信側の余裕（フロー制御）や回線の混み具合（輻輳制御）に合わせて速度を調整
  • HTTP/1.1・HTTP/2、SSH、DB 接続
UDP

投げっぱなしで軽い

  • 接続なし。届いたかどうか、順番も保証しない
  • ヘッダーが小さく、待ちが発生しない
  • 多少欠けても新しいデータの方が大事な用途向き
  • DNS、音声・ビデオ通話、ゲーム、QUIC（HTTP/3）

3 ウェイハンドシェイク

クライアントサーバー SYN → 「つなぎたい。こちらの番号は x から」 ← SYN + ACK 「了解（x+1 を待つ）。こちらは y から」 ACK → 「了解」— ここから データ送信。TLS ならこの後に TLS のハンドシェイク
  • 接続のたびに 1 往復かかるので、HTTP は接続を使い回す（Keep-Alive、HTTP/2 の多重化）。
  • パケットが 1 つ失われると、後ろのデータは届いていてもアプリに渡せず待たされる（Head-of-Line ブロッキング）。QUIC はストリームごとに独立させてこれを避ける。
  • 閉じた側には TIME_WAIT 状態がしばらく残る。短い接続を大量に作るとポートが足りなくなる原因になる。

詳しくは HTTP/1.1・2・3 と TLS・DNS・リアルタイム通信 を参照。

つながらないときの切り分け

下の層から順に確かめると早い。

ip addr                      # 自分の IP とサブネットは正しいか
ip route                     # デフォルトゲートウェイはあるか
dig api.example.com          # 名前は正しい IP に解決されるか
ping 10.0.1.5                # IP で届くか（ICMP を止めている環境もある）
traceroute 10.0.1.5          # どこまで届いて、どこで止まるか
nc -zv 10.0.1.5 5432         # そのポートで TCP 接続できるか
ss -tlnp                     # （サーバー側）どのアドレス・ポートで待ち受けているか
curl -v https://api.example.com/health   # TLS と HTTP まで通るか
Connection refused

たいていは、相手のホストまでは届いたが、そのポートで待ち受けているプロセスがない（または 127.0.0.1 でしか待っていない）。途中のファイアウォールが拒否応答（REJECT）を返している場合も同じ表示になる。

タイムアウト

返事自体が来ない。ファイアウォール・セキュリティグループで落とされている、ルートがない、相手が落ちている、など。

よくある誤解

ping が通らないのでサーバーは落ちている

ICMP だけを止めているネットワークは多い。目的のポートに TCP でつないで確かめる。

プライベート IP なら外部から攻撃されないので安全

直接は届きにくいが、内側の侵害されたマシンや、ポートフォワーディング・VPN 経由では届く。認証や通信の暗号化は別途必要。

UDP は信頼性がないので、重要な通信には使えない

信頼性をアプリ側（QUIC など）で実装すれば、TCP より柔軟に作れる。HTTP/3 はその例。
