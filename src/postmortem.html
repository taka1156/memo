ポストモーテム

ブレームレスな障害のふりかえりと、5 Whys の使いどころ

ざっくり言うと
  • ポストモーテムは、障害のあとに影響・経緯・原因・再発防止策を文書にまとめ、組織で学ぶためのふりかえり。
  • 人を責めず「なぜその判断が当時は正しく見えたか」を問うと、事実が集まり、仕組みの弱点が見つかる。
  • 原因は 1 本の鎖に絞らず、アクションは「気をつける」ではなく担当と期限のある仕組みの変更にする。

ポストモーテムとは

ポストモーテム (postmortem) は、障害（インシデント）が収まったあとに書くふりかえりの文書と、それを読み合う場のことです。元は「検死」の意味ですが、IT の運用では「何が起き、なぜ起き、次にどうするか」を記録して、同じ障害をくり返さないために使います。Etsy の John Allspaw による 2012 年の記事や、Google の SRE 本の「ポストモーテムの文化」の章などを通じて、IT 業界に広まりました。

全部の障害で書くと続かないので、書く条件を先に決めておくのが普通です。SRE 本では次のような例が挙がっています。

  • 利用者から見える停止や劣化が、決めた基準を超えた
  • データが失われた
  • 当番の人が手で介入した（ロールバック・切り替えなど）
  • 解決までの時間が、決めた基準を超えた
  • 監視が気づかず、人が見つけた

条件に当てはまらなくても、関係者が書きたいと言えば書けるようにしておきます。

障害からポストモーテムまで

  1. 検知と対応まず影響を止める（緩和）。原因の追究は後回しにして、ロールバックや切り替えで利用者への影響を小さくする。対応中のやりとりは時刻つきで残す
  2. 下書き記憶が新しいうちに、対応した人が中心になって事実（時刻・数字・判断）を書く。チャットやダッシュボードのリンクを貼る
  3. レビュー関係者で読み合い、抜けている事実、原因の掘り方、アクションの妥当さを確かめる。責める言葉が混ざっていないかもここで見る
  4. アクションの追跡再発防止策を担当と期限つきでバックログに入れ、普段の作業と同じく完了まで追う
  5. 共有関係のないチームも読めるところに置く。似た弱点を持つ別のシステムで役に立つ

通常のスプリントのふりかえりが「チームの進め方」を見直す場なのに対し、ポストモーテムは1 つの出来事を深く掘り、システムと組織の弱点を見つける場です。

ブレームレス：人ではなく条件を見る

ブレームレス (blameless、非難しない) は、障害のきっかけになった操作をした人を責めないという約束です。責められると分かっていると、人は自分に不利な事実を話さなくなり、いちばん大事な情報が集まりません。

代わりに、その人がその時点で知っていたこと・見えていたものから考えると、なぜその判断が妥当に見えたのかを問います。同じ立場なら別の人も同じことをした、と分かれば、直すべきは人ではなく、誤りを招いた画面・手順・権限・情報の出し方です。

責める書き方田中さんが確認を怠り、本番に誤った設定を出した。
ブレームレスな書き方設定の差分はレビュー画面に表示されず、検証環境では別のファイルが上書きしていたため、誤りに気づける手がかりがなかった。
責める書き方当番がアラートを見落とした。
ブレームレスな書き方同じ時間帯に重要度の低いアラートが 40 件出ており、今回のものは見た目で区別できなかった。
責める書き方手順を守らなかったのが原因。
ブレームレスな書き方手順書は 2 年前の構成のままで、今の画面とは項目名が違っていた。
人の注意不足で終わっている誤りを招いた条件まで書いている

ブレームレスは「誰も責任を取らない」ことではありません。名前を出して状況を説明するのはかまいませんし、アクションの担当ははっきり決めます。変わるのは、責任を「処罰」ではなく「改善を進める役目」として扱うことです。人の誤りを潜在的な条件の表れとして見る考え方は、層を重ねて守るのスイスチーズモデルとも共通します。

書く項目

書式はチームで 1 つに決めておくと、書く人も読む人も迷いません。よく使われる項目は次のとおりです。

項目書くことありがちな失敗
要約何が・いつ・どのくらいの間・誰に影響したかを 2〜3 文で原因の細部から書き始め、影響が分からない
影響失敗したリクエスト数、影響した利用者数、売上・SLO への影響など数字で「一部のユーザー」だけで、規模が分からない
タイムライン発生・検知・判断・緩和・復旧を時刻つきで。誰が何を見て何をしたかあとから分かった事実を、その時点で分かっていたように書く
原因と寄与要因きっかけと、それが障害にまで育った条件（検知の遅れ・影響の広がり方）原因を 1 つに絞り、「人為的ミス」で止める
うまくいったこと早く気づけた、すぐ戻せた、など残したい仕組み悪かった点だけを並べ、効いた対策が次に消される
運が良かったことたまたま被害が小さかった理由（深夜だった、詳しい人が居合わせた）書かずに済ませ、次は運が悪くて大きな被害になる
アクション何を・誰が・いつまでに。種類（防ぐ・早く気づく・影響を小さくする）も担当と期限がなく、誰も手を付けない

  2. 14:05データベースの CPU 使用率が 90% を超える（アラートの対象外）

  4. 14:15インシデントとして宣言し、指揮をとる人を決める

この例では、最初の 9 分は監視が気づいていません。原因（設定の誤り）を防ぐ策と同じくらい、「なぜ 9 分気づけなかったか」を問う価値があります。

5 Whys の使いどころと落とし穴

5 Whys（なぜなぜ分析）は、起きたことに「なぜ」を重ねて原因を掘る方法で、トヨタ生産方式から広まりました。手軽で、表面の原因で止まらないようにする助けになります。ただし、1 本の鎖でたどると、最後が人の注意不足に行き着きやすいという落とし穴があります。

  1. エラーが増えた → データベースが過負荷になったから
  2. 過負荷になった → キャッシュが効かず、全部の読み込みが届いたから
  3. キャッシュが効かなかった → 設定の有効期限が 0 になっていたから
  4. 0 になっていた → 担当者が確認を怠ったから
  5. 結論：「今後は確認を徹底する」

4 つ目で人の注意に行き着き、そこで止まっている。この結論では、同じ条件がそろえば別の人が同じ誤りをする。

なぜ起きたか

  1. 本番だけ有効期限が 0 になった
  2. 設定ファイルの読み込み順が変わり、既定値の 0 が使われた
  3. 検証環境は別のファイルで上書きしており、差が出なかった

なぜ気づくのが遅れたか

  1. 9 分間アラートが鳴らなかった
  2. エラー率しか見ておらず、データベースの CPU は対象外だった
  3. 予兆の指標をアラートにする基準がなかった

なぜ影響が広がったか

  1. 全利用者に一度に影響した
  2. 設定の変更はコードと違い、段階的に出していなかった
  3. 設定の変更を小さく出す仕組みがなかった

起きた理由・気づくのが遅れた理由・広がった理由に分けると、どれも仕組みで直せる条件にたどり着く。

人の注意で止まった「なぜ」仕組みで直せる条件にたどり着いた「なぜ」
  • 「5 回」は目安で、回数に意味はない。直せる条件に届いたら止めてよい。
  • 複雑なシステムの障害は、いくつもの条件が重なって起きるのが普通。原因を 1 つに絞らず、寄与要因 (contributing factors) として並べる。
  • 「人為的ミス」が出てきたら、それは答えではなく、次の「なぜ」の出発点として扱う。

アクションの書き方

アクションは、同じ条件がそろっても障害にならない、または小さく済むように仕組みを変えるものにします。人に注意を求める対策は、書いた直後は効いても、人が入れ替わったり忙しくなったりすると効かなくなります。

種類弱いアクション強いアクション
起きにくくする設定は慎重に変える有効期限が 0 の設定を CI のチェックでエラーにする（担当: 基盤チーム、期限: 12/5）
早く気づくダッシュボードをこまめに見るデータベースの CPU が 80% を 5 分超えたらアラートにする（担当: 当番の責任者、期限: 11/30）
影響を小さくする何かあればすぐ戻す設定の変更も 5% の利用者から段階的に出す（担当: 基盤チーム、期限: 12/19）
直しやすくする手順書を見直す設定のロールバックを 1 コマンドにし、手順書から呼ぶ（担当: 当番の責任者、期限: 12/12）

アクションは多すぎると終わりません。効果の大きいものに絞り、残りは「やらない」と決めた理由ごと記録します。完了したかどうかを、次のレビューや定例で確かめます。

よくある誤解

ブレームレスにすると誰も責任を取らなくなる

ブレームレスでも、アクションの担当と期限ははっきり決めます。やめるのは、誤りをした人を処罰したり、評価を下げたりすることです。責めないことで事実が集まり、責任を「仕組みを直す役目」として果たせるようになります。

5 Whys で「なぜ」を 5 回くり返せば、ただ 1 つの根本原因にたどり着ける

回数は目安で、障害の多くはいくつもの条件が重なって起きます。1 本の鎖だけでたどると、たどる人の思い込みで道筋が決まり、人の注意不足で止まりやすくなります。起きた理由・気づくのが遅れた理由・広がった理由のように問いを分け、寄与要因を並べます。

ポストモーテムは大きな障害のときだけ書けばよい

大きな障害は、小さな障害やヒヤリとした出来事（ニアミス）と同じ弱点から起きることが多くあります。書く条件を決めたうえで、条件に当てはまらない出来事も短い形で残しておくと、大きくなる前に弱点を直せます。

原因が分かるまでは、ロールバックなどの対応をしない方がよい

障害の最中は、原因の追究より影響を止めることを優先します。原因を調べるための情報（ログ・時刻・画面）は残しつつ、まず戻すか切り替えます。原因の分析はポストモーテムで落ち着いて行います。

関連メモ

  • ふりかえりの進め方と手法 — チームの進め方を定期的に見直す場。ポストモーテムは 1 つの障害を深く掘る版
  • 層を重ねて守る：スイスチーズモデルと多層防御 — 人の誤りを潜在的な条件の表れとして見る考え方と、アクションで層を足す発想
  • オブザーバビリティと OpenTelemetry — 「なぜ気づくのが遅れたか」を直すときの、何をアラートにするか
  • CI/CD と GitHub Actions — 段階的なリリースや、設定のチェックを仕組みに入れる場所
  • 障害を広げない設計 — 「なぜ影響が広がったか」の答えになりやすい設計の弱点
