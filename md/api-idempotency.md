# 冪等キーとリトライ

二重送信・二重課金を防ぐ API の作り方 ── 判定フロー・原子性・途中で落ちたときの再開

**ざっくり言うと**

- 冪等キーは「これは前と同じ操作です」とサーバーに伝える名札で、同じキーの再送には処理せず 1 回目の応答を返す。
- キーの記録と本処理は同じトランザクションで確定し、処理中の同じキーは `409` 、中身が違えば `422` で弾く。
- キーは操作 1 回ごとにクライアントが作ってリトライで使い回し、外部 API を挟む処理は進み具合を残して再開できるようにする。

冪等性そのもの（何回やっても結果が同じ性質）と、リトライの間隔の空け方（指数バックオフ＋ジッター）は [分散システムの基本](https://memo.taka1156.site/md/distributed-basics.md) にあります。このメモはその続きで、 **POST の API を実際に冪等にするときにサーバーとクライアントが決めること** を扱います。

## 二重はどこで起きるか

**ダブルクリック・連打**

反応が遅いと利用者はもう一度押す。複数タブ・再読み込みでも同じ送信が起きる。

**タイムアウト後の再送**

クライアントの HTTP ライブラリや SDK が自動でリトライする。サーバーでは 1 回目が成功していることがある。

**途中の中継が再送**

リバースプロキシや LB が、上流の接続切れを見て別のサーバーへ送り直す設定がある。

**モバイルの電波切れ**

送った直後に圏外になり、応答だけを受け取れない。アプリは失敗と見て送り直す。

どれも「サーバーは処理したのに、クライアントはそれを知らない」状態から始まります。クライアント側だけでは防げないので、 **サーバーが「前と同じ操作だ」と見分けられる手がかり** が要ります。それが冪等キーです。

### 応答が消えて再送したとき

キーなし

キーあり

キーあり・同時に 2 本

→ クライアントが送る ● サーバーの処理 ← サーバーの応答

→ `POST /payments {amount: 3000}`

● サーバーが課金して `201` を返す（課金 1 回目）

✕ `201 Created` がネットワークで消える

→ タイムアウトしたので同じ内容をもう一度 `POST`

● サーバーには新しいリクエストに見えるので、また課金する

二重課金 課金 2 回・6,000 円。サーバーには 2 本を見分ける材料がない。

→ クライアントが送る ● サーバーの処理 ← サーバーの応答

→ `POST /payments` ＋ `Idempotency-Key: "7f3c…"`

● キーを記録して課金し、応答（ `201` と本文）をキーと一緒に保存

✕ `201 Created` がネットワークで消える

→ **同じキー** ・同じ内容でもう一度 `POST`

● 記録済みのキーなので課金せず、保存した `201` と本文をそのまま返す

1 回だけ 課金 1 回。2 回目の応答にも 1 回目と同じ支払い ID が入るので、クライアントは結果を知ることができる。

→ クライアントが送る ● サーバーの処理 ← サーバーの応答

→ 同じキーの `POST` が 2 本、ほぼ同時に届く（連打・二重のリトライ）

● 1 本目がキーの行を「処理中」で作る。2 本目は一意制約にぶつかる

← 2 本目には `409 Conflict` （同じキーが処理中）

← 1 本目は課金を終えて `201`

409 2 本目は少し待って同じキーで送り直せば、保存された `201` を受け取れる。「行が無いことを確かめてから作る」2 段の書き方では、2 本とも「無い」と見て二重になる。

## サーバー側の判定フロー

キーを受け取ったら、まず記録を探します。見つかったときの状態で、返すものが 4 通りに分かれます。

**(利用者, エンドポイント, キー) で記録を探す**

あわせてリクエスト本文のフィンガープリント（fingerprint。本文のハッシュなど）を計算しておく

↓

記録が無い 新しく処理 行を「処理中」で作ってから本処理。終わったら応答を保存して「完了」に

記録が「処理中」 409 Conflict 同じキーが走っている。待ってから送り直してもらう

「完了」でフィンガープリントが同じ 保存した応答 処理しない。1 回目のステータスと本文をそのまま返す

フィンガープリントが違う 422 同じキーを別の中身に使い回している。クライアントのバグ

新しく処理する 処理せずに再生 待ってから再送 リクエストを直す

ステータスコードは、IETF で標準化が進んでいる `Idempotency-Key` ヘッダーの草案（Internet-Draft）に合わせています。草案では、キーが必須の操作でキーが無ければ `400` 、同じキーで中身が違えば `422` 、同じキーの処理がまだ終わっていなければ `409` を返すことを勧めています。まだ RFC ではないので、実際の API はそれぞれの決まりに従います。

### 決めておくこと

| 項目 | よくある決め方 | なぜ |
| --- | --- | --- |
| キーの範囲 | 利用者（アカウント・API キー）ごと、必要ならエンドポイントごと | 別の利用者が偶然同じ値を送っても、他人の応答を返さないため |
| キーの形 | UUID v4 などの十分に長いランダム値。長さの上限を決める | 推測やぶつかりを避ける。メールアドレスなどの個人情報をキーにしない |
| 有効期限 | 24 時間〜数日で消す。期限を API の文書に書く | 記録が増え続けないように。期限後の同じキーは新しい操作として扱われる |
| フィンガープリント | 本文のハッシュ、または金額・宛先など大事な項目だけ | キーの使い回し（別の操作に同じキー）を見つけて `422` にする |
| 保存する応答 | 本処理を始めた後の応答は、成功も失敗もステータスと本文を保存 | 2 回目に結果が変わると、クライアントがどちらを信じればよいか分からない |
| 保存しない応答 | 認証エラー、入力チェックで弾いたもの、 `409` | 本処理に入っていないので、直して同じキーで送り直せるようにする |

Stripe の API v1 では、キーは 255 文字まで、少なくとも 24 時間たったキーは消されることがあり、本処理が始まった後の応答は `500` も含めて保存される。入力チェックで弾かれたものや同時実行でぶつかったものは保存されず、送り直せる。新しい API v2 では、失敗や途中で止まった処理をリトライ時に Stripe 側で最後までやり直し、更新した応答を返す。

## 記録と本処理を 1 つのトランザクションに

「キーの記録」と「本処理（注文の作成など）」を別々に確定すると、その間で落ちたときにずれます。キーだけ残れば処理されないまま「完了」を返し、処理だけ残れば再送でもう一度処理されます。DB の中で済む処理なら、 **1 つのトランザクション** に入れて両方を一度に確定します（トランザクションの性質は [インデックスとトランザクション](https://memo.taka1156.site/md/db-index-transaction.md) ）。

```
-- (user_id, key) に一意制約。同時に来た 2 本目はここで止まる
CREATE TABLE idempotency_keys (
  user_id       BIGINT  NOT NULL,
  key           TEXT    NOT NULL,
  fingerprint   TEXT    NOT NULL,
  status        TEXT    NOT NULL,      -- 'processing' | 'completed'
  response_code INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)
);

BEGIN;
INSERT INTO idempotency_keys (user_id, key, fingerprint, status)
VALUES ($1, $2, $3, 'processing')
ON CONFLICT DO NOTHING;              -- 0 行なら既にある → 判定フローへ
INSERT INTO orders (...) VALUES (...);  -- 本処理
UPDATE idempotency_keys
   SET status = 'completed', response_code = 201, response_body = $4
 WHERE user_id = $1 AND key = $2;
COMMIT;
```

ポイントは、 **「探してから作る」ではなく「作ってみて、ぶつかったら既にある」** と判断することです。探してから作る 2 段の書き方では、同時に来た 2 本がどちらも「無い」と見て両方とも処理します。一意制約に判断を任せれば、DB が 1 本だけを通します。

同時に来た 2 本目は、1 本目のトランザクションが終わるまで INSERT で待たされ、終わった後に「既にある」と分かる。待たせずにすぐ `409` を返したいなら、キーの行だけを先に短いトランザクションで作り、本処理は別のトランザクションで行う（下の「外部 API を挟むとき」と同じ形になる）。

## 外部 API を挟むとき：進み具合を残して再開する

決済代行やメール送信など、 **自分の DB の外を変える処理** はトランザクションに入れられません。課金した直後に落ちると、DB を巻き戻しても課金は戻りません。そこで、処理を「DB の中で完結する段」と「外を 1 回だけ変える段」に分け、 **どこまで進んだか** （リカバリポイント (recovery point)）をキーの行に記録します。

DB・原子的

**キーの行を作り、注文を「支払い待ち」で作る**

1 つのトランザクション。リカバリポイントを order_created にして確定する。

外部を変える

**決済 API を呼ぶ**

自分のキーから決めた冪等キー（例: `order-123-charge` ）を付ける。ここで落ちても、再開時に同じキーで呼べば決済側が二重を防ぐ。

DB・原子的

**決済結果を保存し、注文を「支払い済み」に**

リカバリポイントを charged に。メール送信は直接呼ばず、送信待ちの行を同じトランザクションで書く。

外部を変える

**別の作業者が送信待ちの行を読んでメールを送る**

送信の重複は受け手側の重複排除で吸収する（アウトボックス (outbox) の形。 [メッセージキューと Pub/Sub](https://memo.taka1156.site/md/message-queues.md) ）。

DB・原子的

**応答を保存して完了**

リカバリポイントを finished 。以後の同じキーは保存した応答を返すだけ。

DB の中だけ（巻き戻せる） 外部を変える（巻き戻せない。1 段に 1 つだけ）

途中で落ちてクライアントが同じキーで送り直したら、行のリカバリポイントを見て **続きから** 実行します。「処理中」のまま長く止まっている行は、ロックの時刻を記録しておき、一定時間たったら再開してよいことにします。この組み立ては、Stripe の社員だった Brandur Leach の記事「Implementing Stripe-like Idempotency Keys in Postgres」で詳しく説明されています。

## クライアント側：キーは「操作」に 1 つ

1. **操作が始まったときに作る** 購入ボタンを最初に押したとき（またはフォームを表示したとき）に UUID を作る。HTTP リクエストを送るたびに作るのではない。
2. **リトライでは同じキーを使い回す** タイムアウト・接続切れ・ `409` ・ `5xx` で送り直すときは、キーも本文も変えない。間隔は指数バックオフ＋ジッターで空ける。
3. **中身を変えたら新しいキー** 利用者が金額や宛先を直したら別の操作なので、新しいキーを作る。同じキーで中身を変えると `422` になる。
4. **直さないと通らない失敗は再送しない** `400` ・ `422` ・ `401` などはリクエストを直す。同じものを何度送っても結果は変わらない。

ボタンを押せなくする・送信中の表示を出すのは、利用者のための工夫としては有効です。ただし、自動リトライ・中継の再送・複数タブは防げないので、サーバー側の冪等キーの代わりにはなりません。

## キーを使わずに冪等にする方法

冪等キーは汎用ですが、記録用のテーブルと期限の管理が要ります。操作の性質によっては、もっと単純な方法で足ります。

| 方法 | やり方 | 向いている場面 |
| --- | --- | --- |
| 自然な一意キー | 業務上 1 回しか起きないものに一意制約（「注文 123 の支払い」は 1 件だけ、など） | 重複の定義が業務で決まっているとき。期限も要らない |
| ID をクライアントが決めて `PUT` | `PUT /orders/{クライアントが作った UUID}` 。何回送っても同じ注文 1 件 | 作成する資源の ID を前もって決めてよいとき。 `PUT` はもともと冪等 |
| 条件付きリクエスト | `If-None-Match: *` （無いときだけ作る）、 `If-Match: "<ETag>"` （読んだときのままなら更新） | 二重作成と更新の取り合いを防ぎたいとき（ [S3 互換ストレージの仕組み](https://memo.taka1156.site/md/s3-compatible.md) の条件付き書き込み） |
| 受け手の重複排除 | メッセージ ID を「処理済み」テーブルに入れてから処理（同じトランザクション） | キュー・Webhook の受信。送り手は少なくとも 1 回届けるだけ |

## よくある誤解

✗ 誤解: 送信ボタンを無効にすれば二重送信は防げる

✓ 正しくは: 防げるのは同じ画面での連打だけ。HTTP ライブラリの自動リトライ、中継の再送、再読み込み、別タブからの送信はサーバーに 2 本届く。最後の砦はサーバー側の冪等キーか一意制約。

✗ 誤解: 冪等キーはリクエストを送るたびに新しく作る

✓ 正しくは: キーは「操作」に 1 つ。リトライのたびに作り直すと、サーバーには毎回別の操作に見えて、二重処理を防げない。

✗ 誤解: 2 回目のリクエストには「処理済み」とだけ返せばよい

✓ 正しくは: 1 回目の応答（作った資源の ID など）を受け取れなかったから送り直しているので、1 回目と同じステータスと本文を返す。そうしないとクライアントは結果を知る手段がない。

✗ 誤解: 冪等キーを付ければ、いつ何度送っても安全

✓ 正しくは: 記録には期限があり、期限を過ぎた同じキーは新しい操作として処理される。また、同じキーで中身を変えた送信は弾かれる。キーは「短い間のリトライを安全にする」仕組み。
