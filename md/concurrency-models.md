スレッド・async・goroutine・アクター ——「同時に動くもの同士で、状態をどう扱うか」の 4 つの答え

**ざっくり言うと**

- 並行処理の難しさはほぼ **「共有している状態を、同時に書き換えてしまう」** ことから来る。4 つのモデルはその避け方が違う。
- **スレッド＋ロック** は共有してロックで守る／ **イベントループ** は 1 本のスレッドで順番に回す／ **goroutine** は軽いスレッドをチャネルでつなぐ／ **アクター** は状態を共有せずメッセージだけ送る。
- Cloudflare の **Durable Objects** はアクターそのもの。「1 つの ID には 1 つの実体、1 度に 1 つずつ処理」なので、在庫やチャットルームをロックなしで正しく扱える。

## 並行と並列

**並行 (concurrency)**

複数の仕事を **途中まで進めては切り替える** 。CPU が 1 つでもできる。「待ち時間（I/O）の間に別の仕事をする」ための考え方。

**並列 (parallelism)**

複数の仕事を **物理的に同時に** 実行する。CPU コアが複数必要。「計算を速く終わらせる」ための考え方。

Web サーバーの多くは「待ち」が中心なので並行が効く。画像処理や圧縮のような計算中心の仕事は並列でないと速くならない。JS のイベントループは並行だが並列ではない（ [JS のイベントループと非同期](https://memo.taka1156.site/md/event-loop.md) ）。

## 4 つのモデル

スレッド＋ロック

イベントループ

goroutine

アクター

**OS スレッドを複数立て、メモリを共有する。** 共有データはミューテックス（ロック）で「同時に 1 人だけ」触れるようにする。C / C++ / Java / C# / Rust の `std::thread` など。

- 得意 本当に並列に計算できる。素直な逐次コードが書ける。
- 苦手 ロック忘れ（競合）・ロックの順序違い（デッドロック）。スレッドは 1 本あたりのメモリと切り替えコストが大きく、数万本は立てにくい。

Rust は「共有して書き換える」をコンパイル時に禁止し（所有権と `Send` / `Sync` ）、ロック忘れをビルドエラーにする（ [Rust](https://memo.taka1156.site/md/rust.md) ）。

**スレッドは 1 本。I/O を待つ間に別のタスクへ切り替える。** 切り替わるのは `await` の所だけなので、それ以外の行は途中で割り込まれない。JS（ブラウザ・Node.js）、Python の asyncio、Rust の tokio（こちらはマルチスレッドにもできる）。

- 得意 大量の同時接続を少ないメモリで捌ける。 `await` の間以外は競合が起きない。
- 苦手 重い計算を 1 つ入れると **全体が止まる** 。async 関数と普通の関数が混ぜにくい（「関数の色」問題）。

```
const v = await db.get('count');   // ← ここで他のリクエストが割り込める
await db.put('count', v + 1);      // 2 つ同時に来ると更新が消える
```

「シングルスレッドだから競合しない」は誤り。 `await` をまたぐ read → write は、上のシミュレーターの「ロックなし」と同じことが起きる。

**ランタイムが管理する軽いスレッド（グリーンスレッド）を大量に作り、少数の OS スレッドに載せて動かす（M:N スケジューリング）。** Go の goroutine、Java 21 の仮想スレッド、Erlang のプロセスなど。

- 得意 書き方は普通の同期コードのまま、10 万単位の同時処理ができる。I/O で止まると、ランタイムが自動で別の goroutine に切り替える。複数コアで並列にも動く。
- 苦手 メモリは共有できるので、共有すれば結局ロックが必要。

```
// Go：「メモリを共有して通信するな。通信してメモリを共有せよ」
ch := make(chan int)
go func() { ch <- heavyWork() }()  // 別の goroutine で計算
result := <-ch                      // チャネルで受け取る
```

**状態を持つ「アクター」同士が、メッセージだけでやり取りする。** アクターは自分の状態を外に見せず、届いたメッセージを **1 つずつ順番に** 処理する。Erlang / Elixir、Akka、Orleans、そして Cloudflare Durable Objects。

- 得意 状態を共有しないので、アクターの中ではロックが要らない。相手が同じマシンでも別のマシンでも同じ書き方（位置透過性）。
- 苦手 1 つのアクターは 1 度に 1 つしか処理しないので、そこに集中すると詰まる。複数のアクターをまたぐ処理は自分で整合を取る必要がある。

## 比べると

|  | スレッド＋ロック | イベントループ | goroutine 型 | アクター |
| --- | --- | --- | --- | --- |
| 実行の単位 | OS スレッド | タスク（Promise など） | 軽量スレッド | アクター（＋メールボックス） |
| 切り替わる所 | どこでも（OS が決める） | `await` の所だけ | I/O・チャネル操作など | メッセージ 1 件の処理の切れ目 |
| 状態の扱い | 共有＋ロック | 共有（1 本なので同時には触れない） | 共有もチャネルもできる | 共有しない |
| 並列（多コア） | できる | 1 本では不可 | できる | アクター同士は並列 |
| 同時に数万 | 重い | 軽い | 軽い | 軽い |
| よくある事故 | デッドロック・ロック忘れ | 重い計算で全停止・await 間の競合 | goroutine リーク・共有時の競合 | 1 アクターへの集中・メッセージの取りこぼし |

## アクターモデル

**1. 状態は自分だけのもの**

アクターの状態は外から直接読めない・書けない。知りたければメッセージで聞く。

**2. メールボックスに並ぶ**

届いたメッセージは列に並び、 **1 件ずつ** 処理される。

+1 +1 get +1

同時に 2 件処理しないので、さっきの count は必ず正しく増える。

**3. 処理中にできること**

自分の状態を変える／他のアクターにメッセージを送る／新しいアクターを作る、の 3 つ。

### 落ちたら作り直す（Let it crash）

Erlang / Elixir では、アクター（プロセス）がおかしくなったら無理に直さず落とし、親の **スーパーバイザー** が作り直します。状態が他と混ざっていないから、1 つだけ再起動しても全体は壊れない、という発想です。

### スケールのさせ方

1 アクター＝1 度に 1 件なので、1 つのアクターの処理量には上限があります。速くしたいときは **アクターを細かく分ける** （ユーザーごと・部屋ごと・ドキュメントごと）。「全ユーザーのカウンター」を 1 つのアクターに持たせるのは典型的な失敗です。

## Durable Objects はアクター

Cloudflare の Durable Objects (DO) は、アクターモデルをサーバーレスで提供するものです。アクターの性質がそのまま当てはまります。

| アクターの性質 | Durable Objects では |
| --- | --- |
| アイデンティティ | 名前（ `idFromName("room-42")` ）か ID で指定。 同じ ID の実体は世界に 1 つだけ で、どこから呼んでも同じオブジェクトに届く |
| 自分だけの状態 | オブジェクトごとに専用の SQLite ストレージ（以前は KV 型もあったが、2026 年 7 月以降、KV 型をまだ使っていないアカウントは新しく作れない）。SQLite はオブジェクトと同じスレッドで動くので読み書きが非常に速い |
| 1 件ずつ処理 | 1 オブジェクトは 1 スレッド。さらに 入力ゲート が、ストレージ操作の完了を待つ間に他のリクエストが割り込むのを防ぐ |
| メッセージ | Worker から stub 経由で `fetch` や RPC メソッドを呼ぶ。WebSocket もオブジェクトで受けられる |
| 細かく分ける | オブジェクトは何百万個作ってもよい前提。部屋・ユーザー・ドキュメントごとに 1 つ |

### 入力ゲートと出力ゲート

**入力ゲート (input gate)**

ストレージ操作を待っている間は、新しいイベント（別のリクエスト）を届けない。だから `get` → `put` の間に他のリクエストが割り込まず、カウンターが正しく増える。

**出力ゲート (output gate)**

書き込みが確定するまで、外への応答を止めておく。コードは書き込み完了を待たずに先へ進めるが、「保存できていないのに成功を返す」ことは起きない。

```
export class Counter extends DurableObject {
  async increment() {
    const v = (await this.ctx.storage.get('n')) ?? 0;  // 入力ゲートが割り込みを防ぐ
    await this.ctx.storage.put('n', v + 1);
    return v + 1;                                       // 出力ゲート：書き込み確定後に返る
  }
}
```

**落とし穴：** ゲートが守るのはストレージ操作の待ち時間だけ。途中で外部 API を `await fetch()` すると、その間に別のリクエストが割り込める。外部呼び出しをまたいで状態を読み書きするなら、呼び出しの前後で状態を確認し直すか、ストレージのトランザクションにまとめる。

どこで使うかは [分散システムの基本](https://memo.taka1156.site/md/distributed-basics.md) （整合性の比較）と [Cloudflare サービス](https://memo.taka1156.site/md/cloudflare-services.md) 。

## どれを選ぶか

| やりたいこと | 向くモデル |
| --- | --- |
| 大量の API 呼び出し・DB 待ち | イベントループ / goroutine |
| 重い計算を全コアで | スレッド（ワーカースレッド・Rayon など） |
| 部屋・在庫・座席など「1 か所で正しく」 | アクター（Durable Objects など） |
| 落ちても全体を止めたくない長時間サービス | アクター＋スーパーバイザー（Erlang / Elixir） |

## よくある誤解

JS はシングルスレッドだから競合状態は起きない

同じ行の途中で割り込まれることはないが、 `await` をまたいだ「読んで → 書く」は他のタスクに割り込まれる。

async にすれば処理が速くなる

速くなるのは待ち時間を重ねられるときだけ。計算そのものは速くならず、重い計算はむしろ全体を止める。

アクターならどれだけ負荷をかけても大丈夫

1 アクターは 1 度に 1 件。1 つに集中すると列が伸びて遅くなる。単位を細かく分けるのが前提。
