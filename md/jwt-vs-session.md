「何を持たせるか」と「どこに置くか」は別の話

**ざっくり言うと**

- **セッション** は、状態をサーバーが持ち、ブラウザには「引換券（セッション ID）」だけを渡す方式
- **JWT** は、ユーザー情報そのものに **署名** を付けて渡す方式。サーバーは照合不要だが、発行後に取り消しにくい
- 「Cookie か localStorage か」は保存場所の話で、JWT かセッションかとは **別の軸** 。混ぜて議論すると話がかみ合わない

## 比較の軸は2本ある

軸1：何を渡すか（形式）

**セッション ID** ：意味のないランダム文字列。中身はサーバー側のストアにある。

**JWT** ：ユーザー ID や権限などの中身を含み、署名で改ざんを防ぐ。

軸2：ブラウザのどこに置くか（保存場所）

**Cookie** ：ブラウザが自動で送る。 `HttpOnly` にすれば JS から読めない。

**localStorage など** ：JS で読み書きし、自分でヘッダーに付けて送る。

JWT を Cookie に入れることも、セッション ID をヘッダーで送ることもできる。この2軸の組み合わせは 後半の表 で整理する。

### 署名の2つの方式

HS256（共通鍵）

同じ秘密鍵で署名も検証もする。発行元と検証側が同じサーバーなら手軽。

検証する側全員に秘密鍵を配る必要があり、誰でも偽造できるようになる。

RS256 / ES256（公開鍵）

秘密鍵で署名し、公開鍵で検証する。検証側は署名を作れない。

OIDC の ID トークンはこちら。公開鍵は JWKS（ `/.well-known/jwks.json` など）で配り、ヘッダーの `kid` でどの鍵かを指す。

## リクエストのたびに起きること

セッション（ステートフル）

Cookie: sid=a8f3k2…

↓

セッションストアを引く Redis、DB、メモリなど

↓

user_id=42, role=editor

毎回ストアへの問い合わせが発生する代わりに、ストアから消せば即ログアウト。

JWT（ステートレス）

Authorization: Bearer eyJ…

↓

公開鍵で署名を検証 exp、iss、aud も確認

↓

sub=42, role=editor

ストア不要でどのサーバーでも検証できる代わりに、有効期限までは取り消せない。

## 比較表

| 観点 | セッション | JWT |
| --- | --- | --- |
| 状態の置き場所 | サーバー（ストア） | トークン自身 |
| 即時ログアウト・権限剥奪 | ◎ ストアから消すだけ | △ 期限まで有効。拒否リストを持つと結局ステートフルに |
| スケール | ○ 共有ストア（Redis など）があれば問題なし | ◎ 鍵さえあればどこでも検証 |
| サービスをまたぐ | △ ストアを共有する必要がある | ◎ 別サービス・別組織にも渡せる |
| サイズ | ◎ 数十バイト | △ 数百バイト〜。毎リクエスト送る |
| 情報の秘匿 | ◎ 中身はサーバーにしかない | △ 誰でも読める。秘密は入れない |
| 実装の落とし穴 | 少ない（フレームワーク任せ） | 多い（alg、鍵管理、検証漏れ） |

## JWT の「取り消せない」問題

JWT は「署名が正しく、期限内なら有効」なので、ログアウトしても、アカウントを停止しても、 **発行済みのトークンは期限まで使えてしまう** 。よくある対策は次の組み合わせ。

アクセストークン JWT・寿命 5〜15 分

＋

リフレッシュトークン サーバーで管理・取り消し可能

被害が続くのは最大でもアクセストークンの寿命まで。取り消しはリフレッシュトークン側で行う。つまり **「状態を完全になくす」のではなく「状態を見る頻度を減らす」** 設計になる。

## どこに置くか（2軸の組み合わせ）

HttpOnly Cookie

localStorage

セッション ID

**◎ 定番** 従来型 Web アプリの標準。XSS で盗まれない。CSRF は SameSite で対策

**△ 珍しい** メリットが薄い。XSS で読まれる

JWT

**○ 可** XSS で読まれない。サイズと CSRF に注意

**△ 要注意** よく見るが、XSS が1つあれば盗まれて外部から使われる

| 保存場所 | XSS（悪意ある JS の実行） | CSRF（他サイトからのなりすましリクエスト） |
| --- | --- | --- |
| HttpOnly Cookie | トークン自体は読めない（ただし、その場で API を叩かれることは防げない） | 自動送信されるので対策が必要。 `SameSite=Lax` 以上 ＋ 必要なら CSRF トークン |
| localStorage | 読み出されて外部に送られ、攻撃者の手元で使い放題になる | 自動送信されないので基本的に起きない |

SPA で外部の認可サーバーを使う場合は、トークンをブラウザに置かず、同じドメインのバックエンドが保持してブラウザとは HttpOnly のセッション Cookie でやり取りする **BFF (Backend for Frontend)** パターンが推奨されている。

## 使い分け

普通の Web アプリ

SPA

サービス間・API

**セッション ＋ HttpOnly Cookie** で十分。フレームワーク（Rails、Django、Laravel など）の標準機能をそのまま使うのが一番安全。

同じドメインに API があるなら、 **セッション Cookie** でよい。外部 IdP の OAuth/OIDC を使うなら **BFF** に寄せる。JWT を localStorage に置くのは、XSS 対策に自信がある場合に限る。

**JWT が本領を発揮する場面** 。マイクロサービス間で「誰の何のリクエストか」を伝える、別組織の API に渡す、ID トークンでログイン結果を伝える、など。寿命は短くする。

## JWT を検証するときのチェックリスト

- **アルゴリズムを固定する** ：ヘッダーの `alg` を信用しない。 `alg: none` や、公開鍵を HMAC の秘密鍵として使わせる「アルゴリズム混同」攻撃がある
- **署名を検証する** ：デコードしただけで中身を信じない（ `decode` と `verify` は別の関数のことが多い）
- **期限を確認する** ： `exp` （期限）、 `nbf` （これより前は無効）。時計のずれを数十秒許容
- **発行者と宛先を確認する** ： `iss` が想定の発行元か、 `aud` に自分が含まれるか
- **鍵のローテーションに備える** ： `kid` で JWKS から鍵を選び、キャッシュを適度に更新する

## よくある誤解

✕ 「JWT は暗号化されているから、中に何を入れても安全」

○ 普通の JWT（JWS）は署名だけ。中身は誰でも読める。暗号化したいなら JWE という別形式を使う。

✕ 「セッションはスケールしない」

○ サーバーごとのメモリに持つとそうなるが、Redis などの共有ストアに置けば何台でも増やせる。数ミリ秒の問い合わせが問題になる規模はまれ。

✕ 「JWT にすればログアウト処理が要らない」

○ クライアントから消しても、盗まれたコピーは期限まで有効。サーバー側でリフレッシュトークンを無効化する処理は必要。

✕ 「HttpOnly Cookie なら XSS は怖くない」

○ トークンを盗まれないだけで、XSS が起きればそのページ上から本人として API を叩ける。XSS 対策そのものは必須。
