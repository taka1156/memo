ハッシュ / HMAC / AES / 鍵交換 / 署名 / 証明書 — 「何を守る道具か」で整理する

**ざっくり言うと**

- 暗号の道具は **ハッシュ・MAC・共通鍵暗号・鍵交換・署名** の 5 つでほぼ足りる。それぞれ守るもの（改ざん検知・秘匿・本人確認）が違う。
- 大量データは速い **共通鍵** で暗号化し、その鍵を安全に共有するために **公開鍵の仕組み（鍵交換）** を使う。
- 「この公開鍵は本当にその相手のものか」は **証明書** が保証し、証明書は OS・ブラウザが信頼するルート CA までの **署名の連鎖** でたどれる。

## 5 つの道具と、守るもの

セキュリティで守りたいものは主に 3 つ。 **秘匿性** （読まれない）、 **完全性** （書き換えられていないとわかる）、 **真正性** （確かにその相手が作ったとわかる）。道具ごとに守れるものが違う。

| 道具 | 守るもの | 鍵 | 代表例 | 出てくる場所 |
| --- | --- | --- | --- | --- |
| ハッシュ | 完全性（偶発的な変化・照合） | なし | SHA-256, SHA-3 | Git のオブジェクト ID, ETag, PKCE |
| MAC | 完全性＋真正性（鍵を持つ者同士） | 共通鍵 | HMAC-SHA256 | JWT の HS256, Webhook の署名検証 |
| 共通鍵暗号 | 秘匿性（AEAD なら完全性も） | 共通鍵 | AES-GCM, ChaCha20-Poly1305 | TLS の通信本体, ディスク暗号化 |
| 鍵交換 | 共通鍵を盗聴者に知られずに作る | 公開 秘密 | ECDHE (X25519)、耐量子ハイブリッドの X25519MLKEM768 | TLS 1.3 のハンドシェイク |
| 署名 | 完全性＋真正性（誰でも検証できる） | 公開 秘密 | Ed25519, ECDSA, RSA-PSS | 証明書, JWT の RS256/ES256, パスキー |

Base64 や URL エンコードは **暗号ではない** 。誰でも元に戻せる「表記の変換」にすぎない。

## ハッシュ — 鍵のない「指紋」

任意の長さのデータを、固定長の値（SHA-256 なら 256 bit）に変換する一方向の関数。

**同じ入力 → 同じ出力** 何度計算しても一致する

**1 文字違えば別物** 出力の約半分のビットが変わる（雪崩効果）

**元に戻せない** 出力から入力を求められない

**衝突を作れない** 同じ出力になる別の入力を見つけられない

TRY · SHA-256 hello

SHA-256（16 進）。直前の値から変わった文字を赤で表示

…

パスワードの保存

SHA-256 は **速すぎる** ので、パスワードの保存には向かない。漏えいしたハッシュに対して、GPU で毎秒数十億通りの総当たりができてしまう。

- **わざと遅く・メモリを食う専用関数** を使う: Argon2id（第一候補）、scrypt、bcrypt
- ユーザーごとにランダムな **ソルト** を混ぜる（同じパスワードでも別のハッシュになり、事前計算表が使えない）。bcrypt や多くの Argon2 ライブラリはソルトを自動で生成してハッシュ文字列に埋め込む。scrypt（Node.js の `crypto.scrypt` など）では、ランダムなソルト（16 バイト以上）を自分で用意して保存する
- 自前で「SHA-256 を 1000 回」などを組まず、ライブラリの関数をそのまま使う

## MAC — 鍵付きハッシュで「改ざんされていない」を確かめる

ハッシュだけだと、改ざんした人がハッシュも計算し直せば気づけない。 **共通鍵を混ぜたハッシュ（HMAC）** なら、鍵を知らない人は正しい値を作れない。

メッセージ + 共通鍵 → HMAC タグ → 受信側も同じ鍵で計算して一致を確認

- Webhook（GitHub, Stripe など）の署名ヘッダーは HMAC。受信側は共有シークレットで再計算して比べる。
- 比較は **定数時間比較** （constant-time comparison。 `crypto.timingSafeEqual` など）で行う。 `===` だと一致した長さで処理時間が変わり、推測の手がかりになる。
- 弱点: 検証する側も同じ鍵を持つので「誰が作ったか」を第三者に証明できない。それが要るなら署名を使う。

## 共通鍵暗号 — 速いが「鍵をどう渡すか」が問題

暗号化と復号に **同じ鍵** を使う。CPU 命令でも支援されていて非常に速く、通信やファイルの本体はすべてこれで暗号化する。

平文 → 鍵 → 暗号文＋認証タグ → 同じ鍵 → 平文

- 今使うのは **AEAD** （AES-GCM, ChaCha20-Poly1305）。暗号化と改ざん検知を同時に行い、書き換えられた暗号文は復号に失敗する。
- AES-GCM では **同じ鍵でナンス（IV）を再利用してはいけない** 。再利用すると平文の情報が漏れ、改ざんもできるようになる。
- 根本の問題: 会ったことのない相手と、盗聴されている回線で、どうやって同じ鍵を持つか → 次の公開鍵の仕組みで解く。

## 公開鍵の仕組み — 鍵交換と署名

公開鍵 は誰に見せてもよく、 秘密鍵 は持ち主だけが持つ。公開鍵は秘密鍵から計算できるが、公開鍵から秘密鍵を求めることは現実的にはできない。用途は大きく 2 つ。

鍵交換

署名

公開鍵で暗号化

**ECDHE** （楕円曲線ディフィー・ヘルマン）: 双方がその場で鍵ペアを作り、公開鍵だけを送り合う。自分の秘密鍵と相手の公開鍵を組み合わせると、 **両者で同じ値** が計算できる。盗聴者は公開鍵 2 つしか見ていないので計算できない。

A の秘密 a ＋ B の公開 = 同じ共有鍵 = B の秘密 b ＋ A の公開

末尾の E (Ephemeral) は「接続ごとに使い捨ての鍵ペア」の意味。後でサーバーの秘密鍵が漏れても、過去の通信は復号できない（前方秘匿性 / forward secrecy）。

**署名** : 秘密鍵でデータに署名し、誰でも公開鍵で「この秘密鍵の持ち主が、この内容に署名した」と検証できる。内容が 1 bit でも変われば検証に失敗する。

データ → 秘密鍵で署名 → データ＋署名 → 公開鍵で検証 → OK / NG

MAC との違いは、 **検証する側が署名を作れない** こと。JWT を RS256/ES256 で発行すれば、検証だけする API サーバーには公開鍵だけを配ればよい。パスキーは、サーバーが送ったランダムな値（チャレンジ）に端末の秘密鍵で署名して本人であることを示す。

署名は秘匿しない。署名付き JWT（JWS）の中身は Base64URL なので誰でも読める。

公開鍵で暗号化し、秘密鍵の持ち主だけが復号する使い方（RSA-OAEP など）もある。ただし遅く、扱えるデータも小さいので、 **実際にはランダムな共通鍵だけを公開鍵で包み、本体は共通鍵で暗号化する** （ハイブリッド暗号。HPKE や PGP、S/MIME など）。

TLS 1.3 では「RSA で鍵を暗号化して送る」方式は廃止され、公開鍵による鍵交換はすべて使い捨ての (EC)DHE になった（主流は X25519。最近は耐量子のハイブリッド方式も）。RSA 鍵の証明書でも、RSA は署名にだけ使われる。

（元のページで操作できます → https://memo.taka1156.site/crypto-basics.html#asymmetric）

## 証明書とチェーン — 「その公開鍵は本物か」

鍵交換の相手が攻撃者だったら意味がない（中間者攻撃）。そこで **証明書** : 「 `example.com` の公開鍵はこれ」という内容に、認証局 (CA) が署名したもの。

**ルート CA** OS・ブラウザの「信頼ストア」に最初から入っている。自分で自分に署名

↓ ルートの秘密鍵で署名

**中間 CA** ルートは普段オフラインで保管し、発行は中間 CA が行う

↓ 中間 CA の秘密鍵で署名

**サーバー証明書（リーフ）** ドメイン名・公開鍵・有効期限。サーバーは中間 CA の証明書と一緒に送る

ブラウザは、リーフ → 中間 → ルートと署名を順に検証し、ルートが信頼ストアにあれば OK とする。加えて **ドメイン名の一致** と **有効期限** を確認する。

- サーバーが中間証明書を送り忘れると、一部の環境（curl、古い Android など）でだけ失敗する。 `fullchain.pem` を設定する。
- 自己署名証明書がブラウザで警告になるのは、チェーンが信頼ストアのルートにたどり着かないため。社内では社内 CA のルートを端末に入れて解決する。
- 証明書の有効期限は短縮が進んでいる。ACME（Let's Encrypt など）で **自動更新** する前提で運用する。

## TLS 1.3 で全部がつながる

HTTPS の最初の 1 往復で、ここまでの道具がすべて使われる。 （🔒 は、ここから暗号化されていることを示す）

クライアント → サーバー ClientHello 対応する暗号の一覧と、使い捨ての **鍵交換用の公開鍵** （key_share）

サーバー → クライアント ServerHello サーバー側の鍵交換用公開鍵。ここで両者が **同じ共通鍵** を計算できる（ECDHE。主要ブラウザでは ML-KEM と組み合わせたハイブリッド方式が標準）

サーバー → クライアント Certificate 🔒 証明書チェーン。クライアントはルート CA までの **署名** を検証する

サーバー → クライアント CertificateVerify 🔒 証明書の秘密鍵で、ここまでのやり取りに **署名** 。「証明書の持ち主本人と鍵交換した」ことの証明

サーバー → クライアント Finished 🔒 ハンドシェイク全体の **MAC** 。途中で書き換えがあれば一致しない

クライアント → サーバー Finished 🔒 クライアント側の確認

双方向 HTTP リクエスト / レスポンス 🔒 共有した鍵で **AEAD（AES-GCM など）** により暗号化

鍵の導出にはハッシュベースの HKDF が使われる。つまり 5 つの道具すべてが登場する。

## よくある誤解

✗ JWT は暗号化されているので、中に個人情報を入れても安全

✓ 通常の JWT は署名されているだけで、中身は誰でも読める。改ざんは検出できるが、隠せはしない。

✗ パスワードは SHA-256 でハッシュ化すれば安全

✓ 速いハッシュは総当たりに弱い。Argon2id / bcrypt / scrypt を使う。

✗ HTTPS（鍵マークなど）で接続できるサイトは安全なサイト

✓ 保証されるのは「そのドメインと暗号化された通信をしている」ことだけ。フィッシングサイトも普通に証明書を取れる。Chrome はこの誤解を避けるため、117 から鍵アイコンの表示をやめている。

✗ 公開鍵暗号でデータ本体を暗号化している

✓ 本体は共通鍵暗号。公開鍵の仕組みは、その鍵を共有する（鍵交換）・相手を確かめる（署名）ために使う。
