**ざっくり言うと**

- プログラムが使うアドレスは **仮想アドレス** 。CPU の MMU が、OS の作った **ページテーブル** を見て、ページ（ふつう 4KiB）単位で実際の物理メモリの位置に変換する。
- おかげで各プロセスは自分専用のメモリ空間を持ち、他のプロセスのメモリは見えない。物理メモリは **実際に触ったページにだけ** 割り当てられる。
- `fork` が速いのも、共有ライブラリが 1 つで済むのも、 `top` の VIRT が巨大でも平気なのも、このしくみのおかげ。

## なぜ仮想にするのか

ISOLATION

プロセスごとに別のページテーブルを持つので、同じアドレス `0x4000` でも指す先が違う。他のプロセスのメモリを壊せない。

ON DEMAND

確保しただけのメモリには物理メモリを割り当てず、初めて触ったときに割り当てる。使っていない部分はディスクに追い出せる。

SHARING

共有ライブラリやファイルの中身は、複数のプロセスのページテーブルから同じ物理ページを指して共有できる。

PROTECTION

ページごとに読み・書き・実行の許可を持つ。コードは書き込み禁止、データは実行禁止にして、攻撃を防ぐ。

## 多段のページテーブルと TLB

64 ビットの CPU でページテーブルを 1 枚の表にすると巨大になる。x86-64 では仮想アドレスの 48 ビット（新しい CPU では 57 ビットの 5 段もある）を 9 ビットずつに分けた **4 段の木** にして、使っている部分の表だけを作る。

- 毎回 4 段をたどると遅いので、CPU は最近の変換結果を **TLB (Translation Lookaside Buffer)** にキャッシュする。TLB に当たれば変換はほぼタダ。
- TLB の項目は数千程度しかない。巨大な配列をランダムに読むと TLB ミスが続き、CPU キャッシュのミスと合わせて遅くなる。
- **huge page** （x86-64 なら 2MiB や 1GiB）を使うと、1 項目で覆える範囲が 512 倍以上になり、TLB ミスが減る。大きなメモリを使う DB や JVM で使われる。Linux の **THP（Transparent Huge Pages）** は自動で使うが、遅延の揺れの原因になることもあり、Redis などは無効にするよう勧めている。
- プロセスを切り替えるとページテーブルが替わるので、TLB の中身の多くが使えなくなる。コンテキストスイッチのコストの一部（ [OS のスケジューリング](https://memo.taka1156.site/md/os-scheduling.md) ）。

## ページフォルト

MMU が変換できない（ページテーブルに「存在する」印がない、許可がない）と、CPU は **ページフォルト** を起こしてカーネルに処理を渡す。カーネルは理由を調べて 3 通りに分ける。

MINOR

**ディスクを読まずに済む。** 確保済みで初めて触ったページに空きの物理ページを割り当てる、ページキャッシュにもうあるファイルの中身を指す、など。マイクロ秒以下。

MAJOR

**ディスクから読み込む。** スワップに追い出したページ、まだ読んでいないファイルを mmap した部分など。SSD でも数十〜数百マイクロ秒、HDD ならミリ秒単位かかる。メモリアクセスの数百倍以上遅いので、多発すると極端に遅くなる。

INVALID

**そもそも使えないアドレス・許可のない操作。** NULL 参照、範囲外、読み取り専用への書き込み。カーネルはプロセスに `SIGSEGV` を送る（Segmentation fault）。

アドレス 0 付近をわざとどのページにも割り当てないのは、NULL ポインタを使ったバグをその場で落とすため。

## 確保と使用は別 — オーバーコミットと OOM killer

`malloc(1GB)` や `mmap` で確保しても、カーネルは「この範囲を使ってよい」と記録するだけで、物理メモリはまだ割り当てない。書き込んで初めてページ単位で割り当てる（ **デマンドページング** ）。

| 表示 | 意味 | 読み方 |
| --- | --- | --- |
| VIRT / VSZ | 確保した仮想アドレス空間の合計 | 予約しただけの領域やマップしたファイルも含む。巨大でも問題ないことが多い |
| RES / RSS | 今、物理メモリに載っているページ | 実際のメモリ使用の目安。共有ライブラリは各プロセスに重複して数えられる |
| SHR | RES のうち共有しうるページ | ライブラリやファイルの mmap、共有メモリ |

- Linux は既定（ `vm.overcommit_memory=0` ）で、確保の合計が物理メモリ＋スワップを超えることを許す（ **オーバーコミット** ）。明らかに大きすぎる 1 回の確保だけは拒否する。全員が確保した分を本当に使うことはまずない、という前提。
- 前提が外れて物理メモリが尽きると、カーネルの **OOM killer** がプロセスを選んで `SIGKILL` で殺す。多くの場合、 `malloc` が失敗するのではなく、ある時点で突然殺される。
- コンテナでは cgroup の `memory.max` （Kubernetes の `limits.memory` ）を超えると、そのコンテナの中で OOM kill が起きる。終了コード **137** （128 + SIGKILL の 9）、Kubernetes では `OOMKilled` と表示される。

## fork と copy-on-write

`fork` は親プロセスを丸ごと複製するが、メモリを実際にコピーはしない。親子のページテーブルを同じ物理ページに向け、両方を **読み取り専用** にしておく。

fork 直後

親と子が同じ物理ページを共有。2GB のプロセスでも、コピーするのはページテーブルだけなので速い。

どちらかが書いた

読み取り専用への書き込みでページフォルトが起き、カーネルがそのページ **だけ** をコピーして書いた側に割り当てる。

- シェルがコマンドを起動するとき（ `fork` → `exec` ）は、子がすぐ別のプログラムに置き換わるので、ほとんどコピーが起きない（ [Linux プロセスの仕組み](https://memo.taka1156.site/md/linux-process.md) ）。
- Redis の `BGSAVE` は fork した子にスナップショットを書かせる。書き込みが多いと親がページを書き換えるたびにコピーが起き、メモリ使用量が最大で 2 倍近くまで増えうる（ [Redis と Valkey](https://memo.taka1156.site/md/redis-valkey.md) ）。

## mmap — ファイルをメモリとして扱う

- `mmap` でファイルをアドレス空間に貼り付けると、読んだ部分だけがページフォルト経由でページキャッシュから読み込まれる。 `read()` でバッファにコピーする手間がない。
- 実行ファイルや共有ライブラリの読み込みもこの仕組み。同じライブラリは全プロセスで同じ物理ページ（ページキャッシュ）を共有する。
- Linux は空いている物理メモリをファイルのキャッシュ（ページキャッシュ）に使う。 `free` の `free` 列が小さくても、 `available` 列が十分なら困っていない。
- メモリが足りなくなると、カーネルはあまり使われていないページを追い出す。ファイルの内容は捨てて後で読み直し、ヒープなどの匿名ページは **スワップ** に書き出す。スワップの出し入れ（ `vmstat` の `si` / `so` ）が続くなら、メモリが足りていない。

### コマンド例

```
getconf PAGESIZE                 # ページの大きさ（多くは 4096。Apple Silicon の macOS は 16KiB）
free -h                          # available が実際に使える量の目安
grep -E 'VmRSS|VmSize' /proc/1234/status
cat /proc/1234/maps              # アドレス空間の配置（コード・ヒープ・ライブラリ・スタック）
pmap -x 1234                     # マッピングごとの RSS
vmstat 1                         # si / so = スワップの出し入れ
perf stat -e page-faults,major-faults ./app
cat /sys/kernel/mm/transparent_hugepage/enabled
```

## よくある誤解

top の VIRT が 20GB なので、このプロセスは 20GB 使っている

VIRT は予約したアドレス空間。実際に物理メモリに載っているのは RES。JVM や Go、ブラウザは大きく予約するのが普通。

malloc が NULL を返さなければ、そのメモリは確保できている

Linux の既定では、物理メモリは触ったときに割り当てる。足りなければ、その時点で OOM killer に殺されうる。

free の free 列が少ないのはメモリ不足

空きはページキャッシュに使われ、必要になれば手放される。見るのは available とスワップの出し入れ。
