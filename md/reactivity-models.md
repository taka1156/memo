仮想 DOM / シグナル / コンパイラ — 「状態が変わったら、どこを書き換えるか」の解き方

**ざっくり言うと**

- UI フレームワークの仕事は、 **状態が変わったときに、画面のどこを書き換えればいいかを突き止めること**
- **仮想 DOM** は「全部作り直して差分を取る」、 **シグナル** は「どの表示がどの値に依存しているかを記録しておく」、 **コンパイラ** は「ビルド時に更新コードを書き出しておく」
- 3つは排他ではなく組み合わさる。Solid はシグナル＋コンパイラ、Vue は仮想 DOM ＋リアクティブ、Svelte 5 はコンパイラ＋シグナル

最終的に書き換わる DOM は **どれもテキスト1つ** で同じ。違うのは、そこに **たどり着くまでの仕事量** 。仮想 DOM は「作り直して比べる」分の計算をし、シグナルは記録済みの依存関係をたどるだけで済む。

## 方式1：仮想 DOM

状態が変わると、コンポーネント関数を実行して「画面がこうあるべき」という **軽い JS オブジェクトの木（仮想 DOM）** を作り直す。前回の木と比べ（diff）、違う部分だけを本物の DOM に反映する（patch）。

div

h1 "Todo"

p

"count: 0"

ul（3件）

比較 →

div

h1 "Todo"

p

"count: 1"

ul（3件）

**強み** ：コンポーネントは「状態を受け取って UI を返す普通の関数」として書ける。いつ・何回実行されても結果が同じになるように書けば、更新の仕組みを意識しなくていい。

**弱み** ：変化と関係ない部分も毎回作り直して比べる。大きな木では無駄が増えるので、 `memo` などで「ここは再実行しなくていい」と教える必要があった（React Compiler はそれを自動化する）。

## 方式2：シグナル（細粒度リアクティブ）

値を **シグナル** という入れ物に入れる。シグナルを **読んだ** 処理を自動で記録しておき、シグナルに **書いた** ときには、記録された処理だけを再実行する。

count signal → doubled computed → 表示更新 effect

仕組みは意外と小さい。核心部分だけ書くとこうなる。

```
let current = null;                  // いま実行中の effect

function signal(value) {
  const subs = new Set();            // この値を読んだ effect の一覧
  return {
    get() {
      if (current) subs.add(current); // 読まれたら「購読者」として記録
      return value;
    },
    set(v) {
      value = v;
      subs.forEach(fn => fn());       // 書かれたら購読者だけ再実行
    },
  };
}

function effect(fn) {
  const run = () => { current = run; fn(); current = null; };
  run();
}

// 使い方
const count = signal(0);
effect(() => { textNode.data = count.get(); }); // このテキストだけが count に依存
count.set(1);                                   // → このテキストだけ書き換わる
```

**強み** ：変化した値に依存する場所だけが動く。コンポーネント全体の再実行も、差分計算もない。

**弱み** ：「読んだ瞬間に記録する」仕組みなので、 **値を変数に取り出してしまうと追跡が切れる** といった独特のルールがある（Solid の props の分割代入など）。

## 方式3：コンパイラ

テンプレートや JSX をビルド時に解析し、「この値が変わったらこの DOM ノードをこう書き換える」という **専用コードを生成** する。実行時に汎用の差分アルゴリズムを持たなくていい。

書くコード

```
<p>count: {count}</p>
```

生成されるコード（イメージ）

```
const p = template('<p>count: </p>');
const text = p.firstChild.nextSibling;
effect(() => { text.data = count(); });
```

コンパイラは単独の方式というより、 **シグナルと組み合わせて** 「どのノードに effect を張るか」を事前に決める役で使われることが多い。React Compiler は少し違い、 **再実行モデルはそのまま** で、メモ化を自動挿入して無駄な再実行を減らす。

「変化をどう見つけるか」と「DOM の書き換え方をどう決めるか」の2軸で並べる。

（直接 DOM 操作）

この組み合わせは少ない

Vue コンポーネント単位で追跡し、その中は仮想 DOM。コンパイラが差分を絞り込む

Solid Svelte 5 Vue Vapor 仮想 DOM なし。シグナルから DOM ノードへ直結

Vue 3.6 の Vapor Mode（2026年7月から RC）はコンポーネント単位で選べる新モードで、Vue を右下の枠にも置けるようにする。Svelte も 4 までは「代入文をコンパイラが検知する」独自方式だったが、5 の runes でシグナルに移った。

## 比較表

| 観点 | 仮想 DOM | シグナル | コンパイラ |
| --- | --- | --- | --- |
| 更新の単位 | コンポーネント（とその子孫） | 値に依存する式・DOM ノード | 生成コードの単位（多くはノード） |
| コンポーネント関数の実行 | 状態が変わるたび | 最初の1回だけ（Solid など） | 方式による |
| 実行時のコスト | 木の再生成と差分計算 | 依存グラフの管理 | 小さい（仕事をビルド時に前倒し） |
| メンタルモデル | 単純：UI ＝ 状態の関数 | 独自ルールあり（追跡が切れる書き方） | 書き方は自然だが、裏で何が起きるかは見えにくい |
| ビルドの必要性 | JSX を使うなら必要 | ライブラリ単体でも動く | 必須 |

## よくある誤解

✗ 誤解: 仮想 DOM は本物の DOM より速い

✓ 正しくは: 仮想 DOM は最終的に本物の DOM 操作を行うので、それ自体が速さを生むわけではない。価値は「宣言的に書いても、まあまあ速い」こと。最適な手書きの DOM 操作より速くはならない。

✗ 誤解: シグナルは新しい発明

✓ 正しくは: Knockout.js（2010年）や MobX など、昔からある考え方。Solid が JSX と組み合わせて再注目させ、今は Angular、Vue、Svelte、Preact も取り入れている。JavaScript の標準に入れる提案（TC39 Signals）も出ている。

✗ 誤解: 仮想 DOM は時代遅れで遅い

✓ 正しくは: 多くのアプリでは差分計算はボトルネックにならない。React Native のように DOM 以外に描画する場合は、中間表現があることが強みにもなる。
