作業をチケットにしてコードの変更と結びつけ、その流れをボードと WIP 制限で整える

**ざっくり言うと**

- チケット駆動開発は、作業を必ずチケットにしてからコミットし、変更の理由をチケットからたどれるようにする運用。
- カンバンは、チケットの流れをボードで見えるようにし、工程ごとに同時に抱える数（WIP）を制限して詰まりを減らす方法。
- 手を広げるほど 1 件が終わるまでの時間は延びるので、新しく始めるより進行中を終わらせることを優先する。

## 2 つの関係

チケット駆動開発とカンバンは別々に生まれた考え方ですが、組み合わせて使うことが多いです。チケットが「作業の単位」、ボードが「その流れを見る場所」、コミットや PR が「作業の結果」で、この 3 つが互いにリンクでつながります。

**チケット (Issue)**

何を・なぜ・どうなったら完了か。作業 1 件の記録と議論の置き場

**カンバンボード**

チケットを工程の列に並べ、どこで止まっているか・抱えすぎていないかを見る

**コミット・PR**

チケット番号を書いて結びつける。マージでチケットを閉じる

GitHub なら Issues ＋ Projects（ボード表示）＋ PR、ほかに Redmine・Jira・Backlog など、どの課題管理ツールでも同じ形で組める。

## チケット駆動開発（TiDD）

チケット駆動開発 (Ticket-Driven Development, TiDD) は、2007 年ごろ日本で Trac と Subversion を使う現場から生まれ、のちに Redmine でも広まった運用です。中心にあるのは次の 2 つのルールです。

| ルール | 中身 | 得られるもの |
| --- | --- | --- |
| No Ticket, No Commit | チケットを参照しないコミットはしない。コミットメッセージにチケット番号を書く | どの行がなぜ変わったかを、コミットからチケットへ、チケットから変更へと両方向にたどれる（トレーサビリティ、traceability） |
| No Ticket, No Work | 作業を始める前にチケットを作る。頼まれごとも口頭で済ませずチケットにする | 誰が何をしているかが全員に見え、「やったのに記録がない作業」が消える |

チケットは仕様書ではなく **作業指示書** です。長い仕様や設計は別の文書に書き、チケットからリンクします。チケットに書くのは、その作業 1 件を終わらせるのに要ることだけです。

### チケットに書くこと

#128 パスワード再設定メールのリンクを 30 分で失効させる

背景・目的

今はリンクが無期限で使える。メールが漏れると誰でも再設定できてしまう

完了条件

- 発行から 30 分を過ぎたリンクは「期限切れ」画面になる
- 一度使ったリンクは再利用できない
- テストを追加し CI が通る

担当

1 人（複数で分けるならチケットを分ける）

関連

設計メモへのリンク、関連チケット `#97`

**完了条件** （受け入れ条件）があると、「終わった」の判断が人によってぶれず、レビューする人も何を確かめればよいか分かります。大きさは、1 人が数日以内に終えられる程度を目安にします。それより大きいものは、親チケットの下に子チケットとして分けます。

| ありがちなチケット | 困ること | 直し方 |
| --- | --- | --- |
| 「ログイン周りの改善」 | 範囲がなく、いつまでも閉じられない | 何がどうなれば完了かを条件で書く。複数あれば分ける |
| 「バグ」とだけ書いた報告 | 再現できず、担当者が聞き直しに行く | 再現手順・期待した結果・実際の結果・環境を書く |
| 担当者が 3 人いる | 誰も自分の仕事だと思わない | 担当は 1 人。手伝う人はコメントやレビュアーで関わる |
| 2 週間たっても「進行中」 | 詰まっているのか進んでいるのか分からない | 小さく分けて、1 つずつ閉じる |

### コミット・PR との結びつけ

ツールごとに、メッセージ中のキーワードとチケット番号を読み取って自動でリンク（や状態の変更）をする仕組みがあります。

GitHub

Redmine

Jira

```
# コミットや PR 本文に #番号 を書くと、Issue 側にリンクが出る
git commit -m "再設定リンクに有効期限を追加 (#128)"

# PR の本文にクローズ用のキーワードを書く
Closes #128
```

クローズ用のキーワードは `close` ・ `fix` ・ `resolve` とその活用形（ `closes` ・ `fixed` など）。PR 本文に書いた場合、 **PR の向き先がリポジトリの既定ブランチ（default branch）のときだけ** 働き、マージで Issue が自動で閉じます。別のブランチ向けの PR では無視されます。コミットメッセージに書いても、そのコミットが既定ブランチに入った時点で閉じます。

```
# 参照用キーワード: チケットにリビジョンが関連付く
git commit -m "再設定リンクに有効期限を追加 refs #128"

# 修正用キーワード: 管理画面で登録しておけばステータスも変わる
git commit -m "期限切れ画面を追加 fixes #128"
```

既定では参照用が `refs` ・ `references` ・ `IssueID` で、修正用キーワードは空。 `fixes` ・ `closes` などの修正用キーワードと、そのとき変えるステータスは管理画面（設定 → リポジトリ）で自分で登録する。登録していないと `fixes #128` はキーワードとして認識されず、関連付けもされない（参照用キーワードに `*` を入れていれば、番号だけで関連付く）。リポジトリとの同期後にリンクされるので、共有リポジトリへの push が先に要る。

```
# 作業項目キー（旧称は課題キー。例: AUTH-128）をメッセージやブランチ名に入れる
git commit -m "AUTH-128 再設定リンクに有効期限を追加"

# スマートコミット: コメント・作業時間・トランジションを同時に記録
git commit -m "AUTH-128 #comment 期限切れ画面を追加 #time 1h #resolve"
```

作業項目キーがあれば、開発ツール連携で作業項目の「開発」欄にコミットやブランチが並ぶ（Jira Cloud は「課題」を「作業項目」、「プロジェクト」を「スペース」に改称した）。スマートコミットは、コミットした人のメールアドレスが Jira のユーザーと一致し、その操作の権限があるときに働く。

### 1 枚のチケットの流れ

1. **起票する** 背景・完了条件を書き、優先度順に並んだ「やること」の列に置く
2. **引いて着手する** 手が空いた人が上から取り、担当を自分にして「進行中」へ動かす。ブランチ名にも番号を入れる（例: `feature/128-reset-expiry` ）
3. **番号付きでコミットする** どのコミットも `#128` を参照する。途中の判断や詰まった点はチケットのコメントに残す
4. **PR を出してレビューへ** PR 本文に `Closes #128` 。カードを「レビュー」へ。CI とレビューが完了条件を満たしているかを確かめる
5. **マージで閉じる** 既定ブランチへのマージでチケットが自動で閉じ、ボードの「完了」へ移る

PR とチケットを 1 対 1 にしておくと、レビューの範囲と完了条件が一致し、差し戻しや取り消し（revert）もチケット単位でできる。

## カンバン

カンバンの名前はトヨタ生産方式の「かんばん」（後工程が使った分だけ前工程に作らせる札）から来ています。ソフトウェア開発のカンバンは、これを知識労働向けに考え直したものです。Kanban Guide では、次の 3 つの実践を合わせたものをカンバンとしています。

- **ワークフローを定義して見えるようにする** : 列（工程）と、「どこから着手・どこで完了とみなすか」などのルールを決めてボードに表す
- **ワークフロー内の項目を主体的に管理する** : WIP を制限し、止まっているアイテムや古くなったアイテムに手を打つ
- **ワークフローを改善する** : 指標を見て列やルールを変え続ける

### WIP 制限があるとき・ないとき

WIP (Work In Progress) は、着手したがまだ終わっていないアイテムの数です。列ごとに上限を決め、上限に達した列には新しく入れません。同じチームの同じ時点のボードで比べます。

進行中は 3 件まで、レビューは 2 件まで。レビューが上限に達した（赤い枠）ので、実装を終えた #127 はレビューへ動かせず、進行中の枠も埋まったままです。手が空いた人は「やること」から新しく引けないので、先にレビューを片付けに行きます。止まっている #131 も件数が少ないので目に入り、朝会で「誰が先方に催促するか」を決められます。

レビュー待ちで滞留 外部の理由で止まっている（ブロック） WIP 上限に達した列

WIP 制限は、 **押し込み (push) から引き取り (pull) への切り替え** です。前の工程が終わった分を次に押し込むのではなく、次の工程に空きができたときだけ引き取ります。上限に当たるとそこで流れが止まるので、詰まっている場所がすぐ分かり、「新しく始める前に、いま進んでいるものを終わらせる (Stop starting, start finishing)」という動き方になります。

### ボードを作るときに決めること

| 決めること | よくある決め方 | なぜ |
| --- | --- | --- |
| 列 | 実際の作業の順に並べる（例: やること → 進行中 → レビュー → 完了）。「待ち」が長い所は「レビュー待ち」のように列を分ける | 理想の工程ではなく実際の流れを映さないと、どこで止まっているかが見えない |
| 着手点と完了点 | 「進行中に動かした時点で開始」「本番に出た時点で完了」などを書いておく | 指標（サイクルタイムなど）の測り始めと測り終わりが人によってずれない |
| 列ごとの完了の定義 | 「レビューへ動かすのは CI が通ってから」など、次の列に移す条件 | 中途半端な状態で次へ流れ、後で戻ってくるのを防ぐ |
| WIP の上限 | まず今の実績より少し少なめに置き、詰まり方を見て調整する | 上限は正解の数ではなく、詰まりを表に出すための道具。きつすぎると全員が待ち、ゆるすぎると効かない |
| ブロックの扱い | 止まったカードに印を付け、理由と次の手をコメントに書く | 止まっているものが進行中に紛れると、WIP の枠だけを食い続ける |
| 例外の扱い | 本番障害など、上限を超えてでも先にやるものを決めておく（急ぎ用の 1 枠など） | 例外をその場の判断にすると、なんでも「急ぎ」になって上限が意味を失う |

## 流れの指標

Kanban Guide は、最低限見る指標として次の 4 つを挙げています。どれもチケットの「着手日」と「完了日」を記録しておけば計算できます。

| 指標 | 意味 | 何に使うか |
| --- | --- | --- |
| WIP | 着手したが終わっていないアイテムの数 | 抱えすぎていないかを見る。下の 3 つすべてに効く |
| スループット (throughput) | 単位時間あたりに完了したアイテムの数（例: 週 6 件） | 「この先 4 週間で何件くらい終わるか」の見積もり |
| サイクルタイム (cycle time) | 1 件の着手から完了までにかかった時間（終わったアイテムについて測る） | 「着手したら何日くらいで終わるか」の目安。平均より「85% は 6 日以内」のような分布で見る |
| ワークアイテムエイジ (work item age) | まだ終わっていないアイテムの、着手から今までの時間 | 今まさに遅れかけているカードを見つける。普段のサイクルタイムを超えそうなものから手を打つ |

リードタイム (lead time) は、ふつう依頼を受けた（起票した）時点から完了までを指し、着手前に待っていた時間も含む。どこからどこまでを測るかはチームによって違うので、ボードの着手点・完了点として書いておく。

### リトルの法則で見る WIP とサイクルタイム

流れが安定している（入ってくる量と出ていく量が長い目で釣り合っている）とき、平均どうしの間に次の関係が成り立ちます。

```
平均サイクルタイム ＝ 平均 WIP ÷ 平均スループット
```

スループットはチームの人数や力量でほぼ決まり、すぐには増えません。そこで WIP だけを増やすと、その分だけ 1 件が終わるまでの時間が延びます。スライダーで確かめてください。

平均 WIP（同時に進める件数） 6 件 平均スループット（1 週間に終わる件数） 3 件

平均サイクルタイムは **2.0 週間** （約 10 営業日）

例: 週 3 件終わるチームで WIP を 6 件から 3 件に減らすと、平均サイクルタイムは 2 週間から 1 週間に縮む。終わる件数は同じでも、1 件ごとの結果が早く届く。

リトルの法則は長い期間の平均についての関係で、個々のアイテムの完了日を予測する式ではない。急に人が抜けたなどで流れが安定していない期間には当てはまらない。

## スクラムとの違い

どちらもチケット（バックログのアイテム）をボードで動かすので見た目は似ていますが、何で流れを区切るかが違います。スクラムのチームがカンバンの WIP 制限や指標を取り入れることもよくあります。

|  | カンバン | スクラム |
| --- | --- | --- |
| 区切り | 決まった期間はなく、アイテムが 1 件ずつ流れる | スプリント（1 か月以内の固定期間）ごとに計画してから進める |
| 量を絞る方法 | 列ごとの WIP 上限 | スプリントに入れるアイテムの量（スプリントバックログ） |
| 途中の差し込み | 上限の空きがあればいつでも優先度順に入れられる | スプリントゴールを危うくする変更はしない。計画はスプリントの単位で見直す |
| 役割 | 決まった役割はない。今のやり方から始めて少しずつ変える | プロダクトオーナー・スクラムマスター・開発者 |
| 見る数字 | WIP・スループット・サイクルタイム・ワークアイテムエイジ | スプリントゴールの達成。ベロシティを見るチームも多い |
| 向いている仕事 | 問い合わせ対応・運用・保守など、差し込みが多く量の読めない仕事 | まとまった機能を、定期的に見直しながら作る仕事 |

## よくある誤解

✗ 誤解: ボードを作ってカードを並べれば、カンバンを始めたことになる

✓ 正しくは: 列を並べただけでは、見える化されたタスク一覧です。WIP の上限、列を移す条件、止まったカードへの手の打ち方といったルールを決めて流れを管理し、指標を見て直していくところまでがカンバンです。

✗ 誤解: 同時にたくさん着手したほうが、全体の作業は早く進む

✓ 正しくは: スループットが変わらないまま WIP を増やすと、リトルの法則のとおり 1 件あたりの時間が延びます。切り替えの手間や待ち時間も増えるので、実際にはスループットまで下がることが多いです。

✗ 誤解: WIP の上限に達したら、空いた人はやることがなくて待つしかない

✓ 正しくは: 空いた人は、上限に詰まっている列の作業（レビュー・テスト・止まっているカードの解決）を手伝いに行きます。新しく始めずに終わらせる側に回るのが、上限を置く狙いです。

✗ 誤解: PR の本文に Closes #12 と書けば、どのブランチにマージしても Issue が閉じる

✓ 正しくは: GitHub がクローズ用のキーワードを読むのは、PR の向き先が既定ブランチのときだけです。 `develop` などへ向けた PR ではリンクも作られず、マージしても閉じません。既定ブランチに入るときに閉じたいなら、そのときの PR に書きます。

✗ 誤解: チケットは仕様が全部分かるように細かく書くほどよい

✓ 正しくは: チケットは作業指示書で、1 件の作業を終えるのに要る背景と完了条件があれば足ります。長い仕様や設計は別の文書に置いてリンクし、チケットは作業中の判断や経過を残す場所にします。
