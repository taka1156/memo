「1 文字」は何バイト？ 何文字？ —— 番号（コードポイント）と、そのバイト列（UTF-8 / UTF-16）を分けて考える

**ざっくり言うと**

- Unicode は文字に **番号（コードポイント、U+3042 など）** を振る表。それを **バイト列にする方法** が UTF-8・UTF-16。「Unicode で保存」ではなく「UTF-8 で保存」が正しい言い方。
- 「1 文字」には数え方が 4 つある： **バイト数・UTF-16 の単位数（JS の `length` ）・コードポイント数・見た目の文字数（書記素クラスタ）** 。絵文字や濁点でずれる。
- 同じ見た目でも内部が違うことがある（「が」が 1 個か「か＋゛」の 2 個か）。比較・検索の前に **正規化** （NFC / NFKC）する。

## 番号と符号化を分ける

文字「あ」 → Unicode の表で U+3042 → UTF-8 で E3 81 82 ／ UTF-16 で 30 42

| 符号化 | 1 文字の長さ | 主な使われ方 |
| --- | --- | --- |
| UTF-8 | 1〜4 バイト（ASCII は 1、日本語の多くは 3、絵文字の多くは 4） | Web・ファイル・DB・API の標準。ASCII とそのまま互換 |
| UTF-16 | 2 か 4 バイト（2 バイト単位 1 つか 2 つ） | JavaScript・Java・C#・Windows の文字列の単位（Java 9 以降は内部で Latin-1 も使うが、 `length()` などは UTF-16 単位） |
| UTF-32 | 常に 4 バイト | 内部処理用。容量が大きく保存にはあまり使わない |
| Shift_JIS / EUC-JP | 1〜2 バイト（EUC-JP は補助漢字で 3 バイト） | Unicode 以前の日本語用。古いシステム・CSV で今も出会う |

### UTF-8 のしくみ

先頭バイトの上位ビットで「何バイトの文字か」がわかり、2 バイト目以降は必ず 10 で始まるので、途中から読んでも文字の切れ目を見つけられます。

| 範囲 | バイト列（x にコードポイントのビットが入る） |
| --- | --- |
| U+0000–007F | 0 xxxxxxx |
| U+0080–07FF | 110 xxxxx 10 xxxxxx |
| U+0800–FFFF | 1110 xxxx 10 xxxxxx 10 xxxxxx |
| U+10000–10FFFF | 11110 xxx 10 xxxxxx 10 xxxxxx 10 xxxxxx |

| ずれる原因 | 例 | 説明 |
| --- | --- | --- |
| サロゲートペア | 𠮷・絵文字 | U+FFFF を超える文字は UTF-16 で 2 単位になる。JS の `length` は 2 |
| 結合文字 | か＋゛（U+3099） | 前の文字にくっつく記号。2 コードポイントで見た目は 1 文字 |
| ZWJ シーケンス | 👨‍👩‍👧 | 複数の絵文字をゼロ幅接合子 (U+200D) でつないで 1 つの絵にする |
| 修飾子 | 👍🏽 | 肌の色を表す修飾子が後ろに付く |
| 国旗 | 🇯🇵 | リージョナルインジケーター（Regional Indicator Symbol）2 つ（J と P）の組み合わせ |

```
// 見た目の文字数を数える・切り出すなら Intl.Segmenter
const seg = new Intl.Segmenter('ja', { granularity: 'grapheme' });
const chars = [...seg.segment('👨‍👩‍👧です')].map(s => s.segment);  // ['👨‍👩‍👧','で','す']
// s.slice(0, 1) だと絵文字が途中で切れて壊れた文字（�）になる
```

## 正規化

Unicode には同じ見た目を表す方法が複数あります。比較・検索・重複チェックの前に、どちらかの形に揃えます。

| 形式 | やること | 例 | 使う場面 |
| --- | --- | --- | --- |
| NFC | 合成できるものは合成 | か＋゛ → が | 保存・比較の標準。Web はこれ |
| NFD | 分解できるものは分解 | が → か＋゛ | macOS 由来のファイル名で見かける |
| NFKC | 互換文字も統一して合成 | ｶﾞ → ガ、ＡＢＣ → ABC、① → 1、㈱ → (株) | 検索キー・ユーザー名の重複判定 |
| NFKD | 互換文字も統一して分解 |  | あまり使わない |

```
'が' === 'が'                        // false（見た目は同じ）
'が'.normalize('NFC') === 'が'       // true
'ﾃｽﾄＡ１'.normalize('NFKC')                // 'テストA1'
```

NFKC は情報を落とす（① と 1 の区別が消える）。元の文字列は NFC で保存し、 **検索用の列にだけ NFKC＋小文字化** した値を持つ、と分けるのが安全。

## 実務の落とし穴

文字数制限

なりすまし

**書いた側と読む側で符号化が違う** と起きます。UTF-8 の「日本語」を Shift_JIS として読むと「譌･譛ｬ隱・」のようになる。

- HTTP は `Content-Type: text/html; charset=utf-8` 、HTML は `<meta charset="UTF-8">` を先頭近くに
- Excel 向けの CSV は、UTF-8 の BOM（先頭の `EF BB BF` ）を付けないと Shift_JIS と判定されて化けることがある
- 逆に、BOM 付きのファイルを読むと先頭に見えない文字が残り、最初の列名が一致しないことがある

MySQL の `utf8` （別名 `utf8mb3` ）は **1 文字 3 バイトまで** しか扱えず、絵文字や 𠮷 が保存できない（エラーや欠落）。必ず `utf8mb4` を使う。

`VARCHAR(255)` の 255 が「文字数」か「バイト数」かは DB によって違う。PostgreSQL・MySQL は文字数（コードポイント数）、Oracle の既定はバイト数。

「20 文字まで」の制限をどの数え方で判定するかを決める。JS の `length` で数えると、絵文字 1 つが 2 文字分以上（組み合わせた絵文字では 10 文字分を超えることもある）に数えられてしまう。

- ユーザーに見せる上限 → 書記素クラスタで数える
- DB・API の上限 → バイト数や DB の数え方に合わせて、サーバー側でも検証する
- 途中で切るときは書記素の切れ目で切る（サロゲートペアの片方だけ残すと壊れる）

見た目が同じ別の文字（ホモグリフ）で偽装できる。キリル文字の「а」（U+0430）とラテン文字の「a」は見分けがつかない。

- ドメイン名ではブラウザが混在を検知して `xn--` で始まる Punycode 表示に切り替えることがある
- ユーザー名は NFKC で正規化したうえで、使える文字の種類を絞る
- 大文字小文字の変換は言語によって違う（トルコ語の i / İ）。ID の比較には言語に依存しない変換を使う

## よくある誤解

✗ 誤解: Unicode は 1 文字 2 バイト

✓ 正しくは: それは UTF-16 の、しかも U+FFFF までの文字の話。Unicode 自体は番号の表で、バイト数は符号化で決まる。UTF-8 なら 1〜4 バイト。

✗ 誤解: JS の length で文字数が数えられる

✓ 正しくは: `length` は UTF-16 の単位数。絵文字や 𠮷 で増える。見た目の文字数は `Intl.Segmenter` で数える。

✗ 誤解: 同じに見える文字列は === で一致する

✓ 正しくは: 合成済みか結合文字か、全角か半角かで別の文字列になる。比較前に正規化する。
