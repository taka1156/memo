**ざっくり言うと**

- RAG は「質問に関係する資料を検索して、プロンプトに入れてから答えさせる」しくみ。 **正しい資料を拾えなければ、どんなに賢いモデルでも正しく答えられない** 。
- ベクトル検索は意味の近さに強く、 **型番・エラーコード・固有名詞の完全一致に弱い** 。キーワード検索と組み合わせる（ハイブリッド検索）のが定番。
- 大量のベクトルから速く探すために **近似最近傍検索（HNSW など）** を使う。速さと取りこぼしはトレードオフ。検索だけを取り出して評価する。

埋め込みと RAG の基本の流れは [LLM の仕組み：埋め込みと RAG](https://memo.taka1156.site/md/llm-basics.md) 。このページはその検索部分を掘り下げる。

## 全体の流れ

**1. 分割**

資料をチャンク（数百トークン程度）に分ける。

**2. 埋め込み**

各チャンクをベクトルに変換して、本文・出典・権限情報と一緒に保存。

**3. 検索**

質問も同じモデルでベクトルにし、近い上位 k 件を取る（＋キーワード検索）。

**4. 再ランキング**

候補を精度の高いモデルで並べ直し、上位だけ残す。

**5. 生成**

選んだチャンクをプロンプトに入れ、出典付きで答えさせる。

## 埋め込みと類似度

| 尺度 | 計算 | メモ |
| --- | --- | --- |
| コサイン類似度 | 2 つのベクトルの向きの近さ（−1〜1） | 最もよく使う。長さ（文章の長さの影響）を無視できる |
| 内積 (dot product) | 成分ごとの積の合計 | ベクトルを長さ 1 に正規化していればコサインと同じ順位になり、計算が軽い |
| ユークリッド距離 (L2) | 点と点の直線距離 | 正規化済みならコサインと順位は同じ |

- **資料と質問は同じ埋め込みモデルで** 変換する。別のモデルのベクトル同士は比べられない。
- モデルを変えたら **全チャンクを埋め込み直す** 。どのモデル・どのバージョンで作ったかを保存しておく。
- 次元数が大きいほど保存容量と検索コストが増える。モデルによっては次元を切り詰めて使える。

## チャンク分割

**大きすぎると**

関係ない話が混ざって類似度がぼやける。プロンプトにも余計な文章が入る。

**小さすぎると**

「それ」「この設定」が何を指すかわからない断片になり、答えに必要な文脈が欠ける。

- 文字数で機械的に切るより、 **見出し・段落・関数** などの構造の切れ目で切る
- 前後を少し重ねる（オーバーラップ）と、切れ目にまたがる情報を落としにくい
- チャンクの先頭に **文書名・見出しの階層** を付けてから埋め込むと、「料金」だけのチャンクでも「どの製品の料金か」が伝わる
- 表やコードは崩さずに 1 まとまりで扱う

## ハイブリッド検索

ベクトル検索とキーワード検索（BM25 など）は得意な質問が逆です。両方で検索して順位を合わせます。下で質問を切り替えて、 **緑** の正解がどこに来るかを見てください（スコアは説明用の例）。

「E-1043 が出る」

「パスワードを忘れた」

「解約したら返金される？」

（元のページで操作できます → https://memo.taka1156.site/rag-vector-search.html#hybrid）

### 順位の合わせ方：RRF

ベクトルの類似度と BM25 のスコアは単位が違うので、そのまま足せません。 **Reciprocal Rank Fusion** は順位だけを使います。

```
RRF(文書) = Σ  1 / (k + その検索での順位)     // k は 60 がよく使われる
// どちらかで 1 位なら大きく加点、両方で上位ならさらに上へ
```

## 再ランキング（リランキング）

埋め込みの検索は「質問」と「文書」を **別々に** ベクトルにして比べるので速い反面、細かい関係を見落とします。再ランキング用のモデル（リランカー。クロスエンコーダーなど）は質問と文書を **一緒に** 読んで関連度を出すので精度が高いが遅い。そこで次のように組み合わせます。

ハイブリッド検索で上位 50 件 → 再ランキングで並べ直す → 上位 5 件だけプロンプトへ

## 大量のベクトルから速く探す：近似最近傍検索

全件と距離を計算すれば正確ですが、数百万件になると質問のたびに重すぎます。 **多少取りこぼす代わりに速く探す** のが近似最近傍検索 (ANN) です。

**HNSW（グラフ）**

近いもの同士をつないだグラフを、質問（赤）に近づく方向へたどる。速くて精度も高く、今いちばん使われる。メモリを多く使う。

**IVF（クラスタ）**

事前にベクトルをいくつかのグループに分け、質問に近いグループの中だけを探す。境界近くの正解を取りこぼすことがある。

| 調整 | 上げると |
| --- | --- |
| HNSW の探索幅（ `ef_search` など） | 取りこぼしが減る（再現率↑）が遅くなる |
| IVF で調べるグループ数（ `nprobe` / `probes` ） | 同上 |
| 量子化（ベクトルを少ないビットに圧縮） | メモリが減るが精度が少し落ちる |

数万件程度なら全件計算でも十分速いことが多い。索引は件数が増えてから考えてよい。

## どこに保存するか

| 種類 | 例 | 向いている |
| --- | --- | --- |
| 既存 DB の拡張 | PostgreSQL ＋ pgvector（HNSW・IVFFlat） | 本文・権限・メタデータと同じ DB で JOIN・トランザクションしたいとき |
| 検索エンジン | Elasticsearch・OpenSearch | キーワード検索とベクトル検索を 1 つで（ハイブリッド） |
| ベクトル DB | Qdrant・Milvus・Weaviate・Pinecone など | 件数が非常に多い・ベクトル検索の機能を細かく使いたい |
| エッジ | Cloudflare Vectorize | Workers から使う（ [Cloudflare サービス](https://memo.taka1156.site/md/cloudflare-services.md) ） |

### メタデータと権限のフィルタ

社内文書の RAG では、 **質問した人が読めない文書を検索結果に入れない** ことが必須です。LLM に「この部分は見せないで」と頼んでも漏れます（ [認可モデル](https://memo.taka1156.site/md/authorization-models.md) ）。

**検索の前（中）で絞る**

「部署 = 営業 OR 公開」を検索条件に入れる。対応している DB なら、権限のある中から上位 k 件が返る。ただし pgvector の HNSW などは索引で探した後に条件で捨てるため、件数が k に届かないことがある（反復スキャンや `ef_search` の引き上げで補う）。

**検索の後で絞る**

上位 k 件を取ってから権限のないものを捨てる。全部捨てられて 0 件、になりやすい。漏れはしないが質が落ちる。

## 評価のしかた

「答えがいまいち」のとき、原因が **検索** か **生成** かを分けて調べます。

**1. 評価セット**

実際の質問と「答えが書いてあるチャンク」の組を数十〜数百件作る。

**2. 検索だけ測る**

正解のチャンクが上位 k 件に入った割合（Recall@k）を測る。

**3. 生成を測る**

正しいチャンクを渡したときに、それに沿って答えているか・書いていないことを足していないか。

**4. 変えて比べる**

チャンクの切り方・ハイブリッドの有無・再ランキングを 1 つずつ変えて数値で比べる。

### RAG を使わない選択肢

- 資料がコンテキストに収まる量なら、 **全部入れる** ほうが簡単で取りこぼしもない
- コードベースのように構造がはっきりしたものは、エージェントに `grep` やファイル読み込みのツールを渡して **自分で探させる** ほうがうまくいくことも多い

## よくある誤解

✗ 誤解: ベクトル検索はキーワード検索の上位互換

✓ 正しくは: 型番・エラーコード・人名など、文字が一致することが大事な検索はキーワード検索のほうが強い。組み合わせる。

✗ 誤解: 回答が間違っているのはモデルの性能が低いから

✓ 正しくは: 多くは検索で正しいチャンクを拾えていない。まず検索結果を見て、Recall を測る。

✗ 誤解: システムプロンプトで禁止すれば機密文書は漏れない

✓ 正しくは: プロンプトに入れた情報は出力されうる。読めない人には、そもそも検索でその文書を返さない。
