# PKI と証明書チェーン

証明書はどう発行され、どう信頼され、どう取り消されるか ── ACME・CT・短命化・社内 CA

**ざっくり言うと**

- PKI は「この公開鍵はこのドメインのもの」を、信頼ストアのルート CA から続く署名の連鎖で保証するしくみ。
- CA はドメインを持っていることを ACME のチャレンジで確かめて発行し、発行した証明書は公開ログ（CT）に必ず載る。
- 失効の確認は当てにしにくいので、期限を短くして自動更新する方向に進んでおり、2029 年には最長 47 日になる。

署名・公開鍵の意味と、ルート CA → 中間 CA → サーバー証明書という連鎖の形は [暗号の基礎](https://memo.taka1156.site/md/crypto-basics.md) にあります。このメモはその先の、 **証明書が発行されてから使われ、取り消されるまでの運用** を扱います。

## 登場人物

**サイト運営者** subscriber

鍵ペアを作り、CA に証明書を申請する。秘密鍵は自分のサーバーから出さない。

**認証局** CA (certificate authority)

申請者がそのドメインを本当に管理しているかを確かめ、証明書に署名する。

**信頼ストア** root store

OS やブラウザに入っているルート CA の一覧。Mozilla・Apple・Google・Microsoft がそれぞれ管理し、CA に厳しい基準を課す。

**CT ログ** Certificate Transparency

発行された証明書を誰でも見られる形で記録する公開ログ。誤発行を後から見つけられる。

**CA/Browser Forum** CA/B Forum

CA とブラウザの業界団体。有効期限の上限など、公開の証明書の決まり（Baseline Requirements）を決める。

## 証明書に書いてあること

Subject / SAN

example.com, www.example.com（ブラウザが照合するのは SAN（Subject Alternative Name）の一覧）

公開鍵

ECDSA P-256 または RSA 2048 ビットなど

Issuer

この証明書に署名した CA（中間 CA）の名前

有効期間

Not Before 〜 Not After

用途

Key Usage・Extended Key Usage（サーバー認証、クライアント認証など）

SCT

CT ログに載せた証拠（Signed Certificate Timestamp）

署名

上の内容全体に対する、発行した CA の署名

```
# サーバーが送ってくるチェーンと、証明書の中身を見る
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null
openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName
```

## 発行：ドメインを持っている証拠を見せる

1. **鍵ペアを作り、CSR を作る** CSR（証明書署名要求）は「この公開鍵とこの名前で証明書がほしい」を自分の秘密鍵で署名したもの。秘密鍵そのものは送らない。
2. **CA がチャレンジを出す** 「このドメインを管理しているなら、この値を決まった場所に置いてみせて」と頼む。
3. **値を置いて CA に確かめてもらう** CA が複数の地点からその場所を見に行き、値が合っていれば合格。
4. **CA が CT ログに登録し、署名した証明書を返す** サーバーは証明書と中間 CA の証明書（fullchain）を設定する。

この手順を機械で回すための約束が **ACME** （RFC 8555）です。Let's Encrypt が広めた方式で、certbot・lego・Caddy の自動 HTTPS などの ACME クライアントが、申請・チャレンジ・更新を全部自動で行います。

### 3 種類のチャレンジ

HTTP-01

DNS-01

TLS-ALPN-01

`http://example.com/.well-known/acme-challenge/<トークン>` にファイルを置き、CA が **ポート 80** で取りに来ます。いちばん手軽で、Web サーバーがある環境ならたいていこれです。

- ポート 80 を外から開けておく必要がある（HTTPS へのリダイレクトはあってよい）
- ワイルドカード証明書（ `*.example.com` ）は取れない
- LB の後ろに複数台あるときは、どの台に来ても同じファイルを返せるようにする

`_acme-challenge.example.com` に TXT レコードを置き、CA が DNS を引いて確かめます。サーバーに外から入れなくても使えます。

- **ワイルドカード証明書はこれでしか取れない**
- DNS を API で書き換える権限が ACME クライアントに要る。その API トークンが漏れると、ドメインの DNS を書き換えられてしまうので、権限を TXT レコードだけに絞れる DNS サービスを選ぶ
- 社内だけのサーバー（外から見えない）にも公開の証明書を取れる

CA が **ポート 443** に TLS でつなぎ、ALPN で `acme-tls/1` を指定したときだけ、特別な自己署名証明書を返すことで答えます。ポート 80 を開けられない環境向けです。

- TLS を終端するソフト自身が ACME に対応している必要がある（Caddy などは対応）
- 手前に CDN や TLS を解く LB があると使えない

| 確認の段階 | CA が確かめること | 今の使われ方 |
| --- | --- | --- |
| DV（ドメイン認証） | そのドメインを管理していること | ほとんどの証明書。ACME で自動発行できる |
| OV（組織認証） | ドメイン＋申請した組織が実在すること | 組織名が証明書に入るが、ブラウザの表示は DV と同じ |
| EV（拡張認証） | OV より厳しい書類審査 | かつてのアドレスバーの緑の組織名表示は主要ブラウザでなくなった |

## クライアントが確かめること

1. **チェーンをルートまでたどる** サーバー証明書の Issuer に当たる中間 CA の証明書で署名を検証し、それをさらに上へ。最後に、信頼ストアにあるルート CA に着けば合格。
2. **名前を照合する** アクセスした名前が SAN の一覧のどれかと一致するか。 `*.example.com` は `a.example.com` には合うが、 `example.com` や `a.b.example.com` には合わない。
3. **期限と用途を確かめる** 今が有効期間の中か、サーバー認証に使ってよい証明書か。
4. **CT に載っているかを確かめる** Chrome・Safari・Firefox（デスクトップ版、135 以降）は、SCT が付いていない公開の証明書を受け付けない。
5. **（できれば）失効していないかを確かめる** 下の「失効」のとおり、ここは確実ではない。

### よくあるエラーと原因

| 症状 | よくある原因 | 直し方 |
| --- | --- | --- |
| ブラウザでは平気、curl や古い Android で失敗 | 中間証明書を送っていない（ブラウザは手元のキャッシュや AIA で補っている） | サーバー証明書だけでなく `fullchain.pem` を設定する |
| 名前が一致しない | SAN に入っていない名前でアクセスした。 `www` の有無、ワイルドカードの階層 | 必要な名前を全部 SAN に入れて取り直す |
| 期限切れ | 自動更新が止まっていた（DNS の API トークン切れ、ポート 80 を閉じた） | 更新ジョブを直し、期限の監視を入れる |
| まだ有効でない・期限切れと出るが新しいはず | 端末の時計がずれている | NTP で時刻を合わせる |
| 信頼されていない発行者 | 自己署名、社内 CA のルートが端末に入っていない | 公開の CA で取る。社内なら社内ルートを配布する |

## 失効：取り消しは当てにしにくい

秘密鍵が漏れたら、期限前でも証明書を無効にしたい。その知らせ方は 3 つありましたが、どれも決め手になりませんでした。

| 方式 | しくみ | 問題 |
| --- | --- | --- |
| CRL | CA が失効した証明書の一覧を公開する | 一覧が大きくなる。ブラウザは自前で集めて圧縮した一覧を配る形に移った |
| OCSP | 接続のたびに CA に「この証明書は有効か」を問い合わせる | 遅い、CA に閲覧先が知られる。応答がないと多くのブラウザは素通しする（ソフトフェイル） |
| OCSP ステープリング | サーバーが OCSP の応答を取ってきて、TLS の中で一緒に渡す | サーバー側の対応がまちまちで広まりきらなかった |

Let's Encrypt は 2025 年に OCSP をやめ、証明書には CRL の URL だけを載せる形にしました。代わりに業界が選んだのが、 **期限そのものを短くする** ことです。漏れても数日〜数週間で使えなくなるなら、失効の知らせが届かなくても被害が限られます。Let's Encrypt は 6 日ほどで切れる短命証明書を選べるようにしていて、これには失効の情報（OCSP・CRL の URL）が入っていません。

## 有効期限の短縮

CA/Browser Forum は 2025 年 4 月に、公開の TLS 証明書の最長有効期間を段階的に縮める案（Ballot SC-081v3）を可決しました。

〜2026/3/14 398 日

2026/3/15〜 200 日

2027/3/15〜 100 日

2029/3/15〜 47 日

棒の長さは日数に比例。ドメインの確認結果を使い回せる期間も、2029 年には 10 日まで縮む。

年に 1 回の手作業の更新は成り立たなくなります。 **ACME での自動更新と、期限の監視** が前提です。更新は期限の 3 分の 1 ほどを残して始め、失敗したら通知が来るようにしておきます。ACME の ARI（ACME Renewal Information、RFC 9773）に対応したクライアントなら、CA が「そろそろ更新して」と勧める時期に合わせて更新できます。

## Certificate Transparency：誤発行を見つける

CA が誤って、あるいは乗っ取られて、他人のドメインの証明書を発行してしまうことがあります。CT は、発行された証明書をすべて追記しかできない公開ログに載せ、 **誰でも後から調べられる** ようにするしくみです。

- 自分のドメインの証明書を crt.sh などで検索し、心当たりのない発行がないかを監視できる。
- 逆に、証明書に入れた名前はすべて公開される。 `staging-secret.example.com` のような社内向けの名前も見える。名前を隠したいならワイルドカード証明書にする。
- DNS の CAA レコードで「このドメインはこの CA だけが発行してよい」と宣言しておくと、ほかの CA の誤発行を防げる（ [HTTP/1.1・2・3 と TLS・DNS](https://memo.taka1156.site/md/web-protocols.md) ）。

## 社内 CA と mTLS

社内のサービス同士の通信や、サーバーがクライアントを確かめたいときは、自分たちで CA を持つことがあります。

社内 CA

mTLS

- ルート CA の秘密鍵はオフラインで保管し、普段の発行は中間 CA で行う（公開の CA と同じ形）。
- ルートを端末やコンテナの信頼ストアに配る手間がかかる。配り漏れた端末では「信頼されていない発行者」になる。
- step-ca、HashiCorp Vault の PKI、クラウドのマネージドな私設 CA などを使えば、社内でも ACME や API で短命の証明書を自動発行できる。
- 公開のサイトには使わない。訪問者の端末に社内ルートは入っていない。

普通の TLS はクライアントがサーバーを確かめるだけですが、 **mTLS（相互 TLS）** ではサーバーもクライアントに証明書を求め、社内 CA の署名を確かめます。パスワードやトークンなしで「このサービスからの通信だ」と分かります。

- サービスメッシュ（Istio・Linkerd など）は、サービスごとの短命の証明書を自動で配り、サービス間を mTLS にする。
- LB や CDN で TLS を一度解く構成では、その先との間を別に mTLS にする（ [ロードバランサ・リバースプロキシ・CDN](https://memo.taka1156.site/md/lb-proxy-cdn.md) ）。

## よくある誤解

✗ 誤解: 証明書を失効させれば、その証明書はすぐ使えなくなる

✓ 正しくは: 失効を確かめないクライアントや、確認に失敗すると素通しするクライアントがある。Let's Encrypt も OCSP をやめた。漏れたときの被害を抑えるいちばん確かな手は、有効期限を短くしておくこと。

✗ 誤解: EV 証明書のほうが安全な通信になる

✓ 正しくは: 暗号の強さは DV と同じ。違うのは発行前の審査だけで、主要ブラウザは組織名の特別な表示もやめている。

✗ 誤解: ワイルドカード証明書はどの階層のサブドメインにも使える

✓ 正しくは: `*.example.com` が合うのは 1 階層だけ。 `example.com` 自身や `a.b.example.com` には合わないので、必要なら SAN に別に入れる。

✗ 誤解: 証明書に入れた社内向けのサブドメインは外から分からない

✓ 正しくは: 公開の CA が発行した証明書は CT ログに載り、誰でも名前を検索できる。名前を出したくないならワイルドカード証明書にする。
