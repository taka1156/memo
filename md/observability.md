ログ・メトリクス・トレース ——「何かおかしい」から「どこの何が原因か」までたどれるようにする

**ざっくり言うと**

- **メトリクス** で「おかしい」に気づき、 **トレース** で「どこが遅い・失敗している」を絞り、 **ログ** で「なぜ」を読む。3 つは役割が違う。
- 3 つを **同じトレース ID でつなぐ** のが要。サービスをまたいでも ID を受け渡す（コンテキスト伝搬）ので、1 つのリクエストを端から端まで追える。
- **OpenTelemetry (OTel)** は計測の書き方と送り方（OTLP）の標準。アプリは OTel で計測し、どの監視サービスに送るかは後から差し替えられる。

## 監視とオブザーバビリティ

**監視 (monitoring)**

「CPU 90% 超え」「エラー率 5% 超え」のように、 **あらかじめ決めた問い** に答える。知っている壊れ方には強い。

**オブザーバビリティ (observability)**

「この顧客だけ昨日から遅い」のような **事前に想定していなかった問い** にも、出ているデータから答えられる状態。マイクロサービスで特に必要になる。

## 3 つのシグナル

プロファイル

**数値の時系列。** 「1 分あたりのリクエスト数」「p99 レイテンシ」など。集計済みなので軽く、長期間保存してグラフ・アラートに使う。

| 種類 | 意味 | 例 |
| --- | --- | --- |
| Counter | 増えるだけの累計 | リクエスト総数・エラー総数 |
| Gauge | 今の値（上下する） | メモリ使用量・キューの長さ |
| Histogram | 値の分布（バケットごとの件数） | レイテンシ → p50 / p95 / p99 を出せる |

**カーディナリティに注意：** ラベル（属性）の組み合わせごとに別の時系列ができる。 `user_id` や `request_id` をラベルにすると時系列が爆発し、保存コストが跳ね上がる。そういう値はトレースやログに入れる。

**1 つのリクエストがどこを通り、各所で何ミリ秒かかったか。** トレースは **スパン** （1 つの処理区間）の木構造。各スパンはトレース ID・自分のスパン ID・親のスパン ID・開始時刻・長さ・属性を持つ。

**出来事 1 件ごとの記録。** 情報量が一番多いが、量も一番多い。検索・集計しやすいよう **構造化ログ（JSON）** で出し、 **トレース ID を必ず入れる** 。

```

 "msg":"payment declined","order_id":"o_8812","code":"card_expired",
```

トレース ID があれば、遅いトレースからそのリクエストのログだけに飛べる。ない場合は時刻で探すしかなく、同時刻の他のリクエストのログと混ざる。

**コードのどの関数が CPU・メモリを使っているか** を継続的に記録する（継続的プロファイリング）。トレースで「このスパンが遅い」とわかった後、「その中のどの関数か」まで掘れる。

### 3 つをどう使い分けるか

メトリクス：エラー率が上がった → トレース：失敗したリクエストを開くと決済 API が 5 秒でタイムアウト → ログ：同じトレース ID のログに「接続プール枯渇」

## コンテキスト伝搬：サービスをまたいで ID を渡す

サービス A が B を呼ぶとき、HTTP ヘッダーにトレース ID と自分のスパン ID を入れて渡します。標準は W3C Trace Context の `traceparent` ヘッダー。

00 - 4bf92f3577b34da6a3ce929d0e0e4736 - 00f067aa0ba902b7 - 01

バージョン トレース ID（リクエスト全体で同じ） 親スパン ID（呼び出し元） フラグ（01 = サンプリング対象）

B はこのヘッダーを読んで、同じトレース ID で自分のスパンを作ります。キュー（ [メッセージキュー](https://memo.taka1156.site/md/message-queues.md) ）経由でも、メッセージの属性に入れて渡せば非同期処理までつながります。

伝搬が 1 か所でも切れると、トレースはそこで 2 つに分かれてしまう。OTel の自動計測ライブラリは主要な HTTP クライアント・フレームワークについてこれを自動でやる。

## OpenTelemetry の構成

**API**

アプリが呼ぶ部分。スパンを作る・メトリクスを記録する。ライブラリはここだけに依存する。

→

**SDK**

サンプリング・バッチ化・リソース情報（サービス名など）の付与。

→

**Exporter**

OTLP（OTel の送信プロトコル。gRPC / HTTP）で送り出す。

→

**Collector**

受け取って加工（属性の削除・サンプリング）し、複数の送り先に振り分ける。任意だが置くと便利。

→

**バックエンド**

保存・検索・可視化。Prometheus・Jaeger・Grafana・各種 SaaS など。

ポイントは **計測（左側）と保存先（右端）が分離している** こと。SaaS を乗り換えても、アプリのコードは変えずに Collector の設定だけ替えればよい。

```
// Node.js：自動計測で HTTP・DB 呼び出しのスパンを自動で作る
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

new NodeSDK({
  serviceName: 'checkout',
  traceExporter: new OTLPTraceExporter({ url: 'http://collector:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()],
}).start();
```

## サンプリング

全リクエストのトレースを保存すると高くつくので、一部だけ残します。

**ヘッドサンプリング**

リクエストの **最初** に残すかを決める（例：10%）。軽いが、「たまたま捨てた中にエラーがあった」が起こる。決定は `traceparent` のフラグで下流に伝わる。

**テールサンプリング**

トレースが **終わってから** 決める。「エラーか、1 秒以上かかったものは全部残す」ができる。Collector で全スパンを一時的に溜める必要があり重い。

## 何をアラートにするか：SLI と SLO

| 用語 | 意味 | 例 |
| --- | --- | --- |
| SLI | ユーザー体験を表す指標 | 成功したリクエストの割合・300ms 以内に返った割合 |
| SLO | SLI の目標値 | 30 日間で 99.9% が成功 |
| エラーバジェット | SLO から逆算した「失敗してよい量」 | 99.9% なら 30 日で約 43 分ぶんの失敗 |

「CPU 80%」のような原因側の指標でアラートを鳴らすと、ユーザーに影響がないのに夜中に起こされる。アラートはユーザーが困る症状（SLO を割りそう）に対して出し、原因の指標は調査に使う。デプロイ後の自動ロールバックの判定にも使える（ [CI/CD と GitHub Actions](https://memo.taka1156.site/md/ci-cd.md) ）。

## よくある誤解

ログを全部取っておけばオブザーバビリティは足りる

ログだけでは、サービスをまたいだ 1 リクエストの流れや、どこで時間を使ったかが見えない。トレース ID でつながっていないと検索も難しい。

OpenTelemetry は監視サービスの一種

OTel は計測と送信の標準（API・SDK・Collector・OTLP）で、データを保存・表示する機能は持たない。保存先は別に用意する。

平均レイテンシを見ていれば十分

平均は一部の極端に遅いリクエストを隠す。p95・p99 のようなパーセンタイルをヒストグラムから見る。
