# メッセージキューと Pub/Sub

> キュー・Pub/Sub・ログ型（Kafka）の違い、ack と再配信・DLQ・順序・Outbox パターンを、SQS・Cloudflare Queues・Kafka の比較で整理する

「今すぐ返事はいらない仕事」を間に置いた箱に預ける —— 送る側と受ける側を切り離すしくみ

**ざっくり言うと**

- キューを挟むと、送る側（プロデューサー）は **受ける側（コンシューマー）が落ちていても遅くても** 処理を続けられる。急なアクセス増もキューが吸収する。
- 形は 3 つ： **キュー** （1 件を誰か 1 人が処理）／ **Pub/Sub** （1 件を購読者全員に配る）／ **ログ型** （Kafka。消さずに保持して、各自が好きな位置から読む）。
- ほとんどのキューは **「少なくとも 1 回」届ける** 。重複は起きる前提で、受ける側を冪等にする。処理できないメッセージは **DLQ** に退避する。

## なぜキューを挟むのか

**直接呼ぶと**

- メール送信サービスが落ちていると、注文 API までエラーになる
- メール送信が 3 秒かかると、注文 API も 3 秒待たされる
- セールで 100 倍のアクセスが来ると、下流がまとめて落ちる

**キューを挟むと**

- 注文 API は「メールを送って」とキューに入れてすぐ返す
- メール送信側は自分のペースで取り出して処理する
- 落ちていても、復旧後に溜まった分から処理すればよい

### 急増をキューが吸収する

プロデューサーが一気に投入しても、コンシューマーは一定のペースで処理します。台数を増やすと溜まった分（バックログ）が早く減ります。

**送る側**

0 件

60 件まとめて投入

受ける側 1 台

3 台

0 台（障害）

「60 件まとめて投入」を押して、台数を切り替えてみてください。

（元のページで操作できます → https://memo.taka1156.site/message-queues.html#buffer）

## 3 つの形

**キュー（1 対 1）**

（図: 送る / queue / 受A / 受B → https://memo.taka1156.site/message-queues.html#patterns）

1 件のメッセージは A か B の **どちらか一方** だけが処理する。仕事の分担（ワーカー）向き。SQS・Cloudflare Queues・RabbitMQ のキュー。

**Pub/Sub（1 対 多）**

（図: 送る / topic / メール / 在庫 / 分析 → https://memo.taka1156.site/message-queues.html#patterns）

「注文が入った」を **購読者全員** が受け取る。送る側は誰が聞いているかを知らなくてよい。SNS・Google Pub/Sub・Redis Pub/Sub。

**ログ型（Kafka）**

（図: 送る / 0 1 2 3 4 5 6 7 … / G1 は 2 から / G2 は 6 から → https://memo.taka1156.site/message-queues.html#patterns）

メッセージは読んでも **消えず** 、保持期間まで残る。グループごとに「どこまで読んだか（オフセット）」を持ち、巻き戻して読み直せる。

組み合わせも多い：Pub/Sub のトピックから購読者ごとのキューへ配る（SNS → SQS など）と、「全員に配る」と「各自のペースで確実に処理」を両立できる。

## ack・再配信・DLQ

キューは「取り出した＝処理完了」とはみなしません。コンシューマーが **処理し終えてから ack（確認応答）** を返したときに初めて消します。

**1. 受け取る**

メッセージは他のコンシューマーから一時的に見えなくなる（SQS の可視性タイムアウト）。

**2. 処理する**

メール送信・DB 更新など。

**3a. ack**

成功を伝える → キューから削除。

**3b. ack なし**

失敗・タイムアウト・クラッシュ → しばらくして **再配信** 。

**4. DLQ**

決まった回数失敗したら、デッドレターキューに移して人が調べる。

「処理は終わったが ack を返す前に落ちた」ときも再配信されるので、 **同じメッセージが 2 回届く** ことがあります。これが「少なくとも 1 回 (at-least-once)」配信の意味で、対策は受ける側の冪等化です（詳しくは [分散システムの基本：配送保証](https://memo.taka1156.site/md/distributed-basics.md) ・ [冪等性](https://memo.taka1156.site/md/distributed-basics.md) ）。

**ポイズンメッセージ（poison message、有害メッセージとも）：** 形式が壊れているなど、何度やっても失敗するメッセージ。DLQ がないと再配信が永遠に続き、後ろのメッセージが詰まったりコストがかさんだりする。DLQ は必ず設定する。

## 順序の保証

順序と並列はトレードオフです。全メッセージを厳密に順番どおり処理するなら、コンシューマーは 1 台しか使えません。そこで多くのしくみは **「同じキーの中だけ順序を守る」** という形をとります。

| しくみ | 順序の単位 | 使い方 |
| --- | --- | --- |
| Kafka | パーティション内 | キー（例： `user_id` ）でパーティションが決まるので、同じユーザーのイベントは順番どおり |
| SQS FIFO | メッセージグループ内 | `MessageGroupId` を注文 ID などにする |
| SQS 標準・Cloudflare Queues | 保証しない前提 | 順序に依存しない設計にする（バージョン番号・タイムスタンプで新旧を判断） |

## 主なサービスの比較

|  | Cloudflare Queues | Amazon SQS | Apache Kafka |
| --- | --- | --- | --- |
| 形 | キュー | キュー（標準 / FIFO） | ログ型（パーティション分割されたトピック） |
| 受け取り方 | Worker に バッチで押し込まれる （push）か、HTTP で取りに行く（pull） | コンシューマーが取りに行く（ロングポーリング） | コンシューマーグループが取りに行き、オフセットを記録 |
| 読んだ後 | ack で削除 | 削除 API で削除 | 消えない（保持期間まで）。巻き戻して再処理できる |
| 失敗時 | 既定で数回リトライ → DLQ。遅延して再試行も可 | 可視性タイムアウト後に再配信 → 規定回数で DLQ | ブローカー自体に DLQ はない。アプリ側でリトライ用・DLQ 用のトピックを用意する（Kafka Connect や Kafka Streams 4.2 以降には DLQ の設定がある） |
| 向いている | Workers からの非同期処理・バッチ書き込み | AWS 上のワーカー・ジョブ | 大量のイベントストリーム・複数システムでの再利用・再処理 |

Kafka のコンシューマーグループでは 1 パーティションを 1 台が担当するため、並列数はパーティション数が上限になる。Kafka 4.2 からは、パーティションに縛られずに 1 件ずつ ack できる share groups（Kafka Queues、KIP-932）が本番利用できるようになり、キューとしても使える。

## DB 更新と送信をそろえる：Outbox パターン

「注文を DB に保存してから、キューに『注文が入った』を送る」とき、保存後・送信前に落ちるとイベントが消えます。逆順だと、送ったのに保存されていない注文が生まれます。

**1. 同じトランザクション**

注文テーブルへの INSERT と、 `outbox` テーブルへのイベント INSERT を 1 つのトランザクションで行う。

**2. 中継役**

別のプロセスが outbox を読み、キューに送る。

**3. 送ったら印**

送信済みにする。途中で落ちても再送するだけ（だから受け手は冪等に）。

トランザクションの話は [インデックスとトランザクション](https://memo.taka1156.site/md/db-index-transaction.md) 。

## リアルタイム通信との違い

WebSocket や SSE（ [リアルタイム通信](https://memo.taka1156.site/md/realtime-comm.md) ）は「今つながっている相手に即座に届ける」もので、相手がいなければ届きません。キューは「相手がいなくても預かって、後で確実に処理させる」もの。チャットなら、送信はキューで確実に保存・配信処理し、表示は WebSocket で即時に、と組み合わせることが多いです。

## よくある誤解

✗ 誤解: キューに入れれば必ず 1 回だけ処理される

✓ 正しくは: 多くは少なくとも 1 回。ack 前の障害で 2 回届くことがあるので、受け手を冪等にする。

✗ 誤解: Kafka は高性能なキュー

✓ 正しくは: Kafka はメッセージを保持し続けるログで、複数のグループが別々の位置から読み直せる。1 件ごとの ack や、パーティション数を超える並列処理は従来のキューのほうが得意。

✗ 誤解: キューを入れれば負荷の問題は解決する

✓ 正しくは: キューは急増を平らにするだけ。平均でも処理能力が足りなければバックログは増え続ける。キューの長さ・最古メッセージの経過時間を監視する（ [オブザーバビリティ](https://memo.taka1156.site/md/observability.md) ）。
