**ざっくり言うと**

- LLM は「ここまでの **トークン** 列の次に来るトークン」の確率を出し、1 つ選んで付け足す、を繰り返しているだけ。
- モデルが会話中に参照できるのは **コンテキストウィンドウ** に入っている分だけ。会話の記憶も社内資料も、毎回そこへ入れ直している。
- 手元の知識を使わせるのが **RAG** （埋め込みで関連箇所を検索して入れる）、外の世界に作用させるのが **ツール呼び出し** 。それをループにしたものが **エージェント** 。

## トークン — LLM が読み書きする単位

文章は単語でも文字でもなく、よく出る文字列のかたまり（ **トークン** ）に分割され、それぞれが番号（ID）になる。料金・速度・上限はすべてトークン数で決まる。

例示（実際の分け方はモデルごとに違う）

Token ization is fun !

トー クン 化 は 楽 しい ！

- 英語はよく出る単語が 1 トークンになりやすい。日本語は文字あたりのトークン数が多めになりやすい。
- 「単語の文字数を数える」「文字列を逆順にする」が意外と苦手なのは、モデルが文字ではなくトークンを見ているから。

## 次のトークンを選ぶ — temperature と top-p

モデルの出力は「次に来るトークンの確率分布」。そこから 1 つ選ぶ方法を調整するのが **temperature** （分布を尖らせる／平らにする）と **top-p** （累積確率が p に達するまでの候補だけを残す）。

今日はいい天気なので、公園へ **…**

temperature 1.00 top-p 1.00

サンプリングする

数値は説明用の架空のもの。灰色は top-p で除外された候補。

- **低い temperature** : 一番確からしいものばかり選ぶ。抽出・分類・コード向き。
- **高い temperature** : 意外な候補も選ぶ。アイデア出し向き。上げすぎると支離滅裂になる。
- temperature 0 でも、計算の並び順などの影響で **完全に同じ出力になる保証はない** 。

## コンテキストウィンドウ — モデルが「見えている」すべて

1 回の呼び出しでモデルに渡す入力と、生成される出力の合計の上限。モデル自体は前の呼び出しを覚えていないので、毎回、過去の会話を **まるごとコンテキストとして読み直している** 。多くの API（Claude の Messages API など）ではアプリが毎ターン履歴を送り直す。会話をサーバー側に保存できる API（OpenAI の Responses API など）でも、過去の分は毎回入力トークンとして数えられる。

system

tools

会話履歴

ツール結果

出力

空き

システムプロンプト（アプリが与える指示） ツールの定義（MCP など） これまでのやり取り（CLAUDE.md などの差し込みも含む） 検索結果・ファイル内容 これから生成する分

- あふれた分は、アプリ側が古い履歴を **捨てるか要約** して収める。「さっき言ったことを忘れた」はこれ。
- 上限内でも、長くなるほど料金と待ち時間が増え、途中に埋もれた情報を見落としやすくなる。 **必要なものだけを入れる** のが基本。
- **プロンプトキャッシュ** : 先頭から同じ部分は計算を再利用でき、安く速くなる。変わらない指示や資料を前に、毎回変わるものを後ろに置く。
- 推論（thinking）を行うモデルは、答えの前に考える過程のトークンも生成する。これも出力トークンとして数えられる。

## どうやって作られるか

事前学習 大量の文章で次トークン予測を学ぶ → 事後学習 指示に従う・役に立つ・安全に答えるよう調整（人のフィードバック・強化学習など） → 推論（利用） 重みは固定。会話から学習はしない

- 知識は学習データの時点まで（ **知識のカットオフ** ）。それ以降のことは、検索やツールで渡さないと知らない。
- もっともらしい文章を作るのが本業なので、知らないことでも自然な文で答えてしまう（ **ハルシネーション** ）。根拠となる資料を渡し、出典を示させると減らせる。

## 埋め込みと RAG — 手元の資料を使わせる

**埋め込み (embedding)** は文章を数百〜数千次元のベクトルに変換したもの。意味が近い文章ほどベクトルの向きが近くなる（コサイン類似度で比べる）。

（図: 返品の手順 / 返金ポリシー / 交換の受付期間 / パスワード再設定 / 2 段階認証 / 配送料金 / 質問「買った服を返したい」 → https://memo.taka1156.site/llm-basics.html#rag）

2 次元に描いた例示。質問のベクトルに近い「返品の手順」「返金ポリシー」が検索で選ばれる。キーワードが一致しなくても意味で引ける。

### RAG (Retrieval-Augmented Generation) の流れ

準備（事前に）

質問のたびに

資料 → チャンク分割 数百トークン単位 → 埋め込み → ベクトル DB 本文・出典と一緒に保存

質問 → 埋め込み → 近い上位 k 件を検索 → プロンプトに挿入 → LLM が回答 出典付き

- 精度の大半は **検索の質** で決まる。チャンクの切り方、キーワード検索との併用（ハイブリッド検索）、再ランキングが効く。
- 型番やエラーコードのような **完全一致** が大事な語は、ベクトル検索だけだと外しやすい。
- 資料が少なくコンテキストに収まるなら、検索せずに全部入れる方が簡単で確実なこともある。

## ツール呼び出しとエージェントのループ

モデル自身は文章を出すことしかできない。アプリが「使えるツール」の説明を渡し、モデルが **呼び出したいツールと引数** を構造化して出力し、 **実際に実行するのはモデルの外側** （通常はアプリ。Web 検索などを API の提供側が実行する「サーバーツール」もある）。

**① アプリ → モデル** 質問＋ツール定義（名前・説明・引数の JSON Schema）

↓

**② モデル** 「 `search_orders({"user": 42})` を呼びたい」と出力して止まる

↓

**③ アプリ** 実際に関数・API を実行し、結果を会話に追加して再度モデルへ

↓ ②〜③ を、モデルが「もうツールは不要」と判断するまで繰り返す

**④ モデル** 結果を踏まえた最終回答

- このループを自律的に回すのが **エージェント** 。ツール結果がコンテキストにどんどん積まれるので、長い作業ほどコンテキスト管理が重要になる。
- ツールの **説明文の書き方** で、モデルが正しく選べるかが大きく変わる。
- ツール結果やWebページに書かれた指示にモデルが従ってしまう **プロンプトインジェクション** に注意。危険な操作は人の確認を挟む。
- AI アプリと外部のツールやデータをつなぐ方法を標準化したのが MCP。

## よくある誤解

✗ 会話するたびにモデルが学習して賢くなっていく

✓ 利用中に重みは変わらない。「覚えている」ように見えるのは、アプリが履歴やメモリ機能の内容をコンテキストに入れているから。

✗ コンテキストウィンドウが大きいモデルなら、全部入れておけば全部正確に使ってくれる

✓ 入れるほど遅く高くなり、埋もれた情報は見落としやすい。関連部分に絞った方が精度も上がることが多い。

✗ LLM がツールを実行している

✓ モデルは「何を呼びたいか」を出力するだけ。実行するのはアプリや API の提供側で、自分で定義したツールの実行と権限管理はアプリ側の責任。
