メモリに置いたデータ構造を、1 本のスレッドで順番にさばく ─ その上に永続化・複製・分散が乗っている

**ざっくり言うと**

- データは全部 **メモリ上** 。コマンドの実行は **1 本のメインスレッドが順番に** 行うので、ロック不要で 1 コマンドは常に原子的 (atomic)。
- ディスクは「落ちたとき用」。スナップショット ( `RDB` ) と追記ログ ( `AOF` ) で残し、レプリカやクラスター (16384 スロット) で冗長化・分散する。
- Valkey は 2024 年の Redis ライセンス変更をきっかけに Redis 7.2.4 から分かれた BSD ライセンスのフォーク。 **仕組みもプロトコルもほぼ同じ** で、違いは「ライセンス」「同梱機能」「その後の性能改善の方向」。

## 全体像

Redis / Valkey のサーバー 1 台（1 プロセス）の中はこうなっています。クライアントは RESP というプロトコルで話しかけ、Redis 用のクライアントライブラリや `redis-cli` はそのまま Valkey にも繋がります。

## なぜ速い？ ─ シングルスレッドのイベントループ

速さの理由は「スレッドが多いから」ではなく、 **メモリ上で完結する短い処理を、待ちなしで順番に回している** からです。メインスレッドは `epoll` / `kqueue` で「データが届いたソケット」だけを拾い、コマンドを 1 つずつ最後まで実行します。

- ロック・コンテキストスイッチが不要 → 1 コマンドあたりマイクロ秒単位
- 実行中に他のコマンドが割り込まない → `INCR` などは何もしなくても原子的
- 裏返すと、 **重いコマンド 1 つ（ `KEYS *` 、巨大な集合の `SMEMBERS` など）で全員が待たされる**

体験：3 つのクライアントが同時に送ったコマンド

待ち行列 → メインスレッド

メモリの中身

▶ 1 つ実行

↺ 最初から

同時に届いても、実行は必ず 1 つずつ。

### I/O スレッド：重いのは「実行」より「通信」

ネットワークの読み書きと解析は CPU を食うので、そこだけ別スレッドに逃がす仕組みがあります。 **コマンドの実行自体はどちらもメインスレッドのまま** です。

Redis 6 → 8

Valkey 8 →

Redis は 6.0 で I/O スレッドを導入。メインスレッドが I/O スレッドに読み書きを配り、 **全員が終わるのを待ってから** まとめてコマンドを実行する「同期的な分担」でした。Redis 8 で I/O スレッドの実装を作り直し、 `io-threads` を増やしたときのスループットを引き上げています（既定値は 1 = 無効）。

Valkey 8.0 は I/O スレッドを **非同期化** 。メインスレッドと I/O スレッドが待ち合わせずに並行して動き、読み書き・解析に加えてメモリ解放などの雑務も I/O スレッド側へ逃がします。9.0 ではパイプライン実行時のメモリプリフェッチ、9.1 ではスレッドモデルのさらなる改良が入り、「1 プロセスあたりのスループット」を伸ばす方向に進んでいます。

（元のページで操作できます → https://memo.taka1156.site/redis-valkey.html#threads）

## ただの KVS ではない ─ 値が「データ構造」

値は文字列だけでなく、サーバー側で操作できるデータ構造です。「取ってきて、アプリで加工して、書き戻す」をせず **サーバー内で 1 コマンドで** 済ませられるのが Redis 系の真価です。

### String

page:views → "1042"

キャッシュ、カウンタ（ `INCR` ）、分散ロック（ `SET k v NX PX 3000` ）

### Hash

user:1 → {name, plan, pts}

オブジェクト・セッション。フィールド単位で読み書き。フィールドごとの TTL も可（Redis 7.4 以降 / Valkey 9.0 以降）

### List

jobs → [j3, j2, j1]

簡易キュー（ `LPUSH` / `BRPOP` ）、最新 N 件

### Set

tags:42 → {go, db, web}

重複なし集合。共通部分（ `SINTER` ）で「共通の友達」など

### Sorted Set

rank → {bob:90, ann:75}

スコア順。ランキング、時刻をスコアにした予約キュー、レートリミット

### Stream

events → 1700…-0 {…}

追記ログ＋コンシューマーグループ。既読管理つきのイベント配信

### Pub/Sub

PUBLISH ch msg

その瞬間の購読者に配るだけ（保存しない）。通知・チャット

### HyperLogLog ほか

uv:today ≈ 12,034

約 12KB で数億件のユニーク数を概算。Bitmap、Geo も標準

内部では件数が少ないうちは詰め込み形式（listpack など）でメモリを節約し、増えたら本格的な構造（ハッシュテーブル、スキップリストなど）に自動で切り替わります。

## メモリが有限 ─ 期限切れ (TTL) とエビクション (eviction)

期限切れの消し方

満杯になったら

`EXPIRE key 60` を付けたキーは、2 つのルートで消えます。

（図: 遅延削除 (lazy) / アクセスされた瞬間に期限を確認 / 切れていたら消して「無い」と返す / → 読まれたキーは必ず正しい / 能動削除 (active) / 定期的に期限付きキーを少しずつ走査 / 切れているものを掃除 / → 読まれないゴミもいずれ消える → https://memo.taka1156.site/redis-valkey.html#expire）

「期限ちょうどにメモリが空く」わけではありません。一時的に期限切れキーがメモリに残ることがあります。

`maxmemory` に達したときの動き（キーを追い出して削除する＝エビクションをするか、どれを追い出すか）は `maxmemory-policy` で決まります。

| ポリシー | 動き | 向いている用途 |
| --- | --- | --- |
| `noeviction` | 何も消さず、書き込みをエラーにする（既定） | 消えては困るデータ（キュー・セッションの主保存先） |
| `allkeys-lru` / `-lfu` | 全キーから「最近使われていない」/「使用頻度が低い」ものを消す | 純粋なキャッシュ |
| `volatile-lru` / `-lfu` / `-ttl` | 期限付きのキーだけを対象に消す | キャッシュと永続データを同居させるとき |
| `*-random` | ランダムに消す | アクセスが均等なとき |

LRU / LFU は厳密ではなく、数個をサンプリングして一番古いものを選ぶ近似です（メモリと速度のため）。

## 永続化 ─ RDB と AOF

メモリのデータは再起動で消えるので、ディスクに残す方法が 2 つあります。どちらもメインスレッドを止めないよう工夫されています。

RDB（スナップショット）

AOF（追記ログ）

どう選ぶ

（図: 親プロセス / 普通にコマンドを処理 / 書き換えたページだけ / コピーされる (CoW) / BGSAVE / save 設定 / fork() / 子プロセス / fork した瞬間の / メモリをそのまま見て / ファイルに書き出す / dump.rdb / 圧縮バイナリ 1 ファイル → https://memo.taka1156.site/redis-valkey.html#persistence）

- ◎ ファイルが小さく、起動時の読み込みが速い。バックアップに向く
- △ 最後のスナップショット以降の書き込みは、落ちたら失われる
- △ 書き込みが多いと CoW でメモリ使用量が一時的に増える（最大で約 2 倍）

書き込みコマンドを実行するたびにログへ追記し、起動時に頭から再生して復元します。

```
SET user:1 ann
INCR page:views
HSET user:1 plan pro     ← 書き込みのたびに追記
```

| `appendfsync` | ディスクへの確定 (fsync) | 最悪失うデータ |
| --- | --- | --- |
| `always` | 毎コマンド | ほぼなし（その分遅い） |
| `everysec` | 1 秒ごと（既定） | 約 1 秒分 |
| `no` | OS 任せ | 数十秒分のこともある |

ログは膨らみ続けるので、裏で「今の状態を作る最短のログ」に **書き直し (rewrite)** ます。現在の版では、書き直しの土台を RDB 形式にして後ろに増分ログを足す形が既定です（RDB と AOF のいいとこ取り）。

- **純粋なキャッシュ** （消えても元 DB から作り直せる）→ 永続化なし、または RDB のみ
- **セッション・キューなど失いたくない** → AOF（ `everysec` ）＋ RDB でバックアップ
- どちらにしても **レプリカは「バックアップ」ではない** 。 `FLUSHALL` も即座に複製される

## 複製と分散 ─ レプリカ・Sentinel・Cluster

レプリケーション

Sentinel

Cluster

（図: プライマリ / 読み書き / レプリカ 1 / 読み取り専用 / レプリカ 2 / ① 初回：RDB を丸ごと送る / ② 以降：書き込みを非同期で流す → https://memo.taka1156.site/redis-valkey.html#cluster）

複製は **非同期** 。プライマリはレプリカの受信を待たずにクライアントへ OK を返すため、直後にプライマリが落ちると直近の書き込みが失われることがあります（ `WAIT` で待つことはできるが、強い一貫性の保証ではない）。切断後の再接続では、手元のバッファ（backlog）に残っている差分だけを送り直します。

Sentinel はプライマリを監視する別プロセス群（通常 3 台以上）。過半数が「プライマリが落ちた」と合意すると、レプリカの 1 台をプライマリに昇格させ、クライアントには新しいプライマリの場所を教えます。 **データは分割しない** ので、全データが 1 台のメモリに収まる場合の高可用化 (HA) 手段です。

Cluster はデータを複数のプライマリに **分割 (sharding)** します。キー空間は **16384 個のハッシュスロット** に分かれていて、各プライマリがスロットの範囲を受け持ちます。

```
slot = CRC16(key) mod 16384
```

キーを入れると、どのスロット・どのノードに行くか計算します（3 ノードで均等に分けた例）。

Node A

Node B

Node C

0 5461 10923 16383

試しに `{user:1000}:cart` と `{user:1000}:profile` を入れてみてください。 `{}` で囲んだ部分（ **ハッシュタグ** ）だけがハッシュされるので、同じスロットに集まります。複数キーをまたぐコマンド（ `MGET` 、トランザクション、Lua）は **同じスロットのキー同士でしか** 使えないため、これで揃えます。

違うノードに送ってしまうと `MOVED 3999 10.0.0.2:6379` のように正しい場所が返ってきます。クライアントライブラリはこれを覚えて、次から直接正しいノードに送ります。

## Redis と Valkey の関係

2009

Redis 誕生。BSD ライセンスのオープンソースとして広く普及

2024-03

Redis が次版（7.4）以降を RSALv2 / SSPLv1 のデュアルライセンスに変更。クラウド事業者が無断でマネージドサービスにすることを制限する、OSI 非承認の「ソースアバイラブル」ライセンス

2024-03

ライセンス変更直前の BSD 版 Redis 7.2.4 から Valkey がフォーク（重大なセキュリティ修正は一定期間 BSD で提供）。Linux Foundation の下、AWS・Google Cloud・Oracle などのメンテナーが参加。ライセンスは BSD 3-Clause のまま

2024-09

Valkey 8.0 ：非同期 I/O スレッド、デュアルチャネルレプリケーションなど独自の改善が始まる

2025-05

Redis 8 ：AGPLv3 を選択肢に追加し OSI 承認のオープンソースに復帰。JSON・検索 (Query Engine)・時系列・確率的データ構造・Vector Set を本体ディストリビューションに同梱

2025-10

Valkey 9.0 ：アトミックなスロット移行、ハッシュフィールドの期限、クラスターモードでの複数 DB（番号付き DB）

2026-05

Valkey 9.1 ：DB 単位の ACL、Lua を切り離せるモジュール化、I/O スレッドとメモリ効率の改善

つまり「Redis 7.2 までの仕組み」は両者共通の土台で、上で説明したイベントループ・データ構造・RDB/AOF・Cluster はどちらにもそのまま当てはまります。

|  | Redis（Open Source 8.x） | Valkey（9.x） |

| ライセンス | RSALv2 / SSPLv1 / AGPLv3 から選択 | BSD 3-Clause（制約が最も緩い） |
| 運営 | Redis 社 | Linux Foundation（複数企業の共同開発） |

| 独自の強み | AI / 検索系の機能群、Redis Cloud・Redis Software との一体性 | マルチスレッド I/O による 1 ノード性能、クラスターでの複数 DB（アトミックなスロット移行は Valkey 9.0 が先行し、Redis も 8.4 で追随） |

## よくある誤解

シングルスレッドだから CPU を 1 コアしか使えない

コマンドの **実行** は 1 スレッドですが、I/O スレッド・永続化の子プロセス・裏での解放処理などで他のコアも使います。それでも 1 プロセスの実行は 1 本なので、さらに伸ばすなら Cluster で複数プロセスに分けます。

MULTI / EXEC はロールバックできるトランザクション

まとめて順番に実行され、間に他のコマンドが割り込まないことは保証されますが、途中のコマンドが失敗しても **前のコマンドは取り消されません** 。条件付き更新には `WATCH` （楽観ロック）か Lua スクリプト / Function を使います。

Valkey は Redis の互換品だから中身は別物

逆で、Valkey は Redis 7.2.4 のソースコードそのものから始まっています。違いが出てくるのはフォーク後に各自が加えた部分だけです。

本番で KEYS * を使って調べればいい

全キーを一度に走査するのでメインスレッドが長時間ふさがり、その間ほかのクライアントは全員待たされます。少しずつ返す `SCAN` を使います。

## コマンド例

```

```
