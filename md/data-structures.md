O 記法の読み方 / 主なデータ構造の操作コスト / 場面ごとの選び方

**ざっくり言うと**

- **O 記法** は「データが n 個に増えたとき、手間がどんな勢いで増えるか」。定数倍は無視して、増え方の形だけを見る。
- データ構造は「どの操作を速くするか」の選択。 **番号で引くなら配列、キーで引くならハッシュ表、順序や範囲が要るなら木、最小・最大を何度も取るならヒープ** 。
- 同じ計算量でも実際の速さは違う。メモリ上で **連続している** ほどキャッシュに乗りやすく速い。最後は測って決める。

## O 記法 — 増え方の形を見る

「配列から値を探す」は、最悪で全部見るので n に比例する手間がかかる。これを O(n) と書く。 `3n + 5` 回でも `n/2` 回でも、n が大きくなれば効いてくるのは「n に比例する」という形だけなので、まとめて O(n) と呼ぶ。

n = 1,000

| 記法 | 呼び方 | 典型例 | n が 10 倍になると |
| --- | --- | --- | --- |
| O(1) | 定数時間 | 配列の i 番目を読む、ハッシュ表で引く（平均） | 変わらない |
| O(log n) | 対数時間 | 二分探索、平衡二分木・B 木での検索 | 少し増えるだけ（二分探索なら比較が約 3.3 回増える。B 木なら段が 1 つ増える程度） |
| O(n) | 線形時間 | 全件をなめる、配列の途中に挿入 | 10 倍 |
| O(n log n) |  | 比較による並べ替え（マージソートなど） | 10 倍ちょっと |
| O(n²) | 二乗時間 | 二重ループで全ペアを比べる | 100 倍 |

（元のページで操作できます → https://memo.taka1156.site/data-structures.html#big-o）

### 計算量の見方の注意

- **最悪・平均・償却** を区別する。ハッシュ表の検索は平均 O(1) だが、衝突が偏ると最悪 O(n)。配列の末尾追加は、ときどき領域を作り直す O(n) が起きるが、ならすと 1 回あたり O(1)（ **償却 O(1)** ）。
- 時間だけでなく **メモリ（空間計算量）** も見る。「速くするために索引を持つ」は、メモリと引き換え。
- n が小さいうちは定数倍のほうが効く。要素が数十個なら、配列を全部なめるほうがハッシュ表より速いこともある。

## 主なデータ構造

ARRAY ** 配列（動的配列）**

3 8 1 5 9

メモリ上に隙間なく並ぶ。番号から位置を計算できるので i 番目を一発で読める。途中に入れると後ろを全部ずらす。JS の Array、Python の list、Go の slice、Rust の Vec。

LINKED LIST ** 連結リスト**

3 → 8 → 1 → 5

各要素が次の要素を指す。位置が分かっていれば付け替えだけで O(1) で挿入・削除できるが、i 番目に行くには先頭からたどる。LRU キャッシュの内部などで使う。

HASH TABLE ** ハッシュ表**

"id" → hash → [2] → 値

キーをハッシュ関数で番号に変え、配列のその位置に置く。キーで引く・入れる・消すが平均 O(1)。順序や範囲での検索は苦手。JS の Map / Set / オブジェクト、Python の dict / set。

BALANCED TREE ** 平衡二分探索木・B 木**

50 ↙ 20 ↘ 80

「左は小さく右は大きく」と並べ、高さを log n に保つ。検索・挿入・削除が O(log n) で、 **順番どおりに取り出す・範囲で絞る** ができる。赤黒木（Java の TreeMap、C++ の std::map）、B 木（DB のインデックス）。

HEAP ** ヒープ（優先度付きキュー）**

1 ↙ 4 ↘ 3 …

「親は子より小さい」だけを守る木（配列で表せる）。最小値を見るのは O(1)、取り出し・追加は O(log n)。全体は並んでいないので、検索は O(n)。タイマー、ジョブキュー、ダイクストラ法。

STACK / QUEUE ** スタック・キュー**

後入れ先出し / 先入れ先出し

端だけを出し入れする。どちらも O(1)。スタックは関数呼び出し・undo・深さ優先探索、キューは幅優先探索・処理待ちの列。JS で配列の `shift()` をキューに使うと先頭を抜くたびに詰め直しが起きうる。

ほかに、前方一致に強い **トライ (trie)** 、「入っているかもしれない／絶対ない」を少ないメモリで答える **ブルームフィルタ** 、点と辺の関係を表す **グラフ** （隣接リスト・隣接行列）などがある。ベクトル検索の近似索引（HNSW）はグラフの応用（ [RAG とベクトル検索](https://memo.taka1156.site/md/rag-vector-search.md) ）。

## 場面ごとの選び方

ID の一覧に含まれるかを何度も調べる

Set（ハッシュ表）

配列の `includes` は毎回 O(n)。ループの中で使うと全体で O(n²) になる。

キーから値をすぐ引きたい（順序は要らない）

Map / dict

JS ではキーが文字列以外のとき・頻繁に足し引きするときはオブジェクトより Map。

「締め切りがいちばん近いもの」を次々取り出す

ヒープ

毎回ソートし直すと O(n log n)。ヒープなら 1 回 O(log n)。

「2026-01〜03 の注文」のように範囲で絞る

ソート済みの構造・B 木

ハッシュは隣のキーが近くに置かれないので範囲検索に使えない。DB のインデックスが B 木なのはこのため。

番号順に読み、末尾に足していく

配列

いちばん単純で、多くの場面でいちばん速い。迷ったらまず配列。

入力補完（前方一致）

トライ・ソート済み配列＋二分探索

共通の接頭辞をまとめて持てる。件数が少ないならソート済み配列で十分。

### よくある O(n²) の直し方

```
// ✗ users ごとに orders を全部なめる: O(users × orders)
for (const u of users) {
  u.orders = orders.filter(o => o.userId === u.id);
}

// ✓ 先に userId → 注文一覧 の Map を作る: O(users + orders)
const byUser = new Map();
for (const o of orders) {
  if (!byUser.has(o.userId)) byUser.set(o.userId, []);
  byUser.get(o.userId).push(o);
}
for (const u of users) u.orders = byUser.get(u.id) ?? [];
```

DB で同じことが起きるのが N+1 問題。こちらは 1 回のクエリにまとめる（JOIN や IN）のが直し方（ [インデックスとトランザクション](https://memo.taka1156.site/md/db-index-transaction.md) ）。

## 並べ替えと二分探索

- 要素同士を比べて並べ替える方法は、どう工夫しても最悪の場合 n log n に比例する回数（Ω(n log n)）の比較が要る。言語の標準のソート（JS の `Array.prototype.sort` 、Python の `sorted` など）はこの速さで、自分で書く必要はほぼない。
- JS の `sort()` は比較関数を渡さないと **文字列として** 比べる。数値なら `a.sort((x, y) => x - y)` 。
- **安定ソート** は、同じ値の要素の元の順番を保つ。「日付順に並べたものを、さらに担当者で並べる」ときに日付順が崩れない。JS と Python の標準ソートは安定。
- **二分探索** は、並んでいる範囲の真ん中を見て半分を捨てていく。100 万件でも 20 回ほどで見つかる。前提は **ソート済み** であること。
- 一度しか探さないなら、ソート（O(n log n)）してから二分探索するより全件なめる（O(n)）ほうが速い。何度も探すときにソートが元を取る。

## 計算量だけでは決まらない — メモリの近さ

CPU はメモリをまとめて（キャッシュライン単位で）読み込み、近くのデータは速く読める。配列はデータが連続しているので、次の要素はもうキャッシュにあることが多い。連結リストや木はノードがメモリのあちこちに散らばり、たどるたびに遠くまで取りに行く。

配列

連結リスト

「途中に挿入」が O(1) の連結リストでも、挿入位置を探すのに O(n) かかる上に 1 歩ずつ遅い。実際には、配列を詰め直すほうが速いことが多い。

- DB の B 木が二分木ではなく「1 ノードに数百のキー」を持つのも同じ理由。ディスクやメモリから 1 回で読める量に合わせ、読む回数（木の高さ）を減らしている（ [DB のしくみ](https://memo.taka1156.site/md/db-internals.md) ）。
- 速さが問題になったら、推測でデータ構造を替える前にプロファイラで測る。

## よくある誤解

✗ O(1) なら O(log n) より必ず速い

✓ O 記法は定数倍を捨てている。ハッシュの計算が重い・キャッシュに乗らない場合は、小さな n では O(log n) や O(n) のほうが速いこともある。

✗ ハッシュ表は常に O(1)

✓ 平均の話。衝突が多いと遅くなる。外部から送られたキーを入れるときは、衝突を狙った攻撃（hash flooding）に備えて、言語のランタイムがハッシュに乱数の種を混ぜていることが多い。

✗ 挿入が多いなら連結リスト

✓ 挿入位置を探すコストとキャッシュの悪さで、配列に負けることが多い。末尾への追加が中心なら配列で十分。
