コードをわざと壊して、テストが気づくかを確かめる「テストのテスト」

**ざっくり言うと**

- 本番コードを 1 か所だけ変えた版（ミュータント）を大量に作り、テストが失敗するかで **テストの検出力** を測る手法。
- テストが失敗すれば kill、全部通れば survive で、生き残りは「その変化を確かめるアサーションがない」ことを示す。
- 重いので対象を絞り、変更分だけを回す。スコア 100% は目指さず、生き残りを読んでテストを足す材料にする。

## 仕組み：1 か所壊して、テストが気づくか

**元のコード** `return age >= 18`

**演算子を当てて変異** `>=` を `>` に、など 1 か所だけ変える

**テストを全部流す** ミュータントごとに、既存のテストをそのまま実行

**失敗した** killed：テストが変化に気づいた

**全部通った** survived：テストの見落とし

killed（テストが検出できた） survived（検出できなかった）

前提にあるのは「本物のバグの多くは、正しいコードからの小さなずれ（境界の 1 つずれ、演算子の取り違え）である」という考え方。小さなずれを検出できるテストなら、似た本物のバグも検出しやすい、とみなす。

テストではなく **本番コード** を変える点に注意。テストコードは一切いじらず、「このテストスイートは、コードが間違っていたら気づけるか」を確かめる。

## 例：テストを足すとスコアがどう変わるか

対象は次の関数。この関数から 5 つのミュータントを作り、テストを 1 つずつ足していく。

```
function isAdult(age) {
  return age >= 18;
}
```

テスト 1 本

＋ 未成年

＋ 境界の 18

```
expect(isAdult(20)).toBe(true);
```

| ミュータント | age=20 の結果 | 判定 |
| --- | --- | --- |
| M1 `age > 18` | true（同じ） | survived |
| M2 `age <= 18` | false | killed |
| M3 `age >= 19` | true（同じ） | survived |
| M4 `age >= 17` | true（同じ） | survived |
| M5 `return true` | true（同じ） | survived |

スコア 1 / 5 = 20%

関数の行はすべて実行されるので、 **行カバレッジは 100%** 。それでも「常に true を返す」壊れ方（M5）にすら気づけない。

```
expect(isAdult(20)).toBe(true);
expect(isAdult(17)).toBe(false);  // 追加
```

| ミュータント | age=17 の結果 | 判定 |
| --- | --- | --- |
| M1 `age > 18` | false（同じ） | survived |
| M2 `age <= 18` | — | killed （age=20 で） |
| M3 `age >= 19` | false（同じ） | survived |
| M4 `age >= 17` | true | killed |
| M5 `return true` | true | killed |

スコア 3 / 5 = 60%

「false になるべき場合」を確かめたことで、常に true や下側の境界ずれは捕まる。残った M1・M3 はどちらも「18 歳ちょうど」で初めて結果が変わる壊れ方。

```
expect(isAdult(20)).toBe(true);
expect(isAdult(17)).toBe(false);
expect(isAdult(18)).toBe(true);   // 追加：境界値
```

| ミュータント | age=18 の結果 | 判定 |
| --- | --- | --- |
| M1 `age > 18` | false | killed |
| M2 `age <= 18` | — | killed （age=20 で） |
| M3 `age >= 19` | false | killed |
| M4 `age >= 17` | — | killed （age=17 で） |
| M5 `return true` | — | killed （age=17 で） |

スコア 5 / 5 = 100%

生き残りが「境界値 18 のテストがない」ことを教えてくれた。カバレッジはずっと 100% のままで、この差はカバレッジでは見えない。

## カバレッジとの違い

### コードカバレッジ

そのコードはテスト中に実行されたか？

- 速い。テストを 1 回流すだけで測れる
- 結果を確かめていなくても上がる（アサーションのないテストでも 100% になりうる）
- 低いと「テストされていない所がある」とわかるが、高くても安心はできない

### ミューテーションテスト

そのコードが間違っていたら、テストは失敗するか？

- 遅い。ミュータントの数だけテストを流し直す
- 結果を確かめるアサーションがないと kill できない
- 「どの変化を見逃したか」がコード上の位置つきでわかる

両者は対立するものではなく、カバレッジは「そもそも実行されているか」の粗いふるい、ミューテーションテストは「実行された所をちゃんと確かめているか」の細かいふるい。実行されていない所のミュータントは必ず生き残るので、ツールはこれを別の状態（No coverage）として分けて表示する。

## 主なミューテーション演算子

「どう壊すか」の規則をミューテーション演算子（mutation operator / mutator）と呼ぶ。名前や種類はツールごとに違うが、だいたい次のようなものがある。

| 種類 | 変異の例 | 生き残ったら疑うこと |
| --- | --- | --- |
| 境界・比較 | `<` → `<=` 、 `>=` → `>` | 境界値のテストがない |
| 算術 | `+` → `-` 、 `*` → `/` | 計算結果の値を確かめていない |
| 論理 | `&&` → `\|\|` | 条件の片方だけが真の場合を試していない |
| 条件の置き換え | `if (x)` → `if (true)` / `if (false)` | 分岐の片側しか試していない |
| 真偽値・定数 | `true` → `false` 、 `0` → `1` | フラグや既定値の影響を見ていない |
| 戻り値 | `return x` → `return null` / 空の値 | 戻り値そのものを確かめていない |
| 文・呼び出しの削除 | `save(user)` の行を消す、ブロックを空にする | 副作用（保存・送信・通知）を確かめていない |
| 文字列・配列 | `"abc"` → `""` 、 `[1, 2]` → `[]` | 中身を見ずに「あること」だけ確かめている |

JavaScript 向けの Stryker には、オプショナルチェーン（ `a?.b` → `a.b` ）や正規表現を変える演算子など、言語に合わせたものもある。

## 結果の読み方とスコア

ツールは各ミュータントに状態を付ける。名前は Stryker のものだが、他のツールもほぼ同じ分け方をする。

| 状態 | 意味 | どうする |
| --- | --- | --- |
| Killed | 少なくとも 1 つのテストが失敗した | 何もしなくてよい |
| Timeout | テストが時間内に終わらなかった（無限ループになった等） | 検出できたとみなす |
| Survived | そのコードを実行するテストはあるが、全部通った | アサーションを足す／等価か調べる（ 次の節 ） |
| No coverage | そのコードを実行するテストが 1 つもない | まずテストで通る道を作る |
| Compile / Runtime error | 変異の結果、コンパイルできない・実行時にテスト以前で落ちた | 無効なミュータント。スコアに数えない |

検出 = Killed + Timeout

未検出 = Survived + No coverage

ミューテーションスコア = 検出 ÷ (検出 + 未検出)

テストが通る範囲だけで測った「カバー済みコードでのスコア」（No coverage を分母から外したもの）も出るツールがある。全体のスコアが低いとき、原因が「テストがない」のか「テストが弱い」のかをこの 2 つの差で切り分けられる。

## 生き残りへの対処

1. **差分を読む** レポートは「どの行をどう変えたら生き残ったか」を示す。まずその変化で何が起きるかを考える。
2. **振る舞いが本当に変わるか** 変えても外から見た結果がまったく同じなら、等価ミュータント（下で説明）。テストでは kill できないので、ツールの無視指定で除外する。
3. **確かめる価値があるか** ログの文言やデバッグ用の出力など、変わっても困らないものなら、そのファイルや行を対象から外す。
4. **テストを足す・強める** 境界値のケースを足す、戻り値や副作用を確かめるアサーションを足す。テストを追加したらそのミュータントが kill されることを確かめる。

### 等価ミュータント

コードは変わったのに振る舞いが変わらないミュータントを等価ミュータント（equivalent mutant）と呼ぶ。どんなテストを書いても kill できない。

```
for (let i = 0; i < n; i++) { … }
// ↓ 変異
for (let i = 0; i != n; i++) { … }
// i は 1 ずつ増えるので、n が 0 以上の整数なら結果は同じ
```

一般に、等価かどうかを機械的に判定することはできないため、最後は人が読んで判断する。スコア 100% を目標にしにくい一番の理由がこれ。

## 実務での回し方

コストはおおよそ「ミュータントの数 × 1 体あたりに流すテストの量」。数千のミュータントに対してテストスイートを流し直すので、何もしないと通常のテストの何十倍もかかる。

1. **対象を絞る** 料金計算・権限判定・状態遷移など、間違えると困るドメインロジックから始める。UI の見た目や設定ファイルは外す。
2. **変更分だけを回す** 前回の結果を保存して、変わったコードのミュータントだけを試す増分モード（Stryker の incremental、PIT の履歴ファイルなど）を使い、PR ごとに回す。
3. **関係するテストだけを流す** 各テストがどの行を通るかを先に測り、そのミュータントを通るテストだけを実行する。多くのツールが標準で行う。
4. **しきい値は下限として使う** 「これを下回ったら CI を落とす」線をチームの現状に合わせて置き、上げることを目標にしない。全体の夜間実行と、PR の差分実行を分けるのもよい。
5. **生き残りをレビューで見る** PR に新しい生き残りが出たら、テストを足すか除外するかをその場で決める。数字よりも「何を見逃したか」の一覧のほうが役に立つ。

### 言語ごとの主なツール

| 言語 | ツール | メモ |
| --- | --- | --- |
| JavaScript / TypeScript | StrykerJS | HTML レポートと増分モードがある。同じ系列に C# 用の Stryker.NET、Scala 用の Stryker4s |
| Java / JVM | PIT（pitest） | バイトコードを変異させるので速い。Maven・Gradle から使う |
| Python | mutmut | pytest と組み合わせて使う |
| Rust | cargo-mutants | `cargo mutants` で動く。関数の戻り値を置き換える変異が中心 |
| PHP | Infection | PHPUnit などと組み合わせる |

## よくある誤解

✗ 誤解: ミューテーションスコアは 100% を目指すべきだ

✓ 正しくは: 等価ミュータントはテストでは kill できず、ログ出力のように確かめる価値の薄い変異もある。100% を目標にすると、除外指定と意味の薄いテストが増える。重要なモジュールで高く保ち、新しい生き残りを毎回読むほうが効く。

✗ 誤解: ミューテーションテストは本番コードのバグを見つける道具だ

✓ 正しくは: 見つけるのは **テストの弱点** 。生き残りを調べる途中で本物のバグに気づくことはあるが、ツールが示すのは「この変化をテストが見逃す」という事実だけ。

✗ 誤解: カバレッジが高ければミューテーションスコアも高くなる

✓ 正しくは: カバレッジは「実行したか」しか見ないので、結果を確かめないテストでも 100% になる。上の例のように、カバレッジ 100% でスコア 20% は普通に起こる。

✗ 誤解: 重すぎるので CI では使えない

✓ 正しくは: 全体を毎回回すと重いが、対象の絞り込みと増分モード（変更したコードのミュータントだけを試す）を組み合わせれば、PR ごとに数分で回せる規模に収まることが多い。
