# ふりかえりの進め方と手法

> ふりかえりの 5 つの段階と、KPT・4Ls・リーンコーヒーなどの手法を、どの段階に効くか・いつ選ぶかで比べて図解。

反省会で終わらせず、次の 1 歩を決めるための段取りと型

**ざっくり言うと**

- ふりかえり (retrospective) は、チームが自分たちのやり方を点検して、次に試す改善を決める定期的な場。
- 場を設定する→データを収集する→アイデアを出す→何をすべきかを決定する→終了する、の 5 段階で進めると話が散らばらない。
- KPT や 4Ls などの型は段階の一部を助ける道具なので、チームの状態に合わせて選び、ときどき変える。

## 何のためにやるのか

アジャイル宣言の原則には「チームは定期的に、もっと効果的になる方法をふりかえり、やり方を調整する」とあり、スクラムではスプリントの最後のイベント（スプリントレトロスペクティブ）として置かれています（ [アジャイルとスクラムの仕組み](https://memo.taka1156.site/md/agile-scrum.md) ）。見るのは **成果物ではなくやり方** です。人の動き方・やり取り・プロセス・ツール・完成の定義などを点検し、次の期間に試すことを決めます。

大事なのは「誰が悪かったか」ではなく「仕組みのどこを変えるか」に話を向けることです。そのために、ふりかえりの古典『Project Retrospectives』の著者 Norm Kerth は、始める前に次の考え方（最優先指令、Prime Directive）を全員で確かめることを勧めています。

何が見つかっても、その時点で分かっていたこと・持っていた技術と能力・使えた資源・置かれた状況のもとで、 **誰もが精一杯の仕事をした** と心から信じる。

上は趣旨を日本語にまとめたもの。原文は Retrospective Wiki などで読めます。

## 5 つの段階

Esther Derby と Diana Larsen の『Agile Retrospectives』（邦訳『アジャイルレトロスペクティブズ』）は、ふりかえりを次の 5 段階で組み立てることを提案しています。いきなり「何が問題？」から始めると、声の大きい人の印象だけで解決策に飛びがちです。段階を分けると、 **全員で同じ事実を見てから原因を考える** 順番を守れます。

1. **場を設定する (Set the Stage)** 目的と時間を共有し、全員が一言は話す。前回決めたことがどうなったかもここで確かめる
2. **データを収集する (Gather Data)** 起きたこと・数字・感じたことを出し合い、同じ絵を共有する。付箋に各自で黙って書く時間を取ると、発言が偏らない
3. **アイデアを出す (Generate Insights)** なぜそうなったかを考える。似た付箋をまとめ、「なぜ」を掘り下げる
4. **何をすべきかを決定する (Decide What to Do)** 試すことを 1〜2 個に絞り、誰が・いつまでに・どうなったら成功かまで決める
5. **レトロスペクティブを終了する (Close the Retrospective)** 決めたことを確認し、ふりかえり自体の良し悪しを一言ずつ聞いて、次回の進め方に活かす

時間の目安は、2 週間のスプリントなら 1 時間〜1 時間半ほどです（スクラムガイドの上限は 1 か月のスプリントで 3 時間）。

**KPT（Keep / Problem / Try、ケプト）**

（元のページで操作できます → https://memo.taka1156.site/retrospectives.html#methods）

#### Keep

うまくいった、続けたいこと

PR を小さく分けたらレビューが速かった

#### Problem

困ったこと、うまくいかなかったこと

仕様の確認待ちで 2 日止まった

#### Try

次に試すこと（Keep を伸ばす・Problem を解く）

着手前に PO と 15 分で受け入れ条件をすり合わせる

**向いている場面** ：最初の 1 つ、毎回の定番。日本でとくに広く使われています。

**落とし穴** ：Problem を並べただけの反省会になりやすい。最初に前回の Try を確かめ、Try を具体的な行動にまで落とします。Try を実行タスクに変えた「KPTA（A は Action）」という変形もあります。

**Start / Stop / Continue**

#### Start

新しく始めること

リリース前にステージングで動作確認

#### Stop

やめること

読まれていない日報

#### Continue

続けること

ペアでのレビュー

**向いている場面** ：すぐ行動に変えたいとき。最初から「やること」の形で出てくるので決めやすい。

**落とし穴** ：原因を考える段階を飛ばしやすい。Stop は人ではなく活動に向けます。

**4Ls（Liked / Learned / Lacked / Longed for）**

#### Liked

良かったこと

デザイナーと同じ席で進めた

#### Learned

学んだこと

CSS の移行は思ったより時間がかかる

#### Lacked

足りなかったこと

テスト環境のデータ

#### Longed for

あったらよかった・次に望むこと

本番に近いテストデータ

**向いている場面** ：プロジェクトの区切りや、学びを残したいとき。「Learned」の列があるので、うまくいかなかったことも学びとして書きやすい。

**落とし穴** ：列が多いぶん付箋も増える。最後に投票で絞る時間を取ります。

**Mad / Sad / Glad**

#### Mad

腹が立った・イライラした

夜間の呼び出しが 3 回

#### Sad

残念だった・がっかりした

デモに間に合わなかった機能

#### Glad

うれしかった

お客さんからのお礼

**向いている場面** ：大変だった期間のあと、気持ちを先に出したほうが話が進むとき。

**落とし穴** ：感情を出すだけで終わらないよう、続けて原因を考え、やることを決める段階を必ず置きます。言いにくい内容が出るので、場の安全をとくに意識します。

**YWT（やったこと / わかったこと / つぎにやること）**

#### Y：やったこと

事実として何をしたか

ログイン画面をフォームライブラリに移行

#### W：わかったこと

やって分かったこと・気づき

バリデーションをスキーマで共有すると重複が消える

#### T：つぎにやること

次の行動

登録画面も同じ方式にする

**向いている場面** ：日本で生まれた型で、個人の日報・週報や、学びを積み上げたいときに使いやすい。「問題」の列がないので、責める空気になりにくい。

**落とし穴** ：困りごとが表に出にくいので、チームの課題を洗い出したい回には KPT などと使い分けます。

**タイムライン**

#### 1 週目

設計レビュー

API 仕様が確定

#### 2 週目

メンバーが 1 人病欠

#### 3 週目

本番障害（2 時間）

デプロイ手順を改善

#### 4 週目

リリース

**向いている場面** ：長い期間やプロジェクト全体、障害のあとなど、出来事の順番と因果を共有したいとき。「データを収集する」段階で使い、その上に気分の上下を線で描き足すこともあります。

**落とし穴** ：準備と時間がかかる。毎回の短いふりかえりには重すぎます。

**帆船（Sailboat / Speedboat）**

#### 風

進めてくれたもの

自動テストが厚い

#### 錨

足を引っ張ったもの

手作業のリリース

#### 岩

この先のリスク

ライブラリのサポート終了

#### 島

目指すゴール

月 4 回リリースできる

**向いている場面** ：目標に対して、追い風・妨げ・リスクをまとめて眺めたいとき。絵を描くので、マンネリ打破にも使えます。

**落とし穴** ：比喩の解釈が人によってずれるので、最初に各要素の意味を決めておきます。

### どれを選ぶか

| こんなとき | 合いやすい型 | 理由 |
| --- | --- | --- |
| 初めてのふりかえり・毎回の定番 | KPT | 枠が 3 つで説明が要らず、Try まで一続きで決められる |
| すぐ行動を変えたい | Start / Stop / Continue | 付箋がそのまま行動の形で出てくる |
| プロジェクトの区切りで学びを残したい | 4Ls・YWT | 「学んだ・わかった」の列がある |
| つらい期間のあとで空気が重い | Mad / Sad / Glad | 気持ちを先に出してから原因に進める |
| 障害や長期プロジェクトを振り返る | タイムライン | 出来事の順番と因果を全員で揃えられる |
| 目標に向けた妨げとリスクを見たい | 帆船 | ゴールとリスクを同じ絵に置ける |
| 議題が人によってばらばら・何を話すかから決めたい | リーンコーヒー | 参加者が議題を出し、投票で順番を決める（下で説明） |
| 毎回同じ型で付箋が出なくなってきた | 型を変える | 問いが変わると、見えていなかったことが出てくる |

## リーンコーヒー

リーンコーヒー (Lean Coffee) は、Jim Benson と Jeremy Lightsmith が 2009 年にシアトルで始めた、 **議題を事前に決めない** 会議の形式です。参加者がその場で話したいことを出し、投票で順番を決め、短い時間で区切って進めます。進行の様子を 3 列のカンバンボードで見せるのが特徴です。ふりかえりの代わりにも、勉強会や定例にも使えます。

#### To Discuss（話す予定）

テストが遅い ●●●

オンボーディング資料 ●●

定例の時間帯 ●

#### Discussing（話し中）

レビュー待ちが長い ●●●●●

残り 2:30

#### Discussed（話した）

デプロイの曜日 ●●●●

→ 金曜はやめる

今話している列・残り時間 ● は集まった票

1. **ボードを用意する** To Discuss・Discussing・Discussed の 3 列。決まったことを書く Actions 列を足すことも多い
2. **議題を出す** 各自が話したいことを付箋に 1 枚 1 件で書く（数分）。書いた人が一言ずつ説明し、似たものはまとめる
3. **投票する** 1 人 2〜3 票のドット投票。同じ議題に複数票を入れてもよい。票の多い順に並べる
4. **時間を区切って話す** いちばん上の議題を Discussing に移し、タイマー（5〜8 分が目安）を回す
5. **続けるかを決める** 時間が来たら親指で投票（上 = 続ける、横 = どちらでも、下 = 次へ）。続けるなら短い延長、そうでなければ Discussed に移して次へ

4 の手順が「今ここ」で、ボードの Discussing の列に当たります。リーンコーヒーは議題を決める・話す部分が強い一方で、 **行動を決める段階が手薄** になりがちです。ふりかえりとして使うなら、最後に Actions 列を見直して担当と期限を決める時間を取ります。

## 回し続けるコツ

| よくある詰まり | 手当て |
| --- | --- |
| Try が毎回たくさん出るが、どれも実行されない | 1〜2 個に絞り、担当と期限を決める。次回は前回の Try の確認から始める。スプリントバックログに入れて、普段の作業と同じに扱う |
| 一部の人しか話さない | 付箋に黙って書く時間を先に取る。順番に一言ずつ話す。上の立場の人は最後に話す |
| 同じ問題が毎回出る | チームで変えられることか確かめる。外の要因なら、誰に何を頼むかを Try にする |
| 犯人探しの空気になる | 最初に最優先指令（Prime Directive）を確かめる。付箋は人ではなく出来事や仕組みについて書く |
| マンネリで付箋が減ってきた | 型を変える。進行役を持ち回りにする |

## よくある誤解

✗ 誤解: ふりかえりは失敗した点を反省する会

✓ 正しくは: 見るのは失敗だけではなく、うまくいったことも含めたやり方全体です。目的は次の期間に試すことを決めることで、反省の言葉を集めることではありません。

✗ 誤解: 改善案は多く出すほど良いふりかえりだ

✓ 正しくは: 実行されない改善案は、次のふりかえりで同じ問題として戻ってくるだけです。1〜2 個に絞って確実に試し、次回に効果を確かめるほうが、改善が積み上がります。

✗ 誤解: KPT さえやっていればふりかえりになる

✓ 正しくは: KPT は事実を集めて行動を決めるための枠で、場を設定することや原因を掘り下げることは自分で補う必要があります。前回の Try の確認を飛ばすと、決めたことが検証されないままになります。

✗ 誤解: リーンコーヒーは議題のない雑談

✓ 正しくは: 議題を事前に決めないだけで、議題出し・投票・タイムボックス・続けるかの投票という決まった手順があります。限られた時間で、参加者がいちばん話したいことから順に扱うための仕組みです。
