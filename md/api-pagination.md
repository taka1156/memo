# ページネーション

オフセットとカーソル ― 一覧を分けて返すときの決めごと

**ざっくり言うと**

- 一覧を分けて返す方法は、 **何件飛ばすか** を指すオフセットと、 **最後に見た行の続き** を指すキーセット（カーソル）の 2 系統。
- オフセットは深いページほど飛ばす行を読むので遅くなり、途中で行が増減すると重複や抜けが出る。
- ページ番号で飛びたい管理画面はオフセット、フィード・無限スクロール・全件の取得はカーソルを選ぶ。

## 3 つの方式

| 方式 | リクエストの例 | SQL のイメージ | 向いている所 |
| --- | --- | --- | --- |
| オフセット（ページ番号） | `?page=3&per_page=20` | `ORDER BY id DESC LIMIT 20 OFFSET 40` | 総ページ数を出し、任意のページに飛ぶ画面 |
| キーセット（シーク法） | `?before_id=1234&limit=20` | `WHERE id < 1234 ORDER BY id DESC LIMIT 20` | 「次へ」だけでよい一覧。内部実装として |
| カーソル | `?after=eyJpZCI6MTIzNH0` | 中身はキーセットと同じ。続きの位置を 不透明な文字列 に包んで渡す | 公開 API・フィード・無限スクロール |

カーソルはキーセットの「続きの位置」をクライアントに意味を持たせずに渡す形。中身（並び順の列や値）を後から変えても、クライアントは文字列をそのまま返すだけなので壊れない。

## 深いページが遅くなる理由

`OFFSET 100000` は「10 万行を飛ばす」ではなく「10 万行を **読んでから捨てる** 」。インデックスがあっても、飛ばす行を数えるためにたどる必要がある。キーセットは `WHERE id < ?` でインデックスの途中に直接降りるので、何ページ目でも読む量は 1 ページ分で済む。

オフセット（斜線） キーセット

ページ番号 1

オフセット

読む行: 20 キーセット

読む行: 20

1 ページ 20 件・最大 10 万行として、読み飛ばしを含めて読む行数の比較。キーセットはインデックスを根から降りる分（数ブロック）が加わるだけで、ページ番号によらない。

## 途中で行が増えると重複・抜けが出る

新しい順の一覧を 3 件ずつ見ている途中で、新しい記事が 1 件増えたときの動き。

1. 1 ページ目
2. 記事が増える
3. 2 ページ目

新しく増えた行 重複して返った行 続きから正しく返った行

（元のページで操作できます → https://memo.taka1156.site/api-pagination.html#drift）

### オフセット `OFFSET 0 LIMIT 3`

#10 #9 #8

#10・#9・#8 を表示。

### カーソル（最初のページ）

#10 #9 #8

同じ 3 件。次のカーソルとして「#8 の続き」を受け取る。

読んでいるあいだに **#11** が投稿される。テーブル全体の並びは次のようになる。

#11 #10 #9 #8 #7 #6 #5 …

先頭に 1 件増えたので、それより後ろの行は 1 つずつ後ろにずれる。

### オフセット `OFFSET 3 LIMIT 3`

#8 #7 #6

4 件目からを返すので、1 ページ目で見た #8 がもう一度出る（重複）。行が削除されたときは逆に 1 件抜ける。

### カーソル `WHERE id < 8 LIMIT 3`

#7 #6 #5

「#8 より古いもの」を返すので、前に増えた行の影響を受けない。#11 は次に先頭から読み直したときに出る。

## キーセットの書き方：並び順を一意にする

並び順の列が重複しうる（ `created_at` が同じ時刻の行がある）と、境目の行を飛ばしたり二度返したりする。 **一意な列（主キー）を最後に足して** 並びを一意にし、その組で比較する。

```
-- 並び順: 新しい順。created_at が同じなら id で決める
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 21;              -- 1 件多く取り、21 件目があれば「次がある」

-- 行値の比較が使えない・インデックスが効かない DB では展開して書く
WHERE created_at < :last_created_at
   OR (created_at = :last_created_at AND id < :last_id)

-- 並びと同じ順の複合インデックスを作る
CREATE INDEX posts_created_id ON posts (created_at DESC, id DESC);
```

- **インデックスは並び順と同じ列の組で作る。** これがないと結局全件を並べ替えることになり、キーセットの利点が消える。
- ** `LIMIT n+1` で次の有無を決める。** 総件数を数えずに「次へ」を出すか決められる。
- **NULL を含む列で並べない。** NULL は比較が成り立たないので、続きの条件から漏れる。並べるなら NULL を値に置き換えた列を使う。

## カーソルの作り方と返し方

1. **最後の行の並び順の値を集める** 例: `{"created_at":"2026-11-19T09:00:00Z","id":1234}` 。並びの向きやフィルタ条件も入れておくと、別の条件のカーソルを取り違えたときに弾ける。
2. **不透明な文字列にする** Base64URL などで符号化する。中身を推測・改変されたくなければ署名（HMAC）を付けるか、サーバー側に保存して ID だけ渡す。
3. **レスポンスに次のカーソルを入れる** 次がなければ `null` にする。クライアントはそれを次のリクエストにそのまま付ける。

```
GET /posts?limit=20&after=eyJjcmVhdGVkX2F0Ijoi...

{
  "items": [ ... 20 件 ... ],
  "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0x...",   // 最後のページなら null
  "has_more": true
}
```

同じ情報を HTTP の `Link` ヘッダー（ `rel="next"` ）で返す API もある（GitHub の REST API など）。GraphQL では、Relay の Connection の形（ `edges` ・ `pageInfo.endCursor` ・ `pageInfo.hasNextPage` ）が定番。

### 総件数は出すか

大きなテーブルの `COUNT(*)` は全件をたどるので、毎回出すと一覧そのものより重くなることがある。カーソル方式では総件数を返さず `has_more` だけにするか、「1,000 件以上」のような概数にするのが普通。どうしても要る画面だけ別の API にして、キャッシュする。

## 選び方

| 場面 | 選ぶ方式 | 理由 |
| --- | --- | --- |
| 管理画面の表（ページ番号で 5 ページ目に飛ぶ・総数を出す） | オフセット | 任意のページに飛べるのはオフセットだけ。件数が少ないなら遅さも問題にならない |
| SNS のタイムライン・無限スクロール | カーソル | 新しい投稿が頻繁に増えても重複・抜けがない |
| 公開 API の一覧 | カーソル | 深いページでも速く、並び順の実装を後から変えてもクライアントが壊れない |
| バッチで全件を取り出す・同期 | キーセット | 何万ページ目でも 1 ページ分の重さで進む。途中で止めても最後の値から再開できる |
| 検索結果（関連度順） | 上限つきのオフセットが多い | 関連度は一意な値で並べにくい。深いページは見られないので上限（例: 1,000 件まで）を設ける |

## よくある誤解

✗ 誤解: OFFSET はインデックスがあれば何ページ目でも速い

✓ 正しくは: インデックスで並び順の先頭は速く見つかるが、OFFSET の分だけ行をたどって捨てる処理は残る。100 ページ目は 1 ページ目のおよそ 100 倍の行を読む。

✗ 誤解: カーソル方式でも、ページ番号を指定して途中のページに飛べる

✓ 正しくは: カーソルは「ある行の続き」しか指せないので、5 ページ目に直接は飛べない。飛びたい画面ではオフセットを使うか、日付などの値で絞り込んでから続きを読む UI にする。

✗ 誤解: 作成日時で並べるなら、カーソルには作成日時だけ入れれば十分

✓ 正しくは: 同じ時刻の行が複数あると、境目の行を飛ばしたり二度返したりする。主キーなど一意な列を並び順の最後に足し、カーソルにもその値を入れる。

✗ 誤解: カーソルは Base64 で符号化してあるので、中身は利用者に読まれない

✓ 正しくは: Base64 は誰でも元に戻せる符号化で、暗号化ではない。改変されると困る値が入るなら、署名を付けるか、サーバー側で権限を確かめ直す。
