**ざっくり言うと**

- ルーターではコントロールプレーンが止まると、時間がたつと通信も止まる。AWS では追加と変更ができなくなるだけ。
- 違いは、データプレーンがコントロールプレーンなしで動き続けるように作られているか（静的安定性）にある。
- それでも隠れた依存があると影響が広がる。復旧手順はデータプレーンだけで済むようにしておく。

用語の意味（狭義・広義、何がどちらのプレーンか）は [コントロールプレーンとデータプレーン](https://memo.taka1156.site/md/control-data-plane.md) で扱う。

## 静的安定性（static stability）

AWS は、作ったあとのリソースへのデータプレーンのアクセスがコントロールプレーンに依存しないことを「静的安定性」と呼んでいる。作る・変える・消すができなくなっても、既存のリソースは使い続けられる、という性質。AWS 自身のサービスの設計方針であり、利用者が自分のシステムに取り入れるパターンでもある。

1. **余裕を先に持っておく** AZ が 1 つ壊れたらオートスケールで増やす、ではなく、残りの AZ だけでさばける台数を最初から動かしておく（コストは増える）。
2. **復旧の手順でコントロールプレーンを呼ばない** 障害のときに新しく作る・設定を変える手順は、コントロールプレーンが止まっていると使えない。必要なものは事前に作っておく。
3. **データプレーンで切り替える** フェイルオーバーは、ヘルスチェックなどデータプレーンの仕組みで自動に行う。

### 狭義での延命策

ルーターでも、コントロールプレーンが一時的に止まる場面（ソフトウェアの再起動など）への手当てはある。BGP の Graceful Restart（RFC 4724）は、再起動中も転送の状態を保てることを相手に伝え、相手に経路をしばらく残してもらう仕組み。ただし猶予を延ばすだけで、戻らなければ結局は経路が取り消される。

## 事例：AWS バージニア北部（us-east-1）

### グローバルサービスのコントロールプレーンの場所

「グローバル」とされる AWS のサービスにも、コントロールプレーンは 1 か所にあるものが多い。データプレーンは各リージョンや世界中の拠点（PoP）に分散している。

| サービス | コントロールプレーン | データプレーン |
| --- | --- | --- |
| IAM | `us-east-1` | 各リージョン |
| AWS Organizations | `us-east-1` | （データプレーンを持たない） |
| AWS アカウント管理 | `us-east-1` | 各リージョン |
| Route 53 | `us-east-1` （パブリックのレコード変更だけ `us-west-2` に待機用あり） | 世界中の PoP と各リージョン |
| CloudFront（と CloudFront 用の ACM・WAF） | `us-east-1` | 世界中の PoP |
| Shield Advanced | `us-east-1` | 各リージョンと世界中の PoP |
| Global Accelerator | `us-west-2` | 世界中の PoP |
| Application Recovery Controller（ARC。旧称 Route 53 ARC） | `us-west-2` | 各リージョン |

設計どおりなら、us-east-1 のコントロールプレーンが止まっても、世界中で動いているものは動き続け、これらのサービスの「変更」だけができなくなる。

### 2025 年 10 月の障害で起きたこと

2025 年 10 月 19〜20 日（米国太平洋時間）、DynamoDB の DNS を管理する自動化の競合状態で、リージョンのエンドポイント `dynamodb.us-east-1.amazonaws.com` の DNS レコードが空になった。そこから EC2 の起動、Network Load Balancer へと影響が広がった。

1. **静的安定性は効いた** 障害の前から動いていた EC2 インスタンスは正常なままだった。止まったのは新しい起動や API 呼び出し。
2. **us-east-1 のデータプレーンが止まった** DynamoDB への新しい接続ができなくなり、それに頼る多くの AWS サービスと利用者のアプリが止まった。
3. **隠れた依存で他のリージョンにも出た** ルート認証情報や signin.aws.amazon.com 経由のフェデレーションで、他のリージョンでもコンソールにサインインできなくなった。Redshift では、us-east-1 の IAM API に頼る不具合のため、IAM ユーザーの認証情報を使うクエリが全リージョンで失敗した。

番号の色は、緑が設計どおりに守られた所、赤が影響が出た所。世界中で同時に障害が見えたのは、コントロールプレーンが止まったからというより、us-east-1 のデータプレーンに頼るものが多く（us-east-1 で動かしているアプリそのものと、他のリージョンからの隠れた依存）、そこが止まったから。障害を報告するサイトで、関係のなさそうな多くのサービスに同じ時刻に山ができるのはこのため。

### Route 53 で考える：どの操作が止まるか

| 操作 | プレーン | us-east-1 のコントロールプレーンが止まると |
| --- | --- | --- |
| レコードを作る・変える・消す | コントロールプレーン | すぐにはできない（パブリックホストゾーンで accelerated recovery を事前に有効にしてあれば、約 60 分後から `us-west-2` 経由でできる） |
| ホストゾーンの作成・削除、ヘルスチェックの作成・変更 | コントロールプレーン | できない |
| DNS の問い合わせに答える | データプレーン | 動き続ける |
| 作ってあるヘルスチェックを実行し、結果で応答を切り替える | データプレーン | 動き続ける |

なので「障害が起きたらレコードを書き換えて別の地域へ切り替える」手順は、肝心なときにすぐには使えない。2025 年 12 月からは、パブリックホストゾーンで accelerated recovery を事前に有効にしておけば、us-east-1 の障害を AWS が検知してから約 60 分で us-west-2 からレコードを変えられる（障害が始まってから有効にはできない）。すぐに切り替えたいなら、ヘルスチェックとフェイルオーバーのレコードを事前に作っておき、データプレーンに任せる。

ELB・RDS・CloudFront など、作るときに Route 53 のレコードを作るサービスの多くは、AWS 内部の同じ仕組みで障害中も作成を続けられる。一方、API Gateway・EKS・Lambda の関数 URL などは us-east-1 の Route 53 コントロールプレーンに頼ったまま。

## 設計・運用で気をつけること

1. **依存の裏にあるリージョンを知っておく** 自分のリージョンが無事でも、使っているグローバルサービスや外部の SaaS が us-east-1 に頼っていることがある。
2. **復旧の手順を「作る・変える」なしで書く** フェイルオーバー先の容量・DNS レコード・ヘルスチェックは平常時に作っておく。
3. **障害時に変更を急がない** コントロールプレーンが不安定なときに設定を変えると、途中で止まって状態がずれることがある。
4. **サインインと権限の非常口を用意する** コンソールへのサインイン経路が止まった場合に、どう作業するかを決めておく。

## よくある誤解

✗ 誤解: コントロールプレーンが止まったときの影響は、どの文脈でも同じだ

✓ 正しくは: ルーターでは時間がたつと経路が取り消されて通信が止まるが、静的安定性を持つクラウドのサービスでは追加と変更ができなくなるだけ。どちらの意味の話かで結論が逆になる。

✗ 誤解: グローバルサービスは、どのリージョンにも依存していない

✓ 正しくは: IAM・Route 53・CloudFront などは、コントロールプレーンが us-east-1 にある。データプレーンは分散しているので動き続けるが、変更は us-east-1 に頼る。

✗ 誤解: 障害時は、Route 53 のレコードを書き換えて切り替えればよい

✓ 正しくは: レコードの変更はコントロールプレーンの操作なので、us-east-1 が不調だとすぐにはできない（accelerated recovery を有効にしていても、再開まで約 60 分かかる）。フェイルオーバーは事前に作ったヘルスチェックで自動に行う。

✗ 誤解: マルチ AZ にしておけば、AZ が落ちてもオートスケールで補えるので余裕は要らない

✓ 正しくは: 台数を増やすのはコントロールプレーンの仕事で、障害時には遅れたり失敗したりする。残りの AZ だけでさばける容量を先に持っておくのが静的安定性の考え方。
