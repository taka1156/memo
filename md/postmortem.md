ブレームレスな障害のふりかえりと、5 Whys の使いどころ

**ざっくり言うと**

- ポストモーテムは、障害のあとに影響・経緯・原因・再発防止策を文書にまとめ、組織で学ぶためのふりかえり。
- 人を責めず「なぜその判断が当時は正しく見えたか」を問うと、事実が集まり、仕組みの弱点が見つかる。
- 原因は 1 本の鎖に絞らず、アクションは「気をつける」ではなく担当と期限のある仕組みの変更にする。

## ポストモーテムとは

ポストモーテム (postmortem) は、障害（インシデント）が収まったあとに書く **ふりかえりの文書** と、それを読み合う場のことです。元は「検死」の意味ですが、IT の運用では「何が起き、なぜ起き、次にどうするか」を記録して、同じ障害をくり返さないために使います。Etsy の John Allspaw による 2012 年の記事や、Google の SRE 本の「ポストモーテムの文化」の章などを通じて、IT 業界に広まりました。

全部の障害で書くと続かないので、 **書く条件を先に決めておく** のが普通です。SRE 本では次のような例が挙がっています。

- 利用者から見える停止や劣化が、決めた基準を超えた
- データが失われた
- 当番の人が手で介入した（ロールバック・切り替えなど）
- 解決までの時間が、決めた基準を超えた
- 監視が気づかず、人が見つけた

条件に当てはまらなくても、関係者が書きたいと言えば書けるようにしておきます。

## 障害からポストモーテムまで

1. **検知と対応** まず影響を止める（緩和）。原因の追究は後回しにして、ロールバックや切り替えで利用者への影響を小さくする。対応中のやりとりは時刻つきで残す
2. **下書き** 記憶が新しいうちに、対応した人が中心になって事実（時刻・数字・判断）を書く。チャットやダッシュボードのリンクを貼る
3. **レビュー** 関係者で読み合い、抜けている事実、原因の掘り方、アクションの妥当さを確かめる。責める言葉が混ざっていないかもここで見る
4. **アクションの追跡** 再発防止策を担当と期限つきでバックログに入れ、普段の作業と同じく完了まで追う
5. **共有** 関係のないチームも読めるところに置く。似た弱点を持つ別のシステムで役に立つ

通常のスプリントのふりかえりが「チームの進め方」を見直す場なのに対し、ポストモーテムは **1 つの出来事を深く掘り、システムと組織の弱点** を見つける場です。

## ブレームレス：人ではなく条件を見る

ブレームレス (blameless、非難しない) は、障害のきっかけになった操作をした人を責めないという約束です。責められると分かっていると、人は自分に不利な事実を話さなくなり、いちばん大事な情報が集まりません。

代わりに、 **その人がその時点で知っていたこと・見えていたものから考えると、なぜその判断が妥当に見えたのか** を問います。同じ立場なら別の人も同じことをした、と分かれば、直すべきは人ではなく、誤りを招いた画面・手順・権限・情報の出し方です。

責める書き方 田中さんが確認を怠り、本番に誤った設定を出した。

ブレームレスな書き方 設定の差分はレビュー画面に表示されず、検証環境では別のファイルが上書きしていたため、誤りに気づける手がかりがなかった。

責める書き方 当番がアラートを見落とした。

ブレームレスな書き方 同じ時間帯に重要度の低いアラートが 40 件出ており、今回のものは見た目で区別できなかった。

責める書き方 手順を守らなかったのが原因。

ブレームレスな書き方 手順書は 2 年前の構成のままで、今の画面とは項目名が違っていた。

人の注意不足で終わっている 誤りを招いた条件まで書いている

ブレームレスは「誰も責任を取らない」ことではありません。名前を出して状況を説明するのはかまいませんし、アクションの担当ははっきり決めます。変わるのは、 **責任を「処罰」ではなく「改善を進める役目」として扱う** ことです。人の誤りを潜在的な条件の表れとして見る考え方は、 [層を重ねて守る](https://memo.taka1156.site/md/layered-defense.md) のスイスチーズモデルとも共通します。

## 書く項目

書式はチームで 1 つに決めておくと、書く人も読む人も迷いません。よく使われる項目は次のとおりです。

| 項目 | 書くこと | ありがちな失敗 |
| --- | --- | --- |
| 要約 | 何が・いつ・どのくらいの間・誰に影響したかを 2〜3 文で | 原因の細部から書き始め、影響が分からない |
| 影響 | 失敗したリクエスト数、影響した利用者数、売上・SLO への影響など数字で | 「一部のユーザー」だけで、規模が分からない |
| タイムライン | 発生・検知・判断・緩和・復旧を時刻つきで。誰が何を見て何をしたか | あとから分かった事実を、その時点で分かっていたように書く |
| 原因と寄与要因 | きっかけと、それが障害にまで育った条件（検知の遅れ・影響の広がり方） | 原因を 1 つに絞り、「人為的ミス」で止める |
| うまくいったこと | 早く気づけた、すぐ戻せた、など残したい仕組み | 悪かった点だけを並べ、効いた対策が次に消される |
| 運が良かったこと | たまたま被害が小さかった理由（深夜だった、詳しい人が居合わせた） | 書かずに済ませ、次は運が悪くて大きな被害になる |
| アクション | 何を・誰が・いつまでに。種類（防ぐ・早く気づく・影響を小さくする）も | 担当と期限がなく、誰も手を付けない |

### タイムラインの例

設定の変更でキャッシュが効かなくなり、データベースが過負荷になった架空の障害です。どこに時間がかかったかを区間で見ると、改善の的が絞れます。

9分

13分

7分

14:02 14:31

影響が出ているのに誰も気づいていない 気づいて対応している 緩和して元に戻りつつある

1. 14:02 設定の変更をデプロイ。本番だけキャッシュの有効期限が 0（キャッシュしない）になる 発生
2. 14:05 データベースの CPU 使用率が 90% を超える（アラートの対象外）
3. 14:11 エラー率のアラートが鳴る 検知
4. 14:15 インシデントとして宣言し、指揮をとる人を決める
5. 14:24 直前のデプロイを疑い、設定をロールバック 緩和
6. 14:31 エラー率が普段の値に戻る 復旧

この例では、最初の 9 分は監視が気づいていません。原因（設定の誤り）を防ぐ策と同じくらい、 **「なぜ 9 分気づけなかったか」** を問う価値があります。

## 5 Whys の使いどころと落とし穴

5 Whys（なぜなぜ分析）は、起きたことに「なぜ」を重ねて原因を掘る方法で、トヨタ生産方式から広まりました。手軽で、表面の原因で止まらないようにする助けになります。ただし、1 本の鎖でたどると、 **最後が人の注意不足に行き着きやすい** という落とし穴があります。

1 本の鎖

問いを分ける

1. エラーが増えた → データベースが過負荷になったから
2. 過負荷になった → キャッシュが効かず、全部の読み込みが届いたから
3. キャッシュが効かなかった → 設定の有効期限が 0 になっていたから
4. 0 になっていた → 担当者が確認を怠ったから
5. 結論：「今後は確認を徹底する」

4 つ目で人の注意に行き着き、そこで止まっている。この結論では、同じ条件がそろえば別の人が同じ誤りをする。

（元のページで操作できます → https://memo.taka1156.site/postmortem.html#five-whys）

#### なぜ起きたか

1. 本番だけ有効期限が 0 になった
2. 設定ファイルの読み込み順が変わり、既定値の 0 が使われた
3. 検証環境は別のファイルで上書きしており、差が出なかった

#### なぜ気づくのが遅れたか

1. 9 分間アラートが鳴らなかった
2. エラー率しか見ておらず、データベースの CPU は対象外だった
3. 予兆の指標をアラートにする基準がなかった

#### なぜ影響が広がったか

1. 全利用者に一度に影響した
2. 設定の変更はコードと違い、段階的に出していなかった
3. 設定の変更を小さく出す仕組みがなかった

起きた理由・気づくのが遅れた理由・広がった理由に分けると、どれも仕組みで直せる条件にたどり着く。

人の注意で止まった「なぜ」 仕組みで直せる条件にたどり着いた「なぜ」

- 「5 回」は目安で、回数に意味はない。直せる条件に届いたら止めてよい。
- 複雑なシステムの障害は、いくつもの条件が重なって起きるのが普通。原因を 1 つに絞らず、 **寄与要因** (contributing factors) として並べる。
- 「人為的ミス」が出てきたら、それは答えではなく、 **次の「なぜ」の出発点** として扱う。

## アクションの書き方

アクションは、 **同じ条件がそろっても障害にならない、または小さく済む** ように仕組みを変えるものにします。人に注意を求める対策は、書いた直後は効いても、人が入れ替わったり忙しくなったりすると効かなくなります。

| 種類 | 弱いアクション | 強いアクション |
| --- | --- | --- |
| 起きにくくする | 設定は慎重に変える | 有効期限が 0 の設定を CI のチェックでエラーにする（担当: 基盤チーム、期限: 12/5） |
| 早く気づく | ダッシュボードをこまめに見る | データベースの CPU が 80% を 5 分超えたらアラートにする（担当: 当番の責任者、期限: 11/30） |
| 影響を小さくする | 何かあればすぐ戻す | 設定の変更も 5% の利用者から段階的に出す（担当: 基盤チーム、期限: 12/19） |
| 直しやすくする | 手順書を見直す | 設定のロールバックを 1 コマンドにし、手順書から呼ぶ（担当: 当番の責任者、期限: 12/12） |

アクションは多すぎると終わりません。効果の大きいものに絞り、残りは「やらない」と決めた理由ごと記録します。完了したかどうかを、次のレビューや定例で確かめます。

## よくある誤解

✗ 誤解: ブレームレスにすると誰も責任を取らなくなる

✓ 正しくは: ブレームレスでも、アクションの担当と期限ははっきり決めます。やめるのは、誤りをした人を処罰したり、評価を下げたりすることです。責めないことで事実が集まり、責任を「仕組みを直す役目」として果たせるようになります。

✗ 誤解: 5 Whys で「なぜ」を 5 回くり返せば、ただ 1 つの根本原因にたどり着ける

✓ 正しくは: 回数は目安で、障害の多くはいくつもの条件が重なって起きます。1 本の鎖だけでたどると、たどる人の思い込みで道筋が決まり、人の注意不足で止まりやすくなります。起きた理由・気づくのが遅れた理由・広がった理由のように問いを分け、寄与要因を並べます。

✗ 誤解: ポストモーテムは大きな障害のときだけ書けばよい

✓ 正しくは: 大きな障害は、小さな障害やヒヤリとした出来事（ニアミス）と同じ弱点から起きることが多くあります。書く条件を決めたうえで、条件に当てはまらない出来事も短い形で残しておくと、大きくなる前に弱点を直せます。

✗ 誤解: 原因が分かるまでは、ロールバックなどの対応をしない方がよい

✓ 正しくは: 障害の最中は、原因の追究より影響を止めることを優先します。原因を調べるための情報（ログ・時刻・画面）は残しつつ、まず戻すか切り替えます。原因の分析はポストモーテムで落ち着いて行います。
