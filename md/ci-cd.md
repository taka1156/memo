パイプライン設計と、ワークフローを安全に速く書くためのポイント

**ざっくり言うと**

- **CI** は push や PR のたびに自動でビルド・テストし、壊れた変更をすぐ見つける仕組み。 **CD** は通った成果物を自動でデプロイ（またはデプロイ可能な状態に）する仕組み。
- GitHub Actions は **ワークフロー（YAML）→ ジョブ（別々のマシンで並列）→ ステップ（順番に実行）** の 3 段構造。
- CI は「リポジトリを書き換えられる権限」と「本番の鍵」を扱う場所。 **権限は最小に、外部の Action は固定し、長期の鍵は置かない** 。

## パイプラインの全体像

**静的チェック** lint・型チェック・フォーマット。数十秒で落ちる場所を先に

**テスト** 単体 → 結合。並列化しやすい

**ビルド** 成果物（イメージ・バンドル）を 1 回だけ作る

**ステージング** 同じ成果物をデプロイし E2E・スモークテスト

**承認** 必要なら人が確認

**本番** 段階的に切り替え、監視して戻せるように

CI（毎回） CD ゲート

- **速く失敗する順に並べる** 。1 分で落ちる lint が 10 分の E2E の後ろにあると、待ち時間が無駄になる。
- **一度ビルドしたものを各環境に流す** 。環境ごとにビルドし直すと「ステージングで試したもの」と「本番に出したもの」が別物になる。環境差は設定（環境変数）で吸収する。
- PR では CI まで、 `main` へのマージで CD まで、という分け方が多い。ブランチ保護で **CI が通らないとマージできない** ようにする。
- Continuous **Delivery** は「いつでも出せる状態まで自動」、Continuous **Deployment** は「本番反映まで自動」。

## GitHub Actions の構造

workflow .github/workflows/ci.yml — `on:` のイベントで起動

job: test runner A

uses: actions/checkout

uses: actions/setup-node

run: npm ci

run: npm test

job: deploy runner B · needs: test

uses: actions/checkout

run: ./deploy.sh

- **ジョブごとに新しいマシン（ランナー）** 。ファイルは引き継がれないので、受け渡しは artifact やキャッシュで行う。 `needs` が無いジョブ同士は並列に動く。
- **ステップは同じマシンで順に** 実行され、ファイルは共有される。 `uses` は再利用部品（Action）、 `run` はシェルコマンド。

### よく使うトリガー（on:）

| イベント | いつ | 使いどころ |
| --- | --- | --- |
| push | ブランチ・タグへの push | main への反映でデプロイ。 `branches` / `tags` / `paths` で絞る |
| pull_request | PR の作成・更新 | CI。フォークからの PR ではシークレットが渡らず、トークンは読み取り専用 |
| workflow_dispatch | 画面や API から手動で | 手動デプロイ、再実行用。 `inputs` で引数を受け取れる |
| schedule | cron（既定は UTC。 `timezone:` で IANA タイムゾーンを指定可） | 夜間の依存関係チェック・定期バッチ。時刻ぴったりには動かないことがある |
| release | リリースの作成・公開・編集・削除など | パッケージの公開。公開時だけ動かすなら `types: [published]` |

## 速くする

CACHE

依存関係のダウンロードを再利用する。 `setup-node` の `cache: npm` のように、言語ごとの setup Action に組み込まれていることが多い。キーはロックファイルのハッシュ。

PARALLEL

独立したジョブは `needs` を付けずに並列に。 `matrix` で OS・バージョン違いを並列に。大きなテストは分割（シャーディング）する。

SKIP

`paths` / `paths-ignore` でドキュメントだけの変更では重いジョブを動かさない。モノレポでは変更のあったパッケージだけ。

CANCEL

`concurrency` と `cancel-in-progress` で、同じ PR に新しい push が来たら古い実行を止める。デプロイ側では止めずに直列化する。

## シークレットと権限

| 危険 | 何が起きるか | 対策 |
| --- | --- | --- |
| GITHUB_TOKEN の権限が広い | 侵害されたステップがリポジトリに push・リリース改ざんできる | トップで `permissions: contents: read` 、必要なジョブだけ追加 |
| サードパーティ Action をタグで参照 | タグは付け替えられる。乗っ取られると次の実行で悪意あるコードが動く | コミット SHA で固定 し、Dependabot で更新 PR を受ける |
| `run:` に `${{ github.event.pull_request.title }}` を直接展開 | PR タイトルに仕込んだシェルコマンドが実行される（スクリプトインジェクション） | `env:` で環境変数に入れてから `"$TITLE"` で参照 |
| `pull_request_target` でフォークのコードを checkout | シークレットと書き込み権限がある状態で他人のコードが動く | 原則使わない。使うならフォークのコードを実行しない。actions/checkout はフォークの checkout を既定で拒否し、2026 年 12 月 2 日からは公開リポジトリで `pull_request_target` 自体が既定でブロックされる（使うにはイベントポリシーで明示的に許可） |
| クラウドの長期アクセスキーを Secrets に保存 | 漏れると無期限に使われる | OIDC （ `id-token: write` ）で実行ごとに短期の認証情報をもらう |

- Secrets はログに出るとマスクされるが、加工（Base64 化など）された値はマスクされない。 `echo` しない。
- **Environments** を使うと、本番用シークレットを特定ブランチ・承認者付きのジョブにだけ渡せる。

## デプロイ戦略

カナリア

プレビュー

インスタンスを少しずつ新バージョンに入れ替える。追加の環境が要らないが、入れ替え中は **新旧が混在** する（DB スキーマや API の互換性が必要）。Kubernetes の Deployment の既定。

新環境（グリーン）を丸ごと用意し、確認後にトラフィックを一気に切り替える。 **戻すのも切り替えるだけ** で速い。一時的に 2 倍のリソースが要る。

まず数 % のトラフィックだけを新バージョンへ流し、エラー率・レイテンシを見ながら広げる。問題の影響範囲を小さくできる。 **監視の仕組みが前提** 。

PR ごとに一時的な環境（URL）を作って、レビュー時に実際の画面で確認する。Cloudflare Pages や Vercel などが標準で提供する。不要になった環境は、サービスの保持期間で消えるか、PR のクローズ時に自分で削除する。

- どの方式でも、 **DB マイグレーションは新旧両方のコードで動く形** にする（列の追加 → コード切り替え → 古い列の削除、と分ける）。
- 「戻す手順」も CD に入れておく。前の成果物を再デプロイするだけで戻れるのが理想。

## よくある誤解

✗ 誤解: CI が緑ならデプロイしても安全

✓ 正しくは: テストが書かれている範囲で壊れていないだけ。段階的な展開と監視・ロールバックと組み合わせる。

✗ 誤解: `actions/xxx@v5` のようにタグを書けば、中身は固定されている

✓ 正しくは: タグは後から別のコミットに付け替えられる。固定したいならコミット SHA を書く。推移的な依存まで固定できる workflow lockfile（ `.github/workflows/actions.lock` 。2026 年 10 月にプレビューを経て一般提供）も使える。

✗ 誤解: Secrets に入れれば、ワークフローのどこからでも安全に使える

✓ 正しくは: そのステップで動くコード（依存パッケージや外部 Action も含む）からは読める。渡すジョブとステップを絞る。
