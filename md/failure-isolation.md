**ざっくり言うと**

- 依存先が 1 つ遅くなるだけで、待ちが積み上がって呼び出し側まで止まり、障害が連鎖する。
- バルクヘッドで資源を区切り、サーキットブレーカーで呼ぶのをやめ、縮退運転で中心の機能だけは返し続ける。
- どれも前提はタイムアウトで、代わりの動きは平常時から試しておかないと、障害のときに働かない。

## 連鎖障害はどう起きるか

連鎖障害のいちばん多い原因は過負荷。とくに怖いのは、依存先が「落ちる」より「遅くなる」とき。

1. **依存先が遅くなる** おすすめ表示のサービスが、ふだん 50 ミリ秒の応答に数十秒かかるようになる。
2. **待ちが積み上がる** 呼び出し側では、おすすめを待つリクエストがスレッドや接続を握ったまま動かない。
3. **共有の枠を使い切る** スレッドや接続の枠を使い切り、関係のない注文や通知の処理まで受け付けられなくなる。
4. **上流へ広がる** 呼び出し側が遅くなったことで、さらにその呼び出し元も待たされる。リトライが負荷を何倍にもする。

3・4 の番号が赤いのは、障害が依存先の外へ広がり始めた段階（1・2 は依存先とその待ちの中にとどまる）。

## 止めてみる

注文・おすすめ・通知の 3 つの機能を持つサービスで、おすすめの依存先が遅くなったとする。対策をオン・オフして、何が動き続けるかを見る。

障害

おすすめを遅くする

対策

バルクヘッド

サーキットブレーカー

- 注文（いちばん大事な機能） 動く 動く 止まる 平常どおり 遅い呼び出しが、注文の分のスレッドや接続を使い切らない おすすめを待つリクエストが共有の枠を使い切り、注文も受け付けられない
- おすすめ表示 動く 止まる エラー（すぐ返る） 代わりの表示（遅い） 代わりの表示 平常どおり 毎回タイムアウトまで待たされた末に失敗する サーキットブレーカーが開き、呼ばずにすぐ失敗を返す。待たされない 毎回タイムアウトを待ってから、定番の人気商品の一覧を返す サーキットブレーカーが開いているので、待たずに定番の人気商品の一覧を返す
- 通知 動く 動く 止まる 平常どおり おすすめの遅れの影響を受けない 注文と同じく、枠が空かないので処理できない

動く 縮退して動く 止まる・失敗

平常時。どの対策も違いが見えない。「おすすめを遅くする」を押して障害を起こしてみる。 **連鎖障害。** おすすめの遅れが、関係のない注文と通知まで止めた。バルクヘッドかサーキットブレーカーを入れてみる。 **障害を閉じ込めた。** 止まったのはおすすめだけ。さらに縮退運転を入れると、おすすめも何かを返せる。 **閉じ込めたうえで縮退運転。** 注文と通知は動き、おすすめも代わりの表示を返す。サーキットブレーカーがあると、代わりの表示も待たずに出せる。

## バルクヘッド（隔壁）

船の船体を隔壁で区切り、1 区画に穴が開いても浸水をその区画だけに止める、という発想から来ている。アプリの部品をそれぞれの枠（プール）に分け、1 つが壊れてもほかは動き続けるようにする。

| 何を区切るか | 例 |
| --- | --- |
| 呼び出し先ごとの接続・スレッド | 依存サービスごとに接続プールを分け、1 つが詰まってもほかの呼び出しは続けられる |
| 利用者・テナントごと | 大口の利用者や重い処理を別のインスタンス群に分け、ほかの利用者に響かないようにする |
| セル（cell）ごと | システム全体を独立した小さなコピーに分け、障害を 1 セルの利用者だけに限る |

区切るほど枠どうしで余りを融通できなくなるので、全体としては多めの資源が要る。どこで区切るかは、業務上の重要さと依存関係で決める。

## サーキットブレーカー

電気のブレーカーのように、失敗が続く相手への呼び出しを一時的に止める。呼ばずにすぐ失敗を返すので、待ちが積み上がらず、弱った相手にも負荷をかけない。

**閉（Closed）** 普通に呼ぶ。失敗の数や割合を数える

失敗がしきい値を超える

**開（Open）** 呼ばずにすぐ失敗を返す

一定時間たつ

**半開（Half-Open）** 少しだけ試しに呼ぶ。成功すれば閉へ、失敗すれば開へ戻る

- 決める値は、開くしきい値・開いている時間・半開で試す回数。
- 開いている間に何を返すか（エラー・キャッシュ・代わりの表示）を、呼び出し側で決めておく。
- 状態が変わったら記録し、監視できるようにする。開いたこと自体が障害の知らせになる。

## 縮退運転（graceful degradation）

依存先が使えなくても、中心の機能だけは返し続ける。AWS はこれを「絶対に必要な依存（ハード）を、なくても動ける依存（ソフト）に変える」と説明している。

| 縮退のしかた | 例 |
| --- | --- |
| 少し古いデータを返す | 在庫数をキャッシュの値で表示する |
| 決めておいた静的な応答を返す | 個人向けのおすすめの代わりに、定番の人気商品の一覧を出す |
| 機能を隠す | レビュー欄を一時的に表示しない |
| 品質を下げる | 検索で調べる範囲を狭め、早く返す |
| 一部のリクエストを断る（負荷を捨てる） | 重要度の低いリクエストから断り、残りを守る |

気をつけたいのは、まったく別の仕組みで同じ結果を出そうとする「フォールバック」。Amazon Builders' Library の記事は、めったに動かないフォールバックは試されにくく、それ自体が失敗の原因になると注意している。縮退運転は「機能を減らして返す」にとどめ、障害を起こす訓練で平常時から試しておく。

## 組み合わせ方

| 対策 | 防ぐもの | 関係 |
| --- | --- | --- |
| タイムアウト | いつまでも待つこと | すべての前提。これがないと、サーキットブレーカーは失敗を数えられない |
| リトライ（指数バックオフ＋ジッター） | 一時的な失敗 | 回数を絞らないと負荷を増やす。詳しくは [分散システムの基本](https://memo.taka1156.site/md/distributed-basics.md) |
| バルクヘッド | 1 つの詰まりが枠を使い切ること | 失敗を数える前から、影響の範囲を限る |
| サーキットブレーカー | 失敗が続く相手を呼び続けること | 開いている間はリトライも止まる |
| 縮退運転 | 依存先の失敗が、そのまま利用者のエラーになること | サーキットブレーカーが開いたときに返すものを決める |

## よくある誤解

✗ 誤解: サーキットブレーカーがあれば、タイムアウトは設定しなくてよい

✓ 正しくは: サーキットブレーカーは失敗を数えて開く。タイムアウトがないと、遅い呼び出しはいつまでも失敗にならず、数えられないまま待ちが積み上がる。

✗ 誤解: リトライの回数を増やすほど、障害に強くなる

✓ 正しくは: 依存先が過負荷のときにリトライすると、負荷が何倍にもなって回復を妨げ、連鎖障害を広げる。回数を絞り、指数バックオフとジッターを入れ、サーキットブレーカーと組み合わせる。

✗ 誤解: 縮退運転とは、別の仕組みで同じ結果を出す予備を用意することだ

✓ 正しくは: 別の仕組みで同じ結果を出すフォールバックは、めったに動かないので試されにくく、それ自体が壊れやすい。縮退運転は、機能や品質を減らしてでも中心の機能を返し続けること。
