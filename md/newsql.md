SQL とトランザクションのまま、書き込みを複数台に広げる

**ざっくり言うと**

- NewSQL は、RDB の SQL とトランザクションを保ったまま、書き込みまで複数台に広げられるようにした DB の総称。
- 既存の MySQL の前にルーターを置いて分割する方式（Vitess）と、最初から分割と合意による複製を組み込んだ方式（Spanner など）がある。
- 台をまたぐ処理ほど往復が増えて遅くなるので、1 台＋レプリカで足りるうちは使わず、主キーの選び方でホットスポットを避ける。

## 分散 SQL の中身: 範囲で分けて、過半数で書く

方式 B の DB は、キー空間を **範囲 (range)** ごとに切り、各範囲を複数台（既定は 3 台が多い）に複製する。各範囲には **リーダー** が 1 台いて、書き込みはリーダーが受け、 **過半数の台が記録したら確定** する（合意アルゴリズム Raft や Paxos）。範囲が大きくなったり負荷が偏ったりすると、自動で分割・移動される。

下のクラスタは 3 ノード・3 範囲。キーを選んで書き込み、ノードを止めると何が起きるかを試せる。

書き込む行:

id = apple

id = kiwi

id = sushi

ノードを止める:

n1

n2

n3

リーダー（書き込みを受ける） フォロワー（複製を持つ） 今書き込んだ範囲の複製 範囲 A = a〜h、B = i〜q、C = r〜z

READY 書き込む行を選ぶ。止めたノードはもう一度押すと戻る。

COMMIT `` は範囲  に入る。リーダー  が書き込みを受け、自分を含む過半数（3 台中 2 台）が記録した時点で確定する。残りの 1 台は後から追いつけばよい。

COMMIT（リーダー交代） 範囲  の元のリーダーが止まったので、生きている台の中から選挙で  が新しいリーダーになった。3 台中 2 台が生きていれば過半数がそろうので、 `` の書き込みは続けられる（交代の間だけ数秒ほど待たされることがある）。

UNAVAILABLE 範囲  は 3 台中 2 台が止まり、過半数がそろわない。古いデータを返したり食い違った書き込みを受けたりしないよう、この範囲の読み書きは止まる（CAP でいう C を選んだ振る舞い）。台が戻れば再開する。

3 台に複製すれば 1 台、5 台なら 2 台まで止まっても動き続ける。その代わり、確定のたびに過半数への往復が要るので、台がリージョンをまたぐと書き込みの遅延はリージョン間の往復時間に近づく。CAP と整合性の考え方は [分散システムの基本](https://memo.taka1156.site/md/distributed-basics.md) 。

## 台をまたぐトランザクションと時刻

**ハイブリッド論理クロック (HLC) と不確実性区間 (uncertainty interval)**

## 使うときの落とし穴

1. **連番の主キーはホットスポットになる** キー範囲で分割する DB では、自動採番や時刻順の主キーだと新しい行がすべて「いちばん後ろの範囲」に集まり、1 台のリーダーに書き込みが集中する。UUID（v4）などのばらけるキーにするか、各 DB の機能（Spanner のビット反転シーケンス、CockroachDB のハッシュシャードインデックス（hash-sharded index）、TiDB の `AUTO_RANDOM` など）を使う。
2. **リトライ処理はアプリの仕事** SERIALIZABLE で競合すると、DB は片方のトランザクションを中止してリトライを求める。トランザクション全体をやり直せるように書き、外部 API の呼び出しなどはトランザクションの外に出しておく。
3. **台をまたぐほど遅い** 関係の深い行（ユーザーとその注文など）が同じ範囲・同じシャードに入るように主キーやシャードのキーを設計すると、1 台で完結する処理が増えて速くなる。Vitess で全シャードに問い合わせる（scatter）クエリも同じく重い。
4. **リージョンをまたぐと物理の壁** 書き込みの確定には過半数への往復が要るので、東京と米国にまたがる構成では 1 回の書き込みに 100ms 前後かかりうる。読み込みは近くの複製から少し古い値を読む機能（stale read・follower read）で速くできる。

## よくある誤解

✗ 誤解: 分散 SQL は台をまたぐので、NoSQL と同じく結果整合性になる

✓ 正しくは: 方式 B の DB は、合意による複製と分散トランザクションで、既定では強い整合性（SERIALIZABLE など）を保つ。わざわざ古い値を読むのは、stale read のように明示したときだけ。

✗ 誤解: NewSQL にすれば、設計を変えずにどこまでも速くなる

✓ 正しくは: 台数で増えるのは全体の処理量（スループット）で、1 件ごとの遅延はむしろ 1 台の RDB より増えやすい。連番の主キーや台をまたぐ JOIN のように 1 か所に集中・往復が増える設計だと、台を足しても速くならない。

✗ 誤解: Vitess を入れれば、シャードをまたぐトランザクションも 1 台の MySQL と同じく原子的になる

✓ 正しくは: 既定のモード（ `multi` ）では、各シャードに順にコミットするだけなので、途中で失敗すると一部だけ確定しうる。原子的にしたいなら `twopc` モードを使うが、コミットは遅くなる。そもそもシャードをまたがないように Vindex を設計するのが基本。
