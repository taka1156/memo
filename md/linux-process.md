- プロセスは実行中のプログラムに、PID・メモリ空間・fd テーブル・シグナル情報などをカーネルがくっつけたもの。

- パイプやリダイレクトは、exec の前に fd を付け替えて作る。コマンドは 0 番から読んで 1 番に書くだけで、相手を知らない。

## プロセスの中身

プロセスは「実行中のプログラム」に、カーネルが管理する情報一式をくっつけたもの。カーネル内では `task_struct` という構造体で表され、 `/proc/<PID>/` から中身を覗ける。

**PID / PPID**

自分の番号と親の番号。親子で木構造になる

**仮想メモリ空間**

コード・データ・ヒープ・スタック。他のプロセスからは見えない

**fd テーブル**

0=stdin 1=stdout 2=stderr …。開いているファイル・パイプ・ソケット・端末への番号

**資格情報**

UID / GID。何にアクセスでき、誰にシグナルを送れるかが決まる

**シグナル情報**

シグナルごとの処理方法、シグナルマスク（ブロック中）、処理待ちの印

**PGID / SID / 制御端末**

所属するプロセスグループ・セッションと、つながっている端末

**状態**

R・S・D・T・Z（下の表）

**カレントディレクトリ・環境変数**

子へコピーされるが、子で変えても親には戻らない（スクリプトの設定を今のシェルに反映するには `source` で同じプロセス内で読む）

### fork と exec で何が引き継がれるか

| 項目 | fork 直後の子 | exec の後 |
| --- | --- | --- |
| PID | 新しい番号 | 変わらない （中身だけ入れ替わる） |
| メモリ | 親のコピー（実際は書き込むまで共有: Copy-on-Write） | 新しいプログラムで丸ごと置き換え |
| fd テーブル | コピー（同じファイルを指し、読み書き位置も共有） | そのまま（ `O_CLOEXEC` 付きだけ閉じる） |
| シグナルの処理方法 | 引き継ぐ | ハンドラは 既定に戻る 。「無視」は無視のまま |
| シグナルマスク（ブロック中のシグナル） | 引き継ぐ | そのまま |
| 処理待ちのシグナル | 空になる | そのまま |
| PGID / SID / 制御端末 | 引き継ぐ | そのまま |

`nohup cmd` が効くのはこの性質のおかげ。nohup は SIGHUP を「無視」に設定してから `exec` するので、無視が新しいプログラムにも残る。

### プロセスの状態（ps の STAT 列）

| 記号 | 状態 | 例と、シグナルとの関係 |
| --- | --- | --- |
| R | 実行中 / 実行可能 | CPU で動いている、または順番待ち |
| S | 割り込み可能な待機 | キー入力や `sleep` を待つ。 シグナルが来ると起こされる |
| D | 割り込み不可の待機 | ディスクや NFS の I/O 待ち。 ふつうはシグナルで起こされない （ただし Linux 2.6.25 以降の TASK_KILLABLE による待機は、表示は D でも SIGKILL では終わる。NFS の待ちの多くはこちら） |
| T | 停止 | SIGSTOP・SIGTSTP（Ctrl+Z）で止まった。SIGCONT で再開（デバッガでの停止は `t` ） |
| Z | ゾンビ | 終了済みだが、親が `wait` するまで終了ステータスだけが残っている |

### プロセスツリーと孤児

systemd (1) ├─ sshd (812) │ └─ sshd（接続ごと） (2301) │ └─ bash (2302) │ └─ vim (2410) └─ gnome-terminal-server (1950) └─ bash (1960) ├─ sleep (1999) └─ ps (2000)

- すべてのユーザープロセスは PID 1（多くは systemd）の子孫。デスクトップでは間に `systemd --user` などが入る。カーネルスレッドは kthreadd (PID 2) の子。
- 親が先に死ぬと、子は **孤児** になり PID 1（またはサブリーパーに指定されたプロセス）の子に付け替えられる。PID 1 は孤児を `wait` して回収する。
- 親が生きているのに `wait` しないと、子は **ゾンビ** のまま残る。

### ファイルディスクリプタとパイプ: `ls | grep txt > out.txt`

ls

0 → /dev/pts/3

1 → パイプ（書き口）

2 → /dev/pts/3

**pipe** カーネル内のバッファ

（既定 64 KiB）

grep txt

0 → パイプ（読み口）

1 → out.txt

2 → /dev/pts/3

シェルは `pipe()` で読み口・書き口の fd を作り、2 回 `fork` し、それぞれの子で `dup2` を使って 0 番・1 番に付け替えてから `exec` する。コマンド側は「0 番から読んで 1 番に書く」だけで、相手がパイプか端末かファイルかを知らない。エラー (fd 2) は端末のままなので、パイプやリダイレクトの後でも画面に出る。

読み手（grep）が先に終わると、書き手（ls）の次の write は SIGPIPE を受けて終了する。 `yes | head -1` がすぐ終わるのはこのため（ [SIGPIPE](https://memo.taka1156.site/md/linux-signal.md) ）。

## よくある誤解

ゾンビプロセスは kill -9 で消せる

ゾンビはすでに終了していて、残っているのは終了ステータスだけ。消すには **親が `wait` する** 必要がある。親を直すか親を終了させれば、ゾンビは PID 1 に引き取られて回収される。

スクリプトの中で cd や export すれば、終わった後のシェルにも反映される

`./script.sh` は子プロセスとして動くので、カレントディレクトリや環境変数の変更は子の中だけで終わり、親のシェルには戻らない。今のシェルに反映したいときは `source script.sh` （または `. script.sh` ）で、同じプロセスの中で読み込む。

パイプの先に渡せば、エラーメッセージも絞り込める

パイプでつながるのは fd 1（stdout）だけで、fd 2（stderr）は端末のまま。エラーもまとめて渡すには `cmd 2>&1 | grep x` （bash なら `|&` ）のように fd 2 を fd 1 と同じ先に付け替える。

## コマンド例

```
echo $$                                   # 今のシェルの PID
ps -eo pid,ppid,stat,cmd --forest         # 親子関係と状態
pstree -p $$                              # 自分から下のツリー
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'    # ゾンビを探す（PPID が犯人の親）
ls -l /proc/$$/fd                         # 開いている fd の行き先
cat /proc/$$/status                       # 状態・親・資格情報など
strace -f -e trace=process bash -c 'ls | wc -l'   # fork(clone)/execve/wait4 を追う
```
