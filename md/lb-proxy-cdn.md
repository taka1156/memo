# LB・リバースプロキシ・CDN

リクエストの通り道 / L4 と L7 / 振り分け方とヘルスチェック / TLS 終端と送信元 IP / CDN の役目

**ざっくり言うと**

- 3 つとも「クライアントとアプリのあいだに立ち、代わりに受けて後ろへ渡す」中継役。違いは **何のために立っているか** : 分散（LB）、入口の集約と加工（リバースプロキシ）、ユーザーの近くでの応答（CDN）。
- 実物は 1 つのソフトが複数を兼ねる。nginx はリバースプロキシ兼 L7 LB、Cloudflare は CDN 兼リバースプロキシ兼 WAF。「名前」より「どの役割をどこでやっているか」で考える。
- 中継が挟まると、アプリから見た接続相手はプロキシになる。 **TLS をどこで解くか** と **本当の送信元 IP をどう伝えるか** を決めておかないと、ログ・レート制限・認可が狂う。

## 3 つの役割

ロードバランサ

リバースプロキシ

CDN

**目的: 複数台に負荷を分け、壊れた台を外す。** 1 台のサーバーでは足りない・止められないときに置く。

- 振り分けアルゴリズムで次の 1 台を選ぶ（ 下で試せる ）
- ヘルスチェックで死んだ台を外し、戻ったら入れる
- 入れ替え時は新規の接続だけ止めて、処理中の接続は終わるまで待つ（ドレイニング）

例: AWS の ALB（L7）・NLB（L4）、Google Cloud Load Balancing、HAProxy、nginx の `upstream` 、Envoy、Kubernetes の Service（L4 相当）

**目的: 外からの入口を 1 つにまとめ、後ろの構成を隠して加工する。** 台数が 1 台でも置く価値がある点が LB との違い。

- パスやホスト名で別のサービスへ（ `/api` → API サーバー、 `/` → フロント）
- TLS 終端・HTTP/2・HTTP/3 の受け口、圧縮、ヘッダーの付け替え
- 静的ファイルの配信、遅いクライアントの吸収（バッファリング）、認証の前段、レート制限

「フォワードプロキシ」は逆向き: クライアント側に立って外へ出るリクエストを代理する（社内プロキシなど）。リバースプロキシはサーバー側に立つ。

**目的: ユーザーの近く（エッジ）で応答し、遠いオリジンまで行かせない。** 世界中の拠点に置かれた、巨大な分散リバースプロキシと考えるとよい。

- キャッシュできる応答はエッジで返す（ルールは [HTTP キャッシュ](https://memo.taka1156.site/md/http-cache.md) の `Cache-Control` ）
- キャッシュしない応答も、TLS をユーザーの近くで張り、オリジンまでは混んでいない経路・張りっぱなしの接続で運ぶので速くなる
- DDoS の吸収・WAF・ボット対策・画像変換など、入口でやると得な処理が集まっている

例: Cloudflare、Amazon CloudFront、Fastly、Akamai。Cloudflare の範囲は [Cloudflare サービス](https://memo.taka1156.site/md/cloudflare-services.md) 。

## L4 と L7: どこまで中身を見るか

#### L4（TCP / UDP）

- 見えるのは IP アドレスとポートだけ。HTTP の中身は読まない
- 接続（コネクション）単位で 1 台に渡す。1 本の接続上のリクエストはずっと同じ台へ
- 速く、HTTP 以外（DB・MQTT・ゲームの UDP）にも使える
- TLS は解かずにそのまま通すこともできる（パススルー）

#### L7（HTTP）

- TLS を解いて、パス・ホスト・ヘッダー・Cookie を読む
- リクエスト単位で振り分けられる。HTTP/2 の 1 本の接続上の各リクエストを別々の台へ
- パスで振り分け・ヘッダー追加・リダイレクト・リトライができる
- 処理は重くなり、証明書をここに置く必要がある

HTTP/2 や gRPC の長い接続を L4 で分けると、接続を張った時点の 1 台に全リクエストが寄り続けて偏る。gRPC を複数台に均等に分けたいなら L7 で分ける（ [API スタイル](https://memo.taka1156.site/md/api-styles.md) ）。

## 振り分け方とヘルスチェック

3 台のうち **B だけ処理が遅い** （1 件に 3 倍かかる）状況で、リクエストを流してみる。棒は「今処理中の件数」。

IP ハッシュ

B を停止 / 復帰

リセット

| 方式 | しくみ | 向いている場面 |
| --- | --- | --- |
| ラウンドロビン | 順番に 1 台ずつ。重み付きなら性能比で回数を変える | 台の性能も 1 件の重さもそろっているとき |
| 最小接続数 | 処理中の接続が一番少ない台へ | 重さがばらつく・遅い台が混じるとき。長い接続（WebSocket） |
| ハッシュ（IP・キー） | 送信元 IP やキーのハッシュで台を固定 | 同じユーザーを同じ台へ寄せたい（キャッシュの当たりを上げる）。台が増減してもずれを小さくするにはコンシステントハッシュ |

- **アクティブヘルスチェック** : LB が定期的に `/healthz` などを叩き、連続で失敗したら外す。
- **パッシブヘルスチェック** : 実際のリクエストのエラーやタイムアウトを数えて外す（外れ値検出）。
- **スティッキーセッション** （同じ人を同じ台へ）は、セッションをサーバーのメモリに持っているときの応急処置。その台が落ちるとセッションも消えるので、本来はセッションを Redis などに外出しする（ [JWT とセッション](https://memo.taka1156.site/md/jwt-vs-session.md) ）。

## TLS 終端と本当の送信元 IP

エッジで終端

再暗号化

パススルー

`ブラウザ ==TLS==> CDN / LB --平文 HTTP--> アプリ`

証明書の管理は入口だけで済み、L7 の機能が全部使える。ただし入口から後ろは平文なので、後ろが同じ閉じたネットワーク内にあるときに限る。

`ブラウザ ==TLS==> LB ==TLS==> アプリ`

入口で一度解いて中身を見たうえで、後ろとも TLS を張り直す。クラウドの別リージョンやインターネット越しのオリジンへ渡すときはこれ。後ろ側の証明書も要る（相互に証明し合う mTLS にすることもある）。

`ブラウザ ==TLS（そのまま通過）==> L4 LB ==> アプリ`

LB は暗号を解かずに TCP として流すだけ。秘密鍵をアプリから出さずに済むが、パスでの振り分けやヘッダー追加などの L7 機能は使えない（TLS の SNI に入っているホスト名だけは見える）。

### アプリから見た送信元はプロキシになる

中継が TCP を張り直すので、アプリのソケットから見える相手の IP はプロキシのもの。本当のクライアント IP はヘッダーで伝える。

```
X-Forwarded-For: 203.0.113.7, 198.51.100.20   # 左から: クライアント, 途中のプロキシ…（各段が右に追記）
X-Forwarded-Proto: https                       # 入口でのスキーム（アプリが http:// のリンクを作らないように）
Forwarded: for=203.0.113.7;proto=https         # 上 2 つを標準化したもの（RFC 7239）
```

- このヘッダーはクライアントが自由に書けるので、 **左端を信じてはいけない** 。自分が管理するプロキシの段数（または IP の範囲）を決めておき、右から数えて最後に信頼できるプロキシが記録した 1 つ前の値を使う。nginx なら `set_real_ip_from` と `real_ip_header` 、Express なら `trust proxy` 。
- L4 で HTTP ヘッダーを書き換えられないときは、TCP の先頭に送信元を載せる **PROXY プロトコル** を使う（受け側も対応が必要）。

## CDN の中で起きていること

HIT

エッジにコピーがあり、まだ新しい。オリジンへは行かずにその場で返す

MISS

エッジに無い。オリジン（または中間層）から取ってきて返し、キャッシュしてよければ保存

REVALIDATED

古くなっていたので、オリジンに `If-None-Match` で確認し、304 なら手元のコピーを延長して返す

BYPASS

キャッシュしない応答（Cookie 付き・ `private` ・ `no-store` など）。中継だけする

- **キャッシュキー** : 何が同じなら同じ応答とみなすか。基本は URL（ホスト＋パス）で、クエリを含めるかは CDN や設定による（Cloudflare は既定で含め、CloudFront は既定で含めない）。含める設定で `?utm_source=` のような無関係なクエリまでキーに入ると当たりが下がり、逆にログイン状態で変わる応答を Cookie を見ずにキャッシュすると他人のページを配ってしまう。
- **オリジンシールド（中間層）** : 世界中のエッジが一斉に MISS してオリジンに殺到しないよう、間に 1 段キャッシュを挟んでオリジンへの取得を 1 回にまとめる。
- **パージ** : デプロイで中身を変えたら消す。ファイル名にハッシュを入れて URL ごと変える方が確実（ [HTTP キャッシュ](https://memo.taka1156.site/md/http-cache.md) ）。

## よくある誤解

✗ 誤解: リバースプロキシとロードバランサは別の機械として両方置くもの

✓ 正しくは: 役割の名前であって、機械の種類ではない。nginx 1 台でパス振り分け・TLS 終端（リバースプロキシ）と複数台への分散（LB）を同時にやれる。小さな構成なら 1 段で足りる。

✗ 誤解: CDN は画像や JS などの静的ファイル専用

✓ 正しくは: キャッシュできない API も CDN を通す価値がある。ユーザーの近くで TLS を張る・オリジンまでの経路を最適化する・DDoS や WAF で守る、はキャッシュと無関係に効く。

✗ 誤解: X-Forwarded-For の先頭がクライアントの IP

✓ 正しくは: クライアントが最初から偽の値を入れて送れるので、先頭は誰でも詐称できる。信頼できるのは自分のプロキシが追記した部分だけ。これを間違えると IP によるレート制限や許可リストがすり抜けられる。

✗ 誤解: LB を置けば落ちない

✓ 正しくは: LB 自体が 1 台なら、そこが単一障害点になる。クラウドの LB は内部で冗長化されているが、自前の場合は 2 台で仮想 IP を引き継ぐ（keepalived など）か、DNS で複数の入口を返す。

## 確かめ方と設定例

```
curl -sI https://example.com/app.js | grep -iE 'cache|age|via|server'
# cf-cache-status: HIT（Cloudflare）/ x-cache: Hit from cloudfront / age: 秒数 など
curl -s https://example.com/ -o /dev/null -w '%{remote_ip} %{time_connect} %{time_starttransfer}\n'
# 接続先の IP（エッジの IP か）と、接続・最初の 1 バイトまでの時間
dig +short example.com          # 場所によって違う IP が返れば、DNS で近いエッジに寄せている
```

```
# nginx: パスで振り分け＋2 台に分散＋送信元を伝える
upstream api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
}
server {
    listen 443 ssl;
    http2 on;
    location /api/ {
        proxy_pass http://api;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location / { root /srv/front; try_files $uri /index.html; }
}
```

オープンソース版の nginx のヘルスチェックはパッシブ（ `max_fails` ）だけ。定期的に叩くアクティブチェックは NGINX Plus・HAProxy・Envoy などにある。
