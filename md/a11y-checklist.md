## 4 つの原則（POUR）

WCAG の全項目は、この 4 つのどれかに分類されています。

P **知覚できる** Perceivable

見えない・聞こえない人にも情報が届く。代替テキスト、字幕、コントラスト。

O **操作できる** Operable

マウスが使えなくても操作できる。キーボード、フォーカス、十分な時間。

U **理解できる** Understandable

内容と操作が予測どおり。ラベル、エラーの説明、言語の指定。

R **堅牢** Robust

支援技術が正しく解釈できる。正しい HTML、名前・役割・状態。

### キーボード 操作とフォーカス

- すべての操作が Tab / Enter / Space / 矢印キーでできる 2.1.1 クリックできる `<div>` は NG。 `<button>` か `<a>` を使う。
- フォーカスが抜け出せなくなる場所がない 2.1.2 モーダルは Esc で閉じられ、閉じたら元の場所にフォーカスを戻す。
- Tab の移動順が見た目の順と一致する 2.4.3 `tabindex` に正の数を使わない。
- フォーカス中の要素がはっきり見える 2.4.7 `outline: none` で消したなら、代わりの見た目を必ず付ける。
- フォーカスした要素が固定ヘッダーやバナーに隠れない 2.4.11 2.2 `scroll-padding-top` でヘッダー分の余白を取る。
- ドラッグ操作には、クリックやボタンでの代替手段がある 2.5.7 2.2 並べ替えなら「上へ」「下へ」ボタンなど。
- クリックできる対象は 24×24px 以上（または周りに十分な余白） 2.5.8 2.2

### フォーム 入力とエラー

- すべての入力欄に `<label>` が紐づいている 1.3.1 / 3.3.2 placeholder はラベルの代わりにならない（入力すると消える）。
- エラーは「どこが・なぜ・どう直すか」を文字で示す 3.3.1 / 3.3.3 `aria-describedby` でエラー文を入力欄に紐づける。
- 名前・メールなどに `autocomplete` 属性を付けている 1.3.5

- ログインでパスワードの貼り付けやパスワード管理ツールを妨げない 3.3.8 2.2 パズル型の認証だけに頼らない。パスキーは有力な選択肢（ [パスキー](https://memo.taka1156.site/md/passkeys.md) ）。

### メディア 画像・動画・動き

- 意味のある画像に、内容を伝える `alt` がある 1.1.1 飾りの画像は `alt=""` （空）にして読み上げを飛ばす。

NG：div にクリック

```
<div class="btn" onclick="save()">
  保存
</div>
<!-- Tab で届かない・Enter で押せない・
     「ボタン」と読まれない -->
```

OK：button を使う

```
<button type="button" onclick="save()">
  保存
</button>

<!-- アイコンだけなら名前を付ける -->
<button type="button" aria-label="閉じる">
  <svg aria-hidden="true">…</svg>
</button>
```

ページを移動するなら `<a href>` 、その場で何かを実行するなら `<button>` 。

```
/* ブラウザが必要と判断したときだけ出す（ボタンのマウスクリックでは通常出ない） */
:focus-visible {
  outline: 3px solid var(--accent);
  outline-offset: 2px;
}
/* 固定ヘッダーにフォーカスが隠れないように */
html { scroll-padding-top: 72px; }

/* スキップリンク：フォーカスされたときだけ見せる */
.skip { position: absolute; left: -9999px; }
.skip:focus { left: 16px; top: 16px; }
```

Tab キーで下の 2 つのボタンにフォーカスを移して違いを比べてみてください。

outline: none（NG）

:focus-visible（OK）

```
<label for="email">メールアドレス</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-err">
<p id="email-err">
  「@」が含まれていません。例：taro@example.com
</p>
```

`aria-describedby` で紐づけると、入力欄にフォーカスしたときにエラー文も読み上げられる。

```
<!-- 最初から DOM に置いておき、中身だけ書き換える -->
<div role="status" aria-live="polite" id="toast"></div>

<script>
  document.getElementById('toast').textContent = '保存しました';
</script>
```

要素ごと後から追加すると読み上げられないことがある。入れ物は先に置いておく。

```
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

## 確かめ方

**1. 自動チェック**

Lighthouse や axe DevTools でコントラスト・alt・ラベル漏れなどを一掃。ただし自動で見つかるのは問題の一部だけ。

**2. マウスを置く**

Tab / Shift+Tab / Enter / Space / Esc だけで全操作。フォーカスが見えるか、順番は自然か、閉じ込められないか。

**3. 200% 拡大**

ブラウザのズームで 200%、スマホ幅でも。文字切れ・重なり・横スクロールがないか。

**4. 読み上げ**

macOS / iOS は VoiceOver、Windows は NVDA。見出し・ボタン名・状態の変化が正しく読まれるか。

## よくある誤解

✗ 誤解: Lighthouse で 100 点ならアクセシブル

✓ 正しくは: 自動チェックは「alt があるか」は見られても「alt の中身が正しいか」や「キーボードで操作できるか」はほとんど判定できない。手での確認が必須。

✗ 誤解: ARIA をたくさん付けるほど親切

✓ 正しくは: 間違った ARIA は付けないより悪い。 `role="button"` を付けた div はキー操作を自分で全部実装する必要がある。まずネイティブ要素を使う。

✗ 誤解: フォーカスの枠は見た目が悪いので消してよい

✓ 正しくは: キーボード利用者は現在地がわからなくなる。 `:focus-visible` を使えば、ボタンをマウスでクリックしたときは枠を出さず、キーボード操作時などには表示できる。

✗ 誤解: アクセシビリティは障害のある人だけのためのもの

✓ 正しくは: 片手がふさがっている、屋外で画面が見にくい、一時的なけが、高齢による視力低下など、誰もが当事者になり得る。字幕やキーボード操作は多くの人の役に立つ。
