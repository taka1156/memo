**ざっくり言うと**

- 個人情報を含むデータが開発環境・ログ・外部サービスへ出る前に、値を隠したり偽物に置き換えたりすること。

## どこで漏れるか：境界でマスクする

本番 DB そのものは厳重に守っていても、 **本番の外へコピーされたデータ** から漏れることが多い。開発・検証環境は権限が緩く、ログや分析基盤は多くの人が見られ、外部サービスに送ったデータは自分では消せない。そこで、データが **守りの弱い側へ境界を越える直前** でマスクする。

点線の枠がマスクする位置。どれも「守りの強い側」から「弱い側」へ出る直前に置く。境界を越えたあとで消しても、途中のバックアップやキャッシュに残る。

いちばん確実なのは **そもそも持たない・渡さない** こと（データの最小化）。マスキングは、どうしても渡す必要があるときに、渡す中身を減らす手段と考える。

## 手法：戻せるか・形を保つか

「マスク」と一口に言っても、やっていることはかなり違う。選ぶときに効くのは、 **あとで元の値に戻せるか** と、 **形式や同一性（同じ人は同じ値になるか）を保つか** の 2 点。

| 手法 | 例 | 元に戻せるか | 同じ入力 → 同じ出力 | 向いている場面・注意 |
| --- | --- | --- | --- | --- |
| 削除・NULL 化 | 山田太郎 → (空) | 戻せない | — | その値を使わないなら最も安全。テストで必須項目が空になると動かないことがある |
| 伏せ字 | 090-1234-5678 → 090-****-**** | 戻せない | — | 画面表示・ログ向け。残す桁が多いと、ほかの情報と合わせて特定できる |
| 種類ラベルへの置換 | 山田太郎 → <PERSON> | 戻せない | — | 文章のマスクの定番。文脈は残るが、誰と誰が同一人物かは消える |
| 偽データへの置換 | 山田太郎 → 佐藤花子 | 戻せない | 乱数なら毎回違う／ハッシュから作れば同じ | 開発・検証の DB 向け。形式が本物らしいのでアプリやテストがそのまま動く |
| ハッシュ | a@x.jp → 9f2c… | 計算では戻せない（総当たりに注意） | 同じ | 表をまたいで結合したいとき。値の種類が少ない項目は秘密の鍵（HMAC の鍵やペッパー）が必須 |
| 暗号化・トークン化 | a@x.jp → tok_8e1… | 鍵・対応表があれば戻せる | 方式による | あとで本人に連絡するなど、元の値が必要なとき。鍵や対応表が漏れれば全部戻る |
| 汎化・ノイズ | 1990-04-12 → 1990 年代 | 戻せない | — | 分析向け。年齢・住所・日付を粗くして、組み合わせによる特定を防ぐ |

### ハッシュは「戻せない」とは限らない

電話番号やマイナンバーのように **取りうる値が少ない** 項目は、全部の候補をハッシュして突き合わせれば元に戻せる。たとえば携帯番号は 090・080・070（今後は 060 も）で始まる 11 桁で、候補は数億通りしかない。対策は、外に出さない秘密の鍵を混ぜること（HMAC の鍵や、ペッパーと呼ばれる秘密の値）。鍵をマスク後のデータと一緒に置かない。

例: Greenmask は決定的な置換に使う秘密の値を環境変数 `GREENMASK_GLOBAL_SALT` で渡し、強い乱数にして秘密にするよう案内している。Presidio のハッシュは、ソルトを指定しなければ値ごとに乱数のソルトを作る（その代わり同じ値でも結果が揃わない）。

### 「仮名化」と「匿名化」は別物

鍵や対応表があれば個人に戻せる加工を **仮名化** 、誰にも戻せない加工を **匿名化** と呼ぶ。仮名化したデータは、鍵や対応表を持つ側にとっては EU の GDPR 上も個人データのまま扱われる（2025 年の EU 司法裁判所の判決で、受け取った側が個人を特定できない場合はその側にとって個人データに当たらないこともあるとされたが、渡す側の義務はなくならない）。日本の個人情報保護法にも「仮名加工情報」と「匿名加工情報」の区分があり、扱いのルールが違う。「マスクしたから個人情報ではない」と決めつけず、どちらに当たるかを確かめる。

## 対象：DB と文章でやり方が違う

DB（構造化データ）

文章（非構造化データ）

id | name | email | birth_date 1 | 山田太郎 | taro@example.jp | 1990-04-12

**どの列に何が入っているかが分かっている** ので、「 `name` は偽の名前に、 `email` はハッシュから作った偽アドレスに」とルールを書くだけで済む。判断に NLP は要らない。

- 大事なのは **整合性** : 外部キーで結んだ表の値が揃うこと、 `created_at < updated_at` のような関係が崩れないこと。
- 大量のデータを速く処理し、どこでも動かせることが求められるので、Go などで書かれた単一バイナリのツールも多い（例: Greenmask は PostgreSQL のダンプとリストアの間で列を置き換える）。
- 落とし穴は、 **自由記述の列** （備考・問い合わせ本文・JSON 列）。中身は文章なので、次のタブのやり方が要る。

お世話になっております。 山田 です。 折り返しは 090-1234-5678 までお願いします。

波線が個人情報。どこに出てくるかは文章ごとに違う。

**どこに個人情報があるか分からない** ので、まず検出してから置き換える。検出は次の組み合わせで行う。

- **正規表現** : メールアドレス・電話番号・カード番号など、形が決まっているもの。
- **チェックサム** : カード番号の検査桁などで、たまたま形が合っただけの数字を外す。
- **固有表現抽出（NER）** : 人名・地名・組織名など、形では見分けられないもの。文脈を読む NLP のモデルが要る。
- **周りの語（コンテキストワード）** : 「電話」「TEL」が近くにあれば確信度を上げる。

NER のモデルやライブラリ（spaCy・Transformers など）が Python に集まっているので、この分野のツールは Python が中心になる（例: Presidio）。

（元のページで操作できます → https://memo.taka1156.site/data-masking.html#targets）

## 検出の限界

文章からの検出は、見逃し（漏れ）と過検出（関係ない語まで消す）のバランスで調整するもので、 **全部見つけることは保証できない** 。Presidio 自身も、自動検出なので全部の機密情報が見つかる保証はなく、ほかの対策と組み合わせるよう明記している。

- **日本語** : 多くのツールは英語向けが標準。日本語の NER モデルへの差し替え、マイナンバーや日本の電話番号・住所の検出ルールの追加、コンテキストワードの日本語化が要る。日本語入力の全角数字（ `０９０` ）は ASCII 向けのパターンに一致しないので、先に正規化する。
- **組み合わせによる特定** : 名前を消しても、郵便番号・生年月日・性別の組み合わせで個人が絞れることがある。こうした項目（準識別子）は汎化して粗くする。
- **思わぬ場所** : URL のクエリ文字列、ファイル名、画像の中の文字、例外メッセージに入った入力値など。

だからマスキングは「これで安全」になる最後の砦ではなく、 **多層防御の 1 枚** として扱う。マスク後のデータにもアクセス制御をかけ、保存期間を決めておく。

## 進め方

1. **データの流れを洗い出す** 本番データがどこへコピー・送信されているか（開発 DB、ログ、分析、外部委託、外部 API）を列挙する。
2. **渡さずに済むものを削る** その先で本当に使う項目だけに絞る。使わない列は削除・NULL 化がいちばん安全。
3. **項目ごとに手法を決める** 元の値が要るか（戻せる方式か）、結合や整合性が要るか（同じ入力 → 同じ出力か）で上の表から選ぶ。
4. **境界の直前に組み込む** ダンプ時・ログ出力時・送信時に自動で必ず通るようにする。人が手で実行する手順にしない。
5. **漏れを検査し続ける** マスク後のデータを正規表現などで抜き取り検査し、新しい列やログ項目が増えたらルールに足す。

## コード例（文章のマスク）

Presidio を使い、英語の文章から人名と電話番号を検出してラベルに置き換える最小の例。日本語で使うには、上の「検出の限界」にある設定が別に要る。

```
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

text = "My name is John Smith, call me at 212-555-1234"
results = AnalyzerEngine().analyze(text=text, language="en")
print(AnonymizerEngine().anonymize(text=text, analyzer_results=results).text)
# 例: My name is <PERSON>, call me at <PHONE_NUMBER>
```

## よくある誤解

✗ 誤解: ハッシュ化すれば元に戻せないので匿名データになる

✓ 正しくは: 取りうる値が少ない項目は総当たりで戻せる。秘密の鍵を混ぜても、鍵があれば同じ計算で照合できるので仮名化にとどまる。同じ人が同じ値になる以上、ほかのデータと突き合わせて特定される余地も残る。

✗ 誤解: 名前と連絡先の列を消せば DB のマスキングは終わり

✓ 正しくは: 備考や問い合わせ本文などの自由記述の列、JSON 列、ファイル名にも個人情報は入る。郵便番号・生年月日・性別のような組み合わせで特定できる項目も残っている。

✗ 誤解: 検出ツールを通した文章には個人情報が残っていない

✓ 正しくは: 検出は確率的で、見逃しは必ずある。特に日本語や、表記ゆれ・全角数字・誤字を含む文章では漏れやすい。マスク後のデータも機密として扱い、ほかの対策と重ねる。

✗ 誤解: 暗号化して渡せばマスキングしたのと同じ

✓ 正しくは: 暗号化は鍵があれば戻せる。受け取り側で復号するなら、受け取り側から漏れたときに守れない。相手が元の値を必要としないなら、暗号化ではなく置換や削除を選ぶ。
