- スイスチーズモデルは、穴のある防御層を何枚も重ね、穴がたまたま一直線に並んだときに事故が起きると見る考え方。

## スイスチーズモデル

心理学者の James Reason が示した事故のモデル。防御・障壁・安全装置を、穴の開いたスイスチーズの薄切りにたとえる。どの層にも穴はあるが、普段は別の層が止めてくれる。すべての層の穴が一瞬だけ一直線に並んだとき、危険がすり抜けて事故になる。

下はソフトウェアのリリースの例。各層の穴をふさいだり開けたりして、どこで止まるかを見る。

3. 段階的リリース 一部の利用者にだけ先に出す 穴あり （すり抜ける） ふさがっている

## 穴が開く 2 つの理由

Reason は、穴の原因を「その場の誤り」と「潜在的な条件」に分けた。ほとんどの事故は両方の組み合わせで起きる。

|  | その場の誤り（active failures） | 潜在的な条件（latent conditions） |
| --- | --- | --- |
| 何か | 現場の人が直接かかわる危険な行為。うっかり・ど忘れ・判断の誤り・手順違反など | 設計・手順・組織の決定が生む、前から潜んでいる弱点 |
| ソフトウェアの例 | 本番の DB で削除のコマンドを打ち間違える | 本番と検証の画面が同じ見た目、権限が強すぎる、確認なしで実行できる、人手が足りない |
| 効き方 | 直接的で、影響は短い。どんな形で起きるかを事前に読みにくい | 長く潜み、その場の誤りと重なったときに表に出る。事前に見つけて直せる |
| 対策 | 1 つずつ注意しても、また起きる | 条件そのものを直す。直せば多くの誤りがまとめて止まる |

Reason はその場の誤りを蚊にたとえた。1 匹ずつたたいても次々に来るので、防御を強め、蚊が湧く沼（潜在的な条件）を干すのがよい、という見方。人を責めるより、人が働く条件を変える方が効く。

## 多層防御（defense in depth）

NIST は多層防御を、人・技術・運用を組み合わせて、組織の複数の層にさまざまな障壁を置く情報セキュリティの戦略と定義している。1 枚が破られても次の層で止める、という点はスイスチーズモデルの裏返し。

Web アプリ

インフラ

リリース

1. **境界** WAF やレート制限で、明らかな攻撃や大量のアクセスを入口で落とす
2. **認証** 誰かを確かめる。多要素認証で、パスワードが漏れても止める
3. **認可** その人がその操作をしてよいかを、サーバーで毎回確かめる
4. **入力の扱い** プリペアドステートメントや出力のエスケープで、注入を無害にする
5. **データ** 暗号化と最小権限で、盗まれても読めない・広がらないようにする
6. **検知** 監査ログとアラートで、すり抜けたものに気づく
1. **ネットワークの分離** 公開する部分と内部を分け、内部へは決まった経路からだけ入れる
2. **通信の許可** セキュリティグループやファイアウォールで、必要なポートと相手だけを通す
3. **権限** 人もプログラムも最小権限にし、1 つの鍵が漏れても範囲を狭く保つ
4. **データ** 保存時・通信時の暗号化
5. **復旧** 別の場所に置いたバックアップ。ほかの層がすべて破られたときの最後の層
1. **レビュー** 人の目で設計と変更を見る
2. **自動テスト** 決まった観点を毎回確かめる
3. **段階的リリース** カナリアや機能フラグで、影響を一部に限る
4. **監視** エラー率や遅延の変化に気づく
5. **ロールバック** すぐ戻せる手段を用意しておく

## モデルと方針の関係

|  | スイスチーズモデル | 多層防御 |
| --- | --- | --- |
| 種類 | 事故がどう起きるかを説明するモデル | どう守るかを決める設計の方針 |
| 主に使う場面 | 起きた事故のふりかえり、潜在的な条件の洗い出し | システムや運用を作るとき |
| 問い | なぜすべての層の穴が並んだのか | 1 枚が破られたら、次はどの層が止めるのか |

## 層が独立していないと、穴は一緒に開く

層を重ねる効果は、それぞれの穴がばらばらに開くことが前提。同じ弱点を共有していると、1 つの原因で複数の層に同時に穴が開き、実際の層の数より薄くなる。

| 共有しがちなもの | 例 |
| --- | --- |
| 同じ人・同じ思い込み | 書いた人がテストも書き、同じ見落としがテストにも入る |
| 同じ基盤 | 監視が本番と同じ基盤の上で動いていて、障害のときに監視も一緒に止まる |
| 同じ依存先 | 本番も予備も同じリージョンの同じサービスに頼っている（ [コントロールプレーンが止まったら](https://memo.taka1156.site/md/static-stability.md) の隠れた依存） |
| 同じ鍵 | 複数の層の認証が 1 つの強い権限の鍵でまとめて突破できる |

層を足すときは、枚数より「別の理由で穴が開く層か」を見る。作る人・動く場所・頼る相手が違う層ほど、穴が並びにくい。

## モデルの限界

スイスチーズモデルには、事故を単純化しすぎている、原因を一直線に並べて見ている、という批判がある。複雑なシステムでは、壊れた部品を探すより、普段なぜうまくいっているのかから見るべきだとする立場（Hollnagel らの Safety-II）もある。一方で、モデルの土台はシステム全体の見方で、高リスクの分野で使われ続けており、今も有効だとする反論もある。図の単純さを「事故は単純」と取り違えず、潜在的な条件を探すための入口として使うのがよい。

## よくある誤解

✗ 誤解: スイスチーズモデルは「防御を何枚も重ねよ」という教えだ

✓ 正しくは: モデルそのものは、事故がなぜ防御をすり抜けるのかを説明するもの。「層を重ねて守る」のはそれに対する方針（多層防御）で、両者は事故の側と対策の側から同じことを見ている。

✗ 誤解: 層を 1 枚増やせば、その分だけ確実に安全になる

✓ 正しくは: 同じ人・同じ基盤・同じ依存先を共有する層は、同じ原因で一緒に穴が開く。枚数より、別の理由で穴が開く独立した層かどうかが効く。

✗ 誤解: 事故の原因は、最後に操作を誤った人だ

✓ 正しくは: その場の誤りは穴の 1 つにすぎず、ほかの層の穴（確認なしで実行できる、権限が強すぎるなどの潜在的な条件）が並んで初めて事故になる。誤りを責めるより、条件を直す方が再発を防げる。
