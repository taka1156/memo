「決める側」と「運ぶ側」を分ける考え方。ネットワーク機器の狭い意味から、クラウドの広い意味まで

コントロールプレーンとデータプレーン [コントロールプレーンが止まったら](https://memo.taka1156.site/md/static-stability.md)

**ざっくり言うと**

- コントロールプレーンは経路や設定を「決める側」、データプレーンは毎回の通信や処理を「運ぶ側」。
- 元はルーターの中の役割分担（狭義）で、クラウドや Kubernetes では仕組み全体の分け方（広義）に広がった。
- 同じ言葉でも文脈で指す範囲が変わるので、「何のコントロールプレーンか」を主語に付けて話す。

## 共通の形

どちらの意味でも形は同じ。決める側が「結果」を作って渡し、運ぶ側はその結果だけを見て、毎回の仕事を速く大量にこなす。

**コントロールプレーン** 何をどう流すかを決める。量は少ないが処理は複雑

**渡す結果** 転送表・設定・「望ましい状態」など

**データプレーン** 結果に従って 1 件ずつ処理する。量は多いが処理は単純

コントロールプレーン（決める側） データプレーン（運ぶ側）

プレーン（plane、層）は「どこで動いているか」ではなく「何の役割か」で分ける言葉。1 台の機器や 1 つのサービスの中に両方があることも多い。

## 狭義：ネットワーク機器の中の役割分担

もともとはルーターやスイッチの中の分け方。CPU で動くソフトウェアが経路を決め、専用のチップ（ASIC）が決まった表のとおりにパケットを転送する。

**マネジメントプレーン** SSH・SNMP・API で機器に設定を入れる、状態を見る

設定

**コントロールプレーン** BGP・OSPF などで隣の機器と経路を交換し、経路表（RIB）を作る。選んだ経路を転送表（FIB）に書き込む

転送表（FIB）

**データプレーン（フォワーディングプレーン）** 届いたパケットの宛先を転送表で引き、出口へ流す。1 秒に何百万件もさばく

マネジメントプレーン コントロールプレーン データプレーン

ネットワークの世界では、このようにマネジメントプレーンを別に数えて 3 層で説明することが多い。VMware NSX も「マネジメント・コントロール・データ」の 3 層で構成を説明している。

## 広義：仕組み全体の分け方

クラウドや分散システムでは、同じ分け方を仕組み全体に当てはめる。AWS も「ネットワークの用語だが、AWS の中のあらゆる所で使っている」と説明している。

| --- | --- | --- |
| コントロールプレーン | kube-apiserver・etcd・スケジューラー・コントローラー | 宣言された「望ましい状態」を保存し、どのノードで何を動かすかを決め、ずれを直し続ける |
| データプレーン | 各ノードのコンテナランタイム・Pod・ネットワーク | 実際にアプリを動かし、リクエストをさばく |

| --- | --- | --- |
| コントロールプレーン | istiod | ルーティングの規則・証明書・ポリシーを作り、各プロキシに配る |
| データプレーン | 各 Pod の横の Envoy プロキシ（サイドカーモード）、またはノードごとの ztunnel と必要に応じた waypoint プロキシ（アンビエントモード） | 配られた規則で、サービス間の通信を 1 件ずつ中継する |

|  | EC2 の例 | IAM の例 |
| --- | --- | --- |
| コントロールプレーン | インスタンスを起動・停止する API、置き場所を決める仕組み | ユーザー・ロール・ポリシーを作る・変える API（us-east-1 にある） |
| データプレーン | 動いているインスタンス、VPC のルートどおりのパケット転送、EBS の読み書き | 各リクエストの認証・認可（リージョンごとに分かれている） |

|  | 部品 | していること |
| --- | --- | --- |
| コントロールプレーン | 管理画面・設定 API | キャッシュの規則・証明書・WAF のルールを受け付け、世界中のエッジに配る |
| データプレーン | 各地のエッジサーバー | 配られた設定で、利用者のリクエストに 1 件ずつ応える |

どの例でも、データプレーンは「配られた結果」で動き、コントロールプレーンに毎回問い合わせない作りを目指す。止まったときにどうなるかは [コントロールプレーンが止まったら](https://memo.taka1156.site/md/static-stability.md) で扱う。

## なぜ分けるか

|  | コントロールプレーン | データプレーン |
| --- | --- | --- |
| 量 | 少ない（設定の変更・経路の更新） | 多い（すべての通信・リクエスト） |
| 処理 | 複雑。部品と依存先が多い | 単純。決まった表を引くだけ |
| 大事にすること | 一貫性（全体で同じ設定になること） | 可用性と速さ（止まらず、遅れないこと） |
| 壊れやすさ | 動く部品が多いぶん、壊れる確率が高い | 単純なぶん、高い可用性を目標にできる |

性質がまったく違うので、まとめて作るとどちらにも合わない。分けておけば、データプレーンを速く単純に保ったまま、コントロールプレーンだけを作り込める。障害の影響も分けられる。

## 現場ではどう呼び分けるか

「狭義」「広義」とはほとんど言わない。「ルーターの」「Kubernetes の」「AWS の」と主語を付けて話せば意味が決まる。主語がないときは、次の手がかりで判断する。

| 手がかり | 狭義（ネットワーク機器） | 広義（クラウド・分散システム） |
| --- | --- | --- |
| 話している人 | ネットワークエンジニア・NOC | SRE・クラウドやプラットフォームのエンジニア |
| 一緒に出る語 | BGP・OSPF・RIB / FIB・ASIC・フォワーディング | API・望ましい状態・調整ループ（reconcile）・オーケストレーション |
| 層の数 | マネジメントプレーンを入れた 3 層が多い | コントロールとデータの 2 層が多い |

### 同じ「設定を入れる API」でも呼び名が変わる

| していること | 狭義での呼び名 | 広義での呼び名 |
| --- | --- | --- |
| 人やツールが API で設定を入れる | マネジメントプレーン | コントロールプレーン |
| 設定や状況から、実際に流す経路・配置を計算する | コントロールプレーン |  |
| 毎回の通信・処理をこなす | データプレーン | データプレーン |

クラウドでいう「コントロールプレーン」は、ネットワーク機器でいうマネジメントプレーンとコントロールプレーンをまとめたものにおおよそ当たる。ネットワークの人とクラウドの人の話がかみ合わないのは、たいていここ。

## SDN：狭義から広義への橋渡し

SDN（ソフトウェア定義ネットワーク）は、各スイッチの中にあったコントロールプレーンを、外のコントローラーに集めた仕組み。スイッチはデータプレーンだけになり、コントローラーが全体の転送表を計算して配る。機器の中の分け方を、そのまま機器の外へ出したことで、「仕組み全体を 2 つに分ける」広義の使い方につながっていった。

## 境界があいまいなところ

真ん中の典型例ははっきり分けられるが、境界では人によって言うことが変わる。

| あいまいな所 | なぜ迷うか |
| --- | --- |
| Kubernetes の kubelet | ノードの上で動くのでデータプレーン側にも見えるが、仕事はコントロールプレーンの指示を受けて Pod を動かす「出先の担当」 |
| オートスケール | 動かしているのは制御のループ（決める側）なのに、止まると今のトラフィックをさばけなくなる |
| ルーター自身に宛てたパケット | BGP や SSH の通信はデータプレーンを通ってから CPU（コントロールプレーン）へ回される（punt）。ここを狙った攻撃から守るのが CoPP（Control Plane Policing） |
| 1 つのサービスに両方がある | AWS の Route 53 は、レコードの変更がコントロールプレーン、DNS の応答とヘルスチェックがデータプレーン。サービス名だけでは、どちらの話か決まらない |
| 隠れた依存 | 設計上は独立しているはずのデータプレーンが、実は動いている最中にコントロールプレーンや別の地域を呼んでいる。障害で初めて分かることが多い |

最後の 2 つは障害のときに効いてくる。具体例は [コントロールプレーンが止まったら](https://memo.taka1156.site/md/static-stability.md) にある。

## よくある誤解

✗ 誤解: コントロールプレーンという言葉は、どの現場でも同じ範囲を指す

✓ 正しくは: ネットワーク機器では経路を決める部分だけを指し、設定を入れる部分はマネジメントプレーンと呼んで分ける。クラウドでは設定 API を含めた「決める側」全体を指す。主語（何のコントロールプレーンか）を付けて話す。

✗ 誤解: どちらのプレーンかは、部品が動いている場所で決まる

✓ 正しくは: 決めるのは役割。ノードの上で動く kubelet がコントロールプレーンの出先として働くように、同じ場所に両方の役割が同居することもある。

✗ 誤解: 1 つのサービスは、丸ごとどちらか一方のプレーンに属する

✓ 正しくは: 多くのサービスは両方を持つ。Route 53 ならレコードの変更はコントロールプレーン、DNS の応答はデータプレーン。障害の影響を考えるときは「どの操作か」まで分ける。
