# API のバージョニングと後方互換

> どの変更がクライアントを壊すか、バージョンの付け方（URL・ヘッダー・日付）、Expand and Contract で無停止に変える手順、非推奨の伝え方を図解。

クライアントを壊さずに API を変えるための決めごと

**ざっくり言うと**

- API は公開した瞬間から、自分では更新できないクライアントとの **約束** になる。
- 追加は基本的に安全で、削除・名前変更・型や意味の変更は壊す。壊す変更だけを新しいバージョンにまとめる。
- 変えるときは「新旧を両方出す → 移ってもらう → 古い方を消す」の順にし、非推奨は期限つきで伝える。

## どの変更がクライアントを壊すか

変更を選ぶと、既存のクライアントにとって安全かどうかと理由が出る。

レスポンスに項目を追加

任意の引数を追加

enum に値を追加

必須の引数を追加

項目の名前を変える

型を変える

検証を厳しくする

安全（ほとんどの場合）

知らない項目を無視するクライアントには影響しない。ただし、知らない項目があるとエラーにする厳しいデシリアライザを使うクライアントは壊れる。だから API の利用規約やドキュメントに「項目は予告なく増える。知らない項目は無視すること」と書いておく。

安全

付けなかったときの動きが今までと同じなら、既存のクライアントは何も変えなくてよい。省略時の既定値を「今までの動き」以外にすると、それは意味の変更になり壊す。

注意（壊すことがある）

`status` に `"refunded"` を足すと、 `switch` で全部の値を書き分けていたクライアントは知らない値で落ちたり、想定外の分岐に入ったりする。値が増える可能性のある enum は、最初から「知らない値が来たら既定の扱いにする」とドキュメントに書き、クライアントにもそう実装してもらう。

壊す

既存のクライアントはその引数を送っていないので、全部のリクエストが 400 になる。追加するなら任意の引数として足し、省略時は今までの動きにする。

壊す

古い名前を読んでいるクライアントからは、項目が消えたのと同じ。新しい名前を足して両方を返し、古い名前を非推奨にしてから消す（下の「Expand and Contract」）。

壊す

`"id": 123` （数値）を `"id": "123"` （文字列）にすると、型のある言語のクライアントは読み込みで失敗する。ID は最初から文字列にしておくと、桁が増えても JavaScript の数値の精度の問題も起きない。

壊す

今まで通っていた値（長い名前・空文字など）を新しく拒否すると、それを送っていたクライアントが失敗する。仕様に書いていなくても、 **実際の動き** に頼っているクライアントがいる。厳しくするなら新しいバージョンで行う。

| 変更 | 判定 |
| --- | --- |
| 新しいエンドポイント・新しい任意の項目や引数を足す | 安全 |
| enum の値・エラーの種類を足す | 注意 |
| 項目・エンドポイントを消す、名前を変える | 壊す |
| 型・単位・意味を変える（円 → 銭、UTC → 現地時刻） | 壊す |
| 必須の引数を足す・検証を厳しくする・省略時の既定値を変える | 壊す |
| ステータスコードやエラーの形を変える | 壊す |

受け取る側は「知らない項目は無視し、知らない enum の値は既定の扱いにする」と作っておくと、送る側が足す変更に強くなる（tolerant reader と呼ばれる考え方）。

## バージョンの付け方

| 方式 | 例 | よい所 | 気をつける所 |
| --- | --- | --- | --- |
| URL のパス | `/v1/orders` | 見てすぐ分かる。ルーティングやキャッシュで分けやすい。いちばん多い | 大きな区切りにしか使えない。v1 と v2 を長く並べて持つことになる |
| ヘッダー（メディアタイプ） | `Accept: application/vnd.example.v2+json` | URL がリソースを指すまま変わらない | ブラウザで開いて試しにくい。キャッシュには `Vary` が要る |
| 日付のバージョン | `Stripe-Version: 2026-10-28.endive` | 細かい変更を日付ごとに積める。アカウントごとに固定し、各自のペースで上げてもらえる | サーバー側で日付ごとの差分を変換する仕組みが要る。Stripe は日付にリリース名を付け、毎月の互換リリースと、壊す変更を含む年 2 回のメジャーリリースに分けている |
| クエリ引数 | `?api-version=2024-05-01` | 試しやすい | 付け忘れたときの既定のバージョンを決めておく必要がある |

どの方式でも、 **バージョンを上げるのは壊す変更をまとめるときだけ** にする。足すだけの変更は今のバージョンに入れる。URL のバージョンは `v1` ・ `v2` のようにメジャーだけにし、 `v1.2.3` のような細かい番号を URL に入れない（足すだけの変更のたびにクライアントが URL を変えることになる）。

## 壊す変更を無停止で入れる：Expand and Contract

`name` を `full_name` に変える例。どの時点でも、古いクライアントと新しいクライアントの両方が動くように段を分ける。DB のスキーマ変更と同じ考え方（Expand and Contract パターン。Parallel Change とも呼ぶ）。

1. **Expand（拡張）：両方を返す** レスポンスに `full_name` を足し、 `name` も同じ値で返し続ける。リクエストもどちらの名前でも受け付ける。
2. **非推奨を伝える** ドキュメントと変更履歴に書き、 `name` を使うリクエストへのレスポンスに `Deprecation` と `Sunset` （廃止予定日）のヘッダーを付ける。
3. **移ってもらう** アクセスログで古い項目・古いバージョンを使っているクライアントを数え、残っている利用者に個別に連絡する。
4. **Contract（縮小）：古い方を消す** 利用がほぼ 0 になり、予告した期日を過ぎてから消す。利用が残っているのに消すと、その時点で壊れる。

```
HTTP/1.1 200 OK
Deprecation: @1767225600          # 非推奨になった（なる）日時。Unix 時刻
Sunset: Wed, 30 Sep 2026 23:59:59 GMT   # この日以降は使えなくなる予定
Link: <https://example.com/docs/migrate-v2>; rel="deprecation"
```

`Sunset` は RFC 8594、 `Deprecation` は RFC 9745 で決められたヘッダー。ヘッダーを読むクライアントは少ないので、メール・ダッシュボードでの告知と組み合わせる。

## gRPC・GraphQL での考え方

### gRPC（Protocol Buffers）

- データはフィールド **番号** で読み書きされる。名前を変えても番号が同じならバイナリの互換は保たれる（JSON に変換して使う所では名前が効くので注意）。
- 消したフィールドの番号と名前は `reserved` にして、 **二度と使わない** 。別の意味で使い回すと、古いクライアントが新しい値を古い意味で読む。
- 壊す変更はパッケージ名にバージョンを入れて分ける（ `package shop.v2;` ）。

### GraphQL

- クライアントは要る項目だけを取りに来るので、項目の追加は既存のクエリに影響しない。だからバージョンを付けず、1 つのスキーマを育てるのが普通。
- 消したい項目には `@deprecated(reason: "...")` を付け、どのクエリがまだ使っているかを計測してから消す。
- バージョンがない分、「消す」判断は利用状況の計測が頼り。

## よくある誤解

✗ 誤解: 項目や値を足すだけの変更なら、どのクライアントも絶対に壊れない

✓ 正しくは: 知らない項目でエラーにする厳しいデシリアライザや、enum の全部の値を `switch` で書き分けたクライアントは壊れる。足す変更を安全にするには、「知らないものは無視する」ことを API の約束として先に書いておく。

✗ 誤解: v2 を公開すれば、v1 はすぐに止めてよい

✓ 正しくは: クライアントのアプリは利用者が更新するまで古いまま動き続ける。モバイルアプリなどは何か月も残る。利用状況を計測し、期日を予告してから止める。

✗ 誤解: 仕様書に書いていない動きなら、変えても互換性の問題にはならない

✓ 正しくは: 利用者が十分に多いと、観測できる動きのどれかに必ず誰かが頼っている（ハイラムの法則）。並び順やエラーメッセージの文言も、変えるときは影響を見積もる。

✗ 誤解: GraphQL ならバージョン管理を考えなくてよい

✓ 正しくは: バージョン番号を付けないだけで、項目を消したり型を変えたりすれば同じように壊れる。 `@deprecated` と利用状況の計測で、Expand and Contract の手順を踏む。
