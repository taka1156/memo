レイヤード / ヘキサゴナル / オニオン / クリーン — 違うのは描き方と言葉、本質は「依存の向き」

**ざっくり言うと**

- **レイヤード** だけが「上から下へ（DB に向かって）」依存する。残り 3 つは **依存性逆転で「外から内へ」依存** させ、ドメインを DB やフレームワークから守る。
- ヘキサゴナル・オニオン・クリーンの違いは、 **図の描き方と用語** 、そして **中心をどこまで細かく分けるか** くらい。
- 実務では「依存の向きを守る」「I/O を境界の外に出す」ができていれば、どの名前を名乗っても大差ない。

### レイヤードアーキテクチャ Layered Architecture

（図: プレゼンテーション層 / Controller / View / ビジネス層 / OrderService / データアクセス層 / OrderDao (SQL) / データベース / MySQL → https://memo.taka1156.site/architecture-compare.html#layered）

**依存の向き** 上 → 下（ビジネス層がデータアクセス層を知っている）

**中心にあるもの** 中心はない。最下層の DB が土台

**良いところ** 直感的。CRUD 中心なら最短で書ける

**つらくなるところ** テーブル設計がビジネスロジックの形を決めてしまう。DB なしでテストしにくい

### ヘキサゴナルアーキテクチャ Ports & Adapters

（図: DRIVING / DRIVEN / アプリケーション / ドメイン＋ユースケース / Web API / テスト / MySQL / メール送信 / = ポート（interface） / アダプターはどちら側もポートに依存する → https://memo.taka1156.site/architecture-compare.html#hexagonal）

**依存の向き** 外側のアダプター → 内側のポート（左右どちらも内向き）

**中心にあるもの** アプリケーション全体（中身の分け方は決めていない）

**良いところ** 「呼ぶ側（Driving）」と「呼ばれる側（Driven）」を左右に分けて考えられる。テストも Web も同じ入口から入れる

**注意** 六角形に意味はない（辺が多くて描きやすいだけ）。中の層構造は自分で決める

### オニオンアーキテクチャ Onion Architecture

（図: ドメイン / モデル / ドメインサービス / アプリケーションサービス / UI ・ インフラ ・ テスト / 依存はすべて中心へ → https://memo.taka1156.site/architecture-compare.html#onion）

**依存の向き** 外 → 内のみ。リポジトリの interface はドメイン側の層に置く

**中心にあるもの** ドメインモデル（エンティティ・値オブジェクト）

**良いところ** DDD の用語とそのまま対応し、ドメインの中も層に分けて描ける

**注意** 層の数に正解はない。小さいアプリでは「ドメイン／アプリ／外側」の 3 つで十分

ディレクトリ構成やリクエストの流れは [DDD とオニオンアーキテクチャ](https://memo.taka1156.site/md/ddd-onion.md) に詳しく書いています。

### クリーンアーキテクチャ Clean Architecture

（図: Entities / Use Cases / Interface Adapters / Controller / Presenter / Gateway / Frameworks & Drivers / Web / DB / UI / 依存ルール：内側は外側を知らない → https://memo.taka1156.site/architecture-compare.html#clean）

**依存の向き** 外 → 内のみ（「依存ルール」と呼ぶ）

**中心にあるもの** エンティティ（業務ルール）

**良いところ** ユースケース（Interactor）を独立した単位として書く、入力／出力の境界を明示するなど、作り方まで具体的（1 クラス 1 操作にするのはよく使われる流儀）

**注意** Presenter・InputPort・OutputPort まで全部作るとファイルが大量に増える。円の数も「4 つでなくてよい」とされている

## 用語の対応表

同じものを違う名前で呼んでいるだけ、という部分が多いです。横に読むと対応がわかります。

| 役割 | レイヤード | ヘキサゴナル | オニオン | クリーン |
| --- | --- | --- | --- | --- |
| 業務ルールの中心 | ビジネス層 | アプリケーション（内部） | ドメインモデル | Entities |
| 操作の手順 | ビジネス層（Service） | アプリケーション（内部） | アプリケーションサービス | Use Cases (Interactor) |
| 外との約束（interface） | （なし。DAO を直接呼ぶ） | ポート | ドメイン層のリポジトリ interface | Gateway / Input・Output Port |
| 入口（HTTP・CLI） | プレゼンテーション層 | 駆動するアダプター (Driving) | UI（外周） | Controller |
| 出口（DB・外部 API） | データアクセス層 | 駆動されるアダプター (Driven) | インフラ（外周） | Gateway 実装 / DB |
| 依存の向き | 上 → 下（DB へ） | 外 → 内 | 外 → 内 | 外 → 内 |

## 本当に違うのはここだけ

**1. 依存の向き**

レイヤードだけが DB に向かって依存する。ほか 3 つは [依存性逆転](https://memo.taka1156.site/md/solid.md) でドメインに向ける。ここが最大の分かれ目。

**2. 中心の分け方**

ヘキサゴナルは中を分けない。オニオンはドメインを層に分ける。クリーンはエンティティとユースケースを分ける。

**3. 境界の作り込み**

クリーンは入出力の境界（Input/Output Port・Presenter）まで決めている。ヘキサゴナルは「ポートを置く」以上は決めない。

補足：レイヤードでも「ビジネス層が interface を持ち、データアクセス層がそれを実装する」形にすれば、実質オニオンと同じになる。名前より矢印の向きを見る。

## 選び方

**Q1**

ほぼ CRUD で、業務ルールは画面とテーブルの写しに近い？

はい → レイヤード（またはフレームワーク標準の構成）で十分

**Q2**

DB・外部 API を差し替えたい／I/O なしでテストしたい？

はい → ヘキサゴナルの「ポートとアダプター」だけ取り入れる

**Q3**

業務ルールが複雑で、DDD のモデリングをしている？

はい → オニオン（DDD の用語とそのまま合う）

**Q4**

チームが大きく、ユースケース単位で書き方を揃えたい？

はい → クリーン（ただし Presenter などは必要な所だけ）

迷ったら「ヘキサゴナル程度（ドメイン／ユースケース／アダプター の 3 フォルダ）」から始めて、必要になった所だけ層を足すのが失敗しにくい。

## よくある誤解

クリーンアーキテクチャは必ず 4 層（4 つの円）にする

円の数は例にすぎず、必要に応じて増減してよいとされている。守るべきなのは「依存は内側へ」というルールだけ。

ヘキサゴナルは 6 つのポートを持つ

六角形は、ポートやアダプターを必要なだけ描き込める余白を作り、一次元の層の図から離れるために選ばれた形で、6 という数に意味はない。正式名も Ports and Adapters。

オニオンとクリーンは別物なので混ぜてはいけない

どちらも依存性逆転でドメインを中心にする同じ系統。オニオンの層分けにクリーンのユースケースクラスを使う、のような組み合わせは普通に行われている。

レイヤードはもう古くて使うべきではない

業務ルールが薄いアプリでは、最も少ないコードで済む合理的な選択。つらくなってから DIP を入れて内向きに変えればよい。
