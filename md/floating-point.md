# 浮動小数点と数値表現

> 0.1 + 0.2 が 0.3 にならない理由を IEEE 754 のビットから確かめ、安全な整数の上限・NaN・お金の扱い・丸め・整数オーバーフローまで実務で困る点を整理する

0.1 + 0.2 ≠ 0.3 —— コンピューターの小数は「2 進数で近い値」を持っているだけ

**ざっくり言うと**

- 多くの言語の小数（JS の Number、 `double` 、 `f64` ）は IEEE 754 の **2 進浮動小数点** 。0.1 は 2 進数で割り切れないので、 **最も近い値** が入っている。だから誤差が出る。
- JS の Number で正確に表せる整数は **±2^53−1 まで** 。大きな ID を数値で受け取ると下の桁が壊れる。
- お金は **最小単位の整数** （円・セント）か **10 進の型** （SQL の DECIMAL など）で持つ。小数の比較は `===` ではなく許容誤差で。

## なぜ 0.1 が正確に入らないのか

10 進数で 1/3 = 0.333… が終わらないのと同じで、2 進数では 1/10 が終わりません。

0.1（10 進） = 0.0001100110011…（2 進、0011 が無限に続く） → 52 ビットに丸める（最も近い値を選ぶ） 少しだけずれた値

```
0.1 + 0.2            // 0.30000000000000004
0.1 + 0.2 === 0.3    // false
0.5 + 0.25 === 0.75  // true（2 進で割り切れる数は正確）
```

これは JS 固有の問題ではない。Python・Java・C・Rust の `double` / `f64` でも同じ結果になる。

### 数が大きいほど、隣の数との間隔が広がる

ビット数は一定なので、大きな数ほど表せる値がまばらになります。2^53 を超えると、間隔が 2 になって奇数が表せなくなります。

2^53−2 2^53−1 2^53 ×（2^53+1 は無い） 2^53+2

```
Number.MAX_SAFE_INTEGER        // 9007199254740991（2^53 − 1）
9007199254740993               // 9007199254740992 になる
JSON.parse('{"id":1234567890123456789}').id  // 1234567890123456800（下の桁が壊れる）
BigInt('1234567890123456789')  // 1234567890123456789n（正確）
```

64 ビット整数の ID（Snowflake ID や DB の BIGINT）を JSON で JS に渡すときは、 **文字列として送る** のが定石。

## 比較と集計

NG

```
if (a + b === 0.3) { … }
```

OK：許容誤差で比べる

```
const near = (x, y, rel = 1e-9) =>
  Math.abs(x - y) <= rel * Math.max(1, Math.abs(x), Math.abs(y));
```

誤差は計算のたびに積み重なり、 **足す順番によって結果が変わります** 。大きな数に小さな数を何度も足すと、小さい側が丸めで消えていきます。

```
let s = 0; for (let i = 0; i < 10; i++) s += 0.1;
s   // 0.9999999999999999
1e16 + 1 - 1e16   // 0（1 が消える）
```

| 方法 | 例 | 向く場面 |

## 整数型のあふれ

固定長の整数型（ `int32` など）は上限を超えると **反対側に回り込む** （ラップアラウンド）か、言語によってはエラーになります。

| 言語・場面 | 上限を超えると |
| --- | --- |
| C / C++ の符号付き整数 | 未定義動作（最適化で予想外の結果になる） |
| Java の int / Go の int32 | 回り込む（2147483647 + 1 → −2147483648）。Go の int は 64 ビット環境では 64 ビット |
| Rust | デバッグビルドはパニック、リリースビルドは回り込み。 `checked_add` などで明示する（ [Rust](https://memo.taka1156.site/md/rust.md) ） |
| JS のビット演算 | 32 ビット整数に変換される（ `2**31 \| 0` → −2147483648） |
| Python の int | 任意精度なのであふれない |

## 精度を落とす使い方：機械学習

LLM などでは、64 ビットどころか 16 ビット（FP16・BF16）や 8 ビット・4 ビットの数で重みを持ちます。少しの誤差より、メモリと速度を優先しているためです（量子化。 [LLM の仕組み](https://memo.taka1156.site/md/llm-basics.md) ）。BF16 は指数のビットを float32 と同じにし、仮数を削って「表せる範囲は広いまま、精度だけ落とした」形式です。

## よくある誤解

0.1 + 0.2 の問題は JavaScript のバグ

IEEE 754 の 2 進浮動小数点を使う言語ならどれでも起きる。仕様どおりの動作。

小数点以下 2 桁で表示すれば計算も正確になる

表示を丸めても内部の値は変わらない。合計や比較で誤差が表に出る。

Number で扱えるのは 2^53 まで

もっと大きな数も入る（約 1.8×10^308 まで）。ただ 2^53 を超えると整数を 1 刻みで表せなくなる。「安全に」扱えるのがそこまで。
