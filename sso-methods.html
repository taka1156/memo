SSO の方式

エージェント / リバースプロキシ / 透過型 / 代理認証 / フェデレーション / Kerberos — どこでログインを肩代わりするか

SSO の方式 SAML 2.0 OAuth 2.0 / OIDC
ざっくり言うと
  • SSO は「一度のログインで複数のシステムを使える」状態のことで、実現する方式はいくつもある
  • 方式の違いは、ログインを誰が肩代わりするか（アプリ内・途中の中継・端末・外部の IdP・OS）
  • 社外の SaaS はフェデレーション（SAML・OIDC）、改修できない社内システムはプロキシや代理認証、と組み合わせる

SSO は状態の名前

SSO (Single Sign-On) は特定の仕様の名前ではなく、「一度ログインすれば、ほかのシステムでは聞かれない」という状態を指す。そうするには、各システムが自分でパスワードを確かめる代わりに、どこか 1 か所でのログインの結果を信用する必要がある。その「どこか」と「結果の伝え方」で方式が分かれる。

国内の解説では「エージェント・リバースプロキシ・代理認証・フェデレーション・透過型」の 5 つに分けることが多い。ここではそれに、Windows の社内システムで使われる Kerberos を足して 6 つにする。SAML と OIDC は別の方式ではなく、フェデレーション方式で使うプロトコル。分け方や呼び名は資料によって違い、実際の現場では複数の方式を組み合わせることも普通。

アプリの手前にリバースプロキシを置き、すべてのアクセスをそこに通す。プロキシがログインを確かめ、通過した通信にだけ「誰か」をヘッダーなどで付けてアプリに渡す。アプリはそのヘッダーを信じるだけでよい。

今のクラウドでは、Google Cloud の IAP (Identity-Aware Proxy)、Cloudflare Access、oauth2-proxy などがこの形。プロキシ自身は裏で IdP にフェデレーション（OIDC・SAML）でログインを頼むことが多い。

向く
  • 改修できない・したくない社内の Web アプリ
  • アクセスの記録と制御を 1 か所にまとめたいとき
弱点
  • 全通信が通るので、プロキシが詰まる・落ちると全部止まる
  • プロキシを迂回してアプリに直接届くと、ヘッダーを偽って誰にでもなれる

2 つ目の弱点が特に大事。アプリはプロキシ以外からの通信を受け付けないようにし（ネットワークで閉じる）、プロキシは利用者が送ってきた同じ名前のヘッダーを消してから付け直す。IAP はさらに、署名付きの JWT をヘッダーに付け、アプリ側で検証することを勧めている（JWT の署名の仕組みそのもの）。

端末とシステムの間の通信経路に、通信を見張る SSO 製品（中継装置）を置く。普段の通信はそのまま通し、ログインが必要な場面だけ、あらかじめ登録した ID・パスワードを利用者の代わりに送る。利用者にもシステムにも中継の存在が見えない（透過的な）ので、この名前がある。

リバースプロキシ方式との違いは、アクセス先の URL や DNS をプロキシに向け直さないこと。代理認証方式との違いは、代行入力を端末ではなく経路上の装置で行うこと（端末にエージェントを入れなくてよい）。

向く
  • URL やネットワーク構成を変えずに、既存のシステムをまとめて SSO にしたいとき
  • 端末やブラウザを選ばない
弱点
  • 代行入力なので、各システムのパスワードはなくならない
  • 透過型に対応した SSO 製品が要る。HTTPS の中身を見るには経路上で暗号を解く必要もある

透過型は特定の標準仕様ではなく、製品ごとの実装の名前に近い。詳しい動きは製品の資料で確かめる。

利用者の PC（やブラウザ拡張）に入れたエージェントが、各システムのログイン画面を見つけると、保管しておいた ID とパスワードを代わりに入力する（代行入力とも呼ぶ）。システム側から見ると、人が手で入力したのと区別がつかない。リバースプロキシが代わりにログインフォームを送る作りもある。

向く
  • 画面でのログインしか持たない古いシステムや、パッケージ製品
  • システムを一切変えずに始められる
弱点
  • 各システムのパスワードはなくならない。保管庫が盗まれると全部漏れる
  • ログイン画面が変わると自動入力が動かなくなる

仕組みはパスワードマネージャーに近い。「使う人が覚えなくてよい」は実現するが、「パスワードを各システムに持たせない」は実現しない。保管庫の守り方はシークレット管理と同じ考え方になる。

ログインを外部の IdP (Identity Provider) に任せ、IdP が署名した「この人は誰か」の証明をアプリが検証して信用する。アプリと IdP は事前に設定（メタデータ・鍵の場所）を交換して信頼関係を結んでおく。証明の運び方で、主に次の 2 つのプロトコルがある。

SAML 2.0

運ぶもの：署名付き XML（アサーション）。ブラウザ経由でアプリに POST する

得意：ブラウザで使う業務 SaaS・社内システム。企業の IdP との接続で今も主流

苦手：スマホアプリ・SPA、API の呼び出し

詳しくは SAML 2.0

OpenID Connect (OIDC)

運ぶもの：署名付き JSON（ID トークン、JWT）。今の推奨である認可コードフローでは、ブラウザで運ぶのは認可コードだけで、トークンはサーバー同士で受け取る（古い Implicit Flow ではトークンもブラウザ経由で届く）

得意：Web に加えてスマホアプリ・SPA。OAuth 2.0 の上に乗るので、同じ流れで API 用のアクセストークンも取れる

苦手：OIDC に対応していない古い業務システムとの接続

詳しくは OAuth 2.0 / OIDC のフロー

向く
  • 社外の SaaS。ドメインも組織もまたげる
  • パスワードがアプリに一切渡らない
弱点
  • アプリが SAML か OIDC に対応している必要がある
  • 署名の検証を誤ると、なりすましを許す

多くの IdP はどちらも話せるので、1 つの IdP が SAML のアプリと OIDC のアプリを同時に受け持つのも普通。新しく作るアプリは OIDC を基本にし、企業向けに売る SaaS なら SAML にも対応する、という分け方が多い。

Windows の Active Directory に参加した PC では、PC へのログオンのときにドメインコントローラーが本人を確かめ、Kerberos のチケットを渡す。社内の Web アプリが 401 と WWW-Authenticate: Negotiate を返すと、ブラウザはそのチケットをヘッダーで送り、利用者は何も入力せずに入れる（統合 Windows 認証）。

向く
  • Windows ドメインの中だけで使う社内システム
  • PC へのログオン以外の操作がまったく要らない
弱点
  • ドメイン参加の PC・社内ネットワークが前提で、社外や個人端末に弱い
  • Kerberos が使えないと古い NTLM に落ちることがある

AD FS や Entra ID のような IdP が、IdP 自身のログインにこの仕組みを使い、そこから先はフェデレーションで SaaS につなぐ、という組み合わせもよくある。

どれを選ぶか

1 つに決めるより、システムごとに当てはめていくことが多い。上から順に見て、最初に当てはまったものを選ぶ。

  1. SAML か OIDC に対応しているか対応していればフェデレーション。社外の SaaS はほぼこれ。新しく作るアプリも、最初から OIDC（業務向け SaaS なら SAML も）に対応させる
  2. 自社で動かしている Web アプリか改修できないなら、手前にリバースプロキシ（IAP など）を置く。URL やネットワーク構成も変えたくないなら透過型。改修できるなら、エージェントを入れるより OIDC に対応させる方が後々楽
  3. Windows ドメインの中だけで使うか社内ネットワークとドメイン参加の PC だけで使うなら Kerberos（統合 Windows 認証）で入力なしにできる
  4. 画面でのログインしかないかどれも無理な古いシステム・パッケージは代理認証（経路上で行うなら透過型）。パスワードが残ることを前提に、保管庫と各パスワードの管理を固める

Cookie はドメインをまたいで共有できないので、アプリ同士がログイン状態を共有しているわけではない。2 つ目のアプリに行くと、そのアプリはやはり IdP にログインを頼む。ただ IdP 側のセッションがまだ生きているので、IdP は画面を出さずにすぐ結果を返す。これが「一度のログインで済む」の正体。

逆に言うと、ログイン後の各アプリは自分のセッションだけで動く。IdP でアカウントを止めると新しいログインは止まるが、発行済みのアプリのセッションはその期限まで生きる。重要なアプリはセッションを短めにし、アプリ側のアカウントの停止は SCIM などで IdP から同期する。

よくある誤解

SSO を入れるには SAML が必要

SAML はフェデレーション方式の手段の 1 つにすぎない。OIDC でも、リバースプロキシや代理認証、Kerberos でも SSO はできる。どれを使うかは、つなぐシステムが何に対応しているかで決まる。

SSO にすれば各システムのパスワードはなくなる

代理認証と透過型は、登録したパスワードを代わりに送るだけなので、各システムのパスワードはそのまま残る。パスワードがアプリに渡らなくなるのは、フェデレーションやリバースプロキシのように、システムが外部の確認結果を受け取る方式だけ。

リバースプロキシで認証するなら、アプリは何もしなくてよい

アプリにプロキシを通らずに届く経路があると、ユーザー名のヘッダーを自分で付けて誰にでもなれる。ネットワークでプロキシ以外からの通信を閉じ、できれば IAP の署名付き JWT のように、プロキシを通ったことをアプリでも検証する。

SSO を入れるとアプリ同士がログイン状態を共有する

フェデレーションで共有しているのは IdP のセッションだけ。各アプリは自分のセッションを別々に持ち、2 つ目のアプリでも IdP への問い合わせは起きている。IdP が画面を出さずに即答するので、利用者には一度で済んだように見える。

IdP でアカウントを無効にすれば、すべてのシステムから即座に締め出せる

止まるのは新しいログインだけ。各アプリのセッションは期限まで残り、アプリ側のアカウントも別に残る。代理認証や透過型でつないだシステムなら、登録していたパスワード自体を変えない限り使えてしまう。
