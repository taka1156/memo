スタックとヒープ / 手動・GC・参照カウント・所有権 / リークの見つけ方

**ざっくり言うと**

- 関数の中だけで使う決まった大きさの値は **スタック** （関数が終われば自動で消える）、大きさや寿命が実行時に決まるものは **ヒープ** に置く。
- 難しいのはヒープの「いつ解放するか」。 **手動（C）・GC（JS, Go, Java）・参照カウント（Swift。Python は参照カウント＋循環検出 GC）・所有権（Rust）** の 4 通りの答えがある。
- GC は「どこからもたどれなくなったもの」を回収する。 **たどれるまま放置したもの** （リスナー、キャッシュ、タイマー）は GC があってもリークする。

## プロセスのメモリ配置

プログラムを起動すると、OS はプロセスに（仮想的な）アドレス空間を与える。典型的な配置は次のとおり。

**スタック ↓** 関数呼び出しごとに積む。スレッドごとに 1 本

（空き）

**ヒープ ↑** 実行時に必要な分だけ確保

**データ** グローバル変数・静的変数

**テキスト** 機械語のプログラム本体（読み取り専用）

スタックとヒープは、どちらも同じ RAM 上の領域。違うのは「確保と解放の決まり方」。

## スタックとヒープ

|  | スタック | ヒープ |
| --- | --- | --- |
| 置くもの | ローカル変数、引数、戻り先。大きさがコンパイル時に決まるもの | 大きさや個数が実行時に決まるもの、関数より長生きするもの |
| 確保・解放 | 関数の開始・終了で自動。ポインタを動かすだけ | 空き領域を探して確保。解放の仕方が言語ごとに違う |
| 速さ | 非常に速い。連続しているのでキャッシュにも乗りやすい | 確保に手間がかかり、散らばりやすい |
| 大きさ | 小さい（数 MB 程度）。深い再帰で溢れる（stack overflow） | 大きい（物理メモリ＋スワップまで） |

### 例: 関数の中でオブジェクトを作る

```
function makeUser(name) {
  const age = 20;                 // 小さな値
  const user = { name, age };     // オブジェクト
  return user;
}
const u = makeUser("Mio");
```

STACK

**makeUser のフレーム** name → "Mio"

age = 20

user → ●

**呼び出し元** u → ●

HEAP

**{ name, age }** name: "Mio", age: 20

**"Mio"** 文字列

`makeUser` が終わるとそのフレームは消えるが、オブジェクトは `u` から指されているのでヒープに残る。 **「誰かが指している間は生かし、誰も指さなくなったら解放する」** のがヒープ管理の課題。

JS エンジンの実際の配置は最適化で変わる（小さな整数を値のまま持つ、逃げないオブジェクトをスタックに置く、など）。上は概念図。

## 解放する 4 つの方式

手動

C / C++（生ポインタ）

プログラマが `malloc` / `free` を書く。速く予測可能だが、忘れればリーク、早すぎれば **解放後使用** 、二回解放で破壊。

トレーシング GC

JS / Java / Go / C#

ランタイムが時々「たどれるもの」を調べ、残りをまとめて回収。書くのは楽だが、回収のタイミングは選べず、一時停止が起きうる。

参照カウント

Swift (ARC) / Rust の Rc・Arc / Python（循環は補助の GC が回収）

指している数を数え、0 になった瞬間に解放。すぐ解放されて予測しやすいが、 **循環参照** は 0 にならない。

所有権

Rust（C++ の RAII も近い）

値の持ち主を 1 人に決め、持ち主のスコープが終わると解放するコードを **コンパイラが挿入** 。実行時のコストなしで安全。代わりに借用のルールを守る必要がある。

手動管理のミスは重大な脆弱性につながりやすい。Microsoft は自社が CVE を割り当てた脆弱性の約 7 割（2019 年）、Chromium は深刻なセキュリティバグの約 7 割（2020 年）がメモリ安全性の問題だと報告している。新しいコードをメモリ安全な言語で書く流れはここから来ている。

## GC のしくみ — マーク＆スイープ

GC は「生きているか」を **到達可能性** で判断する。ルート（スタック上の変数・グローバル変数）から参照をたどって届くものは生きている、届かないものはゴミ。

① マーク

② スイープ

リセット

root はスタック上の変数。どのオブジェクトが回収されるか予想してから ① を押す。

- **D と E は互いに指し合っている** が、ルートから届かないのでトレーシング GC では回収される。参照カウントだけの仕組み（Swift の ARC など）だと、それぞれ 1 のまま残ってしまう（循環参照リーク）。
- 回収後に生き残ったものを詰めて隙間をなくす **コンパクション** を行う GC もある。

## 世代別 GC — 「ほとんどのオブジェクトはすぐ死ぬ」

**若い世代**

新しいオブジェクトはここに作る。小さいので頻繁に、短時間で回収できる。生き残ったものだけを移す。

**古い世代**

何回か生き残ったものを移す。大きいのでたまにしか回収しない。V8 ではメインの処理と並行・少しずつ進めて停止時間を短くしている。

- 一時的なオブジェクトを大量に作っても、若い世代で安く回収されるので、多くの場合は気にしなくてよい。
- 大量のオブジェクトが長生きする（巨大なキャッシュなど）と古い世代の GC が重くなる。
- ゲームやアニメーションで定期的にカクつくなら、DevTools の Performance で GC の時間を確かめる。

## Rust の所有権 — コンパイル時に解放を決める

```
fn main() {
    let a = String::from("hi");  // ヒープに確保。持ち主は a
    let b = a;                   // 所有権が b に移動（ムーブ）。a はもう使えない
    print_len(&b);               // 借用: 貸すだけで、持ち主は b のまま
}                                // b のスコープ終了 → ここで自動的に解放（drop）

fn print_len(s: &String) { println!("{}", s.len()); }
```

- 持ち主は常に 1 人なので、二回解放は起きず、通常は解放忘れも起きない（ただし `Rc` の循環や `mem::forget` ではリークしうる）。借用中に持ち主が消えるコード（ダングリング参照）は **コンパイルエラー** になる。
- 共有の持ち主が本当に必要なときだけ `Rc` / `Arc` （参照カウント）を使う。循環させるなら片方を `Weak` にする。

## GC があってもリークする — JS の典型例

GC が回収できるのは「たどれなくなったもの」だけ。 **不要になったのに、どこかから参照が残っている** とずっと生き続ける。

| 原因 | 例 | 対策 |
| --- | --- | --- |
| イベントリスナー | コンポーネントのマウントごとに `window` に登録し、外さない | アンマウント時に `removeEventListener` 、または `AbortController` の `signal` で一括解除 |
| タイマー | `setInterval` のコールバックが大きなデータをクロージャで持ち続ける | `clearInterval` 。React なら effect のクリーンアップで |
| 無制限のキャッシュ | グローバルな `Map` にリクエストごとの結果を足し続ける | 上限付き（LRU）にする。オブジェクトをキーにするなら `WeakMap` |
| 切り離された DOM | 画面から消した要素を変数や配列が持ち続ける | 参照を消す。DevTools のヒープスナップショットで「Detached」を検索 |
| サーバーのモジュール変数 | Node.js でリクエストごとにモジュールスコープの配列へ push | リクエストの外に状態を溜めない。外部ストアを使う |

### 調べ方（Chrome DevTools）

1. Memory タブで **ヒープスナップショット** を取る
2. 疑わしい操作（画面の開閉など）を何度か繰り返す
3. もう一度スナップショットを取り、 **Comparison** で増え続けているオブジェクトを探す
4. そのオブジェクトの **Retainers** （誰が参照を持っているか）をたどって、原因の参照を見つける

## よくある誤解

✗ GC のある言語ではメモリリークは起きない

✓ 不要な参照が残っていれば回収されない。リスナー・タイマー・キャッシュが典型的な原因。

✗ スタックが速いのは、速い種類のメモリだから

✓ どちらも同じ RAM。確保がポインタを動かすだけで済み、連続していてキャッシュに乗りやすいから速い。

✗ 変数に null を入れれば、その場でメモリが解放される

✓ 参照が 1 つ減るだけ。他に参照がなければ回収の対象になり、その後 GC が動いたときに回収される（いつになるかはランタイム次第）。
