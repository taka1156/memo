- Rust は GC（ガベージコレクタ）なしでメモリ安全を実現する言語。その鍵が **所有権 (ownership)・借用 (borrowing)・ライフタイム (lifetime)** 。

## 仕組み 1: コンパイル時に何をしているか

Rust のコンパイラ `rustc` は、ソースコードを段階的に変換しながらチェックする。安全性の要となる **借用チェッカ (borrow checker)** は、中間表現 MIR の上で動く。

太枠が「Rust らしい安全性」を保証する段階。ここで弾かれたコードは実行ファイルにならないので、実行時のコスト（GC やチェック処理）がかからない。

## 仕組み 2: 所有権 — スタックとヒープで見る

`String` の中身（文字列データ）はヒープ、変数はスタックにある「ポインタ・長さ・容量」の組。代入したときに何が起きるかを比べる。

ムーブ

clone

借用 &

Copy 型

（図: スタック / ヒープ / s1 / 無効（ムーブ済） / s2 / ptr/len/cap / "hello"）

```
let s1 = String::from("hello");
let s2 = s1;           // 所有権が s2 へ移動（ムーブ）
// println!("{s1}");  // ✕ コンパイルエラー: borrow of moved value
println!("{s2}");      // ○
```

ヒープのデータはコピーされず、 **持ち主の名札だけが付け替わる** 。もし s1 も有効なままだと、スコープを抜けたとき同じメモリを 2 回解放してしまう（二重解放）。Rust はそれをコンパイル時に禁止する。

（図: スタック / ヒープ / s1 / 有効 / s2 / "hello" / ↑ 複製）

```
let s1 = String::from("hello");
let s2 = s1.clone();   // ヒープのデータごと複製
println!("{s1} {s2}"); // ○ 両方使える
```

持ち主が 2 人になる代わりに、 **データも 2 つ** になる。コストがあるので明示的に `.clone()` と書かせる設計。

（図: スタック / ヒープ / s1 / 所有者 / &s1 / 借用（参照） / "hello"）

```
fn len(s: &String) -> usize { s.len() }

let s1 = String::from("hello");
let n = len(&s1);      // 貸すだけ。所有権は s1 のまま
println!("{s1} {n}");  // ○ s1 はまだ使える
```

参照は「 **持ち主を指す矢印** 」。借りた側がスコープを抜けても、データは解放されない。

```
let a: i32 = 5;
let b = a;             // i32 は Copy 型 → ビットごと複製
println!("{a} {b}");   // ○ 両方使える
```

整数・浮動小数点・ `bool` ・ `char` ・それらだけのタプルなど、 **スタックだけで完結する小さな型** は `Copy` トレイトを持ち、代入してもムーブではなくコピーになる。ヒープを持つ `String` や `Vec` は Copy にならない。

スコープを抜けた値は、所有者が自動で `drop` して解放する（RAII）。手動の `free` は不要。

## 仕組み 3: 借用ルール

同じ値に対して、ある時点で持てる参照は **次のどちらか一方だけ** 。

### &T 共有参照

何個でも OK。ただし **読み取り専用** 。

&s &s &s

読む人は大勢いてもいい

### &mut T 可変参照

同時に **1 つだけ** 。他の参照と共存できない。

&mut s &s &mut s

書く人がいる間は誰も見られない

```
let mut v = vec![1, 2, 3];
let first = &v[0];     // 共有参照
// v.push(4);          // ✕ 可変借用と共有参照が同時に存在
println!("{first}");   // ← first の最後の使用。ここで共有参照は終わる
v.push(4);             // ○ もう共有参照がないので OK
```

なぜ禁止？ `push` で Vec が再確保されると、 `first` は解放済みメモリを指す「ダングリング参照」になる。このルールはその事故とデータ競争を同時に防いでいる。参照の有効範囲は「最後に使われた場所まで」で判定される（NLL: Non-Lexical Lifetimes）。

## 仕組み 4: ライフタイムとエラー処理

ライフタイム

Result と ?

```
// 戻り値の参照は、x と y の「短い方」と同じだけ生きる
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

ライフタイムは「寿命を延ばす」ものではなく、 **参照同士の寿命の関係をコンパイラに伝える注釈** 。これがあるから「関数が返した参照が、元データより長生きしていないか」を検査できる。

引数が 1 つ、または `&self` メソッドなどは **省略規則 (lifetime elision)** で自動推論されるので、普段書く場面は限られる。

```
use std::{fs, io};

fn read_config() -> Result<String, io::Error> {
    let text = fs::read_to_string("config.toml")?; // 失敗なら即 Err を返す
    Ok(text)
}

match read_config() {
    Ok(t)  => println!("{t}"),
    Err(e) => eprintln!("読めなかった: {e}"),
}
```

例外 (exception) はない。失敗の可能性は **戻り値の型に現れる** ので、呼び出し側は無視できない（match しないと値を取り出せない）。

## メモリ管理の比較

| 方式 | 代表言語 | 解放のタイミング | 安全性 | 実行時コスト |
| --- | --- | --- | --- | --- |
| 手動管理 | C | プログラマが `free` | 解放忘れ・二重解放が起き得る | なし |
| GC | Java, Go, Python | GC が不要と判断したとき | 高い | GC の停止・メモリ余分 |
| 所有権 + 借用 | Rust | 所有者がスコープを抜けたとき（コンパイル時に決定） | 高い（safe Rust の範囲で） | ほぼなし |

## よくある誤解

clone() を使うのは負け

学習初期は clone で回避して動かすのが正解。動いてから、借用に置き換えて最適化すればいい。

ライフタイムを毎回書く必要がある

省略規則で大半は不要。コンパイラに求められたときに書けば足りる。

GC がない ＝ 手動でメモリを解放する

所有者がスコープを抜けると自動で `drop` される（RAII）。free を書くことはない。

unsafe はバグだらけの危険なコード

「借用チェッカが証明できない部分を、人間が責任を持って保証する」という印。範囲を小さく閉じ込め、safe な API で包むのが作法。

コンパイルエラーが多い ＝ 書きにくい言語

実行時に出るはずだったバグを前倒しで見せている。エラーメッセージには直し方の提案（help:）まで付くので、読むこと自体が学習になる。
