Linux プロセスとシグナル

ターミナル・PTY・シェル・カーネルの関係 / fork と exec / セッションとジョブ制御 / シグナルが届くまで

ざっくり言うと
  • ターミナルは「画面とキーボード」、シェルは「コマンドを起動するプログラム」。どちらも普通のプロセスで、間をつなぐ端末デバイス (PTY) とラインディシプリンはカーネルの中にある。
  • プロセスは fork（自分を複製）→ exec（中身を別のプログラムに入れ替え）→ wait（親が終了を回収）で生まれて消える。
  • シグナルはカーネルがプロセスに付ける「割り込みの印」。Ctrl+C も kill も、カーネルが印を付け、プロセスが次に動くときに既定動作・ハンドラ・無視のどれかで処理される。

全体像: OS の層とシステムコール

Linux は大きくユーザー空間とカーネル空間に分かれる。アプリはハードウェアを直接触れず、必ずシステムコール (system call) でカーネルに頼む。シェルもターミナルも、ユーザー空間で動くただのプロセス。

登場人物: ターミナル・TTY・シェル

ターミナルエミュレータ (terminal emulator) は GUI アプリ（GNOME Terminal、iTerm2、Windows Terminal、xterm など）。仕事は 2 つだけ。

  • 押されたキーをバイト列にして PTY のマスター側へ書く（a → 0x61、Ctrl+C → 0x03、↑ → \e[A）。
  • PTY から読んだバイト列を解釈して描画する。色やカーソル移動は \e[31m のようなエスケープシーケンスで指示される。

コマンドの意味もプロセスのことも知らない。Ctrl+C でプロセスを止めているのもターミナルではない。

TTY はカーネルの「端末デバイス」。昔、物理的なテレタイプ (teletypewriter) がシリアル線でつながっていた名残の名前。

PTY（擬似端末, pseudo terminal） はソフトウェアで作る端末で、マスター（ターミナルエミュレータが持つ）とスレーブ（/dev/pts/3 など。シェルが stdin/stdout/stderr として持つ）の対になっている。スレーブ側のプログラムからは本物の端末に見える（isatty() が真）。

間に入るラインディシプリン (line discipline) が、設定（termios、コマンドなら stty）に従って次をこなす。

  • カノニカルモード: Enter まで 1 行ためる。Backspace の処理もここ。cat や read コマンドの入力で使われる（対話シェル自体は readline などで非カノニカルにして自前で行編集する）。
  • エコー: 打った文字を画面側へ送り返す（パスワード入力ではオフにされる）。
  • 特殊文字 → シグナル: Ctrl+C → SIGINT、Ctrl+Z → SIGTSTP、Ctrl+\ → SIGQUIT。
  • raw / 非カノニカルモード: vim・less・top、対話シェルの行編集（bash の readline、zsh の ZLE）などは 1 キーずつ自分で読むためにこれに切り替える。

シェル (shell) は bash・zsh・fish などの普通のプロセス。stdin（PTY スレーブ）から 1 行読み（対話時は readline などで 1 キーずつ受け取って行を組み立てる）、解釈して、コマンドを起動する。

  • 外部コマンドは fork → exec で起動し、wait で終わりを待つ。
  • パイプ・リダイレクトは、起動前に子のファイルディスクリプタを付け替えて実現する。
  • ジョブ制御: ジョブごとにプロセスグループを作り、どのグループを端末の「フォアグラウンド」にするかをカーネルに伝える（tcsetpgrp）。

cd が外部コマンドではなく組み込みなのは、カレントディレクトリがプロセスごとの属性だから。子プロセスで変えても親（シェル）には伝わらない。

  • SSH: 手元のターミナル → ssh クライアント → ネットワーク → サーバーの sshd が PTY マスターを持つ → スレーブにつながった bash。サーバー側ではターミナルエミュレータの代わりを sshd がしている。
  • 仮想コンソール（Ctrl+Alt+F3 など）: GUI なしで、カーネル自身が画面に文字を描く端末（/dev/tty3）。
  • 端末なし: cron や systemd のサービス、bash script.sh < in.txt のように stdin がファイルやパイプのとき。isatty() が偽になり、Ctrl+C も SIGHUP も「端末由来」では届かない。

プロセスツリーと孤児

systemd (1) ├─ sshd (812) │ └─ sshd（接続ごと）(2301) │ └─ bash (2302) │ └─ vim (2410) └─ gnome-terminal-server (1950) └─ bash (1960) ├─ sleep (1999) └─ ps (2000)
  • すべてのユーザープロセスは PID 1（多くは systemd）の子孫。デスクトップでは間に systemd --user などが入る。カーネルスレッドは kthreadd (PID 2) の子。
  • 親が先に死ぬと、子は孤児になり PID 1（またはサブリーパーに指定されたプロセス）の子に付け替えられる。PID 1 は孤児を wait して回収する。
  • 親が生きているのに wait しないと、子はゾンビのまま残る。

シェルは pipe() で読み口・書き口の fd を作り、2 回 fork し、それぞれの子で dup2 を使って 0 番・1 番に付け替えてから exec する。コマンド側は「0 番から読んで 1 番に書く」だけで、相手がパイプか端末かファイルかを知らない。エラー (fd 2) は端末のままなので、パイプやリダイレクトの後でも画面に出る。

読み手（grep）が先に終わると、書き手（ls）の次の write は SIGPIPE を受けて終了する。yes | head -1 がすぐ終わるのはこのため。

セッション・プロセスグループ・ジョブ制御

端末からのシグナルは「1 つのプロセス」ではなくプロセスグループ単位で届く。シェルはパイプライン 1 本を 1 グループ（= 1 ジョブ）にまとめ、そのグループを端末のフォアグラウンドに設定する。下のボタンで、何が起きると誰に何が届くかを見る。

  • セッション: ログイン 1 回分のまとまり。作ったプロセス（多くはシェル）がセッションリーダーで、制御端末を 1 つ持てる。
  • プロセスグループ: ジョブ 1 本分。kill -TERM -- -200 のように負の番号でグループ全体に送れる。
  • 端末から切り離して動かすには nohup（SIGHUP を無視）、disown（bash が SIGHUP を転送する対象から外す）、setsid（新しいセッションを作って制御端末を持たない）、または tmux / screen（PTY ごとサーバー側に残す）。

シグナルの仕組み

シグナル (signal) は、カーネルがプロセスに付ける小さな非同期の通知。データはほぼ運べず、「何番が来たか」だけを伝える。

① 発生誰かが送る
  • 他のプロセス: kill()
  • 端末: Ctrl+C など
  • カーネル: 不正なメモリアクセス (SIGSEGV)、子の終了 (SIGCHLD)、読み手のいないパイプ (SIGPIPE)、タイマー (SIGALRM)
② 処理待ち (pending)印を付ける

対象プロセスの pending に印を立てるだけ。同じ番号がもう処理待ち中なら1 個にまとめられる（数は数えない）。ブロック中なら印は残ったまま待つ。

③ 配送動くときに見る

カーネルからユーザー空間へ戻る直前（システムコールや割り込みの帰り）に「処理待ち かつ ブロックされていない」ものを探す。S 状態で寝ていれば起こされる。D 状態はふつう起こされない（SIGKILL でだけ起きる待ち方もある）。

④ 処理3 通りのどれか
  • 既定動作（終了・コアダンプ・停止・再開・無視）
  • 登録したハンドラを実行
  • 無視

SIGKILL と SIGSTOP だけは変更もブロックもできない。

試す: 処理待ちとブロック

「送る」で pending に印が付く。「配送チェック」はカーネルからユーザー空間へ戻る瞬間を表す。同じシグナルを 2 回送ったり、ブロックしてから送ったりしてみる。

  • ハンドラは処理の途中に割り込むので、printf や malloc など内部で状態を持つ関数を呼ぶと壊れることがある。安全なのはフラグを立てるだけにして、本処理はメインループで見る書き方（使ってよい関数は async-signal-safe と呼ばれる）。
  • 寝ていたシステムコール（read など）がシグナルで起こされると、エラー EINTR で戻ることがある（SA_RESTART を付ければ多くは自動で再開）。
  • マルチスレッドのプロセスでは、プロセス宛てのシグナルはブロックしていないどれか 1 つのスレッドに届く。
  • シェルスクリプトでは trap 'cleanup' INT TERM EXIT がハンドラ登録にあたる。

主なシグナル図鑑

番号は x86 / ARM の Linux のもの。MIPS や SPARC など一部のアーキテクチャでは番号が違うので、スクリプトでは kill -TERM のように名前で書くのが確実。一覧は kill -l。SIGRTMIN〜SIGRTMAX のリアルタイムシグナルは、標準シグナルと違って送った回数分キューに積まれる。

よくある誤解

Ctrl+C はターミナルアプリがプロセスを止めている

ターミナルは 0x03 という 1 バイトを書くだけ。それを SIGINT に変えてフォアグラウンドのプロセスグループ全員に送るのはカーネルのラインディシプリン。だから SSH 越しでも、どのターミナルアプリでも同じように効く。stty intr ^X にすれば Ctrl+X が割り込みキーになる。

Ctrl+D はプロセスを終わらせるシグナル

シグナルではない。cat などカノニカルモードで読んでいるプログラムに対して行が空のときに押すと、ラインディシプリンが読み手の read() に 0 バイトを返し、プログラムが入力の終わり (EOF) と判断して自分で終わる。行の途中で押すと、それまでの文字をすぐ渡すだけ。

kill はプロセスを終了させるコマンド

kill はシグナルを送るコマンド。指定がなければ SIGTERM を送り、その既定動作がたまたま「終了」。kill -STOP で一時停止、kill -0 PID で存在と権限の確認だけ、といった使い方もする。

止まらなければとりあえず kill -9

SIGKILL は捕捉できないので、一時ファイルの削除・バッファの書き出し・子プロセスの停止・ロックの解放などの後始末が一切動かない。まず SIGTERM を送って数秒待ち、それでも終わらないときだけ SIGKILL にする（systemd も docker stop もこの順番）。

ゾンビプロセスは kill -9 で消せる

ゾンビはすでに終了していて、残っているのは終了ステータスだけ。消すには親が wait する必要がある。親を直すか親を終了させれば、ゾンビは PID 1 に引き取られて回収される。

コンテナのアプリも SIGTERM で普通に止まる

コンテナ内で PID 1 になったプロセスは特別扱いで、ハンドラを登録していないシグナルには既定動作が適用されない（SIGTERM で終了しない）。docker stop が 10 秒待ってから SIGKILL するのはこれが原因のことが多い。アプリで SIGTERM を処理する、docker run --init や tini を PID 1 にする、Dockerfile の CMD を exec 形式（["node", "app.js"]）にしてシェルを挟まない、などで解決する。

コマンド例

# 今の端末とシェル
tty                                   # → /dev/pts/3
echo $$                               # シェル自身の PID
stty -a                               # intr = ^C; susp = ^Z; icanon echo isig …

# 親子・グループ・セッションを見る
ps -o pid,ppid,pgid,sid,tty,stat,cmd -t pts/3
pstree -p $$
jobs -l

# シグナルを送る
kill -l                               # 一覧
kill -TERM 1234                       # 行儀よく終了を頼む（既定）
kill -KILL 1234                       # 最後の手段
kill -TERM -- -1234                   # プロセスグループ 1234 全体へ
kill -0 1234 && echo alive            # 存在確認だけ

# シグナルの状態を覗く（16 進のビットマスク）
grep -E 'State|Sig(Pnd|Blk|Ign|Cgt)' /proc/$$/status

# スクリプトで後始末する
trap 'rm -f "$tmp"; exit 130' INT TERM

# fork / exec / wait / シグナルをシステムコールで追う
strace -f -e trace=process,signal bash -c 'sleep 1 | cat'

# 端末から切り離す
nohup ./long.sh &     # SIGHUP を無視して起動
./long.sh & disown    # 起動済みのジョブを bash の管理から外す
setsid ./long.sh      # 新しいセッションで起動（制御端末なし）
