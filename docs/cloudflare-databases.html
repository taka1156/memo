D1 と Hyperdrive＋PlanetScale

Workers から使う DB は「SQLite を大量に」か「Postgres / MySQL を1つ大きく」か

ざっくり言うと
  • D1 は Cloudflare の中で動く SQLite。1つの DB は小さく（最大 10GB）書き込みは1本ずつだが、DB を大量に作って分ける前提で横に広げる。
  • Hyperdrive は DB ではなく、Workers から既存の Postgres / MySQL へ速くつなぐための接続プール＋キャッシュ。PlanetScale はその先に置く本格的な DB で、Cloudflare のダッシュボードから作れて請求もまとめられる。
  • テナントごとに分けられる・SQLite で足りるなら D1。1つの大きなデータを全員で共有する、Postgres の機能や既存資産を使いたいなら Hyperdrive＋PlanetScale。

DB は外のクラウドにある。Hyperdrive はその「距離」と「接続の重さ」を吸収する役。

なぜ Hyperdrive が要る？

Postgres や MySQL は、つなぐたびに TCP・TLS・認証の往復が何回も要る。普通のサーバーは接続を張りっぱなしにして使い回すが、Worker はリクエストごとに起動して終わるので、毎回この往復をやり直すことになる。

直接つなぐ
  1. TCP 接続（1往復）
  2. TLS ハンドシェイク（1〜2往復）
  3. DB の認証（数往復）
  4. やっとクエリ（1往復）

遠い DB だと、これを毎リクエスト

Hyperdrive 経由
  1. Worker → 近くの Hyperdrive（すぐ）
  2. Hyperdrive は DB への接続を張りっぱなしでプールしている
  3. クエリだけを DB に送る。よく使う読み取りはキャッシュから返す

重い往復は最初の1回だけ

Hyperdrive は無料プランでも使える。PlanetScale 以外の Postgres / MySQL（AWS RDS、Supabase、Neon など）にもつなげられ、ドライバや ORM はいつものものが使える。

組み合わせる

どちらか一方にしなくてよい。Workers からは両方を同時にバインドできる。

  • 本体は PlanetScale、利用者ごとの状態は D1：会員・注文・決済のように全員で共有するデータは Postgres、ユーザーごとの下書きや設定、AI エージェントの作業メモは D1 に1人1 DB。
  • Durable Objects の SQLite：チャットルームや共同編集の部屋のように「1つの単位に1つの状態」で、しかも即時に同期したいものは、Durable Objects に内蔵された SQLite（2025年4月に正式提供）が向く。
  • KV・R2 は別枠：設定値や読み込み中心の小さな値は KV、画像やファイルは R2（Cloudflare サービス参照）。

よくある誤解

✕ Hyperdrive は Cloudflare の Postgres サービス

○ Hyperdrive 自体はデータを持たない。外にある Postgres / MySQL へのつなぎ役（接続プール＋キャッシュ）。DB 本体は PlanetScale などで別に用意する。

✕ Hyperdrive を挟めば書き込みも速くなる

○ 速くなるのは接続の確立と、キャッシュできる読み取り。書き込みは毎回 DB まで届く。DB のリージョンが遠いなら、Placement で Worker を DB の近くで動かす方が効く。キャッシュは書き込みで消えず、既定で最大 60 秒ほど古い値を返し得る。書いた直後の読み取りや認証・権限まわりは、キャッシュを無効にした別の Hyperdrive 設定（バインディング）から読む。

✕ D1 は Postgres と同じように使える

○ SQL の方言は SQLite。型がゆるい、使えない関数や構文がある、などの違いがあり、Postgres 向けの ORM 設定やマイグレーションはそのまま流用できないことが多い。

✕ D1 も読み取りレプリカを増やせば書き込みが捌ける

○ レプリカは読み取り専用。書き込みが詰まるなら DB を分ける。
