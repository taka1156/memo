分散システムの基本

CAP・結果整合性・冪等性・リトライ ——「ネットワークは失敗する」前提で設計する

ざっくり言うと
  • 複数台に分けた瞬間、「ネットワークが切れる・遅れる・二重に届く」が日常になる。設計はそれが起きる前提で考える。
  • CAP：通信が切れたとき「エラーを返してでも正しさを守る (C)」か「古いかもしれない値でも返す (A)」かを選ぶしかない。
  • リトライすると処理は二重に届き得る。だから受ける側を冪等（何回やっても結果が同じ）にし、リトライは指数バックオフ＋ジッターで間隔を空ける。

なぜ難しいのか

1 台なら「関数を呼んだら、成功か失敗かが必ずわかる」。ネットワーク越しになると、もう 1 つの結果が増えます。

成功

レスポンスが返ってきた。

失敗

エラーが返ってきた（処理されていない、と言える場合もある）。

わからない

タイムアウト。相手が処理したのか、していないのか判別できない。分散システムの難しさの大半はここから来る。

「送金 API がタイムアウトした。もう一度送るべきか？」—— この問いに安全に答えられるようにするのが、後半の冪等性とリトライの話。

CAP 定理

データを複数のノードに複製しているとき、次の 3 つを同時に完全には満たせない、という定理です。

文字意味
C Consistencyどのノードから読んでも、最新の書き込み結果が返る（線形化可能性）
A Availability生きているノードは、必ず（エラーでない）応答を返す
P Partition toleranceノード間の通信が切れても、システムとして動き続ける

ただしネットワーク分断は避けられない現実なので、P は「選ぶ」ものではなく前提です。実際の選択は「分断が起きている間、C と A のどちらを諦めるか」だけ。下で試してみてください。

ノード 1（東京）100
⇄ 同期
ノード 2（大阪）100
①〜④を順に押してください。CP / AP を切り替えると、分断中の振る舞いが変わります。

分断していない平常時は？ — PACELC

CAP は「分断中」の話だけ。平常時にも「速さ (Latency) と整合性 (Consistency) のどちらを取るか」という選択があります。これを足したのが PACELC。

分断中 (P)→A か C か／平常時 (E: Else)→L か C か

例：全リージョンへの同期完了を待ってから応答する（C 寄り・遅い）か、近くのリージョンに書いたらすぐ返して後で伝える（L 寄り・速い）か。

整合性モデル

「強い整合性」と「結果整合性」の 2 択ではなく、間にいくつか段階があります。強いほど直感的、弱いほど速くて落ちにくい。

STRONG
強い整合性（線形化可能）

書いた直後から、誰がどこで読んでも新しい値。1 台の DB に近い感覚で書ける。

SEQUENTIAL
逐次整合性

全員が同じ順番で更新を見る。ただし「今この瞬間の最新」とは限らない。

SESSION
自分の書き込みは読める
Read-your-writes

他人の更新は遅れてもいいが、自分が書いたものは次の読み取りで必ず見える。

EVENTUAL
結果整合性

しばらく待てばいずれ揃う。その間は古い値が返り得る。いいね数・閲覧数などに向く。

Cloudflare のサービスに当てはめると

サービス整合性向いている用途
Workers KV結果整合性。書き込みが他の拠点に届くまで60 秒以上かかることがあり、その間は古い値が返り得る設定値・フラグ・キャッシュなど、読み取りが圧倒的に多いもの
D1（レプリカなし）書き込みも読み取りも 1 か所（プライマリ）なので強い整合性普通のリレーショナルデータ
D1（読み取りレプリカ・ベータ）Sessions API のブックマークを引き継ぐと、自分の書き込みが次の読み取りで見える（逐次整合性）読み取りを世界中で速くしつつ、ユーザー単位の一貫性は保ちたいとき
Durable Objects1 オブジェクト＝1 か所で処理するので強い整合性在庫・座席・チャットルームなど、同時更新を正しく捌きたいもの

詳しくは D1 と Hyperdrive＋PlanetScale、Cloudflare サービス。KV で在庫数を管理すると、書き込みが各地に届くまでの間に売り越しが起き得る、という具合に整合性モデルの選択がそのままバグになる。

冪等性 (idempotency)

同じ操作を 1 回やっても 10 回やっても、結果が同じになる性質。タイムアウト時に安心してリトライするための土台です。

もともと冪等
  • PUT /users/1 {name: "A"} — 何回送っても名前は A
  • DELETE /items/9 — 2 回目は「もうない」だけ
  • SET stock = 5
そのままだと冪等でない
  • POST /payments — 2 回届けば 2 回課金
  • UPDATE stock = stock - 1
  • メール送信・プッシュ通知

冪等キーで POST を冪等にする

クライアントが操作ごとに一意なキーを作って送り、サーバーは「そのキーで処理済みなら、前回の結果をそのまま返す」。Stripe などの決済 API で使われている方法です。

1. キーを作る

クライアントが操作 1 回ごとに UUID を生成。リトライでは同じキーを使い回す。

2. 送る

Idempotency-Key: 7f3c… ヘッダーを付けて POST。

3. 照合

サーバーはキーを保存済みか確認。初めてなら処理し、結果をキーと一緒に保存。

4. 2 回目

同じキーが来たら処理せず、保存した結果を返す。課金は 1 回だけ。

-- キーの一意制約で「同時に 2 つ届いた」ケースも弾く
CREATE TABLE idempotency_keys (
  key        TEXT PRIMARY KEY,
  response   TEXT,
  created_at TIMESTAMP
);
-- 処理本体とキーの保存は同じトランザクションで

キーの保存と本処理を別々にすると「処理したがキー保存前に落ちた」でまた二重になる。同じトランザクションに入れるのが要（インデックスとトランザクション）。

リトライ

何をリトライしてよいか

状況リトライ理由
タイムアウト・接続切れする（冪等なら）一時的な可能性が高い。冪等でない操作は冪等キー必須
429 Too Many RequestsするRetry-After があればその秒数待つ
502 / 503 / 504する相手側の一時的な不調
400 / 401 / 403 / 404 / 422しない何度送っても同じ結果。リクエストを直す必要がある
500慎重にバグの可能性もある。回数を少なく

指数バックオフ＋ジッター

失敗のたびに待ち時間を倍にし（1 秒 → 2 秒 → 4 秒…）、さらにランダムなずれ（ジッター）を足します。ジッターがないと、同時に失敗した全クライアントが同じ瞬間に再送し、復旧しかけたサーバーをまた落とします（サンダリングハード）。

クライアント ABC
async function withRetry(fn, max = 5) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i + 1 >= max || !isRetryable(e)) throw e;
      const cap  = Math.min(30_000, 1000 * 2 ** i);   // 上限つき指数
      const wait = Math.random() * cap;               // フルジッター
      await new Promise(r => setTimeout(r, wait));
    }
  }
}

さらに、失敗が続く相手にはしばらく呼ぶこと自体をやめるサーキットブレーカーを組み合わせると、障害の連鎖を止められる。

配送保証：「ちょうど 1 回」は作るもの

at-most-once
最大 1 回

リトライしない。消えることはあるが重複はない。ログ・計測向き。

at-least-once
最低 1 回

届くまでリトライ。重複はあり得る。キュー（Cloudflare Queues・SQS など）の多くはこれ。

exactly-once
ちょうど 1 回

ネットワークだけでは保証できない。at-least-once ＋ 受け手の冪等処理で「結果的に 1 回」を実現する。

よくある誤解

CAP は 3 つのうち 2 つを自由に選べる

分断（P）は起きるものなので、実際に選ぶのは「分断中に C と A のどちらを諦めるか」。分断していない平常時は C と A を両立できる。

結果整合性 ＝ データが壊れることがある

壊れるのではなく、一時的に古い値が見えるだけ。いずれ全ノードが同じ値に揃う。問題になるのは「古い値を見て判断する処理」を載せたとき。

リトライは回数を増やすほど安全

冪等でない操作では重複を増やし、障害中のサーバーには負荷を上乗せする。回数の上限・バックオフ・ジッター・リトライ対象の選別がセット。

キューを使えば exactly-once になる

多くのキューは at-least-once。同じメッセージが 2 回届く前提で、受け手を冪等に書く。
