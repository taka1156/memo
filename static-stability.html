コントロールプレーンが止まったら

止まったときの影響は、狭義と広義でまったく違う。静的安定性と、AWS バージニア北部（us-east-1）の事例で見る

コントロールプレーンとデータプレーン コントロールプレーンが止まったら
ざっくり言うと
  • ルーターではコントロールプレーンが止まると、時間がたつと通信も止まる。AWS では追加と変更ができなくなるだけ。
  • 違いは、データプレーンがコントロールプレーンなしで動き続けるように作られているか（静的安定性）にある。
  • それでも隠れた依存があると影響が広がる。復旧手順はデータプレーンだけで済むようにしておく。

用語の意味（狭義・広義、何がどちらのプレーンか）はコントロールプレーンとデータプレーンで扱う。

止まり方の違い

狭義（ルーター）広義（AWS などのクラウド）
すぐ起きること経路の更新が止まるリソースの追加・変更・削除ができなくなる
時間がたつと隣のルーターが経路を取り消し、通信が止まる動いているものはそのまま動き続ける
理由データプレーンが使う経路は、コントロールプレーンが隣と保ち続けて初めて有効だからデータプレーンが、コントロールプレーンなしで回るように作られているから

止めてみる

狭義・広義を選び、時間を進めて、何が動き続けて何が止まるかを見る。

  • 今の通信の転送 動く動く止まる データプレーンが転送表どおりに流している 直前の転送表のまま流れ続ける 隣のルーターがこのルーター経由の経路を取り消すので、通信は迂回するか行き場を失う
  • 隣のルーターとの BGP セッション 動く期限つきで保たれる止まる 定期的に KEEPALIVE を送り合っている 相手はホールドタイマーが切れるまでは待つ ホールドタイマーが切れてセッションが落ちる
  • 経路の更新（障害の迂回・新しい経路） 動く止まる止まる コントロールプレーンが経路表を作り直して転送表に反映する 転送表を作り直す担当がいない 転送表を作り直す担当がいない
動く期限つきで保たれる止まる

ホールドタイマーは RFC 4271 の推奨が 90 秒で、実装の既定値は 90 秒（Juniper など）や 180 秒（Cisco）が多い。

  • 動いているインスタンス・今の通信 動く動く動く データプレーンが処理している データプレーンはコントロールプレーンに頼らない 時間がたっても変わらない（静的安定性）
  • 新しいリソースの作成・設定の変更 動く止まる止まる API が受け付ける 受け付ける API そのものが止まっている 復旧するまで変わらない
  • オートスケールで台数を増やす 動く止まる止まる 負荷に応じて新しいインスタンスを起動する 起動は「追加」なのでコントロールプレーンが要る 負荷が増えても台数は増えない。余裕を先に持っていないとさばけなくなる
  • 壊れたインスタンスの自動の置き換え 動く止まる止まる 新しいインスタンスを起動して入れ替える 置き換えも「追加」 壊れた分だけ容量が減っていく
動く止まる

これは設計どおりに分かれている場合。実際の障害では、データプレーン側に隠れた依存があると影響が広がる（下の「事例」）。

静的安定性（static stability）

AWS は、作ったあとのリソースへのデータプレーンのアクセスがコントロールプレーンに依存しないことを「静的安定性」と呼んでいる。作る・変える・消すができなくなっても、既存のリソースは使い続けられる、という性質。AWS 自身のサービスの設計方針であり、利用者が自分のシステムに取り入れるパターンでもある。

  1. 余裕を先に持っておくAZ が 1 つ壊れたらオートスケールで増やす、ではなく、残りの AZ だけでさばける台数を最初から動かしておく（コストは増える）。
  2. 復旧の手順でコントロールプレーンを呼ばない障害のときに新しく作る・設定を変える手順は、コントロールプレーンが止まっていると使えない。必要なものは事前に作っておく。
  3. データプレーンで切り替えるフェイルオーバーは、ヘルスチェックなどデータプレーンの仕組みで自動に行う。

狭義での延命策

ルーターでも、コントロールプレーンが一時的に止まる場面（ソフトウェアの再起動など）への手当てはある。BGP の Graceful Restart（RFC 4724）は、再起動中も転送の状態を保てることを相手に伝え、相手に経路をしばらく残してもらう仕組み。ただし猶予を延ばすだけで、戻らなければ結局は経路が取り消される。

事例：AWS バージニア北部（us-east-1）

グローバルサービスのコントロールプレーンの場所

「グローバル」とされる AWS のサービスにも、コントロールプレーンは 1 か所にあるものが多い。データプレーンは各リージョンや世界中の拠点（PoP）に分散している。

サービスコントロールプレーンデータプレーン
IAMus-east-1各リージョン
AWS Organizationsus-east-1（データプレーンを持たない）
AWS アカウント管理us-east-1各リージョン
Route 53us-east-1（パブリックのレコード変更だけ us-west-2 に待機用あり）世界中の PoP と各リージョン
CloudFront（と CloudFront 用の ACM・WAF）us-east-1世界中の PoP
Shield Advancedus-east-1各リージョンと世界中の PoP
Global Acceleratorus-west-2世界中の PoP
Application Recovery Controller（ARC。旧称 Route 53 ARC）us-west-2各リージョン

設計どおりなら、us-east-1 のコントロールプレーンが止まっても、世界中で動いているものは動き続け、これらのサービスの「変更」だけができなくなる。

2025 年 10 月の障害で起きたこと

2025 年 10 月 19〜20 日（米国太平洋時間）、DynamoDB の DNS を管理する自動化の競合状態で、リージョンのエンドポイント dynamodb.us-east-1.amazonaws.com の DNS レコードが空になった。そこから EC2 の起動、Network Load Balancer へと影響が広がった。

  1. 静的安定性は効いた障害の前から動いていた EC2 インスタンスは正常なままだった。止まったのは新しい起動や API 呼び出し。
  2. us-east-1 のデータプレーンが止まったDynamoDB への新しい接続ができなくなり、それに頼る多くの AWS サービスと利用者のアプリが止まった。
  3. 隠れた依存で他のリージョンにも出たルート認証情報や signin.aws.amazon.com 経由のフェデレーションで、他のリージョンでもコンソールにサインインできなくなった。Redshift では、us-east-1 の IAM API に頼る不具合のため、IAM ユーザーの認証情報を使うクエリが全リージョンで失敗した。

番号の色は、緑が設計どおりに守られた所、赤が影響が出た所。世界中で同時に障害が見えたのは、コントロールプレーンが止まったからというより、us-east-1 のデータプレーンに頼るものが多く（us-east-1 で動かしているアプリそのものと、他のリージョンからの隠れた依存）、そこが止まったから。障害を報告するサイトで、関係のなさそうな多くのサービスに同じ時刻に山ができるのはこのため。

Route 53 で考える：どの操作が止まるか

操作プレーンus-east-1 のコントロールプレーンが止まると
レコードを作る・変える・消すコントロールプレーンすぐにはできない（パブリックホストゾーンで accelerated recovery を事前に有効にしてあれば、約 60 分後から us-west-2 経由でできる）
ホストゾーンの作成・削除、ヘルスチェックの作成・変更コントロールプレーンできない
DNS の問い合わせに答えるデータプレーン動き続ける
作ってあるヘルスチェックを実行し、結果で応答を切り替えるデータプレーン動き続ける

なので「障害が起きたらレコードを書き換えて別の地域へ切り替える」手順は、肝心なときにすぐには使えない。2025 年 12 月からは、パブリックホストゾーンで accelerated recovery を事前に有効にしておけば、us-east-1 の障害を AWS が検知してから約 60 分で us-west-2 からレコードを変えられる（障害が始まってから有効にはできない）。すぐに切り替えたいなら、ヘルスチェックとフェイルオーバーのレコードを事前に作っておき、データプレーンに任せる。

ELB・RDS・CloudFront など、作るときに Route 53 のレコードを作るサービスの多くは、AWS 内部の同じ仕組みで障害中も作成を続けられる。一方、API Gateway・EKS・Lambda の関数 URL などは us-east-1 の Route 53 コントロールプレーンに頼ったまま。

設計・運用で気をつけること

  1. 依存の裏にあるリージョンを知っておく自分のリージョンが無事でも、使っているグローバルサービスや外部の SaaS が us-east-1 に頼っていることがある。
  2. 復旧の手順を「作る・変える」なしで書くフェイルオーバー先の容量・DNS レコード・ヘルスチェックは平常時に作っておく。
  3. 障害時に変更を急がないコントロールプレーンが不安定なときに設定を変えると、途中で止まって状態がずれることがある。
  4. サインインと権限の非常口を用意するコンソールへのサインイン経路が止まった場合に、どう作業するかを決めておく。

よくある誤解

コントロールプレーンが止まったときの影響は、どの文脈でも同じだ

ルーターでは時間がたつと経路が取り消されて通信が止まるが、静的安定性を持つクラウドのサービスでは追加と変更ができなくなるだけ。どちらの意味の話かで結論が逆になる。

グローバルサービスは、どのリージョンにも依存していない

IAM・Route 53・CloudFront などは、コントロールプレーンが us-east-1 にある。データプレーンは分散しているので動き続けるが、変更は us-east-1 に頼る。

障害時は、Route 53 のレコードを書き換えて切り替えればよい

レコードの変更はコントロールプレーンの操作なので、us-east-1 が不調だとすぐにはできない（accelerated recovery を有効にしていても、再開まで約 60 分かかる）。フェイルオーバーは事前に作ったヘルスチェックで自動に行う。

マルチ AZ にしておけば、AZ が落ちてもオートスケールで補えるので余裕は要らない

台数を増やすのはコントロールプレーンの仕事で、障害時には遅れたり失敗したりする。残りの AZ だけでさばける容量を先に持っておくのが静的安定性の考え方。
