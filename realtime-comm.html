リアルタイム通信

「サーバーから押したい」を叶える 6 つの方法と、それぞれの向き不向き

ざっくり言うと
  • HTTP は本来「聞かれたら答える」だけ。サーバーから送るには、聞き続ける（ポーリング）・開いたままにする（SSE）・別の双方向チャネルを張る（WebSocket など）のどれか。
  • 通知・進捗・AI の逐次出力のようなサーバー → クライアントだけなら SSE が手軽（自動再接続つき、普通の HTTP）。チャットや共同編集のような双方向・高頻度なら WebSocket。
  • 接続を張りっぱなしにする方式は、サーバーが接続を覚えているので、台数を増やすときに「別のサーバーにいる相手へどう届けるか」が課題になる。

6 つの方式

一定間隔でリクエストする。一番単純で、どこでも動き、キャッシュや認証も普通の HTTP のまま。ただし更新は最大で間隔ぶん遅れ、何もなくても通信が発生する。数十秒〜分単位で十分なダッシュボードならこれでよい。

setInterval(async () => render(await (await fetch('/api/status')).json()), 30_000);

サーバーは新着が出るまでレスポンスを返さずに保留する。返ったらクライアントはすぐ次を投げる。遅延はほぼない一方、保留中のリクエストがサーバーの接続とメモリを占有し、プロキシのタイムアウトとの戦いになる。SSE と WebSocket が使える今は、古い環境向けのフォールバック。

Server-Sent Events。1 つの HTTP レスポンスを閉じずに、テキストの行を流し続ける。ブラウザの EventSource は切れたら自動で再接続し、最後に受け取った id を Last-Event-ID ヘッダーで送ってくれるので、取りこぼしの再送も作りやすい。

// クライアント
const es = new EventSource('/events');
es.addEventListener('progress', e => update(JSON.parse(e.data)));

// サーバーが流すテキスト（空行が 1 件の区切り）
id: 42
event: progress
data: {"done": 3, "total": 10}

送れるのはテキストだけで、サーバー → クライアントの片方向。EventSource はカスタムヘッダーを付けられないので、認証は Cookie で行う（ヘッダーが必要なら fetch でストリームを読む）。HTTP/1.1 では同じオリジンへの接続が 6 本程度に制限され、タブをたくさん開くと詰まる。HTTP/2 以降なら多重化されるので問題になりにくい。LLM の逐次出力（ストリーミング応答）もこの形式が多い。

HTTP で始めて 101 で別プロトコルに切り替え、1 本の TCP の上で双方向にメッセージ（テキスト／バイナリ）を送り合う。ヘッダーのやり取りがない分、小さいメッセージを高頻度に送るのに向く。

const ws = new WebSocket('wss://example.com/chat');
ws.onmessage = e => append(JSON.parse(e.data));
ws.onclose = () => setTimeout(connect, backoff());   // 再接続は自分で書く
ws.send(JSON.stringify({ type: 'say', text: 'hi' }));

自動再接続も、届いたかの確認も、取りこぼしの再送もないので、アプリ側で作る（Socket.IO などのライブラリはここを埋める）。送信側が速すぎるとバッファが膨らむ（bufferedAmount を見る）。Cookie で認証する場合はハンドシェイクの Origin を必ず検証する（他サイトからつながれる CSWSH 攻撃）。

WebTransport は HTTP/3（QUIC）の上で、複数の独立したストリームと、届かなくてもよいデータグラム（UDP のような送りっぱなし）を使える。1 つのメッセージが詰まっても他が待たされず、ゲームの位置情報やライブ配信のように「古いデータは要らない」用途に向く。

const wt = new WebTransport('https://example.com:4433/game');
await wt.ready;
const writable = typeof wt.datagrams.createWritable === 'function'
  ? wt.datagrams.createWritable()   // 新しい API（writable は非推奨）
  : wt.datagrams.writable;          // 未対応のブラウザ（Chrome など）は旧 API
const w = writable.getWriter();
w.write(new Uint8Array([x, y]));   // 落ちても再送しない

サーバー側は HTTP/3 対応が必要。ブラウザは 2026 年 3 月の Safari 26.4 で主要ブラウザがすべて対応した（Baseline 新規）が、古い OS やブラウザの利用者がいるなら WebSocket へのフォールバックを用意する。社内ネットワークなどで UDP が塞がれている場合も同じ。

WebRTC はブラウザ同士を直接（P2P）つなぐ。映像・音声の通話と、任意のデータを送る DataChannel がある。NAT を越えるために STUN（自分の外向きアドレスを知る）と TURN（直結できないときの中継）を使い、接続の準備（シグナリング）には別途 WebSocket などが要る。

参加者が多い会議では全員が全員に送ると回線が持たないので、SFU という中継サーバーで束ねる。サーバーとクライアントのやり取りだけなら WebSocket か WebTransport のほうが単純。

台数を増やすときの問題

Alice と Bob が別のサーバーにつながっていると、Server 1 は Bob に直接送れない。全サーバーが共通のメッセージ基盤を購読して中継するか、同じ部屋の人を同じサーバーに集める（スティッキーセッション、Cloudflare の Durable Objects のように「部屋＝1 つのオブジェクト」にする）。

デプロイで全接続が一斉に切れると、全員が同時に再接続してサーバーを叩く。再接続の待ち時間にランダムな揺らぎ（ジッター）付きの指数バックオフを入れる。

選び方

  1. 数十秒遅れても困らない？はい → ポーリング。インフラもキャッシュもそのまま使える。
  2. サーバーから送るだけ？はい → SSE。自動再接続が標準でついてくる。再接続時に最後のイベント ID が届くので、サーバー側で差分を送れば取りこぼしも防げる。
  3. クライアントからも高頻度に送る？はい → WebSocket。
  4. 古いデータを捨ててでも遅延を減らしたい／ブラウザ同士でつなぎたいWebTransport ／ WebRTC。

関連メモ

  • HTTP/1.1・2・3 と TLS・DNS — HTTP/2・3 と QUIC の土台
  • Redis と Valkey の仕組み — 複数サーバーへ配る Pub/Sub
  • 分散システムの基本 — 再接続のバックオフ＋ジッターと、重複に備える冪等処理
  • Durable Objects と celld — 部屋ごとの WebSocket を Durable Objects で持つ
  • 実装起因の脆弱性（入力の扱い） — 受け取ったメッセージを画面に出すときの XSS
  • 実装起因の脆弱性（リクエストと権限） — CSWSH の土台になる CSRF と Origin の確認
