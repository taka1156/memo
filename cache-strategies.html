キャッシュ戦略

Cache-Aside・Write-Through・無効化 ── アプリ側のキャッシュで古い値と殺到を防ぐ

ざっくり言うと
  • アプリ側のキャッシュは DB の前に置く速い一時置き場で、読み方と書き方の組み合わせで性格が決まる。
  • 更新時は「DB を書いてからキャッシュを消す」が基本だが、順番の入れ替わりで古い値が残り得るので TTL を必ず付ける。
  • 人気のキーが切れた瞬間の殺到は、1 本だけに作り直させる・期限前に作り直す・古い値を返しつつ裏で更新する、で防ぐ。

どこのキャッシュの話か

ブラウザ・CDN

HTTP のヘッダーで決まる。HTTP キャッシュ

アプリのメモリ

プロセスの中の Map や LRU。最速だが台ごとにばらばら

共有キャッシュ

Redis・Memcached など。全台から同じ値が見える

DB

DB 自身もページをメモリに持つ（バッファプール）

破線の枠が、このメモで主に扱う「アプリが自分で読み書きするキャッシュ」。アプリのメモリにも同じ考え方が当てはまる。キャッシュの置き場所としての Redis の中身は Redis と Valkey の仕組み。

読み方：Cache-Aside と Read-Through

アプリキャッシュDB
  1. アプリがキャッシュを見るあれば（ヒット）それを返して終わり。
  2. 無ければ（ミス）アプリが DB から読むキャッシュは DB のことを知らない。間を取り持つのはアプリ。
  3. アプリが読んだ値を TTL 付きでキャッシュに入れる次からはヒットする。
async function getUser(id) {
  const hit = await cache.get(`user:${id}`);
  if (hit) return JSON.parse(hit);
  const user = await db.findUser(id);                          // ミス → DB
  await cache.set(`user:${id}`, JSON.stringify(user), { EX: 300 }); // 5 分で切れる
  return user;
}

いちばんよく使う形で、遅延読み込み (lazy loading) とも呼ばれます。読まれたものだけが入り、キャッシュが落ちても DB から読めば動き続けます。弱みは、最初の 1 回は必ず遅いことと、DB を更新してもキャッシュは自動では変わらないことです（下の「無効化」）。

アプリキャッシュDB
  1. アプリはキャッシュにだけ聞くDB の場所や読み方を知らない。
  2. ミスしたらキャッシュ側が DB から読んで入れる読み込み方はキャッシュのライブラリや層に登録しておく。
  3. アプリには値だけが返るヒットかミスかを意識しない。

動きは Cache-Aside と同じで、「ミスしたときに DB を読む役」をアプリからキャッシュ層に移したものです。読み込みを 1 か所にまとめられるので、同じキーのミスを 1 本にまとめる（下の「スタンピード」）のもキャッシュ層でできます。Java の Caffeine の LoadingCache のように、プロセス内のキャッシュライブラリでよく見る形です。

書き方：Write-Through・Write-Behind・Write-Around

方式書くとき強み弱み
Write-ThroughDB に書くたびに、キャッシュにも新しい値を書く書いた直後の読み込みもヒットし、値が新しい書き込みが毎回 2 か所で遅くなる。読まれないデータまでキャッシュに入る
Write-Behind（Write-Back）キャッシュにだけ書いてすぐ返し、DB には後でまとめて書く書き込みが速い。同じキーへの連続した書き込みを 1 回にまとめられるDB に書く前にキャッシュが落ちると、書いたはずのデータが消える
Write-AroundDB にだけ書き、キャッシュは消す（または触らない）読まれないデータでキャッシュを埋めない。単純書いた直後の読み込みはミスして DB へ行く

実際によく使うのは Cache-Aside ＋「書いたらキャッシュを消す」の組み合わせです。読まれたものだけがキャッシュに入り、次に読まれたときに DB の新しい値で作り直されます。Write-Through は「書いた直後に必ず読まれる」データ（自分のプロフィールなど）で効き、Write-Behind はアクセス数のカウンターのように「多少消えても困らず、書き込みが多い」データ向けです。

AWS の ElastiCache の資料では、遅延読み込み（Cache-Aside）は古い値が残り得るがキャッシュが空でも動き、Write-Through は値が新しいがキャッシュが空になると欠け、読まれないデータも入る、と整理し、どちらにも TTL を足すことを勧めている。

無効化：消すか、上書きするか

DB を更新したら、キャッシュの古い値をどうにかしないといけません。選択肢は「新しい値で上書きする」と「消して、次に読む人に作り直させる」の 2 つです。基本は消すほうです。消す操作は何回やっても結果が同じ（冪等）なので、失敗したら単純にやり直せますし、更新が重なっても「新しい値を後から古い値で上書きする」ことが起きにくくなります。Facebook の memcache の論文でも、更新時はキャッシュの値を書き換えず、消すことを選んでいます。

それでも、順番の入れ替わりで古い値が残ることがあります。W（書く人）と R（読む人）として、よくある 3 つの形を見ます。

キャッシュの値 = 100、DB = 100 から始める
Wキャッシュを消す
Rミスしたので DB を読む → まだ 100
WDB を 200 に更新
R読んだ 100 をキャッシュに入れる
古い値DB は 200 なのに、キャッシュは TTL が切れるまで 100。消すのが早すぎて、間に入った読み込みが古い値を入れ直した。順番は「DB を更新 → 消す」にする。
キャッシュは空、DB = 100 から始める
Rミスしたので DB を読む → 100（ここで R が少し止まる）
WDB を 200 に更新
Wキャッシュを消す（まだ空なので何も起きない）
R止まっていた R が、読んだ 100 をキャッシュに入れる
まれに起きるR の「読む → 入れる」の間に W の更新と削除が丸ごと挟まったときだけ起きる。Facebook の論文はこれを stale set と呼び、ミスした人にリース（入れてよい権利の札）を渡し、その間に削除が来たら札を無効にして書き込みを断ることで防いでいる。
Write-Through で、2 人が同じキーを続けて更新する
W1DB を 200 に更新
W2DB を 300 に更新
W2キャッシュに 300 を書く
W1遅れていた W1 が、キャッシュに 200 を書く
古い値DB は 300、キャッシュは 200。DB の更新順とキャッシュへの書き込み順が入れ替わった。上書き方式でよく起きるので、更新では消すほうを選ぶか、値にバージョン番号を持たせて古い版では上書きしないようにする。

取りこぼしに備える

  1. TTL を必ず付ける削除の失敗やレースで古い値が残っても、TTL が来れば消える。古さの上限を決める最後の安全網。
  2. 削除は DB の変更から起こすアプリのコードで消すと、別の経路（管理画面・バッチ・手作業の SQL）の更新で消し忘れる。DB の変更ログを読んで消す仕組み（CDC (change data capture)）にすれば、経路によらず消える。
  3. キーに版を入れるuser:42:v7 のように版を入れ、更新したら版を上げる。古いキーは読まれなくなり、TTL で消える。データの形を変えたときも、キーの接頭辞を変えれば古い形の値を読まずに済む。

TTL の決め方

考えること決め方の例
どれだけ古くてよいか商品の在庫数は数秒、ランキングは数分、国の一覧は 1 日。古さが業務で困る上限より短くする
一斉に切れないか同時に入れたキーが同時に切れると DB に集中する。TTL に ±10% ほどのランダムな幅（ジッター）を足す
無いものを何度も聞かれないか存在しない ID を聞かれるたびに DB へ行くと、攻撃にも使われる。「無い」という結果も短い TTL でキャッシュする（ネガティブキャッシュ）
自分の更新がすぐ見えるか更新した本人には DB から読むか、Write-Through で入れ直す。他人には少し遅れて見えてもよいことが多い

スタンピード：人気のキーが切れた瞬間

毎秒 1,000 回読まれるキーの TTL が切れると、作り直しが終わるまでの間に来たリクエストが全部ミスして、同時に DB へ行きます。作り直しに 0.5 秒かかれば、約 500 本が同じ重い問い合わせを投げます。これをキャッシュのスタンピード（cache stampede、dog-piling とも）と呼びます。

対策なし
DB へ: ミスした全員

作り直しが遅いほど DB への集中がふくらみ、DB が遅くなってさらに作り直しが遅れる。

1 本だけに作り直させる
DB へ: 1 本・ほかは待つ

キーごとのロック（Redis の SET key val NX PX 3000 など）を取れた 1 本だけが DB へ行き、ほかは少し待ってキャッシュを読み直す。プロセス内なら、同じキーの読み込みを 1 つの Promise にまとめる（Go の singleflight と同じ考え方）。

期限前に確率的に作り直す
DB へ: ほぼ 1 本・誰も待たない

切れる少し前から、読んだ人がくじを引き、当たった人が先に作り直す。期限に近いほど当たりやすい。

古い値を返しつつ裏で更新
DB へ: 1 本・古い値で応答

期限を過ぎても少しの間は古い値を返し、裏で 1 本だけが作り直す。HTTP の stale-while-revalidate と同じ考え方。

同時に DB へ行くリクエスト（多い）DB へ行くのが 1 本で済む

確率的な早期の作り直し（XFetch）

Vattani らの論文（VLDB 2015）が示した方式で、値と一緒に「作り直しにかかった時間 δ」と「期限」を保存しておき、読むたびに次の条件で作り直すかを決めます。

今の時刻 − δ × β × ln(乱数) ≥ 期限　なら作り直す

乱数は 0〜1 なので ln(乱数) は負で、左辺は「今」より少し先の時刻になります。期限が近いほど、そして作り直しが重い（δ が大きい）ほど、早めに当たりやすくなります。β は早さの調整で、論文では 1 で十分よく働くとしています。読む人どうしで連絡を取り合わずに、作り直す人がだいたい 1 人に絞られるのが利点です。読まれる回数が少ないキーでは、期限前にくじを引く人がいないので効きません。

よくある誤解

キャッシュを置けば必ず速くなる

ヒット率が低いと、キャッシュへの往復とシリアライズの分だけ遅くなる。ほとんど同じものが読まれない処理（検索結果の組み合わせが多いなど）には効きにくい。ヒット率を測ってから決める。

更新時はキャッシュを新しい値で上書きするのがいちばん新しい

同時に更新が重なると、キャッシュへの書き込み順が DB の更新順と入れ替わって古い値が残る。消して、次に読む人に DB から作り直させるほうが安全。

更新のたびに消しているなら TTL は要らない

削除の失敗、別の経路からの更新、読み込みとのレースで古い値は残り得る。TTL が無いと、その値は永遠に残る。TTL は古さの上限を決める安全網。

キャッシュが落ちても DB があるから困らない

普段キャッシュが受けていた読み込みが全部 DB に来るので、DB が耐えられないことが多い。キャッシュが空の状態から戻すとき（再起動・台の追加）も同じで、少しずつ流す・事前に温めるなどの準備が要る。
