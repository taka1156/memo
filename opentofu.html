OpenTofu 概念図

設定ファイルから State・Provider を経てインフラに反映されるまでの流れと、役割ごとのファイル名の対応

ざっくり言うと
  • *.tf ファイル（設定）に「あるべき状態」を書く。手順ではなく結果を書く点が Ansible と違う
  • tofu plan は State（前回の実行結果の記録）を実体の現状で更新したうえで設定と比べ、変更点だけを洗い出す
  • 実際のクラウド API を叩くのは Provider（プラグイン）。tofu apply が Provider 経由でインフラに反映する

概念図

青＝自分で書く定義ファイル、緑＝実行時の処理ステップ、紫＝State（実行結果の記録）、黄＝外部との接続。破線は参照・取り込みを表す。

定義ファイル 実行ステップ State（記録） 外部との接続 破線＝参照・取り込み

役割ごとのファイル名

ファイル名は 1 ファイルにまとめても動くが、慣例として役割ごとに分けることが多い。同じディレクトリ内の .tf（OpenTofu 1.8 以降は .tofu も）ファイルはすべてまとめて 1 つの「設定」として読み込まれる。

概念種別ファイル / 場所役割
Terraform Block全体設定 設定 versions.tf OpenTofu 自体のバージョン制約、required_providers（使う Provider とそのバージョン）を書く。
Provider 設定 定義 providers.tf どの Provider をどの認証情報・リージョンで使うか（provider "aws" { region = ... }）。
Resource 定義 main.tf 作りたいインフラの「あるべき状態」。resource "aws_instance" "web" { ... } のように書く。
Variables入力値 定義 variables.tf variable "name" { type = ... } で入力項目を宣言する（値そのものではなく器）。
Variables値 定義 terraform.tfvars*.auto.tfvars variables.tf で宣言した変数に実際の値を入れる。環境ごとに分けられる。
Outputs 定義 outputs.tf apply 後に表示・他の仕組みから参照したい値（IP アドレスなど）を定義する。
Locals 定義 locals.tf 設定内だけで使う計算済みの値。変数のように外からは渡せない。
Module 定義 modules/<名前>/ Resource 群をひとまとめにした再利用部品。自前でも Registry 公開のものでも可。
Backend 設定 接続 backend.tf State をどこに保存するか（backend "s3" { ... } など）。チームで共有する場合は必須。
State 記録 terraform.tfstate 最後に apply した時点の実体の記録。手で編集しない。Backend 未設定時はローカルに作られる。
Lock File依存関係 設定 .terraform.lock.hcl init 時に決まった Provider の正確なバージョンを固定する。Git にコミットする。
キャッシュ 生成物 .terraform/ init でダウンロードされた Provider 本体・Module の実体。.gitignore に入れる。

ディレクトリ構成例

project/
├── versions.tf           # OpenTofu / Provider バージョン
├── providers.tf          # Provider 設定
├── backend.tf            # State の保存先
├── main.tf                # Resource 定義
├── variables.tf          # 入力変数の宣言
├── outputs.tf             # 出力値
├── locals.tf               # 内部変数
├── terraform.tfvars      # 変数の値
├── .terraform.lock.hcl  # 依存バージョンの固定
├── .terraform/            # init の生成物（Git 管理外）
└── modules/
    └── web-server/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
# main.tf
resource "aws_instance" "web" {
  ami           = "ami-0abcd1234"
  instance_type = var.instance_type   # variables.tf を参照

  tags = {
    Name = "server-${var.env}"
  }
}
# variables.tf（器の宣言）
variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "env" {
  type = string
}

# terraform.tfvars（実際の値）
env = "staging"

各要素の考え方

Resource 何を作るか

手順ではなく「こうあってほしい」という結果を宣言する（宣言的）。同じ Resource ブロックを何度 apply しても、既に望む状態ならなにも変わらない。

State 今の状態の記録

OpenTofu が「前回自分が何を作ったか」を知っている唯一の手がかり。plan はこの State を実体の現状で更新（refresh）してから設定ファイルと比較して差分を出す。壊れたり他人と競合したりすると大きな事故につながるため、チームでは Backend（S3 など）で共有しロックをかける。

Provider 誰が実行するか

AWS・GCP・Azure など、クラウドごとの API 呼び出しを引き受けるプラグイン。init でダウンロードされ、apply 時に実際の作成・変更・削除リクエストを送る。Ansible の Connection Plugin に近い役割だが、対象は「サーバーへの接続」ではなく「API」。

Module まとめて使い回す

複数の Resource をまとめた部品。呼び出し元からは Resource と同じ感覚で module "web" { source = "./modules/web-server" } のように使う。

Plan と Apply 安全に反映する

plan は「何が変わるか」を事前に見せるだけで何も実行しない。内容を確認してから apply で実際に反映する、という 2 段階が事故を防ぐ仕組みになっている。

実行の流れ

初めてのディレクトリで tofu apply までを行う場合の順序。

tofu init設定を解析し、必要な Provider と Module をダウンロードする。.terraform.lock.hcl を書く（または検証する）。
tofu planまず Provider 経由で実際のリソースの現状を読んで State を最新にし（refresh。State ファイル自体は書き換えない）、それと設定ファイルを比較して（State がなければ空として扱う）、作成・変更・削除される Resource の一覧（実行計画）を作る。
内容を確認するplan の出力（+ 追加 / ~ 変更 / - 削除）を見て、意図通りか確認する。
tofu apply承認後、計画どおりに Provider 経由で API を呼び、実際にインフラを作成・変更する。
State を更新する成功した Resource の情報を State に書き込む。次回の plan はこの新しい State を基準にする。

よくある質問

OpenTofu と Terraform は別の言語？いいえ
State を手で直接編集してよい？非推奨
.terraform/ は Git にコミットする？しない
.terraform.lock.hcl は Git にコミットする？する

OpenTofu は、Terraform のライセンスが BSL に変わったことを受けて、最後のオープンソース版（1.5 系）からフォークされたプロジェクトで、現在は Linux Foundation 配下の CNCF でホストされている。HCL 構文・State 形式・Provider エコシステムに高い互換性がある。コマンド名が terraform から tofu に変わるほか、State の暗号化など OpenTofu 独自の機能も追加されている。State を直接編集したい場合は tofu state コマンド群（mv / rm など）や tofu import を使う。
