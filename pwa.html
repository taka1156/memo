PWA の仕組み

Web アプリを「インストールできて、オフラインでも動く」アプリにするための構成と実装チェックリスト

ざっくり言うと
  • PWA (Progressive Web App) は HTTPS・Manifest・Service Worker の 3 つでできている
  • Manifest が「アプリとしての見た目」、Service Worker が「通信の間に入る代理人」を担う
  • オフラインで動くのは、Service Worker がキャッシュしたものだけ

必須の 3 要素

01 / HTTPS 安全な配信

Service Worker は通信を書き換えられるため、HTTPS でしか動かない。開発中の localhost は例外。

02 / MANIFEST アプリの名刺

manifest.webmanifest に名前・アイコン・起動 URL・表示モードを書く。インストール可否の判定材料になる。

03 / SERVICE WORKER 通信の代理人

ページとネットワークの間に立つ JS。リクエストを横取りしてキャッシュから返したり、プッシュ通知を受け取ったりする。

全体の構成図

ページの通信はすべて Service Worker を通る。SW はキャッシュにあればそれを返し、なければネットワークに取りに行く（どちらを先にするかは「キャッシュ戦略」で決める）。

Service Worker のライフサイクル

1. register

ページが sw.js を登録する

2. install

必要なファイルを先にキャッシュしておく

3. waiting

旧 SW が動いている間は待機する

4. activate

古いキャッシュを掃除して有効になる

5. fetch

以降の通信を横取りして応答する

更新時に 3 で止まるのがつまずきやすい点。タブをすべて閉じるか、skipWaiting() を呼ぶまで新しい SW は有効にならない。

キャッシュ戦略

リクエスト→キャッシュ→ なければネットワーク

向いているもの：CSS・JS・画像・フォントなど、ファイル名にバージョンが付いて中身が変わらない静的ファイル。

速くてオフラインに強い。そのかわり、更新はキャッシュ名やファイル名を変えないと反映されない。

リクエスト→ネットワーク→ 失敗したらキャッシュ

向いているもの：API のレスポンスや HTML など、常に最新を見せたいもの。

オンライン時は常に最新。そのかわり、回線が遅いとタイムアウトまで待たされる。

リクエスト→キャッシュを即返す＋ 裏でネットワークで更新

向いているもの：アバター画像やニュース一覧など、多少古くてもすぐ表示したいもの。

表示は速く、次回には新しくなる。そのかわり、今回表示する内容は 1 つ前の版になる。

最小構成のコード

{
  "name": "My App",
  "short_name": "MyApp",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#1a73e8",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/maskable-512.png", "sizes": "512x512",
      "type": "image/png", "purpose": "maskable" }
  ]
}
<meta name="viewport" content="width=device-width, initial-scale=1">
<link rel="manifest" href="/manifest.webmanifest">
<meta name="theme-color" content="#1a73e8">
<link rel="apple-touch-icon" href="/icons/icon-180.png">

<script>
  if ('serviceWorker' in navigator) {
    navigator.serviceWorker.register('/sw.js');
  }
</script>
const CACHE = 'v1';
const ASSETS = ['/', '/index.html', '/style.css', '/main.js', '/offline.html'];

self.addEventListener('install', e => {
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(ASSETS)));
});

self.addEventListener('activate', e => {
  e.waitUntil(
    caches.keys().then(keys =>
      Promise.all(keys.filter(k => k !== CACHE).map(k => caches.delete(k)))
    )
  );
});

self.addEventListener('fetch', e => {
  e.respondWith(
    caches.match(e.request)
      .then(r => r || fetch(e.request))
      .catch(() => caches.match('/offline.html'))
  );
});

手書きが大変なら Workbox、Vite なら vite-plugin-pwa、Next.js なら @serwist/next で生成できる。

よくある誤解

Service Worker を入れれば、アプリ全体がオフラインで動く

動くのはキャッシュしてあるものだけ。API の結果や未訪問のページは、自分でキャッシュしない限りオフラインでは表示できない。

sw.js を書き換えればすぐ反映される

新しい SW は waiting 状態で止まる。すべてのタブを閉じるか、skipWaiting() を呼ぶまで古い SW が動き続ける。

sw.js は /js/ などに置いてもよい

SW が制御できるのは置いた場所以下だけ。/js/sw.js だと /js/ 配下しか制御できない。サーバーが Service-Worker-Allowed ヘッダーを返せば広げられるが、通常はルートに置くのが簡単。

fetch ハンドラがないとインストールできない

以前の Chrome では必須だった。Chrome 108（モバイル）／112（デスクトップ）でメニューからのインストールには不要になり、現在の Chrome のインストール基準にも Service Worker の条件は載っていない。ただし他のブラウザでは基準が異なることがあり、オフライン対応のためにも実装するのが普通。

iPhone でもインストールボタンが自動で出る

iOS の Safari には自動のプロンプトも beforeinstallprompt もない（Firefox も非対応）。ユーザーに共有メニューから追加してもらう必要がある。
