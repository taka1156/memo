Linux のファイルシステムと権限

名前・inode・データ / ハードリンクとシンボリックリンク / rwx の判定順と特殊ビット / umask / マウント

ざっくり言うと
  • ファイルは名前 → inode → データの 3 段。名前はディレクトリが持つ「名前と inode 番号の対応表」の 1 行にすぎず、権限・所有者・サイズなどは inode が持つ。
  • 権限は「所有者・グループ・その他」の 3 組の rwx。カーネルは最初に当てはまった 1 組だけを見る。ディレクトリの rwx はファイルとは意味が違い、ファイルを消せるかはディレクトリの w で決まる。
  • ディスクが何本あっても見えるのは / から始まる 1 本のツリー。各ファイルシステムを途中のディレクトリにマウント（接ぎ木）してできている。

ファイルの中身そのもの。ext4 なら連続した範囲（extent）単位で管理する。

  • ls -i で inode 番号、stat で inode の中身が見える。inode 番号はファイルシステムの中でだけ一意。
  • ctime は作成時刻ではない。権限や所有者を変えても更新される「inode の変更時刻」。作成時刻（birth）は ext4・XFS・Btrfs などが持っていれば stat の Birth に出る。
  • inode の数はファイルシステムを作るときに決まることが多い（ext4）。小さいファイルを大量に作ると、容量が空いていても inode が尽きて書けなくなる（df -i）。
  • そのファイルを開いたままのプロセスがあると、rm しても inode とデータは残る（下で試せる）。

同じファイルシステム内の mv はディレクトリの表の書き換え（rename）だけで、inode もデータも動かない。だから巨大なファイルでも一瞬で終わる。別のファイルシステムへの mv はコピーして消す処理になる。

rwx と 8 進数

r (4)
w (2)
x (1)
0644-rw-r--r--chmod 644 file

ディレクトリの rwx は意味が違う

ビットファイルに対してディレクトリに対して
r中身を読める中にある名前の一覧を読める（ls）
w中身を書き換えられる中に作る・消す・名前を変える（表の行を書き換える）。x も必要
xプログラムとして実行できる通り抜けられる。中の名前を使って inode にたどり着ける（cd・パスの途中に使う）
  • r だけで x が無いディレクトリは、名前の一覧は見えても、中のファイルを開くことも ls -l で詳細を見ることもできない。逆に x だけなら、名前を知っているファイルは開ける（一覧は見えない）。
  • ファイルを消せるかはファイル自身ではなく、親ディレクトリの w と x で決まる。読み取り専用のファイルでも、ディレクトリに書ければ消せる（rm は確認を出すだけ）。
  • パスの途中のディレクトリ全部に x が要る。/home/u/site/index.html が Web サーバーから読めないときは、namei -l で途中のどこが閉じているかを見る。

カーネルの判定順

0プロセスが root（正確には CAP_DAC_OVERRIDE を持つ）なら、読み書きはほぼ素通り。ただし実行は、x がどこにも立っていないファイルは root でもできない。
1プロセスの UID がファイルの所有者と同じ → 所有者の rwx だけを見て決める。
2そうでなく、プロセスのグループ（補助グループを含む）にファイルのグループがある → グループの rwx だけを見る。
3どちらでもない → その他の rwxを見る。

「最初に当てはまった組だけ」なので、chmod 077 file にすると、所有者だけが読めない（グループと他人は読める）という逆転が起きる。ACL（getfacl、ls -l で末尾に +）を使うと、特定のユーザーやグループを個別に追加できる。

umask: 新しく作るときの既定

プログラムは普通、ファイルを 666、ディレクトリを 777 で作ろうとし、そこから umask のビットを落としたものが実際の権限になる。umask はプロセスの属性で、子プロセスに引き継がれる（Linux プロセス）。

umask新しいファイル新しいディレクトリ使われ方
022644755システム全体や root の既定。他人も読める
002664775ユーザーごとに専用グループがある環境（Ubuntu・Fedora の一般ユーザーの既定）。グループで共同編集
077600700自分しか触れない。秘密情報を扱うスクリプト

マウント: 1 本のツリーへの接ぎ木

/ ← ext4 (/dev/nvme0n1p2) ├─ boot/efi ← vfat (/dev/nvme0n1p1) ├─ etc/ usr/ var/ ├─ home ← btrfs (/dev/nvme1n1) ここから下は別のディスク ├─ proc ← proc プロセスの情報をカーネルがその場で見せる ├─ sys ← sysfs デバイス・カーネルの設定 ├─ dev ← devtmpfs デバイスファイル（/dev/null, /dev/sda…） ├─ run, tmp ← tmpfs メモリ上。再起動で消える（/tmp はディストリによる） └─ mnt/nas ← nfs ネットワーク越し
  • mount /dev/sdb1 /mnt/usb で、/mnt/usb から下がそのディスクの中身に差し替わる。元の /mnt/usb にあったファイルは消えたのではなく、隠れて見えないだけ（外すと戻る）。
  • ハードリンクや mv の速さは「同じマウントの中か」で決まる。/home が別ディスクなら、/tmp から /home への mv はコピーになる。
  • バインドマウントはディレクトリを別の場所にもう 1 つ見せる（mount --bind）。Docker の -v ./src:/app はこれ。
  • Docker のイメージのレイヤーは overlayfs で重ねて 1 つに見せ、コンテナごとにマウントの名前空間を分けて別の / を見せている（Docker 動作原理）。

よくある誤解

読み取り専用（444）のファイルは消せない

消すのはディレクトリの表から 1 行を取り除く操作なので、必要なのは親ディレクトリの w と x。ファイル自身の権限は関係ない。他人のファイルを消されたくない共有ディレクトリには sticky ビットを立てる。

大きなログを rm したのに、df の空き容量が増えない

まだそのファイルを開いているプロセスがあると、名前が消えても inode とデータは残る（du には出ないが df には残る）。lsof +L1 で見つけて、そのプロセスを再起動するか、ファイルを : > file で空にしてから消す。

困ったら chmod 777 にすれば動く

誰でも書き換えられるファイルは、他のユーザーや侵入したプロセスが中身を差し替えられる。たいていの原因は所有者の違いかパスの途中の x 不足なので、namei -l と ls -l で見て、所有者（chown）かグループで解決する。

ctime はファイルを作った日時

ctime は inode を最後に変えた時刻（change）。chmod でも mv でも変わる。作成時刻が欲しいときは stat の Birth を見る（ファイルシステムが記録していれば出る）。

コマンド例

ls -li                        # 先頭が inode 番号、権限の次がリンク数
stat memo.txt                 # inode の中身（mode・uid・3 つの時刻・Birth）
find . -samefile memo.txt     # 同じ inode を指す名前（ハードリンク）を探す
namei -l /home/u/site/index.html   # パスの途中の各ディレクトリの権限
id                            # 自分の UID と所属グループ（判定に使われる）
chmod u+x,go-w script.sh      # 記号で足し引き
chmod 2775 /srv/share && chgrp team /srv/share   # チームの共有ディレクトリ
umask                         # 今のシェルの umask
df -h; df -i                  # 容量と inode の空き
lsof +L1                      # 消されたのに開かれたままのファイル
findmnt                       # マウントのツリー（種類とオプション付き）
