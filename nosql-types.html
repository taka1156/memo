NoSQL の種類

キーバリュー / ドキュメント / ワイドカラム / グラフ / 問い合わせから設計する / 分散と整合性

ざっくり言うと
  • NoSQL は「SQL でない」ではなく「RDB の表と JOIN 以外の形」の総称。4 種類はデータの形と、得意な問い合わせがまるで違うので、ひとまとめに比べても意味がない。
  • 多くの NoSQL は、JOIN や自由な検索を諦める代わりに、キーで台を決めて横に増やせるようにしている。だから先に「どんな問い合わせをするか」を決め、それに合わせてデータを置く。
  • 迷ったらまず RDB（PostgreSQL の JSONB も含む）。NoSQL は、規模・アクセスの形・データのつながり方が RDB と合わないとはっきりしたときに選ぶ。

前提: RDB の中身（B-Tree・WAL・MVCC）は DB のしくみ、インデックスとトランザクションは インデックスとトランザクション。

同じデータを 4 つの形で持つ

EC サイトの「ユーザー u1、その注文 2 件、フォローしているユーザー」を、それぞれの種類で持つとこうなる。

users (id, name) u1 | 佐藤 orders (id, user_id, total) o1 | u1 | 3200 o2 | u1 | 980 follows (from, to) u1 | u2 u1 | u3 -- 表に分けて重複なく持ち、問い合わせのときに JOIN でつなぐ

どんな切り口の問い合わせにも後から対応でき、トランザクションで複数の表を一度に正しく更新できる。苦手なのは、1 台に収まらない書き込み量を横に分けることと、何段も続くつながりをたどること。

user:u1 → {"name":"佐藤"} user:u1:orders → ["o1","o2"] order:o1 → {"total":3200} session:9f2c… → {"uid":"u1"} TTL 30 分 # 値の中身は DB からは見えない（Redis はリストやハッシュなどの型を持つ）

得意

キーが分かっている 1 件の読み書き。とにかく速く、台を増やすのも簡単。期限付きのデータ（TTL）。

苦手

値の中身での検索（「3000 円以上の注文」）、範囲や並べ替え、複数キーにまたがる一貫した更新。

例: Redis / Valkey（メモ）、Memcached、etcd、Cloudflare Workers KV。用途: キャッシュ、セッション、レート制限のカウンタ、設定値。

{ "_id": "u1", "name": "佐藤", "orders": [ // 一緒に読むものは埋め込む { "id": "o1", "total": 3200, "items": [...] }, { "id": "o2", "total": 980 } ], "following": ["u2", "u3"] } // 別のドキュメントは ID で参照

得意

画面 1 枚分のまとまりを 1 回で読み書き。項目がものによって違うデータ。中のフィールドにインデックスを張って検索もできる。

苦手

ドキュメントをまたぐ JOIN（できるが遅く、設計の前提にしない）。埋め込んだデータが際限なく増える形（注文が何万件にもなる人）。

例: MongoDB、Firestore、Couchbase、Amazon DocumentDB。PostgreSQL の JSONB 列でも近いことができる。用途: CMS、商品カタログ、ユーザープロフィール、モバイルアプリの同期。

-- テーブル orders_by_user：「ユーザーの注文を新しい順に」専用 partition key = user_id clustering key = ordered_at DESC u1 │ 2026-11-05 o2 980 │ 2026-10-21 o1 3200 │ …（行が横に何百万でも伸びる） u2 │ 2026-11-06 o7 1500 │ … -- 別の問い合わせ（日付ごとの売上など）には、同じデータを別のテーブルにもう一度書く

得意

大量の書き込み（ログ・センサー・メッセージ）。パーティションキーを指定した範囲読み出し。台を足すだけで容量も書き込み性能も伸びる。

苦手

パーティションキーを指定しない検索、JOIN、集計、後から問い合わせを増やすこと（テーブルを作り直す）。

例: Apache Cassandra、ScyllaDB、HBase、Google Cloud Bigtable。Amazon DynamoDB も「パーティションキー＋ソートキー」で同じ考え方をする。用途: 時系列、チャット履歴、アクティビティフィード、IoT。

(u1:User {name:"佐藤"}) -[:FOLLOWS]-> (u2:User) (u1) -[:FOLLOWS]-> (u3:User) -[:BOUGHT]-> (p9:Product) // 「u1 がフォローしている人が買った商品のうち、u1 がまだ買っていないもの」 MATCH (me:User {id:'u1'})-[:FOLLOWS]->(:User)-[:BOUGHT]->(p) WHERE NOT (me)-[:BOUGHT]->(p) RETURN p, count(*) ORDER BY count(*) DESC

得意

つながりを何段もたどる問い合わせ。ノードが隣へのつながりを直接持つので、段数が増えても JOIN のように爆発しにくい。経路・影響範囲・推薦。

苦手

全件の集計や大量の単純な読み書き。データを多数の台に分けること（つながりが台をまたぐと遅い）。

例: Neo4j（Cypher）、Amazon Neptune、Memgraph。問い合わせ言語の国際標準として GQL がある。用途: SNS の関係、不正検知、権限のつながり（ReBAC）、依存関係、ナレッジグラフ。

問い合わせ別の向き不向き

問い合わせから設計する

RDB の進め方

  1. 実体と関係を洗い出す
  2. 正規化して表に分ける（重複させない）
  3. 問い合わせは後から SQL で自由に書く
  4. 遅いものにインデックスを足す

NoSQL（特にワイドカラム・KV）の進め方

  1. アプリがする問い合わせを先に全部書き出す
  2. 問い合わせ 1 つにつき、1 回で読める置き方を決める
  3. 必要なら同じデータを複数の場所に重複して書く
  4. 新しい問い合わせが増えたら、置き方を足す

重複して書くので、更新はアプリ（または DB のストリーム機能）が複数箇所を書き換えることになる。読み出しを速くする代わりに、書き込みと整合性の手間を自分で持つ、という取引。

パーティションキーで台が決まる

キーをハッシュして、どのノード（パーティション）に置くかを決める。キーの選び方で負荷の偏りが決まる。

分散と整合性

  • 複数の台にコピーを持つので、「書いた直後に別の台から読むと古い値が見える」ことがある（結果整合性）。多くの NoSQL は、読み書きのたびにどこまで整合性を求めるかを選べる（Cassandra は ONE / QUORUM / ALL で何台の応答を待つかまで指定でき、DynamoDB は読み込みごとに「強力な整合性のある読み込み」にするかを選ぶ）。強い整合性を求めるほど新しく正確になり、遅く・落ちやすくなる。考え方は 分散システムの基本。
  • 「NoSQL はトランザクションが無い」は今は不正確。1 件（1 ドキュメント・1 パーティション）の中の更新はたいてい原子的で、MongoDB や DynamoDB は複数件にまたがるトランザクションも持つ。ただし台をまたぐほど遅く、制限も多いので、1 件の中で完結するように置くのが基本。
  • RDB のまま横に広げる NewSQL（Spanner・CockroachDB・TiDB）という選択肢もある。SQL とトランザクションを残したまま台を増やせる代わりに、仕組みが重く遅延も増える。

4 種類以外によく並べられるもの

種類得意なこと例
全文検索エンジン文章のあいまい検索、関連度順、絞り込みの件数集計Elasticsearch、OpenSearch、Meilisearch
時系列 DB時刻つきの数値の大量書き込みと、期間での集計・間引きPrometheus、InfluxDB、TimescaleDB
ベクトル DB意味の近さでの検索（埋め込みベクトル）pgvector、Qdrant など（RAG とベクトル検索）
列指向の分析 DB大量の行の集計（OLAP）BigQuery、ClickHouse（BigQuery と BI）

よくある誤解

スキーマレスだから設計しなくていい

DB がスキーマを強制しないだけで、どのフィールドがどんな型で入っているかの約束は、アプリのコードが持つことになる。古い形のドキュメントと新しい形が混ざると、読む側が全部の形に対応しなければならない。MongoDB のスキーマ検証や、アプリ側のスキーマ（Zod など）で縛るのが普通。

NoSQL は RDB より速い

速いのは、設計どおりのキーで読むときだけ。想定していない問い合わせは全件走査になり、RDB よりはるかに遅いか、そもそもできない。1 台に収まる規模なら、インデックスを張った RDB で十分速いことが多い。

ドキュメント DB なら、関連するものは全部 1 つに埋め込むのが正解

一緒に読むものは埋め込み、際限なく増えるもの・単独で更新されるもの・多くの場所から参照されるものは別のドキュメントにして ID で参照する。注文を全部ユーザーに埋め込むと、ドキュメントの上限サイズ（MongoDB は 16MB）に当たったり、毎回巨大なドキュメントを読み書きすることになる。

グラフ DB は SNS のためのもの

「つながりを何段もたどる」問い合わせがあれば対象になる。不正検知（同じ端末・同じ住所でつながった口座）、権限（グループの中のグループ）、マイクロサービスの依存関係、部品表など。逆に SNS でも、タイムラインの表示はワイドカラムや KV の方が向くことが多い。
