パッケージマネージャとロックファイル

npm・pnpm・uv・Cargo・Go modules を並べて見る。違うのは「依存がぶつかったときにどう決めるか」

ざっくり言うと
  • どの言語のパッケージマネージャも、マニフェスト（欲しい範囲）・ロックファイル（実際の版）・キャッシュの 3 層でできている。
  • 大きく違うのは依存がぶつかったときで、npm は複数版を並べ、Python は 1 つに絞り、Go は全員の要求を満たす最も古い版（下限のうち最大）を選ぶ。
  • アプリはロックファイルをコミットし、CI では「ロックファイルと食い違ったら失敗する」コマンドで入れる。

3 つの層

マニフェスト

人が書く。「この範囲なら動く」

  • package.json
  • pyproject.toml
  • Cargo.toml
  • go.mod

ロックファイル

ツールが書く。「実際にこの版を入れた」＋ハッシュ

  • package-lock.json・pnpm-lock.yaml
  • uv.lock・poetry.lock
  • Cargo.lock
  • go.sum（ハッシュだけ）

キャッシュ・ストア

PC に 1 つ。ダウンロード済みの実体

  • npm: ~/.npm からコピー
  • pnpm・uv: 共通の置き場からリンク
  • Cargo: ~/.cargo/registry
  • Go: $GOPATH/pkg/mod（読み取り専用）

マニフェストの範囲（^1.2.0 など）だけだと、入る版が日によって変わります。解決（resolution: 範囲を満たす具体的な版の組み合わせを決める作業）の結果をロックファイルに書き残し、次からはそれをそのまま使うことで、開発者・CI・本番で同じものが入ります。JavaScript の node_modules の作り方（npm の平らな並べ方と pnpm のリンク）は JS のモジュールと依存管理 にあります。

版の範囲の書き方

多くのエコシステムがセマンティック バージョニング（SemVer: メジャー.マイナー.パッチ。メジャーが上がると互換性が壊れる）を前提に、「互換の範囲なら上がってよい」と書きます。書き方と既定の意味がエコシステムで少しずつ違います。

やりたいことnpmCargoPython（PEP 440）Go
1.2.3 以上・2 未満^1.2.3"1.2.3"（何も付けないとこの意味）>=1.2.3,<2require … v1.2.3（下限だけ書く）
1.2.3 以上・1.3 未満~1.2.3"~1.2.3"~=1.2.3—
1.2 以上・2 未満^1.2"1.2"~=1.2—
ちょうどこの版1.2.3"=1.2.3"==1.2.3—（下限が選ばれやすい。解決を参照）

npm と Cargo では、0.x の間はマイナーが上がると互換が壊れる扱いになり、^0.2.3 は「0.2.3 以上・0.3 未満」になる。Python の ~= は compatible release（互換リリース）と呼ばれ、最後の桁だけを上げてよいという意味。Go では v2 以上は example.com/lib/v2 のように別のモジュールパスになる。

依存がぶつかったときの解決

アプリが A と B に依存し、A と B がそれぞれ同じ lib の別の範囲を要求している場面で比べます。lib は 1.2.0・1.5.0・1.9.0・2.0.0 が公開されているとします。

エコシステム入る lib決め方
npm・pnpm1.9.0 を 1 つ両方を満たす中で最新を選び、重複を 1 つにまとめる
Cargo1.9.0 を 1 つ互換の範囲（同じメジャー）は 1 つにまとめ、最新を選ぶ
Python（pip・uv）1.9.0 を 1 つ環境に 1 版しか置けない。両方を満たす最新を探す
Go1.5.0要求された下限（1.2.0 と 1.5.0）の大きいほう。1.9.0 が出ていても上げない（最小バージョン選択, MVS）

Go だけ結果が違います。最新を選ぶ方式は「今日解決すると明日と違う結果になる」のでロックファイルが要りますが、MVS は go.mod の下限だけで結果が 1 つに決まります。そのため Go には版を固定するためのロックファイルが無く、go.sum はダウンロードした中身が改ざんされていないかを確かめるハッシュの一覧です。

エコシステム結果しくみ・注意
npm・pnpm1.9.0 と 2.0.0 が共存A の下に 1.x、B の下に 2.x を置く（入れ子の node_modules）。React のように1 つだけでないと壊れるものは peerDependencies で「使う側が入れたものを共有する」と宣言する
Cargo1.9.0 と 2.0.0 が共存互換でない版は別物としてビルドされる。両方の型は別の型なので、A が返した lib の値を B に渡すとコンパイルエラーになる
Python（pip・uv）解決できずエラー1 つの環境に同じ名前は 1 版だけ。A か B の古い版で両立する組み合わせを探し（バックトラック）、無ければ失敗する
Gov1.2.0 と v2.0.0 が共存v2 は lib/v2 という別のモジュールなので、そもそもぶつからない。v1 側は A の下限 v1.2.0 がそのまま選ばれる（MVS）

緑は共存して動く、赤はインストールの時点で失敗するエコシステムです。共存できるほうが楽に見えますが、同じライブラリが 2 つ入ると、サイズが増え、グローバルな状態（シングルトン）や型が分かれて実行時・コンパイル時の問題になります。1 つに絞る Python は、ぶつかりをインストールの時点で必ず知らせるとも言えます。

uv の --locked は「ロックファイルが古ければ失敗」、--frozen は「古いかどうか確かめずにそのまま使う」。Python の共通のロックファイル形式として pylock.toml（PEP 751）も決まり、pip は pip lock での書き出しと pip install -r pylock.toml でのインストールに（実験的に）対応した。uv も読み書きできるが、主に使うのは uv.lock。

コミットするか

  1. アプリ・サービス必ずコミットする。入れたら動いた組み合わせを、そのまま本番に届けるため。
  2. ライブラリコミットしてよい（Cargo も 2023 年に、ライブラリでもコミットを判断の出発点として勧め、cargo new が Cargo.lock を無視しないように変えた）。ただし、ライブラリのロックファイルは使う側には効かない。使う側では、マニフェストの範囲をもとに、使う側のロックファイルで決め直される。
  3. 衝突したらロックファイルを手で直さない。マニフェストの変更を取り込んでから、ツールにもう一度解決させて作り直す。

ライブラリでロックファイルをコミットしたときは、範囲の中で最新の依存でも動くかを CI で定期的に確かめると、使う側で初めて壊れるのを防げます（Dependabot などで更新を自動で出す）。

言語本体の版も固定する

依存を固定しても、Node.js や Python 自体の版が違うと結果が変わります。言語の版も、リポジトリのファイルに書いておきます。

言語書く場所読んで切り替えるもの
Node.js.nvmrc・.node-version、package.json の enginesnvm・fnm・mise など。パッケージマネージャ自体の版は packageManager で揃える
Python.python-version、pyproject.toml の requires-pythonuv（Python 本体の取得もする）・pyenv
Rustrust-toolchain.tomlrustup が自動で切り替える
Gogo.mod の go・toolchain の行go コマンド自身（足りなければ新しいツールチェーンを取得する）

よくある誤解

ロックファイルがあれば、マニフェストの範囲はどう書いてもよい

範囲は「上げるときにどこまで上がってよいか」を決めます。さらにライブラリでは、使う側がその範囲をもとに解決するので、範囲が狭すぎると使う側でぶつかりやすく、広すぎると動かない版が選ばれます。

Go も npm と同じく、範囲の中の最新版を入れる

Go は要求された下限の中で最も大きいもの（＝全員の要求を満たす最も古い版）を選びます。新しい版が出ても、go get -u などで明示しない限り上がりません。

npm install と npm ci は、入るものが同じ

npm install は package.json に合わせてロックファイルを書き換えることがあります。npm ci は node_modules を消してロックファイルどおりに入れ、package.json と食い違えば失敗します。CI では npm ci を使います。

Python でも依存ごとに別の版を入れれば、ぶつかりは避けられる

1 つの仮想環境の site-packages には同じ名前のパッケージを 1 版しか置けません。どうしても両立しないなら、環境を分ける（別のサービス・別の仮想環境）か、どちらかの依存を上げ下げします。
