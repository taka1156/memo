正規表現のしくみ

パターンは状態の図（オートマトン）になる。エンジンがそれをどうたどるかで、使える機能と速さが決まる

ざっくり言うと
  • 正規表現は「1 文字読むごとに状態を移る図」（NFA）に組み立てられ、マッチはその図を入力でたどる作業になる。
  • たどり方は、分かれ道を 1 本ずつ試して戻るバックトラックと、ありうる状態を全部同時に持って進む方式の 2 つ。
  • 多くの言語の標準はバックトラックで多機能だが、書き方しだいで指数時間（ReDoS）になる。線形時間の方式は後方参照などが使えない。

パターンは状態の図になる

エンジンはまずパターンを解析して、状態（丸）と、文字で進む矢印の図に組み立てます。これをオートマトンと呼び、同じ文字で行き先が複数ありうるものを NFA（非決定性有限オートマトン, Nondeterministic Finite Automaton）、行き先が常に 1 つに決まるものを DFA（決定性有限オートマトン）と呼びます。

例として a(b|bc)d を図にします。状態 1 から b で進む矢印が 2 本ある（どちらの選択肢か、読んだ時点では決まらない）ので、これは NFA です。右端の二重丸が「ここに着いたらマッチ」の受理状態です。

図: a(b|bc)d の NFA と入力 abcd。下の手順を進めると、紫の枠で「今いる状態」と「今読む文字」が光る

部品の組み立て方

どんなに長いパターンも、次の 3 つの部品の組み合わせで図にできます（トンプソンの構成法, Thompson's construction）。図の大きさはパターンの長さにほぼ比例します。

構文意味図にすると
ab連結a の図の出口を、b の図の入口につなぐ
a|b選択入口から 2 本に分かれ、出口で合流する（ここで行き先が複数になる）
a*繰り返しa の図の出口から入口へ戻る矢印と、a を飛ばす矢印を足す

+・?・{2,5}・文字クラス [a-z] は、この 3 つの言い換えとして図にできる。実際の図では文字を読まずに進む矢印（ε 遷移）も使うが、上の例では省いている。

図のたどり方は 2 通り（＋表にする方式）

同じ図・同じ入力 abcd を、方式ごとにたどってみます。「次へ」で 1 手ずつ進むと、上の図の今いる状態が光ります。

分かれ道に来たら1 本を選んで進み、行き詰まったら最後の分かれ道まで戻って（バックトラック, backtracking）次の道を試します。深さ優先探索と同じ考え方です。

  1. 状態 0・位置 0a を読んで状態 1 へ。
  2. 状態 1・位置 1（分かれ道）行き先が 2 つある。まず 1 本目（b → 状態 2）を選び、「ここに戻れる」と覚えておく。
  3. 状態 2・位置 2（行き詰まり）次は d が要るのに、入力は c。失敗したので、覚えておいた分かれ道まで戻る。
  4. 状態 1・位置 1（戻った）読む位置も 1 に戻す。2 本目（b → 状態 3）を試す。
  5. 状態 3・位置 2c を読んで状態 2 へ。
  6. 状態 2・位置 3d を読んで受理状態 4 へ。マッチ成功。

赤の手順が行き詰まり、緑の手順が成功です。同じ文字（位置 1〜2）を 2 回読んでいる点に注目してください。分かれ道が重なると、この「読み直し」が掛け算で増えます（ReDoS）。そのかわり、戻る前提なので「さっき取り込んだ文字列と同じか」を確かめる後方参照のような機能を足しやすい方式です。

分かれ道で 1 本を選ばず、ありうる状態を全部まとめて持ったまま 1 文字ずつ進みます（NFA シミュレーション。トンプソンの方式とも呼ばれる）。行き詰まった状態は集合から消えるだけで、戻りません。

  1. {0} で a を読む状態 0 から a で 1 へ。集合は {1}。
  2. {1} で b を読む行き先が 2 つあるので両方入れる。集合は {2, 3}。
  3. {2, 3} で c を読む状態 2 は c で進めないので消える。状態 3 は 2 へ。集合は {2}。
  4. {2} で d を読む受理状態 4 に入ったのでマッチ成功。

緑の手順がマッチ成功です。バックトラックと違って、赤の「行き詰まり」の手順がありません。どの文字も 1 回しか読みません。1 文字ごとの仕事は「集合の中の状態を全部進める」だけで、集合の大きさは図の状態の数（≒パターンの長さ m）を超えないので、全体で O(n × m)（n は入力の長さ）に収まります。Go の regexp・RE2・Rust の regex はこの考え方で線形時間を保証しています。

「状態の集合」そのものを 1 つの状態とみなして、あらかじめ表にしておく方式です（部分集合構成法, subset construction）。マッチ中は 1 文字ごとに表を 1 回引くだけになり、最も速く動きます。

DFA の状態中身（NFA の状態の集合）abcd
A{0}B———
B{1}—C——
C{2, 3}——DE
D{2}———E
E{4}（受理）————

「—」は進めない（その時点で失敗）。C で d を読めば abd にマッチする。

弱点は表の大きさです。NFA の状態が m 個なら、集合の組み合わせは最大 2m 通りあり、パターンによっては表が爆発します。そこで RE2 などは、実際に通った集合だけを表に足していく（遅延 DFA, lazy DFA）作り方をし、表が大きくなりすぎたら捨てて作り直したり、集合で進む方式に切り替えたりします。GNU grep も DFA を中心に使います。

方式マッチの時間使える機能主な採用先
バックトラック多くは速いが、最悪で指数時間後方参照・先読み・後読みなど全部JavaScript・Python・Java・.NET・Ruby・PCRE（PHP など）
状態の集合で進むO(n × m) を保証後方参照・先読み後読みはなしGo・RE2・Rust の regex
DFA（遅延構築）O(n)＋表を作る手間同上。取り込み（キャプチャ）の位置を出すのは苦手RE2・Rust の regex（内部で使い分け）・GNU grep

線形時間のエンジンで使えない機能

状態の集合で進む方式は、「状態」と「今の位置」しか覚えません。過去にどの文字列を取り込んだかや、今の位置より先・後ろの文字を見る機能は、この形に収まらないため外されています。

機能例バックトラック系Go・RE2・Rustなぜ
後方参照(\w+) \1（同じ単語の繰り返し）使える使えない取り込んだ文字列の中身は無数にあり、有限の状態で覚えられない。後方参照つきのマッチは一般に NP 困難
先読み・後読み\d+(?=円)、(?<=\$)\d+使える使えない位置の前後を別に確かめるため、1 回の通しのたどりに収まらない
アトミックグループ・強欲な量指定子（possessive）(?>a+)、a++Java・PCRE・Ruby・Python 3.11 以降は両方、.NET はアトミックグループだけ（JavaScript にはどちらも無い）不要「戻らない」と指示してバックトラックを抑える機能。戻らない方式には要らない
最短一致・キャプチャ.*?、(\d+)-(\d+)使える使える状態に優先順位や位置を持たせれば、線形のまま扱える

Go で regexp.MustCompile(`(\w+) \1`) と書くと、実行時にパターンを組み立てる段階で panic します（regexp.Compile ならエラーが返ります）。「速さの保証」と「表現力」はトレードオフで、どちらを優先するかが言語ごとの設計の違いです。

ReDoS はバックトラックの組み合わせ爆発

バックトラックの弱点は「分かれ道の組み合わせを全部試す」ことです。^(a+)+$ は、a を内側の + で読むか、外側の + で読み直すかの分かれ道が文字ごとにあります。入力 aaa…a! は最後の ! で必ず失敗するので、エンジンは a の並びの分け方を全部試してから諦めます。

バックトラック

a が n 個なら、分け方は 2n−1 通り。

  • n = 10 → 512 通り
  • n = 20 → 約 52 万通り
  • n = 30 → 約 5.4 億通り

状態の集合で進む

同じ図でも、集合は「a を読める状態」に落ち着いたまま進み、! で空になって終わる。

  • n = 30 でも 31 文字を 1 回ずつ読むだけ

同じ文字を 2 通り以上で読める形（量指定子の入れ子 (a+)+、選択肢の重なり (\d|\w)+、省略できる区切り (\w+\s?)*）がそろうと危険です。危ない形の一覧と、実際にブラウザで時間を測るデモは 実装起因の脆弱性（入力の扱い） にあります。

  1. 形で避ける同じ文字を複数の道で読めないように書く（(a+)+ → a+）。lint（eslint-plugin-regexp など）で機械的に見つける。
  2. 入力を短く切るマッチの前に長さの上限を確かめる。指数時間でも n が小さければ終わる。
  3. エンジンを選ぶユーザーがパターンを入力できる機能や、外から来る長い文字列の検査には、線形時間のエンジン（RE2・Go・Rust、.NET の NonBacktracking）を使う。

よくある誤解

正規表現はどの言語でも同じ意味・同じ速さで動く

構文は似ていても、エンジンの方式が違います。Go で後方参照がエラーになる、JavaScript では指数時間になるパターンが Rust では一瞬で終わる、ということが普通に起きます。\w や \d が Unicode の文字まで含むかも言語やフラグで変わります。

ReDoS は長くて複雑な正規表現だけの問題だ

^(\w+\s?)*$ のような 1 行の短いパターンでも起きます。長さではなく「同じ文字を複数の道で読めるか」が問題です。

最短一致の .*? にすれば、バックトラックの爆発は防げる

最短一致は「どの道から先に試すか」の順番を変えるだけです。マッチが失敗する入力では結局すべての道を試すので、試す回数は減りません。

線形時間のエンジンに変えれば、今のパターンはそのまま全部動く

後方参照・先読み・後読みを使ったパターンは、RE2・Go・Rust の regex ではコンパイルエラーになります。置き換える前に、それらを使っていないか確かめ、使っていればコードでの判定に分けます。

関連メモ

  • 実装起因の脆弱性（入力の扱い） — ReDoS の危ない形の一覧と、ブラウザで時間を測るデモ
  • JS のイベントループと非同期 — Node.js で重い正規表現 1 回がサーバー全体を止める理由
  • グラフ探索と最短経路 — バックトラックは深さ優先探索、集合で進むのは幅優先探索に近い
  • フォームとバリデーション — pattern 属性など、入力検証で正規表現を使う場面
  • 文字コードと Unicode — 「1 文字」が何を指すかで、. や文字クラスの結果が変わる
