Docker 動作原理

コンテナは「隔離と制限をかけた、ただの Linux プロセス」

ざっくり言うと
  • イメージは読み取り専用のレイヤーの積み重ね。コンテナはその上に薄い書き込み層を 1 枚のせて動く（OverlayFS + Copy-on-Write）。
  • 「見える範囲」を分けるのが名前空間 (namespace)、「使える量」を抑えるのが cgroups。
  • カーネルはホストと共有。だから VM より軽く速いが、Linux コンテナは Linux カーネルの上でしか動かない。

OverlayFS と Copy-on-Write

upperdir読み書きできる層（コンテナ専用）…/overlay2/<id>/diff
＋
lowerdir読み取り専用の層（イメージレイヤー群）
▼ カーネルが重ねてマウント
mergedコンテナから見えるファイルシステム（ルート /）…/overlay2/<id>/merged

パスは overlay2 ストレージドライバーの例。containerd の image store を使う設定では置き場所が変わるが、重ね方の考え方は同じ。

ファイルを書き換えたときの動き

  1. 読むだけなら下の層をそのまま見るコンテナが /etc/nginx/nginx.conf を読む → lowerdir のファイルが透過的に見える。
  2. 書き込んだ瞬間に上の層へコピーカーネルがそのファイルを lowerdir から upperdir にコピーする（copy-up）。
  3. 変更は upperdir のコピーにだけ入る元の lowerdir（イメージ）は一切変わらない。
  4. コンテナを消すと upperdir だけ消えるイメージはそのまま残り、次のコンテナで再利用される。

名前空間（namespace）— 見える範囲を分ける

PIDProcess ID

コンテナ専用のプロセス番号の空間。コンテナの最初のプロセスは PID 1 に見え、ホストのプロセスは見えない。

NETNetwork

NIC・ルーティングテーブル・ポートを独立させる。外とは veth ペアでつなぐ。

MNTMount

マウントポイントを独立させる。ここに OverlayFS をマウントして専用のファイルシステムにする。

IPCInter-Process Communication

共有メモリ・セマフォなどをコンテナ間で分け、意図しない通信を防ぐ。

UTSUNIX Time-Sharing

ホスト名・ドメイン名を独立させる。コンテナごとに別のホスト名を持てる。

USERUser ID

コンテナ内の root をホストの一般ユーザーに対応づける（userns-remap や rootless モード）。

cgroups は制限だけでなく、使用量の計測や優先度付けもする。設定は /sys/fs/cgroup/ 以下にファイルとして見える。メモリ上限を超えるとコンテナ内のプロセスが OOM で止められる。

docker run の流れ

$ docker run -it ubuntu:22.04 bash
  1. CLI → dockerdDockerDocker CLI が Unix ソケット経由で dockerd（デーモン）に API リクエストを送る。
  2. イメージの確認・取得Dockerローカルにイメージがなければレジストリ（Docker Hub など）からレイヤーを pull して展開する。
  3. containerd → shim → runc に委譲containerddockerd が containerd に指示し、containerd はコンテナごとの shim を立てて OCI ランタイムの runc を呼ぶ。
  4. 名前空間を作るカーネルrunc が clone() / unshare() で PID・NET・MNT・UTS・IPC などの名前空間を作り、プロセスをその中に置く。
  5. OverlayFS をマウントカーネルlowerdir（イメージ層）と upperdir（書き込み層）を merged に重ね、コンテナのルートファイルシステムにする。
  6. cgroups を設定カーネル/sys/fs/cgroup/ にコンテナ用のグループを作り、CPU・メモリなどの上限を書き込む。
  7. pivot_root → PID 1 を起動runcpivot_root() で merged をルートに切り替え、CMD / ENTRYPOINT を exec。ここでは bash がコンテナ内の PID 1 になる。runc は起動後に抜け、以降は shim がプロセスを見守る。
