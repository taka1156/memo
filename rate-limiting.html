レート制限のアルゴリズム

固定ウィンドウ・スライディングウィンドウ・トークンバケット・リーキーバケットを同じリクエスト列で比べる

ざっくり言うと
  • レート制限は「この相手からは一定時間に N 回まで」と数えて超えた分を断る仕組みで、過負荷・総当たり・使いすぎを防ぐ。
  • 数え方で振る舞いが変わり、固定ウィンドウは境目で上限の 2 倍まで通し、トークンバケットは決めた量の連続を許して平均を守る。
  • 複数台では共有の場所で原子的に数え、断るときは 429 と待つ秒数を返し、IP より利用者や API キーを単位にする。

何を守るのか・どこで数えるか

レート制限で守るものは主に 4 つです。サーバーの過負荷（1 つの相手の暴走で全員が遅くなる）、総当たり（ログインやクーポンコードの試行）、公平さ（1 社が共有の枠を使い切らない）、費用（外部 API や LLM の従量課金）。どれを守りたいかで、数える単位と上限の決め方が変わります。

CDN・WAF

IP やパスごとの大まかな制限。オリジンに届く前に落とせる

リバースプロキシ・API ゲートウェイ

nginx の limit_req など。API キーやパスごとに数える

アプリ

利用者・プラン・操作の重さなど、業務の情報を使って細かく数える

手前の層ほど安く大量に落とせるが、使える情報が少ない（誰のリクエストかまで分からないことが多い）。実際は手前で大まかに、アプリで細かく、と重ねる。中継が挟まると送信元 IP の扱いに注意が要る（ロードバランサ・リバースプロキシ・CDN）。

5 つの数え方

固定ウィンドウfixed window counter

時計で区切った枠（毎分 0 秒から）ごとにカウンターを 1 つ持ち、上限に達したら次の枠まで断る。

持つもの: カウンター 1 つ

スライディングウィンドウ（ログ）sliding window log

通したリクエストの時刻を全部記録し、「今から 1 分前まで」の件数で判定する。正確。

持つもの: 時刻の一覧（上限の件数ぶん）

スライディングウィンドウ（カウンター）sliding window counter

今の枠と 1 つ前の枠のカウンターから、「直近 1 分」の件数を重み付きで見積もる。

持つもの: カウンター 2 つ

トークンバケットtoken bucket

一定の速さでトークンが貯まる容量 B のバケツ。1 回ごとに 1 個使い、空なら断る。B 回までの連続を許す。

持つもの: 残りトークン数と最後に補充した時刻

リーキーバケットleaky bucket

来たリクエストをバケツ（待ち行列）に入れ、底の穴から一定の速さで流す。あふれた分を断る。出ていく速さが一定になる。

持つもの: 待ち行列の長さ（と次に流せる時刻）

同じリクエスト列で比べる

上限はどれも「1 秒に 5 回」。トークンバケットは容量 5・毎秒 5 個補充（最初は満タン）、リーキーバケットは 0.2 秒に 1 本流し、待てるのは 5 本まで（nginx の limit_req で burst=5 を付けた形）とします。印は届いた順に並べ、1s・2s の点線は固定ウィンドウの枠の境目（そこで秒が変わる）です。

0.8〜1.0 秒に 5 本、1.0〜1.2 秒に 5 本、その後ぽつぽつ 3 本。固定ウィンドウは枠ごとに 5 本以内なので、0.4 秒で届いた 10 本を全部通す。ほかの窓で数える方式とトークンバケットは 6〜7 本目から断る。リーキーバケットは大半を待たせて 0.2 秒おきに流し、待ち行列からあふれた分（8・9 本目）だけ断る。

最初の 0.45 秒に 10 本、1.0 秒からは 0.25 秒おきに 8 本。トークンバケットは満タンの 5 本に、その間に補充された分を足して 6 本を続けて通し、少し間をおいて補充された 1 個でもう 1 本通す（最初の 10 本のうち 7 本）。窓で数える 3 方式は 6 本目から断る。リーキーバケットは受け取った分を 0.2 秒おきに流すので、ほとんどが遅れて処理される。

0.15 秒おき（毎秒約 6.7 本）。窓で数える 3 方式は、枠や窓ごとに 5 本を超えた分を断る。トークンバケットは最初の 5 個の貯金を少しずつ使うので、3 秒の間はほぼ通し続ける（続けば補充の速さ以上は通らない）。リーキーバケットは断らないが、待ちがだんだん長くなる（続けば待ち行列があふれて断り始める）。

すぐ通す待たせてから通す断る（429 など）

選び方

方式正確さ連続（バースト）記録の量向いている場面
固定ウィンドウ枠の境目で上限の 2 倍まで通る枠の始まりに集中しやすいとても少ない日ごと・月ごとの利用枠、多少の超過を気にしない場面
スライディング（ログ）正確直近の窓の中で上限まで多い（相手ごとに上限件数）上限が小さい制限（ログイン試行 5 回/15 分など）
スライディング（カウンター）ほぼ正確（見積もり）直近の窓の中で上限まで少ない（2 つ）「1 分に N 回」と約束する API。大量の相手を数える CDN
トークンバケット平均の速さを守る容量 B までは一気に通す少ない（2 つ）普段は少なく、ときどきまとめて呼ぶクライアントがいる API
リーキーバケット出ていく速さが一定待ち行列で受けて遅らせる少ない後ろのサーバーを一定の速さで守りたいとき（遅れてもよい処理）

固定ウィンドウの境目問題

「1 分に 100 回」を固定ウィンドウで数えると、0:59 に 100 回、1:00 に 100 回送られたとき、どちらの枠でも上限内なので2 秒で 200 回が通ります。枠の中でしか数えていないので、枠をまたいだ集中が見えません。

200
0:001:00（枠の境目）2:00

赤い帯: 境目をはさむ 2 秒間に、それぞれの枠の上限 100 回ずつ、合わせて 200 回が通る。

日ごとの利用枠のように「長い目で見て合っていればよい」用途なら、この粗さは問題になりません。秒〜分の単位で後ろのサーバーを守りたいときは、スライディングウィンドウかトークンバケットにします。

スライディングウィンドウ（カウンター）の見積もり

ログ方式は正確ですが、相手ごとに時刻を上限件数ぶん持つので、相手が多いと記録が膨らみます。カウンター方式は「1 つ前の枠のリクエストは枠の中に均等に来ていた」と仮定して、直近の窓に重なっている割合だけ数えます。

見積もり = 前の枠の件数 × (窓の長さ − 今の枠の経過時間) / 窓の長さ + 今の枠の件数

例: 上限 50 回/分、前の 1 分に 42 回、今の枠は始まって 15 秒で 18 回なら、42 × 45/60 + 18 = 49.5 回。まだ 50 未満なので通します。Cloudflare はこの方式でレート制限を作り、実際の 4 億リクエストで調べた結果、正確なスライディングウィンドウと判定が食い違ったのは 0.003% だったと報告しています。

トークンバケットの実装

「毎秒トークンを足す」タイマーは要りません。リクエストが来たときに、前回から経った時間ぶんをまとめて補充してから判定します。

function allow(b, now, rate = 5, cap = 5) {
  // 経過時間ぶんを補充（容量を超えない）
  b.tokens = Math.min(cap, b.tokens + (now - b.last) * rate);
  b.last = now;
  if (b.tokens >= 1) { b.tokens -= 1; return true; }   // 1 個使って通す
  return false;                                        // 空なら断る
}
// 待つべき秒数（Retry-After に使える）＝ (1 - b.tokens) / rate

容量 B は「どれだけまとめて呼んでよいか」、補充の速さ r は「長い目で見た平均」です。Stripe はブログで、利用者ごとのトークンバケットを Redis に置いてリクエスト数を制限していると説明しています。

リーキーバケット：断るか、待たせるか

リーキーバケットは、超えた分をすぐ断らずに待ち行列で受けて、一定の速さで流すことができます。nginx の limit_req はこの方式で、burst が待ち行列の長さです。

limit_req_zone $binary_remote_addr zone=api:10m rate=5r/s;  # IP ごとに毎秒 5 回

location /api/ {
    limit_req zone=api burst=10 nodelay;  # 10 回までの超過は待たせずに通し、それ以上は断る
    limit_req_status 429;                 # 既定は 503
}

nodelay を付けないと、burst に入った分は決めた速さになるまで遅らせて処理します。利用者には「遅いが失敗しない」、後ろのサーバーには「一定の速さで来る」振る舞いです。画面の操作のように待たされると困るリクエストでは nodelay を付け、遅れてもよいバッチの受け口では付けない、と使い分けます。nodelay を付けると、待ち行列の枠を「すぐ通してよい連続の量」として使うことになり、振る舞いはトークンバケットに近づきます。

複数台で数える

サーバーが 3 台あって、それぞれが自分のメモリで数えると、上限は実質 3 倍になります。同じ相手のカウンターは全台から見える 1 か所に置き、読んで・判定して・書くを一度に（原子的に）行います。

固定ウィンドウなら、Redis の INCR が「1 足して新しい値を返す」を原子的に行うので、それだけで数えられます。枠が終わったら消えるように期限を付けます。

key = "rl:{user_id}:{now // 60}"   # 利用者 × 何分目か
n = INCR key
if n == 1: EXPIRE key 60          # 最初の 1 回で期限を付ける
if n > 100: reject(429)

トークンバケットやスライディングウィンドウは「読む → 計算 → 書く」が複数の命令になるので、Lua スクリプトにまとめて Redis の中で 1 回で実行します。Redis 自体は Redis と Valkey の仕組み。

  1. サーバー A が残りを読む残り 1。
  2. サーバー B も残りを読むA がまだ書いていないので、こちらも残り 1。
  3. 両方が「通してよい」と判定A も B も 1 を使って 0 を書く。上限を 1 回超えて通した。

赤い番号の 3 番目が、上限を破ってしまった手順です。読んでから書くまでの間に、ほかのサーバーが割り込めることが原因です。INCR のような原子的な命令か、Lua スクリプトで 1 回にまとめれば起きません。

毎回 Redis に問い合わせると、その往復の時間がすべてのリクエストに乗ります。避け方は 2 つあります。

  • 拠点ごとに数える: Cloudflare は拠点（PoP）ごとに memcached 系のストアでカウンターを持ち、拠点をまたいだ合計はとらない。1 つの相手はたいてい同じ拠点に着くので、これで足りる。
  • 相手ごとに 1 か所へ集める: Cloudflare の Durable Objects なら「利用者 1 人 = 1 オブジェクト」にして、その利用者のリクエストの判定を 1 本の流れで順番に行える（Durable Objects と celld）。

どちらも、厳密な全体の合計より、速さと「だいたい合っている」ことを選んでいる。上限を少し超えて通しても困らない用途で使う。

断るときに返すもの

HTTP/1.1 429 Too Many Requests
Retry-After: 12                        # 12 秒後なら通る
RateLimit-Policy: "default";q=100;w=60   # 方針: 60 秒に 100 回（IETF の草案）
RateLimit: "default";r=0;t=12            # 残り 0 回、12 秒後に回復（同上）
Content-Type: application/problem+json
  • 429 Too Many Requests: 送りすぎを表すステータス（RFC 6585）。Retry-After で何秒待てばよいかを伝えられる。
  • RateLimit-Policy と RateLimit: 上限と残りを伝えるヘッダー。IETF で草案が進んでいる段階で、まだ RFC ではない。古い草案の RateLimit-Limit・RateLimit-Remaining・RateLimit-Reset や、X-RateLimit-* の名前で同じ情報を返す API も多い。
  • 成功した応答にも残りを付ける: クライアントは 429 になる前に速さを落とせる。

クライアント側は、429 を受けたら Retry-After の秒数を待ってから送り直し、無ければ指数バックオフ＋ジッターで間隔を空けます（分散システムの基本）。すぐ再送すると、それもまた数えられて回復が遅れます。

何を単位に数えるか

単位強み落とし穴
送信元 IPログイン前でも使える。CDN やプロキシで数えやすいNAT の後ろの大勢が 1 つの IP に見える（会社・携帯回線）。攻撃側は IP を替えられる。中継の後ろでは X-Forwarded-For のうち信頼できる部分だけを使う
利用者・API キー公平さと料金プランに直結する認証の後でしか数えられない。キーを大量に作られると抜けられる
アカウント × 操作ログイン試行は「アカウントごと」と「IP ごと」を両方数えるアカウントごとだけだと、攻撃者がわざと失敗させて本人を締め出せる
重み（コスト）重い検索は 10、軽い取得は 1 のように消費量を変える重みの根拠を文書にしないと、利用者が予測できない

回数ではなく「同時に処理中の数」を制限する方法もある。Stripe は回数の制限に加えて、重いエンドポイント向けに同時実行数の制限を使っているとブログで書いている。

よくある誤解

IP ごとに制限しておけば十分

会社や携帯回線では大勢が同じ IP を共有するので、無関係な人まで締め出す。逆に攻撃側は多数の IP から少しずつ送れる。ログイン後は利用者や API キーで数え、IP は前段の大まかな制限に使う。

固定ウィンドウでも上限は守られる

枠の中では守られるが、境目をまたいだ短い時間には上限の 2 倍まで通る。秒単位で後ろを守るならスライディングウィンドウかトークンバケットにする。

アプリにレート制限を入れれば DDoS も防げる

アプリに届いた時点で、接続や TLS の処理にはもう資源を使っている。回線を埋めるような大量の攻撃は、CDN や回線の手前の対策で受ける。アプリのレート制限は、行儀の悪い利用者から公平さを守るためのもの。

429 が返ったら、すぐ送り直せばそのうち通る

すぐの再送も数えられるので、上限から抜け出せなくなる。Retry-After の秒数を待つか、指数バックオフで間隔を空ける。
